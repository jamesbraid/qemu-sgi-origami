.. _sgi-ip32:

================
IP32: O2 and O2+
================

The ``o2`` machine (``hw/mips/sgi/o2.c``) builds one :term:`IP32 <IP
number>` board with one processor, two serial ports, the MACE I/O, the
GBE display and the two onboard SCSI controllers, and starts the boot
:term:`PROM` image the user supplies. ``variant=o2plus`` selects the O2+
processor on the same board. No test in this tree runs a stock IP32 PROM
or boots an operating system on the machine, so whether IRIX or another
system boots on it is not established here. This page is the hardware
contract the machine models in ``hw/mips/sgi/models/`` cite for the O2:
what is fitted, how it is wired, what the emulator chose where the
hardware is not known, and which sources back each statement.

Facts are rated as described in :ref:`sgi-ratings`.

The O2 is a Silicon Graphics entry workstation. A published hardware
page dates it to 1996 as the successor of the Indy and names its chips
as CRIME, MACE and GBE (:src:`bukosek-sgi-o2 Architecture`), *observed*.
It keeps memory, graphics and I/O data in one pool of main memory
(:src:`o2-technical-report p. 4`), *established*. The CRIME 1.5
specification gives CRIME's roles (:src:`sgi-crime-1.5-spec Table 3-1,
PDF p. 48`), *established*.

.. _sgi-ip32-current:

Machines
========

One machine type, ``o2``, builds both products. Its ``variant`` property
is ``o2`` (the default) or ``o2plus``.

.. list-table::
   :header-rows: 1

   * - Selection
     - Processor
     - Memory
     - Basis
   * - ``-M o2``
     - one R10000, 195 MHz, 1 MiB secondary cache
     - exactly 1 GiB
     - the product guide and a published 195 MHz capture
   * - ``-M o2,variant=o2plus -cpu R12000,...``
     - one R12000, 400 MHz, 2 MiB secondary cache
     - exactly 1 GiB
     - a model selection (:ref:`sgi-ip32-o2plus`); the machine's default
       R10000 is refused for this variant, so ``-cpu R12000`` with the
       listed properties is required

Every other part is the same in both. The catalogue's configurations
``o2`` and ``o2plus`` (``hw/mips/sgi/models/o2.yaml`` and
``o2plus.yaml``) describe these two selections.

.. _sgi-ip32-processor:

Processor
---------

The product guide lists one R10000 with 1 MiB secondary cache
(:src:`sgi-o2-product-guide-1065 p. 4`), *established*. The OpenBSD
report shows a 195 MHz R10000 revision 2.7 with a 1024 KB secondary cache
(:src:`dmesgd-2432 cpu0`), *observed*. The machine fits that processor,
big-endian, at a fixed 195 MHz, with QEMU's default R10000 identity,
revision 2.6.

The machine sets the R10000 reset mode word to ``0x00198603``, which
reads back as Config0 ``0x6c198603`` and selects 64-byte secondary cache
blocks. The fields are legal values from the processor manual
(:src:`nec-vr10000-series-um-4`), but the board's real reset word is
*unknown*; this one is an *approximation*. A CPU ``reset-mode`` option
is refused. The CPU's cache-data visibility must stay off, so processor
and DMA accesses share QEMU's coherent RAM, an *approximation*: the
model has no cache incoherence for software to manage.

The O2 sold with other processors. The technical report lists the R5000
and R10000 (:src:`o2-technical-report Table 2-1`), *established*, and the
published hardware page lists RM5271, R5000, RM7000, R10000 and R12000
modules (:src:`bukosek-sgi-o2 Processor options`), *observed*. The
machine accepts only the R10000, and the R12000 with ``variant=o2plus``.
QEMU's ``R5000`` CPU type is refused.

.. _sgi-ip32-o2plus:

O2+ processor
-------------

``variant=o2plus`` fits one R12000 at 400 MHz with 2 MiB secondary cache.
The NetBSD report shows a real O2 with an R12000
(:src:`dmesgd-5290 cpu0`), *observed*, and a published module list gives
an R12000 at 400 MHz with 2048 KB secondary cache
(:src:`bukosek-sgi-o2 Processor options`), *observed*. The identity
values below are model selections, not readings of an O2+ module,
*approximation*; the capture's PRId and cache differ from them
(`Published machines`_). ``-cpu R12000`` alone is enough: the board
fits the module's part, PRId ``0xe35``, FPU identification ``0x900`` and
reset mode word ``0x11a8603``, which selects a 2 MiB secondary cache with
16-word blocks. It refuses a ``-cpu`` value that differs.

Config0 then reads ``0x6d1a8603``. The CPU's R12000A mode is refused, so
the variant has a plain R12000 identity although the catalogue names the
configuration "O2+ R12000A". The reset word's fields are legal values
from the processor manual (:src:`nec-vr10000-series-um-4`); the module's
real word is *unknown*. The register test profile cannot select this
variant.

.. _sgi-ip32-memory:

Memory
------

The guide describes four pairs of DIMMs of equal capacity and requires
the first pair to be fitted (:src:`007-3275-003 p. 28-31`), and the
product guide gives 64 MB to 1 GB (:src:`sgi-o2-product-guide-1065 p. 12`),
*established*. The machine accepts exactly 1 GiB and nothing else, held
as eight 128 MiB CRIME banks; ``-m 1G`` is the default. The eight banks
are a model selection that gives the full capacity, not the board's
socket-to-bank wiring, *approximation*: DIMM pairs and CRIME's logical
banks are different things, and how a fitted board maps one to the other
is *unknown*. Memory slots and extra RAM are refused.

Two reset-time choices stand in for behaviour the model does not
otherwise have, the PROM using memory and the processor cache before it
has programmed the memory controller. Both are *approximation*:

- Until the first bank-control write, the first 32 MiB of RAM answer at
  address 0, as if bank 0 were already set up (:doc:`hardware/crime`).
- While the processor runs from the boot flash, its cached accesses to
  the first ``0x1008`` bytes of memory go to a private store. The store
  is released once the PROM has moved its stack to uncached memory and
  the same bytes have reached RAM. Running code from that range, or
  switching stacks before the bytes match, logs ``LOG_UNIMP``.

.. _sgi-ip32-test-profile:

Register test profile
---------------------

``-M o2,register-test-profile=on`` drops the product's fixed population
and admits the diagnostic options the chip qtests use: 64 or 128 MiB of
RAM, the eight-bank profile, the CRIME, GBE, flash and PHY options and
several test fixtures. It works only under QTest. It is a fixture for
register tests, not a model of any O2. The chip pages describe the
options. The product refuses all of them.

==========================

The processor reaches CRIME over its system interface, and CRIME owns
memory (:src:`sgi-crime-1.5-spec PDF p. 47-48`), *established*. In the
model, CRIME's five processor interrupt outputs drive CPU interrupt lines
2 to 6, GBE's four interrupt outputs drive CRIME's external inputs 0 to 3,
and MACE drives sixteen CRIME inputs. The CRIME page gives the bit
assignment (:src:`sgi-crime-1.5-spec PDF p. 106-108`). MACE's Ethernet,
peripheral and PCI DMA reach memory through CRIME's decoded banks.

The machine always builds every part in the table except VICE. QEMU has
a VICE model, but the machine does not fit it, so the VICE aperture is
unmapped. The machine fixes these settings, each described on its chip's
page:

- CRIME interface revision 1 with the ``legacy-software`` profile, whose
  ID matches the published O2 captures (:ref:`sgi-ip32-published`), and
  its functional memory transfer engine.
- MACE's 32-bit identity word access, its native PCI byte swap and an
  Ethernet DMA view of low memory.
- GBE revision 1.1 with a display, its ``legacy-software`` memory view
  and a 20 MHz TTL pixel clock input.
- An ICS1890 PHY at MII address 8, where the published O2s report a
  DP83840 (:ref:`sgi-ip32-published`).

Each is an *approximation* where its chip page says so. None identifies a
fitted ASIC revision.

.. _sgi-ip32-firmware:

Firmware and boot
=================

The board boots from a 512 KiB Atmel flash that MACE decodes in a 4 MiB
window (:src:`sgi-crime-1.5-spec PDF p. 48`, Table 3-1, which sizes the
System ROM window at 4 MB; :src:`sgi-mace-2.0-spec p. 8` names the Atmel
512Kx8 flash), *established*. The machine
requires all of these:

- ``rom-image=FILE``: a complete 512 KiB PROM image, with
  ``rom-size=524288``, ``rom-offset=0`` and ``rom-pad-byte``.
- ``rom-at29c040a-protection``, ``rom-at29c040a-lower-lock`` and
  ``rom-at29c040a-upper-lock``: the flash's software data protection and
  boot block lock states at power-on (:doc:`hardware/at29c040a`). A real
  part's states depend on its history, so the user states them.
- ``password-clear-input=0`` or ``1``: the board's password-clear input,
  whose fitted level is *unknown*.

The identity chip MACE reads back (:doc:`hardware/mace`) is built from the
machine's identity properties, so it needs no input of its own
(:ref:`sgi-ip32-system-serial`).

The machine refuses ``-bios``, ``-kernel``, ``-initrd`` and ``-append``.
Block backends named ``o2flash`` and ``o2flash-state`` keep the flash and
its protection state across runs. ``nvram0`` and ``nvram0-clock`` keep
the DS1685's RAM and clock.

At reset the processor fetches from ``0xbfc00000``, the uncached view of
the flash. What happens next depends on the image. The qtests run
synthetic images only.

.. _sgi-ip32-storage:

Storage, network and serial
===========================

The two AIC-7880 buses are ``aic0.0`` and ``aic1.0``. The machine accepts
one SCSI disk or CD-ROM in total, at LUN 0 and target 0 to 6, on either
bus. It refuses a second, other device kinds and unplugging. It refuses
any other PCI device, and PCI and SCSI hotplug.

The CD-ROM's INQUIRY text and block size follow :ref:`sgi-cdrom-identity`:
the O2 PROM sets 512-byte blocks on any type-5 unit, whatever its vendor.

The default network card is ``sgi-mace-eth``. Its station address is the
machine's own (``mac=`` or the address the identity inputs give), whether
or not ``-nic`` names one; a ``-nic`` or ``-netdev`` ``mac=`` that differs
is refused with a message naming both addresses. The guest never reads the
adapter's address, only the identity chip's (:ref:`sgi-ip32-system-serial`), so
honouring a different ``mac=`` would only mislead: the adapter's address
shows in ``info network`` and in packet captures.

MACE's two serial ports take the first two ``-serial`` backends. The
first is the console port. A third is refused.

.. _sgi-ip32-running:

Running
=======

A minimal command line, with a PROM image ``ip32prom.bin``::

    qemu-system-mips64 -nographic -m 1G \
      -M o2,rom-image=ip32prom.bin,rom-size=524288,rom-offset=0,\
    rom-pad-byte=255,rom-at29c040a-protection=disabled,\
    rom-at29c040a-lower-lock=unlocked,rom-at29c040a-upper-lock=unlocked,\
    emu-id=42,password-clear-input=0 \
      -drive if=none,id=d0,file=disk.img,format=raw \
      -device scsi-hd,bus=aic0.0,scsi-id=1,drive=d0

``emu-id=42`` gives the station address ``08:00:69:e1:02:a0`` and the host
id ``69e102a0``. The machine names any input that is missing or malformed.

Migration is refused for the product: the eight-bank memory model has no
saved state, so the machine registers a migration blocker and an
unmigratable state description. The register test profile, with 64 or
128 MiB of RAM, has no blocker.

.. _sgi-ip32-system-serial:

System serial number
====================

An IRIX guest builds its system id, and so ``sysinfo -s`` and the FLEXlm
host id, from a number the hardware gives it. On the O2 that is the station
address, which the PROM reads from the identity chip, not the real-time
clock's serial. The machine takes the same identity inputs as the Octane
(:ref:`sgi-identity`): ``emu-id``, ``serial``, ``hostid`` and ``mac``, and
reports ``hostids``. They pick the station address by the shared rule. The O2
needs the address to start ``08:00:69`` as the Octane does, but that is this
project's policy, not the firmware's: a PROM and IRIX accepted
``02:00:00:e1:02:a0`` in a model boot.

- MACE lists a unique 56-bit silicon serial number embedded in the
  calendar clock module and describes it as the "system serial # and
  ethernet address" (:src:`sgi-mace-2.0-spec p. 121`), *established*. The
  DS1685 and DS1687 hold it in bank 1: ``40h`` is the model number
  ``71h``, ``41h`` to ``46h`` a 48-bit serial and ``47h`` a CRC byte that
  validates them (:src:`maxim-ds1685-ds1687-rev-10-12 p. 19`),
  *established*.
- IRIX 6.5.30 and the stock 6.5.30 PROM take the station address, the
  ``eaddr`` environment variable, the interface's link address and the host id
  from the identity chip's memory, bytes 0 to 5 in reverse order, so
  ``08:00:69:e1:02:a0`` is ``a0 02 e1 69 00 08`` and the host id is
  ``69e102a0`` (*software expectation*, measured in model boots). A different
  address on the Ethernet adapter changed nothing the guest printed, and
  removing the adapter's backend entirely changed nothing. The flash
  environment, the clock's RAM and the disk kept no copy: a machine booted
  with a different chip took the new address on its next boot. Only the PROM
  performed one-wire transactions; none followed after power-on. That the
  early transactions are the PROM's is *inferred* from boot order.
  A boot with ``0x00`` filler in bytes 6 to 127 printed the same ``sysinfo``,
  ``hinv -v`` and ``nvram`` output as one with ``0xff``.
- The model builds the chip's memory from the station address: bytes 0 to 5
  as above and every other byte ``0xff``, the DS2502's unprogrammed state
  (:src:`maxim-ds2502-datasheet p. 5, 12`). That filler is an *approximation*:
  the contents of a fitted O2 chip are *unknown*, and no guest output depended
  on them.
- The chip's ROM serial is the constant ``45 4d 55 01 00 00``, the marker, the
  kind and two zero bytes, with family code ``09``, so Read ROM returns
  ``09 45 4d 55 01 00 00 a5``. A die's serial belongs to the part and not to
  the system, so it carries no machine id. It is synthetic. The seven status
  bytes are ``0xff``, no page write-protected or redirected, and the eighth
  is the responder's fixed ``0x00``; the status bytes are an *approximation*
  like the filler, since a fitted chip's are *unknown*.
- The adapter takes the same address as host-side labelling, and a different
  ``-nic mac=`` is refused (:ref:`sgi-ip32-storage`).
- The model never writes MACE's station-address register or the PROM's
  ``eaddr``. The firmware reads the chip and programs both.
- ``identity-eprom-file=FILE``, a debug input of exactly 128 bytes, replays a
  captured chip. It wins over ``emu-id``, ``serial``, ``hostid`` and ``mac``.
  ``hostids`` reads bytes 3, 2, 1 and 0 of the file and the adapter takes the
  address its first six bytes spell, reversed, when that is a unicast
  address. The file is read when the machine starts.
- The clock's serial is ``45 4D 55`` (``EMU``), the machine's kind and the
  ``emu-id`` as two bytes, most significant first, so ``emu-id=42`` on a QEMU
  machine is ``45 4d 55 01 00 2a`` in registers ``41h`` to ``46h``. With no
  ``emu-id`` the last two bytes are zero. Register ``41h`` holds the most
  significant byte. The CRC is the one-wire CRC (``x^8 + x^5 + x^4 + 1``) over
  ``40h`` to ``46h``. The data sheet gives neither the byte order nor the
  algorithm, so both are *inferred*, and the values are synthetic, not any
  machine's factory serial. The model returned zero in all seven bytes before
  the serial existed, an *approximation*. No run shows a guest reading the
  clock's serial.
- Whether a fitted O2 carries the chip on this line on every assembly, or the
  clock module's serial holds the address on some, is *unknown*; NetBSD's
  ``if_mec.c`` notes a DS2502 on the PCI riser of some machines. A published
  dump of a real O2's identity chip would settle the chip's contents.

.. _sgi-ip32-graphics:

Graphics
========

GBE scans the frame buffer out of main memory, and its display binds to
a QEMU console (:doc:`hardware/gbe`). CRIME's rendering engine draws a
functional subset of its operations into memory (:doc:`hardware/crime`).

.. _sgi-ip32-published:

Published machines
==================

Three published sources show real O2s. Each is rated *observed*.

- An OpenBSD 5.2 boot report of an O2 with a 195 MHz R10000 revision 2.7
  and a 1024 KB secondary cache (:src:`dmesgd-2432 cpu0`). It shows CRIME
  revision 10.1, a MACE PCI bridge revision 1, the MAC-110 revision 1
  with a DP83840 PHY at MII address 8, an AD1843 revision 1 and GBE
  revision 1.
- A NetBSD 9.99.31 boot report of an O2 with an R12000
  (:src:`dmesgd-5290 cpu0`). It shows a CRIME ID of ``0x1000000000a1``
  (NetBSD prints it in decimal, 17592186044577, converted here),
  a MACE PCI bridge revision 1 and a DP83840 PHY at MII address 8.
- A published hardware inventory of an O2 with a 300 MHz R5000-family
  processor (:src:`bukosek-sgi-o2 My O2`). The same page lists the
  processor modules, among them an R12000 at 400 MHz with 2048 KB
  secondary cache (:src:`bukosek-sgi-o2 Processor options`).

The machine differs from these. These are model limits:

.. list-table::
   :header-rows: 1

   * - Item
     - Published machines
     - ``o2``
   * - CRIME ID low byte
     - ``0xa1``
     - ``0xa1``, the same
   * - Ethernet PHY
     - DP83840 at MII address 8
     - ICS1890 at MII address 8
   * - R10000 revision
     - 2.7
     - 2.6
   * - R12000 identity (PRId)
     - ``0xe23``, revision 2.3, FPU ``0x900``
       (:src:`dmesgd-5290 cpu0`), *observed*
     - ``0xe35`` and FPU ``0x900``, fitted by the board,
       *approximation*
   * - R12000 secondary cache
     - 1024 KB, 64-byte blocks (:src:`dmesgd-5290 cpu0`), *observed*;
       1 MB in the product guide (:src:`sgi-o2-product-guide-1065 p. 4`);
       2048 KB for the 400 MHz module
       (:src:`bukosek-sgi-o2 Processor options`, part 030-1529)
     - 2 MiB, 64-byte blocks, *approximation*
   * - Processors
     - R5000, RM5271, RM7000, R10000 and R12000 modules
     - R10000 at 195 MHz, or R12000 at 400 MHz
   * - Memory
     - 64 MB to 1 GB
     - 1 GiB only
   * - Parallel port
     - fitted
     - absent

.. _sgi-ip32-limits:

Model limits
============

- No stock PROM run or operating system boot is tested in this tree.
- VICE, the parallel port, USB, the camera and video inputs, and PCI
  expansion cards are not fitted.
- Memory is 1 GiB only, as eight logical banks. ECC, cache incoherence
  and the board's DIMM wiring are not modelled.
- The processor reset words, the O2+ identity values and the pixel clock
  are model choices.
- The product refuses migration; the register test profile does not.
- The clock's silicon serial is synthetic, and its byte order and CRC
  algorithm are inferred (:ref:`sgi-ip32-system-serial`).
- The identity chip's bytes 6 to 127 are ``0xff`` filler, an approximation:
  a fitted chip's contents are unknown.
- Each chip page lists its own limits and how an unexpected access shows
  up.

.. _sgi-ip32-tests:

Tests
=====

- ``tests/qtest/sgi-o2-test.c``: the product's composition, required
  inputs and refusals, both variants' processor and Config0, serial
  backends, native PCI, the eight-bank memory and its aliases, the
  private boot store, the interrupt chain, the flash aliases, and the SCSI
  paths, and the clock serial the identity key gives; with
  ``register-test-profile=on``, the diagnostic options.
- ``tests/qtest/sgi-o2-id-test.c``: the MACE identity line, and the
  product machine's chip: its Read ROM, Read Memory and Read Status answers
  with checksums worked independently, ``hostids``, the refused inputs,
  the adapter's address and refused ``-nic mac=``, and the replay file.
- ``tests/qtest/sgi-o2-platform-inputs-test.c``: the password-clear input
  and the DS1685 backends and silicon serial.
- ``tests/qtest/sgi-o2-rom-test.c``: the flash window and synthetic
  images.
- ``tests/qtest/o2-r10k-scache-reset-test.c``: the secondary cache
  selection after a CPU reset.
- ``tests/qtest/sgi-catalogue-launch-test.c``: launches every catalogue
  offering, including ``o2`` and ``o2plus``, with synthetic inputs.
- ``scripts/tests/test_sgi_model_ip32.py``: the catalogue's two
  configurations.

The chip pages list the CRIME, MACE, GBE and Ethernet tests.

.. _sgi-ip32-unknowns:

Open questions
==============

- The board's reset mode word, and the O2+ module's identity and reset
  word. A reset-time read of Config0 and PRId on a real O2 and O2+ would
  settle them.
- How DIMM sockets map to CRIME banks. A real board's bank control
