.. _sgi-ip35:

====================================================
SGI IP35: Origin 300, Fuel and the Origin 350 family
====================================================

IP35 is the software platform of SGI's second Scalable Node generation,
built around the Bedrock node controller. QEMU models it as the
``origin300``, ``fuel``, ``origin350``, ``onyx350``, ``tezro`` and
``onyx4-host`` machines on the shared base described in :doc:`sn`. This
page covers the platform's physical address map and the IP53 board's
I/O and compatibility components.

.. _sgi-ip35-address-map:

IP35 physical address map (Origin 300, IP45)
============================================

This page is the address map the Origin 300 and Fuel machine models
(``hw/mips/sgi/sn1.c`` and ``sn1-node.c``) follow: how an R10000-family
processor selects a space, how the node number sits in a physical
address, node memory, the crosstalk windows, the Bedrock's register
space, the hand-off and reset registers, and the interrupt-send address.
The Bedrock units behind the register space are on :doc:`/system/mips/sgi/hardware/bedrock`.
Ratings follow :ref:`sgi-ip30`.

.. _sgi-ip35-address-map-spaces:

Processor-side spaces
---------------------

The processor selects a space with two bits beside the address, not inside
it: an R10000-family processor takes the uncached attribute from
virtual-address bits 58:57 of an uncached xkphys address and drives it with
the 40-bit physical address (OpenBSD ``cpu.h`` lines 92-113; linux-ip35
``spaces.h`` lines 13-16; Linux SN1 ``bedrock.h`` lines 40-44).

.. list-table::
   :header-rows: 1
   :widths: 18 10 26 46

   * - Space
     - Attribute
     - Base an unmapped R10000 guest uses
     - Source (all established)
   * - cached memory
     - none
     - ``0xa800_0000_0000_0000``
     - OpenBSD ``mnode.h`` line 40, ``cpu.h`` line 87, ``GENERIC-IP27``
       line 20; linux-ip35 ``spaces.h`` line 17; same value as the
       Origin 200.
   * - Hub special
     - 0
     - ``0x9000_0000_0000_0000``
     - ``cpu.h`` line 98, ``mnode.h`` line 46; ``spaces.h`` line 19.
   * - I/O
     - 1
     - ``0x9200_0000_0000_0000``
     - ``cpu.h`` line 99, ``mnode.h`` line 47, ``ip27_machdep.c`` line
       161; ``spaces.h`` line 20.
   * - memory special
     - 2
     - ``0x9400_0000_0000_0000``
     - ``cpu.h`` line 100, ``mnode.h`` line 48; ``spaces.h`` line 21.
   * - uncached memory
     - 3
     - ``0x9600_0000_0000_0000``
     - ``cpu.h`` line 101, ``mnode.h`` line 49; ``spaces.h`` line 22.

There are exactly four uncached spaces on the MIPS side. The Itanium port's
seven bases do not apply. The Origin 200's 42-bit machine-bus carrier
(a two-bit window number above the 40-bit physical address) fits this
generation unchanged (emulator choice).

     - 8 GB
     - 4 GB
     - the same lines; OpenBSD ``mnode.h`` line 55.
   * - maximum nodes
     - 128
     - 128
     - ``sn1/arch.h`` ``MAX_NASIDS``; OpenBSD ``mnode.h`` line 438 (the
       64-node M-mode cap in ``sginode.c`` is an OpenBSD choice).
   * - Origin 200
     - bits 39:32, 4 GB
     - bits 39:31, 2 GB

The vendor's own Origin 300 field-diagnostics manual prints a sample
configuration for an Origin 3000 pair in which node 1's cached memory base
is ``0xa800000200000000``, 2^33 above node 0's (108-0264-004 printed page
A-2), agreeing with the seven-bit field at bit 33 (established).

How a guest learns the mode conflicts across consumers: OpenBSD takes bit
18 of the network port status register (offset ``0x680000``) as "more nodes
than M mode holds" (``sginode.c`` lines 100-103, ``hub.h`` line 218), the
Origin 200 rule; the Bedrock register file defines only bits 2:0 of that
register (Linux SN1 ``sn1/hubni.h`` lines 1015-1033), and the Itanium
port reads the local block's system-size field, bits 47:46 of its revision
register, where 2 means N mode (``hublb_next.h`` lines 19-32, ``ip37.c``
lines 34-38). The model returns zero in both (an approximation): OpenBSD
prints "Machine is in M mode" on real Origin 300s, one chassis and two
cabled, so bit 18 reading clear is observed; what an N-mode Bedrock
returns, and which register the PROM consults, are unknown.

.. _sgi-ip35-address-map-memory:

Node memory and the low-memory map
----------------------------------

Memory is reported per bank in 1 GB steps (OpenBSD ``sginode.c`` lines
549-590); the Linux SN1 headers give a 1 GB slot shift, a 64 MB minimum and
eight slots per node (``sn1/arch.h`` lines 47 and 53-54). OpenBSD does not
manage the first 64 MB of a node on IP35, against 32 MB on IP27
(``sginode.c`` lines 566-575, 519-528). The Origin 300 has four DIMM slots
as two pairs, 512 MB to 4 GB per chassis, the pairs allowed to differ
(007-4365-002 printed page 11). Established.

The firmware's low-memory map, as the Linux SN1 tree draws it
(``kldir.h`` lines 164-283 for the diagram, 310-361 for the constants):

.. list-table::
   :header-rows: 1
   :widths: 16 54 30

   * - Offset
     - Contents
     - Fixed-offset readers
   * - ``0x0000``
     - processor 0 exception handlers; cache-error frame at ``+0x400``,
       early cache-exception stack at ``+0x800``
     - firmware
   * - ``0x1000``
     - ARCS system parameter block, 1 KB
     - every ARCS guest
   * - ``0x2000``
     - low-memory directory, 1 KB, 16 entries of 64 bytes
     - OpenBSD ``mnode.h`` line 90; both Linux trees
   * - ``0x2400``
     - launch area: four entries of ``0x100``
     - firmware
   * - ``0x3000``
     - NMI handler page, four entries of ``0x40``
     - firmware
   * - ``0x8000``, ``0x10000``, ``0x18000``
     - processors 1 to 3: handlers, cache-error frame, early stack
     - firmware
   * - ``0x9000``, ``0xa000``
     - NMI register save and exception-frame areas, ``0x400`` per
       processor
     - OpenBSD ``ip27.h`` lines 29-31
   * - ``0xb000``
     - global data area, 1 KB (directory slot 3)
     - guests via the directory
   * - ``0x20000``
     - processor-interface error spools, 64 KB (slot 6)
     - via the directory
   * - ``0x30000``
     - configuration graph (KLCONFIG), 64 KB (slot 1)
     - via the directory
   * - ``0x40000``
     - first free memory; non-debug kernel load address
     - ``kldir.h`` line 336; linux-ip35 ``Platform`` line 11; OpenBSD
       links the same address (``GENERIC-IP27`` line 19, one kernel for
       both boards)

The directory slot numbers are unchanged from the Origin 200 (0 launch, 1
KLCONFIG, 2 NMI, 3 GDA, 4 free memory, 5 symmon stack, 6 PI error, 7
kernel variables, 8 kernel cross-partition, 9 partition id: OpenBSD
``mnode.h`` lines 91-100; both Linux trees). That the stock IP35 PROM
places its configuration graph at ``0x30000`` is measured from the stock
image (``firmware:ip35-prom-6.210``, ``init_klcfg: nasid 0 start
9600000000030000``). The Origin 200's offsets (NMI save area ``0x11400``,
GDA ``0x11000``, KLCONFIG ``0x4000``, kernel ``0x19000``) do not apply to
IP35.

Crosstalk windows
-----------------

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - Item
     - Value
     - Source (established unless marked)
   * - small window
     - 16 MB per widget; widget ``w`` at node I/O base ``+ w << 24``;
       devices are widgets 8 to 15.
     - OpenBSD ``hub.h`` lines 22-26, ``ip27_machdep.c`` lines 488-489;
       both Linux trees' ``sn/addrs.h``.
   * - big window
     - 512 MB in M mode, 256 MB in N mode; window ``k`` at node I/O base
       ``+ (k + 1) << 29`` (28 in N mode).
     - OpenBSD ``ip27_machdep.c`` lines 69, 236-237, 493-497; linux-ip35
       ``sn1/addrs.h`` lines 65 and 51; Linux SN1 lines 86 and 72.
   * - translation entries
     - seven, at hub offsets ``0x400160`` to ``0x400190`` in 8-byte
       steps; software numbers them 0 to 6, hardware manuals 1 to 7.
     - OpenBSD ``hub.h`` lines 191-193; Linux SN1 ``hubio.h`` lines
       132-174.
   * - entry encoding
     - bit 12 space (1 device, 0 memory), bits 11:8 widget, low bits the
       XIO address above the window size.
     - OpenBSD ``hub.h`` lines 195-201; Linux ``sn/io.h`` lines 20-46.
   * - widget 0
     - reached through big window 6, which the PROM programs for it.
     - OpenBSD ``ip27_machdep.c`` lines 478-486, 535-536; both Linux
       trees. Whether the remap is still needed on a Bedrock is open
       (Linux's own header asks, ``hubio_next.h`` line 144); reading
       entry 6 after a stock PROM boot would settle it, and the model
       answers both forms.

The crossbar is at widget 0, the XBridge heads at widgets 14 and 15 and the
Bedrock enters at port ``0xa`` (observed on real Origin 300s in three
owners' inventories, ``ASIC XBOW Rev 2`` with ``ASIC BRIDGE Rev 2`` at
widgets 14 and 15, and a verbose PROM trace printing ``HUB at 0x0 attached
as widget 0xa`` and ``xbow_base= 0x9200000000000000``); the XBridge
specification, revision 0.5 printed pages 17 and 44-46, gives the XBridge
mode with internal ports ``0xe`` and ``0xf`` (:doc:`/system/mips/sgi/hardware/xbridge`). A device
register behind the XBridge composes as I/O space plus the node offset plus
the widget window (``widget << 24``) plus the bridge's device window plus the
register offset; the device windows are two 2 MB windows from ``0x200000``
and six 1 MB windows from ``0x600000``.

.. _sgi-ip35-address-map-hub:

Hub register space
------------------

The Bedrock's registers are XIO widget 1 of its own node.

.. list-table::
   :header-rows: 1
   :widths: 30 30 40

   * - Form
     - Address
     - Source (established)
   * - local register ``r``
     - ``0x9200_0000_0100_0000 + r``
     - OpenBSD ``hub.h`` lines 28-29; both Linux trees' ``IALIAS_BASE``.
   * - remote register ``r`` on node ``n``
     - ``0x9200_0000_0180_0000 + (n << 33) + r``
     - ``hub.h`` lines 30-31; ``sn/addrs.h`` ``REMOTE_HUB_ADDR``.
   * - second processor interface
     - remote form ``+ 0x200000``
     - ``hub.h`` lines 32-34 and 110-114; ``hubpi_next.h`` lines 16-19.

Unit bases inside the 8 MB window (hub-relative; established): processor
interface 0 at ``0x000000`` (OpenBSD ``hub.h`` line 85); processor
interface 1 at ``0x200000`` (lines 110-114); I/O interface ``0x400000``
(line 189); local block ``0x600000`` (line 208); network interface
``0x680000`` (line 215); crossbar ``0x700000`` (line 233); memory and
directory ``0x780000`` (line 180); each matches the first register of the
corresponding ``hub*.h`` header. OpenBSD expects the local form to reach the
requester's own interface; whether the Bedrock selects the interface that
way is unmeasured, and the two-processor board needs a PI0/PI1 local-read
test to settle it.

Hub special space
-----------------

   * - second PROM, boot-window offset ``0x0200_0000``

   * - remote register window of node ``n``, ``0x3000_0000``

     - 128 MB

       OpenBSD never forms it.
   * - directory backdoor, ``0x1c000_0000``
     - 1 GB aperture
     - observed: Linux v2.5.0 (``linux-history:381ab1f538162``)
       ``sn/addrs.h`` maps one Bedrock directory word at ``+0`` and
       names ``+8`` as the page-counter address.

The uncached alias of the reader's own node memory at offset 0 is
inherited text from the Origin 200 headers and no IP35 consumer uses it
(observed, linux-ip35 ``sn/addrs.h`` lines 119-133). The cached-alias size
register in each processor interface (``0x28``) takes a 4-bit code, 0 off
and 1 to 15 for 4 KB doubling to 64 MB (``hubpi_next.h`` lines 199-215;
OpenBSD ``hub.h`` lines 89-90); OpenBSD writes 0 to both interfaces and all
ones to both region-present registers at setup (``ip27_machdep.c`` lines
338-345). Whether IP35 flips the bottom 128 KB of the uncached alias per
processor as the Origin 200 does is unknown; observing where a stock PROM
places each processor's handler copies would settle it.

.. _sgi-ip35-address-map-interrupt:

Interrupt send
--------------

A widget raises a Bedrock interrupt by writing to an XIO address naming the
node, the Bedrock's own widget 1, the remote form and the
interrupt-pending-modify register: bit 47, the node shifted by 39 (38 on
IP27) and ``0x0180_0090`` (OpenBSD ``ip27_machdep.c`` lines 350-353; Linux
``sn/xtalk/xtalkaddrs.h`` lines 66-91, adding ``0x200000`` for a target
on the second interface, ``hub_intr.c`` line 145). Writing ``0x100 | level``
sets, ``level`` alone clears (``hub.h`` lines 98-100; Linux ``sn1/intr.h``
lines 122-143). The bridge's interrupt-destination registers carry the
Bedrock's crossbar widget number in bits 51:48 (``xbridge.c`` lines
2177-2191), from the configuration graph's crossbar record, default ``0xa``
(``sginode.c`` lines 159-160, 338). For a Bridge-class bridge on a node
other than 0 OpenBSD places the node at bit 9 and linux-ip35 at bit 8
(``xbridge.c`` lines 1393-1394; ``pci-sgipic.c`` line 77): open, and
irrelevant until a second node exists. Established, except the open item.

IP53 IO and compatibility components
====================================

This page records the component boundaries used by the IP53 module profiles.
Those profiles are software constructions for the Origin 350 and Tezro, and
for proposed captured Onyx 350 compatibility work. They do not establish that
every selected device, setting, or connection matches a physical board.
Chip-level behavior and evidence limits are stated below; the detailed
reviewed Origami contracts remain the authority for experiment-specific
policies.

.. _sgi-ip53-pic:

PIC PCI host bridge
-------------------

The profile exposes one PIC with two PCI heads. Public OpenBSD sources show
the second head at offset ``0x800000`` within the same XIO widget; public
Linux sources describe the PIC configuration-device numbering used by these
profiles. The two-head layout is selected from those software sources.

The Origin 350, Tezro, and proposed Onyx 350 profiles select PIC widgets and
direct-DMA settings as explicit software inputs. In particular, the supported
direct-DMA fields and the direct64 path are emulator policies for those
experiments. They do not establish the complete PIC revision 3 register
contract, reset image, or physical Bedrock-to-PIC wiring. Unsupported fields
and untranslated DMA remain observable. See the PIC model and qtests for the
implemented boundary.

.. _sgi-ip53-ioc4:

IOC4 on IO9
-----------

The selected IO9 component uses one IOC4 PCI function, with PCI identity
``0x10a9:0x100a``. The profile selects the existing QEMU revision value
``0x53``; this is not a measured revision for either selected IO9 board.
The experiment profiles enable the existing serial-DMA option. The Origin
350 and proposed Onyx 350 profiles choose a 33,333,333 Hz clock; Tezro chooses
66,666,667 Hz. These are software inputs, not claims about board straps or
the complete IOC4 reset state.

The public serial-console contract covers byte-wide UART windows and the
IOC4-local interrupt state used by the selected subset. ATA, keyboard and
mouse, general-purpose pins, full byte-bus behavior, and board-level
interrupt routing are outside this profile page. Unimplemented accesses
must remain visible. Exact reset values, the complete access-width matrix,
and the physical interrupt route remain unresolved.

.. _sgi-ip53-bcm570x:

BCM5701 Ethernet controller
---------------------------

The profile selects the existing generic BCM570x model as a single-port
BCM5701, PCI identity ``0x14e4:0x1645``. The selected PCI revision value is
an emulator setting, not an observed IO9 card revision. The model uses
QEMU's network backend interface; the IP53 profile does not claim that a
particular host network backend or physical network route exists.

The QEMU BCM570x model's register, DMA, and interrupt behavior is exercised
by ``tests/qtest/bcm570x-test.c`` and ``tests/qtest/sn0-bcm570x-test.c``.
Those qtests establish model behavior, not physical BCM5701 behavior on IO9.
Startup timing includes a bounded model approximation. Physical startup
timing and the exact fitted IO9 Ethernet component remain unverified. DMA
must continue through the selected PCI device's bus-master address space.

.. _sgi-ip53-ds1742:

DS1742-compatible clock resource
--------------------------------

The legacy clock-only selection links the existing DS1742 model to IOC4.
It exposes the eight clock-byte addresses used by the selected
compatibility contract and retains the model's 2 KiB backing image. It does not
establish the fitted IO9 package, full IOC4 byte-bus decode, SRAM aliases, or
physical address wiring. The reported IOC4 clock label does not identify the
fitted part. The broader storage span and PROM environment/checksum area
remain outside this legacy selection.

.. _sgi-ip53-ds1744:

DS1744-compatible timekeeper resource
-------------------------------------

The serial IO9 profiles select a 32 KiB DS1744-compatible geometry through
the board's standard system-timekeeper record. IOC4 maps the child's complete
byte-wide region at BAR0 offset ``0x80000``. Device offsets
``0x0000`` through ``0x7ff7`` are ordinary SRAM. The eight clock bytes occupy
``0x7ff8`` through ``0x7fff``. Firmware owns all SRAM contents, including
PROM variables and checksums. The emulator does not construct or repair
those records.

This geometry follows Analog Devices/Maxim's published DS1744/DS1744P
specification, document 19-5502, revision 6/13. OpenBSD's public SGI driver
uses the same 32 KiB span at IOC4 BAR0 plus ``0x80000`` and the same final
eight clock offsets. These sources support a compatibility mapping. They do
not identify the physical IO9 package or establish its address wiring.

The device shares the DS1742 calendar and backing-store implementation.
Its data image is exactly 32768 bytes and its paired clock-reference image
uses the existing 16-byte format. The board retains the IP53
``fresh-year-base=1968`` policy for fresh or blank clock initialization.
Valid saved calendars retain their values. Guest reset retains SRAM and
calendar state. DS1744 has a separate migration identity, while the legacy
DS1742 migration format remains unchanged. An existing 2 KiB backing image
is rejected rather than resized.

The public specification is available at:
https://www.analog.com/media/en/technical-documentation/data-sheets/DS1744-DS1744P.pdf

.. _sgi-ip53-io-profile:

Profile boundaries
------------------

These component selections describe the software model projection. The
Origin 350 and Onyx 350 captures differ in board identity and context; their
topologies and unmeasured board behavior must not be inferred from one
another. The PIC attachment, IOC4 settings, PCI revisions, and linked clock
are profile choices where explicitly identified above. Physical behavior
that lacks matching evidence remains unknown.

.. _sgi-ip53-serial-profiles:

-------------------------------

The machine catalogue selects the following inputs for serial IRIX configurations.

separate public capture or manual references.

The six listed compositions select the same internal R16000 experiment
properties with or without the ``ip53-experimental`` machine option.
The machine checks the resolved processor population, fitted socket count,
memory, clock, cache and reset word before enabling the profile. Other
already-admitted experimental populations still require that option and
explicit CPU properties. These are software inputs, not measured silicon
values. The Onyx 350 and Onyx 4 rows project a captured module into a
single-module host. The
Onyx 4 capture reports an IP59 board in a system called Onyx 350; assigning
that module to the Onyx 4 host is an inference. Its profile uses the IP53
guest-board path as a compatibility mapping, not a physical IP59 schematic.
The public IP59 module inventory reports HUB revision 2 at 200 MHz.
Mapping that report to Bedrock revision 2 is a profile choice; raw NI and

The Origin 350, Onyx 350 and Onyx 4 host profiles each select one PIC at XIO
widget 15. Tezro selects two PIC widgets, 11 and 15, and places the modeled
IO9 behind widget 15. The one-CPU and four-CPU Tezro tower profiles share
the same selected board, memory and I/O construction. The rack profile models
only the first enclosure. The four-CPU Tezro tower and Onyx 350 profiles
take an optional V12 in graphics slot ``widget-12``
(``-device sgi-odyssey,slot=widget-12,product=v12``). Both default to no
graphics. The widget position follows published Tezro and Onyx 350 inventories
respectively; on the Onyx 350 it is an alternative to an InfiniteReality
configuration. The pipe links to that port
of the PXBOW of the PIC that owns widget 0, reuses Odyssey and Bedrock PI
credit handling, and is marked alive and routed once it has realized. No profile attaches a G2/G2N brick or a NUMAlink peer.
Direct-link XIO and the PIC interrupt and DMA settings are emulator choices
where physical routing remains unknown.

These profiles select an IP35 PROM 6.210 payload and a profile-specific flash
seed. Flash read and write cycle inputs are both 16, and the machine-type
input is 0 for the six standard profiles. The ``tezro-deskside-700mhz-4mib-serial-trial`` topology keeps
its own inputs. The Origin 350 and Onyx 350 profiles select a 33,333,333 Hz IOC4
clock; Tezro selects 66,666,667 Hz. The linked clock resource uses a 1968
fresh-year base. Platform identity ``0x2001`` is a selected software input.
Origin 350, Onyx 350 and the Onyx 4 host select L1 type ``0x37``. The Tezro
tower and rack profiles select ``0x39`` and ``0x51`` respectively, following
the published Linux IP35 machine-name mapping. Physical L1 type replies
remain unmeasured. The public captures do not establish the selected clocks,
an installed flash image, or the complete PIC and IO9 interrupt wiring.
