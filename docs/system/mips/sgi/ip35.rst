.. _sgi-ip35:

=========================
IP35: Origin 300 and Fuel
=========================

:term:`IP35 <IP number>` is the :term:`SN1` software platform, SGI's second Scalable
Node generation, built around the :term:`Bedrock` node controller. Its
boards are the Origin 300's IP45, the Fuel's IP34, the Origin 3000
C-brick's IP35 and the IP53 of the Origin 350 family. This page covers
two products: ``origin300`` (board IP45) and ``fuel`` (board IP34). The
Origin 3000 C-brick compositions are under
:ref:`sgi-ip35-brick-composition`. The IP53 board of
the Origin 350, Onyx 350, Tezro and Onyx4 host has its own page
(:doc:`ip53`); it shares this page's Bedrock node, address map and :term:`PROM`.
The machine classes are in ``hw/mips/sgi/sn1.c``. Each node is an
``sgi-sn1-node`` (``hw/mips/sgi/sn1-node.c``), and the shared Scalable
Node builder in ``hw/mips/sgi/sn-machine.c`` assembles the nodes from the
compiled catalogue (:doc:`sn`). Every machine boots a stock IP35 PROM that
the user supplies. This page is the hardware contract the IP35 model
layers in ``hw/mips/sgi/models/`` cite: what each product fits, how it is
wired, the physical address map, and where the emulator chose a value
the hardware does not settle. Chip register behaviour is on the part
pages listed under :ref:`sgi-ip35-devices`.

Facts are rated as described in :ref:`sgi-ratings`.

The Origin 300 and Fuel are modelled from manuals and published
captures of those products.

.. _sgi-ip35-machines:

Machines
========

Each machine builds one or two Bedrock nodes. ``-M <machine>,topology=``
selects a wiring the catalogue lists. An unknown name, such as
``topology=help``, makes the machine print the topologies it accepts and
exit.

second processor is not a Fuel option.

.. _sgi-ip35-processors:

Processors
----------

The Origin 300 and Fuel fit QEMU's R14000 at 500 MHz with 2 MiB of
secondary cache. :doc:`hardware/r10000` describes the identity words,
the reset mode word and how the R14000 inputs are checked.

A Bedrock has two processor interfaces with two processors each. The
machine populates them diagonally: a two-processor node fits interface 0
position A and interface 1 position A first (``sn1-topology.c``), as the
published two-processor board does.

.. _sgi-ip35-identity:

Board identity inputs
---------------------

Each product carries the values its firmware reads to recognise it. They
are catalogue defaults. Machine properties of the same names override
them: ``board-id-word``, ``l1-type-code``, ``l1-revision``,
``bedrock-revision`` and ``ioc3-subsystem-id``. The IP53 products' values
are on :ref:`sgi-ip53-identity`. On the Fuel the catalogue
also keeps a mask of ``0xf000`` requiring ``0x4000``, so a
``board-id-word`` override must keep the Fuel's product code in bits
15:12.

.. list-table::
   :header-rows: 1

   * - Product
     - Board word
     - L1 type
     - L1 revision
     - Flash machine type
   * - Origin 300
     - ``0x8001``
     - ``0x34`` (``4``)
     - 1.18.5
     - 1
   * - Fuel
     - ``0x4004``
     - ``0x41`` (``A``)
     - 1.48.1
     - 2

- Board word bits 15:12: OpenBSD reads them as the product code and
  assigns C-brick 0, Fuel 4 and Origin 300 8 (``ip27.h``
  lines 43-46, ``ip27_machdep.c`` lines 165-185), a *software
  expectation*. The low bits are *unknown* on every product. The stock
  PROM uses the low nibble to pick a row of its processor-configuration
  table: 1 on the Origin 300 and 4 on the Fuel select the 500 MHz, 2 MiB
  R14000 rows (:src:`ip35-prom-6.210`), a *software expectation*. The
  register is on :doc:`hardware/bedrock`.
- L1 type: Kaloz's series maps ``4`` to Origin 300 and ``A`` to Fuel
  (:src:`lore-kaloz-ip35-35`), a *software expectation*. No captured L1
  type reply exists for either, *unknown*.
- L1 revision: the Fuel captures report 1.48.1 and 1.14.4, and neither
  is tied to the modelled board. The Fuel defaults to 1.48.1, the
  revision one public capture reports, a model choice. IRIX in the model
  boots without the L1 version warnings at that value, a software effect
  that did not decide it. ``l1-revision=`` replaces it. The Origin 300's
  1.18.5 is a choice too.
- L1 brick serial: the Fuel's L1 answers the brick-serial request with
  the synthetic ``EMUN`` and the node number as a hex byte (the node's system
  board, node 0), a model choice. It follows no identity input: the PROM ties
  its NVRAM to the node board's serial and starts the NVRAM afresh when it
  changes (:ref:`sgi-identity`). The real format is *unknown*. Setting ``brick-serial`` on the ``sgi-l1`` device, for example
  with ``-global``, replaces it.
- L1 system serial: every Bedrock machine but the Fuel (the Origin 300
  family, the Origin 3000 and Onyx 3000 topologies, the IP53 machines and
  the Tezro) gives all its L1s the same system serial. With ``emu-id=N`` it is
  ``LEMU``, the kind digit, ``N`` as four digits and ``0``, ten characters, a
  model choice; with no input ``LEMU100000``. ``serial=`` gives any text of up
  to ten characters as written, and ``hostid=`` gives the eight-character
  spelling of an id, such as ``M2100887`` for ``d2100887``. They must agree
  when both are given, and ``mac=`` sets only the port's address, in the L1
  record and the IOC3, and leaves the id alone. IRIX reads the text for
  ``sysinfo -s`` and FLEXlm's ``lmhostid``, which fold the low nibble of each
  of the first ten characters into eight hex digits, so ``emu-id=42`` gives
  ``LEMU100420`` and the host id ``d5100420`` (*software expectation*, measured on an Origin 300
  guest on this model; on the other machines it is read from the kernel's code
  and untested in a guest). ``system-serial`` on the ``sgi-l1`` device is a
  debug input that wins over all of them. The format of a real serial's digits is
  *unknown* beyond the published samples, and a real L2's check of the text is
  *unknown* (:ref:`sgi-identity`). Real IRIX prints one id per node, so the
  machine's ``hostids`` repeats the id for each node. The Fuel keeps its
  station address as the serial. The kernel reads hex digits 4 to 11 of those
  twelve as the host id, so the Fuel's is ``69E``, the kind digit and the
  ``emu-id`` and sub-index digits: ``69e102a0`` for ``emu-id=42``. On the Fuel
  ``hostid=`` sets the address (8 digits starting ``69``, or 6 digits with the
  ``69`` implied), ``serial=`` is refused unless it folds to an id starting
  ``69``, and ``mac=`` sets the id; they must agree. A real Fuel's value is
  *unknown*. ``system-serial`` and ``fuel-mac-eeprom=`` are debug inputs that
  override them, and the ``hostid`` and ``hostids`` properties follow the
  override.
- Flash machine type: the value written into the PROM's configuration
  block. The PROM's Origin 300 rows carry type 1 and its Fuel rows type 2,
  a *software expectation*. A real Fuel's ``flash -f`` session answers 2
  (:src:`graphica-o350-notes`), *observed*. :doc:`prom-image`
  gives the block layout.
- Bedrock revision 2 at 200 MHz: every published Origin 300 and Fuel
  inventory reports ``HUB`` revision 2, *observed*. The
  raw register value behind that field is *unknown*.
- The IOC3 subsystem identity is ``0xc30a`` on the Fuel, the code Linux
  ``pci-xtalk-bridge.c`` assigns the IP34 board (*software expectation*),
  and ``0xffff`` on the Origin 300 (*unknown*).

Barcodes and serial numbers in board records are synthetic ``EMU``
values carrying a ``QEMU`` marker, not taken from a real machine.

.. _sgi-ip35-address-map:

IP35 physical address map (Origin 300, IP45)
============================================

This is the address map the Origin 300 and Fuel models
(``hw/mips/sgi/sn1.c`` and ``sn1-node.c``) follow: how an R10000-family
processor selects a space, how the node number sits in a physical
address, node memory, the :term:`crosstalk` windows, the Bedrock's register
space, the hand-off and reset registers, and the interrupt-send address.
The IP53 profiles share it. The Bedrock units behind the register space
are on :doc:`hardware/bedrock`.

.. _sgi-ip35-address-map-spaces:

Processor-side spaces
---------------------

The processor selects a space with two bits beside the address, not
inside it: an R10000-family processor takes the uncached attribute from
virtual-address bits 58:57 of an uncached xkphys address and drives it
with the 40-bit physical address (OpenBSD ``cpu.h`` lines 92-113;
linux-ip35 ``spaces.h`` lines 13-16; Linux SN1 ``bedrock.h`` lines
40-44), a *software expectation*.

.. list-table::
   :header-rows: 1
   :widths: 18 10 26 46

   * - Space
     - Attribute
     - Base an unmapped R10000 guest uses
     - Source (all *software expectation*)
   * - cached memory
     - none
     - ``0xa800_0000_0000_0000``
     - OpenBSD ``mnode.h`` line 40, ``cpu.h`` line 87, ``GENERIC-IP27``
       line 20; linux-ip35 ``spaces.h`` line 17; same value as the
       Origin 200.
   * - :term:`Hub` special
     - 0
     - ``0x9000_0000_0000_0000``
     - ``cpu.h`` line 98, ``mnode.h`` line 46; ``spaces.h`` line 19.
   * - I/O
     - 1
     - ``0x9200_0000_0000_0000``
     - ``cpu.h`` line 99, ``mnode.h`` line 47, ``ip27_machdep.c`` line
       161; ``spaces.h`` line 20.
   * - memory special
     - 2
     - ``0x9400_0000_0000_0000``
     - ``cpu.h`` line 100, ``mnode.h`` line 48; ``spaces.h`` line 21.
   * - uncached memory
     - 3
     - ``0x9600_0000_0000_0000``
     - ``cpu.h`` line 101, ``mnode.h`` line 49; ``spaces.h`` line 22.

There are exactly four uncached spaces on the MIPS side. The Itanium
port's seven bases do not apply. The model carries the two attribute bits
above the 40-bit physical address in a 42-bit machine-bus address, as it
does for the Origin 200, an *approximation* of an internal path no
software sees.

register the PROM consults, are *unknown*.

.. _sgi-ip35-address-map-memory:

Node memory and the low-memory map
----------------------------------

Memory is reported per bank in 1 GB steps (OpenBSD ``sginode.c`` lines
549-590). The Linux SN1 headers give a 1 GB slot shift, a 64 MB minimum
and eight slots per node (``sn1/arch.h`` lines 47 and 53-54). OpenBSD
does not manage the first 64 MB of a node on IP35, against 32 MB on IP27
(``sginode.c`` lines 566-575, 519-528). All *software expectation*.

The firmware's low-memory map, as the Linux SN1 tree draws it
(``kldir.h`` lines 164-283 for the diagram, 310-361 for the constants),
a *software expectation*:

.. list-table::
   :header-rows: 1
   :widths: 16 54 30

   * - Offset
     - Contents
     - Fixed-offset readers
   * - ``0x0000``
     - processor 0 exception handlers; cache-error frame at ``+0x400``,
       early cache-exception stack at ``+0x800``
     - firmware
   * - ``0x1000``
     - ARCS system parameter block, 1 KB
     - every ARCS guest
   * - ``0x2000``
     - low-memory directory, 1 KB, 16 entries of 64 bytes
     - OpenBSD ``mnode.h`` line 90; both Linux trees
   * - ``0x2400``
     - launch area: four entries of ``0x100``
     - firmware
   * - ``0x3000``
     - NMI handler page, four entries of ``0x40``
     - firmware
   * - ``0x8000``, ``0x10000``, ``0x18000``
     - processors 1 to 3: handlers, cache-error frame, early stack
     - firmware
   * - ``0x9000``, ``0xa000``
     - NMI register save and exception-frame areas, ``0x400`` per
       processor
     - OpenBSD ``ip27.h`` lines 29-31
   * - ``0xb000``
     - global data area, 1 KB (directory slot 3)
     - guests via the directory
   * - ``0x20000``
     - processor-interface error spools, 64 KB (slot 6)
     - via the directory
   * - ``0x30000``
     - configuration graph (KLCONFIG), 64 KB (slot 1)
     - via the directory
   * - ``0x40000``
     - first free memory; non-debug kernel load address
     - ``kldir.h`` line 336; linux-ip35 ``Platform`` line 11; OpenBSD
       links the same address (``GENERIC-IP27`` line 19, one kernel for
       both boards)

The directory slot numbers are unchanged from the Origin 200 (0 launch,
1 KLCONFIG, 2 NMI, 3 GDA, 4 free memory, 5 symmon stack, 6 PI error,
7 kernel variables, 8 kernel cross-partition, 9 partition id: OpenBSD
``mnode.h`` lines 91-100; both Linux trees). The stock IP35 PROM places
its configuration graph at ``0x30000``: a diagnostic message in the image
places node 0's configuration graph at ``0x9600000000030000``, the
uncached-memory alias of that offset (:src:`ip35-prom-6.210`), a *software
expectation*. The Origin 200's offsets (NMI save area
``0x11400``, GDA ``0x11000``, KLCONFIG ``0x4000``, kernel ``0x19000``)
do not apply to IP35.

Interrupt send
--------------

A widget raises a Bedrock interrupt by writing to an XIO address naming
the node, the Bedrock's own widget 1, the remote form and the
interrupt-pending-modify register: bit 47, the node shifted by 39 (38 on
IP27) and the register offset (OpenBSD ``ip27_machdep.c`` lines 350-353;
Linux ``sn/xtalk/xtalkaddrs.h`` lines 66-91). The register and its value
word are on :ref:`sgi-bedrock-pi-interrupts`. The bridge's
interrupt-destination registers carry the Bedrock's crossbar widget
number in bits 51:48 (``xbridge.c`` lines 2177-2191), from the
configuration graph's crossbar record, default ``0xa`` (``sginode.c``
lines 159-160, 338). All a *software expectation*. For a Bridge-class bridge on a node other than 0, OpenBSD
places the node at bit 9 and linux-ip35 at bit 8 (``xbridge.c`` lines
1393-1394; ``pci-sgipic.c`` line 77); which is right is *unknown*.

.. _sgi-ip35-fuel:

The Fuel
========

The ``fuel`` machine builds the IP34 board: one Bedrock with one
processor, an XBridge whose head F carries the onboard ISP12160, IOC3 and
OHCI (the ``fuel`` preset of ``sgi-baseio``), an empty head E, an L1,
and the VPro graphics connector at crossbar widget 13
(:ref:`sgi-ip35-graphics`). The guide's rear panel shows no external XIO
connector (:src:`007-4480-001 p. 6`), *established*.

The IOC3 serves the guide's two serial ports, PS/2 keyboard and mouse,
parallel port and 10/100 Ethernet (:src:`007-4480-001 p. 35-38`),
*established*. An OpenBSD boot on a Fuel reports a DP83843 at MII
address 1 (:src:`miod-openbsd-sgi-story`), *observed*, and the model fits
that transceiver. The guide's lower connector, Serial 1, is IOC3 UART A,
*inferred* from OpenBSD's port map and a PROM menu captured on that
connector (:src:`graphica-o350-notes`).

The onboard Ethernet address comes from the L1. Without input it is
derived: SGI's ``08:00:69`` prefix, which the firmware checks, then
``0xE`` and the kind digit, then the ``emu-id``'s high byte and its low nibble
over the node number (:ref:`sgi-identity`). A machine with no ``emu-id`` has
``08:00:69:e1:00:00`` for node 0. The address is no machine's factory value,
and ``mac`` replaces it. It seeds the L1's address
reply (request ``0x0008``, the address as twelve uppercase hexadecimal
digits, which the PROM turns back into the six bytes), the component-1
board record and the IOC3, and follows ``mac`` when that is set. ``fuel-mac-eeprom=<file>``
replaces it with a 512-byte record image, and a ``-nic mac=`` that
disagrees with the record is refused. Where a physical Fuel stores this
record is *unknown*. :doc:`hardware/l1` has the record format.

A photograph of a revision B Fuel board shows a DS1742W, a 2 KiB clock
part (:src:`graphica-o350-notes`, board photograph), *observed*.
OpenBSD's ``dsrtc.c`` comment names the same package, a *software
expectation*. Its decode on the IOC3 byte bus is *unknown*, and OpenBSD calls its own
mapping a guess. The model fits the flat 32 KiB M48T35-compatible
timekeeper the Origin 300 uses, an *approximation*.

.. _sgi-ip35-numalink:

Origin 300 NUMAlink module and routed topologies
================================================

The Origin 300 topologies beyond one chassis:

``origin300-two-chassis``
  Two complete base modules, each with its own IP45 board, Bedrock,
  XBridge, IO-8 and L1, joined LINK connector to LINK connector by one
  NUMAlink 3 cable with no router, as the guide's "Connecting Two
  Servers" procedure builds them (:src:`007-4365-002 p. 38`),
  *established*. Two published cabled pairs show the per-module parts
  (:src:`marc-openbsd-sgi-139223952727384 lines 17-62`,
  :src:`nekonomicon-17314`), *observed*. The same cable carries the two
  L1s' RS-422 pair (:src:`108-0240-002 p. 2-47`), *established*. Accepted
  ``-smp`` splits are 2+2, 4+2, 2+4 and 4+4, and ``population=`` chooses
  between 4+2 and 2+4. The stock PROM numbers the nodes itself at every
  boot.

``origin300-pci-expansion``
  One base module cabled from its LINK connector to a PCI expansion
  module (:src:`007-4499-002 p. 12`), *established*. The expansion's
  Bedrock interface card (:doc:`hardware/bic`) has no processors or
  memory. Every launch binds the expansion's 16 MiB configuration
  storage, the ``expansion-enclosure-flash`` store
  (:ref:`sgi-sn-storage`). Its startup,
  power, register visibility, interrupt map and identity are
  each an *approximation* listed on :doc:`hardware/pci-expansion`.

``origin300-numalink-pci-expansion``
  Two base modules and a PCI expansion module through one logical
  eight-port SN1 router (:doc:`hardware/sn1-router`). The cables are
  selections: the first module's LINK to router port 1, the second's to
  port 6, the expansion's to port 4. The manual allows base modules on
  ports 1 and 6 and expansion modules only on ports 2 to 5
  (:src:`007-4498-002 p. 10-11, 96`), *established*. The router answers
  as chip revision 1, *inferred* from a six-chassis inventory's router
  "Revision 1" (:src:`nekonomicon-16727514`), and its L1 type ``0x52``
  is the router type letter ``R`` in the Linux SN1 headers
  (``include/asm-ia64/sn/ksys/l1.h`` line 266, v2.5.0 at
  ``381ab1f53816``), a *software expectation*; no captured router reply
  exists. USB and L2 transport, router main power and reset
  propagation between modules are not modelled.

The NUMAlink module has eight external ports, A to H on the rear panel.
Ports 2 to 5 also carry USB and take base or PCI expansion modules;
ports 1, 6, 7 and 8 take base modules only. The module contains an L1
and a USB hub to the rack's L2. A documented system has two to eight
base modules in a tall rack (:src:`007-4498-002 p. 2, 10-16, 93-98,
130-133`). All *established*. The router chip's part number, ASIC count
and silicon revision are *unknown*. Linux SN1 headers name an
eight-port router family with chip identifier ``0x3017``. That this
module carries it is *inferred*. The ``origin300-numalink-module``
composition that records the full rack is a reference model;
:doc:`hardware/bricks` gives its tall-rack cabling.

The NUMAlink module uses the R-brick's router board (:ref:`sgi-bricks-rbrick`).
Ports 1, 6, 7 and 8 take base modules only. Ports 2 to 5 take base or

:src:`007-4498-002 pp. 4, 10-11, 16, 93-98`). In the tall rack

The mapping is *established* from the manual's figure. A live
six-chassis rack whose modules at U12, U14, U18, U22 and U24 reported

:src:`nekonomicon-16727514`). The layer's eight router-port buses carry
these port numbers.

The routed Origin 300 topology selects one logical eight-port SN1 router
(:doc:`hardware/sn1-router`). The public Linux v2.5.0 tree
(``linux-history:381ab1f538162eb985c9244aa7d56e54315881ab``) names router
chip identity ``0x3017`` in ``include/asm-ia64/sn/sn1/bedrock.h`` lines
19-20 and defines the router status fields in
``include/asm-ia64/sn/sn1/router.h`` (*software expectation*). A
published six-chassis Origin 300 inventory reports router revision 1
(:src:`nekonomicon-16727514 lines 390-409 and 1860-1869`). The model
selects chip revision one by inference from that software report
(*inferred*). Neither the inventory nor the manuals measure the fitted
silicon or establish how many router ASICs the enclosure holds. Chip
inputs of zero are an emulator choice (*approximation*).

The router's L1 type is ``0x52`` (``R``), a software profile and not a
measured controller reply (*approximation*). Linux v2.5.0
``include/asm-ia64/sn/ksys/l1.h`` line 266 assigns uppercase ``R`` to
that code. Its ``arch/ia64/sn/io/l1_command.c`` lines 413-436 normalise
uppercase types for module names, and lines 1031-1074 identify the
router module independently of the returned type (*software
expectation*). The NUMAlink module guide establishes a separate L1
controller (:src:`007-4498-002 pp. 14, 96, 130`) but gives no raw type
response. A binary type-query capture from a matching controller would
settle that byte. The module's enclosure and connectors are on
:ref:`sgi-bricks-numalink-module`.

An SN1 router is built as ``/machine/module<M>/router`` beside its
module's L1 and that L1's UART, whether or not the topology carries the
L1 management registry the Origin 300 PCI expansion experiment uses, so
an R-brick needs no I/O peer. Its L1 keeps the type profile above. An
R-brick's own L1 type is *unknown*. A router record's ``node-ports``
lists the only ports a node's cable may use; the builder checks every
cable against it before any device exists.

.. _sgi-ip35-brick-composition:

Origin 3000 brick compositions
==============================

The Origin 3000 servers are built from C-bricks, whose IP35 board
carries a Bedrock, and separate I/O and router bricks
(:doc:`hardware/bricks`). ``-M origin3000`` builds the Origin 3200, the
Origin 3400, the Onyx 3000 and the Onyx 3400 with InfiniteReality3. The
shared builder's rules for a brick composition are described here.

An Origin 3000 C-brick's IP35 board has no XBridge: an XIO cable joins
its Bedrock to port A or B of the XBridge in an I/O brick. The builder
creates that chip as ``/machine/module<M>/xbridge``, or ``xbridge0`` to
``xbridge3`` where a module holds several, as the N-brick's four chips do.
It gives the chip the cable's port as its host port and its module's
catalogue id as its bus prefix, and hands it to the cabled node through
the node's ``xbridge`` link. The node joins and realizes it as an
Origin 300 node does its own. The node's Bedrock decodes the chip at the
cable's port and at each of the chip's heads the node hosts, and nothing
at the chip's other Crosstown2 port.

The builder refuses a second host node on one XBridge, because the model
takes one host port and whether one chip serves hosts on A and B at once
is *unknown*. It refuses a host that is also cabled to a router, for which
it has no rule. It checks a cable between two crossbars, such as the
P-brick's links from its first chip to each of the others, like any other
cable and then refuses it while the cables are built. No source cited
here gives the downstream chips' mode (*unknown*;
:ref:`sgi-sn-family-pbrick`).

An XIO cable from one of the chip's other link ports, 8 to 0xd, reaches
one XIO board: a card in an X-brick slot, or a board on the I-brick's
free Crosstown2 port. The board's own attachment names that port and the
chip's host node, whose Bedrock decodes the board's widget there. The
builder creates the board as ``/machine/module<M>/<board id>`` in the
board's own module and joins it to the port with one XIO link once the
nodes have realized. Only the XIO cards ``pci-carrier``,
``pci-shoehorn``, ``menet`` and ``mscsi``, the V-brick's VPro V12 and
the InfiniteReality pipe of a G-brick are built at such a port. The
builder refuses any other graphics pipe, a BaseIO card or any other
preset cabled there. A V12 record cabled to a crossbar port is a
graphics slot named by the record's catalogue id: ``-device
sgi-odyssey,slot=<id>`` fits the pipe there, it is built in the record's
module, and the chip's host node reaches it at that port. The V-brick's
midplane XBridge takes one host, so a two-pipe V-brick, whose second pipe
needs a second C-brick on the other Crosstown2 port, is refused like any
second host.

A G-brick pipe record at such a port is a slot, named by the record's
label, that ``-device sgi-kona,slot=<label>`` claims after machine init,
as the Onyx2's pipe slot is. The pipe joins the chip's port, sits in its
G-brick's module as ``/machine/module<M>/<board id>`` and composes its
packets for the chip's host port, which the crossbar delivers to the
hosting Bedrock. Each pipe of an N-brick is therefore reached only from
the C-brick cabled to the same chip. A G-brick pipe on an Origin 3000
machine is a model arrangement (*approximation*): no Onyx 3000 hardware
graph or widget listing has been captured, so the widget number at which
a C-brick sees its pipe and the pipe's identity there are not
established.

The machine places the I-brick's ``io7`` base I/O instance as
``/machine/module<M>/io7``, directly on head F of the XBridge in the
I-brick's module, with no board class (:ref:`sgi-sn-family-ibrick`).

A node with ``role: memory`` is a Bedrock with memory banks and no
processor, the shape of the CX-brick's zero-processor board. It realizes
with no CPUs, its boot flash image left as supplied, and answers other
nodes' memory traffic once they have configured and numbered it, as the
firmware reaches a peer through its vector engine. It cannot be the
console node, and a population that fits it a processor is refused.
Whether such a board carries boot flash is *unknown*, so the builder still
requires one.

A controller with ``owner: module`` is built once as
``/machine/module<M>/l1`` and linked into the module's node through the
node's ``l1`` link, in place of the node's own ``/machine/node<N>/l1``.
The node configures it exactly as it would its own, so the guest sees
the same L1. A module with several nodes may own its L1 only with
``profile: cx-brick``: the machine builds the :ref:`Cx-brick L1
<sgi-l1-cxbrick>` itself for one to four IP53 nodes in distinct slots 0
to 3, and each node adds its own UART window on the link its slot names.
A node with the memory role is a board without processors. The brick's
console is the first listed node's L1 serial line. Every other
module-owned L1 shared by several nodes is refused, because how several
Bedrocks reach one L1 is *unknown* outside that profile.

.. _sgi-ip35-firmware:

Firmware and boot
=================

Every machine boots a stock IP35 PROM. ``-bios`` takes the raw payload or
SGI's distribution container, which the machine decodes
(:doc:`prom-image`). The payload must be exactly 1,476,264 bytes
(``0x1686a8``), the size of :src:`ip35-prom-6.210`.

Given only ``-bios``, the PROM's writes to its boot flash do not persist.
On the model the Origin 300 then prints the L1 banner and "Starting PROM
Boot process", resets, and repeats that sequence without reaching a
prompt. A writable boot flash fixes this. ``qemu-sgi-machine-init``
(:doc:`/tools/qemu-sgi-machine-init`) creates one, with the timekeeper
stores, from the same PROM image. With every store bound, ``-bios`` may
be left out.

.. list-table::
   :header-rows: 1

   * - Store
     - Size
     - Starts from
   * - ``node0-flash``
     - 16 MiB
     - the PROM image in the first 8 MiB flash position, with the
       product's configuration-block values, and the blank-media label
       in the second
   * - ``nvram0``
     - 32 KiB
     - zero; the IOC3 timekeeper on the Origin 300 and Fuel, the IO9
       timekeeper on the IP53 products
   * - ``nvram0-clock``
     - 16 bytes
     - zero

A two-node topology adds ``node1-flash``, ``nvram1`` and
``nvram1-clock``. Both topologies with a PCI expansion module add
``expansion-enclosure-flash``, 16 MiB, starting from zero.
:ref:`sgi-sn-storage` describes how stores bind.

Where the processor's reset fetch reaches flash, which flash part is
fitted, and what answers outside the image are *unknown*.
:ref:`sgi-prom-image-ip35-views` gives the views the model maps and why.

The console is the L1's serial line, the first ``-serial``. The PROM
prints through the L1 and its maintenance menu appears there. On the
Origin 300 and Fuel the next serial lines are IOC3 ports A and B; on the
IP53 products they are the four :term:`IOC4` ports (:ref:`sgi-ip53-firmware`). The PROM keeps its console
choice in the boot flash, so it is firmware state, not a board property.

.. _sgi-ip35-running:

Running
=======

Each command below reaches the stock 6.210 PROM's "System Maintenance
Menu" on the L1 line. Create
the stores once per machine, naming the selection as
``qemu-sgi-machine-init --machine help`` spells it:

.. code-block:: shell

   qemu-sgi-machine-init --machine origin300,topology=origin300,nodes=1 \
       --boot-prom ip35prom.img state

Then start the machine on them. For the Origin 300:

.. code-block:: shell

   qemu-system-mips64 -M origin300,node0-flash=f,nvram0=n,nvram0-clock=c \
       -blockdev driver=file,filename=state/node0-flash.raw,node-name=f \
       -blockdev driver=file,filename=state/nvram0.raw,node-name=n \
       -blockdev driver=file,filename=state/nvram0-clock.raw,node-name=c \
       -display none -nodefaults -monitor none -serial file:console.txt

The PROM reports two processors and 512 MB. The same pair of commands,
with the product's own state, runs the Fuel; only the selection and
the start of ``-M`` change (the IP53 products are on
:ref:`sgi-ip53-running`):

.. list-table::
   :header-rows: 1

   * - Product
     - ``qemu-sgi-machine-init --machine``
     - Start of ``-M``
     - PROM reports
   * - Fuel
     - ``fuel,topology=fuel,nodes=1``
     - ``fuel``
     - one processor, 512 MB

The commands pass ``-nodefaults``, which leaves the Fuel's graphics
connector empty, as ``-vga none`` does (:ref:`sgi-ip35-graphics`). Drop
``-nodefaults`` or add ``-device sgi-odyssey,slot=widget-13,product=v12``
to fit a V12.

Booting IRIX from here needs a disk on ``scsi.0``, the first onboard SCSI
controller, or a netboot through the IOC3. :ref:`sgi-sn-launch-metadata`
lists each product's launch hints.

.. _sgi-ip35-graphics:

Graphics
========

``fuel`` fits a V12 VPro at its graphics connector by default, as
``-device sgi-odyssey,slot=widget-13,product=v12`` would. Both
``-vga none`` and ``-nodefaults`` leave the slot empty. A Fuel IRIX inventory and an OpenBSD capture both
place the VPro at widget 13 (:src:`tingo-fuel-irix-console`,
:src:`miod-openbsd-sgi-story`), *observed*. The captured Fuel carried a
V10, so fitting a V12 there is a choice.

The other IP35 topologies have no graphics slot, and the IP53 products'
optional V12 is on :ref:`sgi-ip53-graphics`. :ref:`sgi-sn-graphics-pipes`
describes how slots, defaults and refusals work, and
:doc:`hardware/odyssey` describes the board.

.. _sgi-ip35-unknowns:

Open questions
==============

- The low bits of every product's board-identification word.
- The Origin 300 IO-8's timekeeper part.
- The Fuel's DS1742W decode, its interrupt wiring on revision G, where
  its Ethernet-address record lives, and its L1 type reply.
- The physical-to-software memory bank mapping on every product.
- How the reset fetch reaches flash, the fitted flash part, and which
  register the stock PROM reads on a warm reset.
- How a guest learns M or N mode, and whether a Bedrock still needs the
  widget-0 remap through big window 6.
- The NUMAlink module's router silicon and the L1's USB branch.
- The Origin 300 rear XIO connector's crossbar port.

The IP53 board's open questions are on :ref:`sgi-ip53-unknowns`.
