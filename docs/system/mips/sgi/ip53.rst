.. _sgi-ip53:

===========================================
IP53: Origin 350, Onyx 350, Tezro and Onyx4
===========================================

:term:`IP53 <IP number>` is the :term:`node board` of SGI's Origin 350, Onyx 350 and Tezro, and the
board the Onyx4 host path stands on. It is an IP35-platform board: a
:term:`Bedrock` node controller, a :term:`PIC` instead of the :term:`XBridge`, and an IO9 PCI
board carrying :term:`IOC4`, an ISP12160 SCSI controller and a BCM5701
Ethernet controller. QEMU models four products on it, ``origin350``,
``onyx350``, ``tezro`` and ``onyx4``
(``hw/mips/sgi/sn1.c``). Each node is an ``sgi-sn1-node``
(``hw/mips/sgi/sn1-node.c``), and the shared Scalable Node builder in
``hw/mips/sgi/sn-machine.c`` assembles the nodes from the compiled
catalogue (:doc:`sn`). Every machine boots the stock IP35 :term:`PROM` that the
user supplies (:ref:`sgi-ip53-firmware`). This page is the hardware
contract the IP53 model layers in ``hw/mips/sgi/models/`` cite: what
each product fits, how it is wired, and where the emulator chose a value
the hardware does not settle. The Bedrock node, the physical address map
and the PROM are shared with the Origin 300 and Fuel and are described
on :doc:`ip35`. Chip register behaviour is on the part pages listed
under :ref:`sgi-ip53-devices`.

Facts are rated as described in :ref:`sgi-ratings`.

The four products are serial software profiles. Each fixes a processor,
memory, PIC and IO9 population drawn from one published capture or
manual, and fills the gaps with stated choices. They run the stock PROM
and IRIX on the model. They do not establish that any physical IP53
board is wired the way they are.

.. _sgi-ip53-machines:

Machines
========

Each machine builds one Bedrock node. ``-M <machine>,topology=`` selects
a wiring the catalogue lists. A topology name is unique and fixes the
node board: a name ending ``-ip53`` builds the IP53, one ending ``-ip59``
the IP59 (:ref:`sgi-ip59-profiles`). An unknown name, such as ``topology=help``,
makes the machine print the topologies it accepts, each once, and exit.

.. _sgi-ip53-processors:

Processors
----------

The profiles fit the R16000 with each profile's clock, cache size and
reset mode word (:ref:`sgi-ip53-serial-profiles`). :doc:`hardware/r10000`
describes the identity words, the reset mode word and how the R16000
inputs are checked.

The model's 700 MHz Origin 350 and Tezro profiles report PRId ``0x0f41``, the
revision 2.1 part their node boards carry. ``-cpu R16000,r16000-prid=``
names another revision. The Onyx 350 and the IP59 profiles keep
``0x0f50``.

A Bedrock has two processor interfaces with two processors each. The
machine populates them diagonally: a two-processor node fits interface 0
position A and interface 1 position A first (``sn1-topology.c``).

.. _sgi-ip53-offerings:

Processor offerings
~~~~~~~~~~~~~~~~~~~

An IP53 node board's processors are soldered to it, so each offering is
a board's part with its own revision, cache, cache clock, reset word and
flash word, not a free choice of clock and cache. The first offering of
each machine is its default; ``processor=`` names another, and an offering
that is not listed is refused with the ones that are.

.. list-table::
   :header-rows: 1

   * - Machine
     - ``processor=``
     - Part
     - PRId
     - Reset mode
     - Flash word
     - Node board
   * - ``origin350``, ``tezro``
     - default
     - R16000 700 MHz, 4 MiB, cache at 350 MHz
     - ``0x0f41``
     - ``0x009bad85``
     - ``0x589bad85``, tap ``0xc``
     - ``030-1868-001``, ``030-1869-001``
   * - ``tezro``
     - ``r16000-800mhz-4mb-rev22``
     - R16000 800 MHz, 4 MiB, cache at 400 MHz
     - ``0x0f42``
     - ``0x009baf85``
     - ``0x549baf85``, tap ``0xa``
     - ``030-1956-002``
   * - ``origin350``, ``tezro``
     - ``r16000-800mhz-8mb-rev22``
     - R16000 800 MHz, 8 MiB, cache at 400 MHz
     - ``0x0f42``
     - ``0x009caf85``
     - ``0x549caf85``, tap ``0xa``
     - ``030-1959-003``

The Origin 350 offers the 700 MHz and the 800 MHz, 8 MiB parts. The Tezro
offers all three, on both its single-enclosure and rack topologies;
the 800 MHz boards are four-processor boards, so the one- and
two-processor Tezro keeps its 700 MHz part. The id carries the revision
because the Onyx 350's 800 MHz, 8 MiB part is revision 3.0
(``0x0f50``), so the two share a clock and cache and not an id. An
offering fits its board's flash word, the L1's node-board record and CPU
context, the processor clock and the Config0 reset word together.

Published inventories print each tuple with its part, cache clock and tap
(*observed*). The PRId follows from the printed revision by the rule
IRIX and the PROM apply to print it, major nibble the printed major plus
2 (*inferred*). Each flash word is a row of the PROM's configuration
table (rows 26, 20 and 21), which carries machine type 2 where the
profiles store 0, and each reset word is its low 25 bits, a model
derivation, not a measured value (*approximation*). The FPU
identification stays ``0x0900``, the R12000 and R14000 value, a model
choice no R16000 reading supports (*approximation*).

.. _sgi-ip53-memory:

Memory
------

Each topology fixes one memory population, and ``-m`` must name its
total. The bank positions are model choices unless stated.

.. list-table::
   :header-rows: 1

   * - Product
     - Banks (MiB) at positions
     - Basis
   * - Origin 350
     - 1024, 1024 at banks 0 and 1
     - *approximation*; no DIMM part or SPD is supplied
   * - Onyx 350
     - eight banks of 1024 at 0-7
     - *observed* logical banks of the captured Onyx 350 module
       (:src:`graphica-onyx350-hinv`)
   * - Onyx 4 host
     - eight banks of 1024 at 0-7
     - *approximation*; the bank map is borrowed from the Onyx 350
       capture
   * - Tezro
     - 1024, 1024, 512, 512, 512, 512 at 0-5
     - *observed* logical banks of the captured 700 MHz Tezro
       (:src:`graphica-tezro-hinv`)

The Origin 350 has eight DIMM slots as four pairs of 512 MB or 1 GB
DIMMs, 1 to 8 GB, and a :term:`NUMAlink` module takes a system to 4 to 32
processors (:src:`007-4566-001 p. 69`; :src:`007-4566-001 p. 114, 116`),
*established*. Larger and unequal populations are not offered. The
Bedrock's memory banks are described on :doc:`hardware/bedrock`.

A fixed IP53 profile may give its nodes different bank totals
(:ref:`sgi-sn-topology`). QOM bank values and address-map checks do not establish the stock PROM's memory
configuration entries for such a layout, so an unequal-memory IP53
profile needs a full-composition boot before its memory is trusted.

.. _sgi-ip53-identity:

Board identity inputs
---------------------

Each product carries the values its firmware reads to recognise it. They
are catalogue defaults. Machine properties of the same names override
them: ``board-id-word``, ``l1-type-code``, ``l1-revision`` and
``bedrock-revision``.

.. list-table::
   :header-rows: 1

   * - Product
     - Board word
     - L1 type
     - L1 revision
     - Flash machine type
   * - Origin 350, Onyx 4 host
     - ``0x2001``
     - ``0x37`` (``7``)
     - 1.18.5
     - 0
   * - Onyx 350
     - ``0x2001``
     - ``0x38`` (``8``)
     - 1.18.5
     - 0
   * - Tezro tower
     - ``0x2001``
     - ``0x39`` (``9``)
     - 1.48.1
     - 0
   * - Tezro rack
     - ``0x2001``
     - ``0x51`` (``Q``)
     - 1.48.1
     - 0

- Board word bits 15:12: OpenBSD reads them as the product code and
  assigns Origin 350 2 (``ip27.h`` lines 43-46, ``ip27_machdep.c`` lines
  165-185), a *software expectation*. The low bits are *unknown* on
  every product. On the IP53 products the low bits ``0x001`` are a
  choice. The register is on :doc:`hardware/bedrock`.
- L1 type: Kaloz's series maps ``9`` and ``Q`` to the Tezro deskside and
  rack (:src:`lore-kaloz-ip35-35`), a *software expectation*. The stock
  IP35 PROM names type ``7`` the 2U server and ``8`` the graphics module,
  and on a fresh NVRAM picks the graphics console for ``8``, ``9`` and
  ``Q`` (:src:`ip35-prom-6.210`), a *software expectation*. A published
  POD session on a real Onyx 350 graphics module with a VPro board prints
  the graphics-module class and then installs the graphics console
  (:src:`graphica-o350-notes`), *observed*, so the Onyx 350
  profile reports ``8``, *inferred*. ``0x37`` on the Origin 350 and the
  Onyx 4 host is a choice. No captured L1 type reply exists for any of
  them, *unknown*. No published L1 image labels type ``8`` in its
  ``brick`` reply, so the model leaves that reply unanswered for the
  Onyx 350, an *approximation*.
- L1 revision: the Tezro's 1.48.1 is the image in the IP35 patch
  :src:`ip35-patch-sg0007149`. The others are choices.
- Flash machine type: the value written into the PROM's configuration
  block. The IP53 value 0 is a choice. :doc:`prom-image` gives the block
  layout.
- Bedrock revision 2 at 200 MHz: every published Origin 350 and Onyx 4
  inventory reports ``HUB`` revision 2, *observed*. The raw register
  value behind that field is *unknown*.

Barcodes and serial numbers in board records are synthetic ``EMU``
values carrying a ``QEMU`` marker, not taken from a real machine.

.. _sgi-ip35-ip53:

IP53 profiles
=============

The four IP53 machines run serial profiles, one per topology and board.
Each fixes one memory map, one I/O construction and the processor
populations it accepts, and the machine fits the processors itself with
no machine option or ``-cpu`` property. A population, memory size or
processor the topology does not describe is refused, and so is a
``maxcpus`` above the ``-smp`` count. A ``-cpu`` ``reset-mode`` that
differs from the board's word is refused. None fits a graphics pipe by
default.

Each processor profile also carries a flash configuration word that the
stock PROM prints as the secondary-cache tap. Each word is the word of a row
of the PROM's configuration table; the rows carry machine type 2 where the
profiles store 0: ``0x589bad85`` for the Origin 350 and the Tezro,
700 MHz with 4 MiB and tap ``0xc``, and ``0x549caf85`` for the Onyx 350,
800 MHz with 8 MiB and tap ``0xa``, the taps the captured boards of those
tuples print (all but one ``030-1868-001`` board; that one prints ``0x1c``
under an older PROM). The Origin 3900 Cx-brick uses ``0x549cad85``, 700 MHz
with 8 MiB and tap ``0xa``. The reset words in the table are not table rows:
each is the low 25 bits of its flash word, a model derivation, as is the
Onyx 4 host's pair below. The tap bits (28:25) lie outside the low 25 bits
only for taps up to ``0xf``; a ``0x1x`` tap such as the 1 GHz ``0x15`` sets
bit 22, which the reset word keeps. The Origin 350 profile uses the 4 MiB
tuple of the ``030-1868-001`` board; the only 700 MHz, 8 MiB board is
``030-1812-002``, seen in one Onyx 350, and the Cx-brick word borrows its
tap.

The reset mode words, PIC placement and revision, IOC4 clocks, Bedrock
board word ``0x2001`` and L1 identities are software inputs, not
measured values (*approximation*). The capture facts behind each profile
follow. Two profiles carry a node-board identity record for the L1 to
serve, taken from their captures: ``IP53_4CPU``, ``030-1868-001``,
revision C on ``origin350`` and ``IP53_4CPU``, ``030-2013-001``, revision
D on ``onyx350``. The Tezro records are in :ref:`sgi-ip35-tezro`. No
capture supplies raw EEPROM bytes.

.. _sgi-ip35-origin350:

Origin 350
~~~~~~~~~~

The Origin 350 compute module holds two or four R16000, eight DIMM
slots in four pairs for 1 to 8 GB, one
Bedrock, one external NUMAlink 3 port, an L1 with a display, and the IO9
in the lowermost PCI slot (:src:`007-4566-001 p. 68-75, 114, 116`),
*established*. One published inventory reports the board
``030-1868-001`` revision C, a PIC carrier at widget 15 and IO9
``030-1771-005`` revision A (:src:`nekonomicon-16724207`), and another
reports Bedrock revision 2 (:src:`nekonomicon-16729141`), *observed*.

The profile's four 700 MHz R16000 with 4 MiB of secondary cache each
are the tuple of the ``030-1868-001`` board it cites, the catalogue's
choice, an *approximation*; the cache fitted to each processor option is
*unknown*. Its 2 GiB in two banks is not a captured
population, also an *approximation*.
The Bedrock's entry widget on an Origin 350 server is *unknown*. A
published PROM trace from a four-processor IP53 module attaches the
Bedrock at widget ``0xb`` (:src:`graphica-o350-notes lines 949-952`),
*observed*. The module reads as an Onyx 350 graphics blade (*inferred*),
and the split may follow the blade type rather than the product, so an
Origin 350 with graphics could also use ``0xb``. No Origin 350 trace is
published. The ``origin350`` profile reports ``0xa``, an *approximation*
that may disagree with the hardware. The profile names no netboot
adapter.

The ``origin350`` machine is a one-node software profile, an emulation
target with explicit model choices, not a claim that its memory,
firmware seed, PIC setup or board wiring reproduce a measured machine.
The hardware facts its layers cite, beyond those above:

- Each DIMM pair feeds a pair of banks, and 4 MB of secondary cache per
  processor is the guide's figure (*established*,
  :src:`007-4566-001 pp. 69, 114, 116`).
- The Bedrock's NUMAlink 3 port is one external LINK connector, empty
  in a one-module system (*established*, :src:`007-4566-001 p. 69`).
  Revision 2 at 200 MHz is *observed* in one inventory
  (:src:`nekonomicon-16729141`).
- The L2 controller is present only with a NUMAlink module
  (*established*, :src:`007-4566-001 pp. 68-75`).
- The PIC has two PCI-X heads on one widget, the second head's
  registers ``0x800000`` above the first (*software expectation*:
  OpenBSD ``sys/arch/sgi/xbow/xbridgereg.h`` lines 24-28 and
  ``xbowdevs``, part ``0xd102``, second head ``0xd112``, manufacturer
  ``0x024``, at ``2df91d80c104636deeef8124252ddd5951b55fbf``). Widget
  15 is *observed* in one inventory (:src:`nekonomicon-16724207`).
- The IO9 card is in the lowermost slot, on bus 1 (*established*,
  :src:`007-4566-001 p. 69`). The IOC4 ``10a9:100a`` is at configuration
  device 1, the ISP12160 ``1077:1216`` revision 6 at 3 and the BCM5701
  ``14e4:1645`` at 4 (*observed* in every captured IP53 inventory;
  :ref:`sgi-ip35-ip53-io9`). PIC's configuration devices are its
  internal slots plus one (OpenBSD ``xbridge.c``), so the PCI ids IRIX
  prints are OpenBSD's devices plus one (*inferred*).

The Origin 350's widget identity words for Bedrock and PIC are
*unknown*. The Onyx 350 trace above comes from an IP53 graphics module
with four processors and 8 GiB. That an Origin 350 server board enters
at the same widget is *inferred* from the shared IP53 board.

.. _sgi-ip35-onyx350:

Onyx 350
~~~~~~~~

The profile builds one module, ``001c01``, of a published multi-module
Onyx 350 (:src:`graphica-onyx350-hinv`), without its graphics or the
other modules. The capture reports board ``IP53_4CPU`` ``030-2013-001``
revision D, four 800 MHz R16000 revision 3.0 with 8 MiB caches, Bedrock
revision 2 at 200 MHz, 8 GiB in eight logical 1 GiB banks, a
``2U_INT_53`` carrier ``030-1809-006`` revision D at widget 15 and IO9
``030-1771-006`` revision A, *observed*. A published PROM trace of a
four-processor IP53 module attaches the Bedrock at widget ``0xb``
(:src:`graphica-o350-notes lines 949-952`), *observed*, and reads as an
Onyx 350 graphics blade (*inferred*). The profile sets the Bedrock's
``host-widget`` property to ``0xb`` so the widget control register reads
that value. This sets the register only. The XBridge stays wired to
port ``0xa`` (``SN1_XBRIDGE_HOST_PORT``), an *approximation* where the
trace puts the entry at ``0xb``; the stock PROM and IRIX 6.5.30 run with
it, which shows compatibility only. The capture does not show the
module booting alone, and it reports PROM 6.211 where the model runs
6.210. The guide describes the base module's factory disk, four-port USB
card, IO9 and serial daughtercard (:src:`007-4632-001 p. 47, 50, 53`),
*established*. The capture does not tie them to this module, and none
of them is built. The netboot adapter is the BCM5701.

.. _sgi-ip35-tezro:

Tezro tower and rack
~~~~~~~~~~~~~~~~~~~~

The tower guide allows one, two or four processors with 4 MB of cache
and places IO9 at bus 1, slot 1. The two- and four-processor board has a
second :term:`XIO` connector for an optional board; the one-processor board has
one (:src:`007-4564-001 p. 26-30, 38`). The rack guide gives the same
processor choices and 8 or 16 GiB in one or two enclosures
(:src:`007-4643-003 p. 21-32`). All *established*.

The profiles take their processors, memory and IO9 from a published
four-processor Tezro captioned as a deskside (:src:`graphica-tezro-hinv`):
``IP53_4CPU`` ``030-1868-001`` revision C, four 700 MHz R16000 revision
2.1 with 4 MiB caches, Bedrock revision 2, 4 GiB in six banks,
``WS_INT_53`` boards at widgets ``0xb`` and ``0xf``, and IO9
``030-1771-005`` revision A at ``0xf``, *observed*. Applying it to a
tower or a rack is *inferred* from the product family. An 800 MHz
Tezro inventory reports the same two interface-board widgets
(:src:`irixnet-post-26015`), *observed*.

The ``tezro`` topology holds both interface boards, and ``-smp`` picks
one: one processor builds the one-processor board, two or four the
two/four-processor board. The two/four-processor board builds two PICs,
at widgets 11 and 15, with the IO9 on the widget-15 PIC's head 0 and
nothing on the other. The model routes its widget-0 view through the PIC
that owns the IO9, an *approximation*: through the widget-11 PIC, the
stock PROM could not build its configuration for the node on the model.
The one-processor board builds one PIC, at widget 15. That it has one is
*inferred* from that board's two PCI-X buses
(:src:`007-4564-001 p. 26-31`); no inventory shows it. ``tezro-rack``
builds one PIC, at widget 15, and models the first enclosure only. Every
Tezro profile builds the IO9 BCM5701, and the netboot adapter is the
BCM5701 on each.

The 4 GiB is a selected memory kit, not a measured population. It
matches the observed four-processor 700 MHz population above, with the
bank placement *inferred*. The one-processor board's installed DIMMs are
*unknown*, so its 4 GiB, and the rack's, only reuse that kit.

The Tezro's L1 serves the node board the published Tezro inventories
print: ``IP53_4CPU``, part ``030-1868-001``, revision ``-C``, with four
processors on slices A to D (:src:`nekonomicon-16728583`;
:src:`nekonomicon-16726767`), and ``IP53_2CPU``, part ``030-1869-001``,
revision ``-C``, with two on slices A and C (:src:`preterhuman-tezro`;
:src:`nekonomicon-16727444`), *observed*. No inventory shows a
one-processor board, so one processor keeps the L1's generic record. The
rack's first enclosure takes the record for its processor count,
*inferred*.

.. _sgi-ip35-onyx4:

Onyx 4 host
~~~~~~~~~~~

An Onyx 4 host carries the system's PCI cards, including the boot IO9 at
bus 1, slot 1, and connects to G2N bricks over NUMAlink. A serial
terminal attaches to the host's L1 (:src:`007-4634-002 p. 1-2, 15,
20-23, 30-32`). All *established*. The profile takes module ``001c01`` of
a published two-module inventory: board ``IP59_4CPU`` ``030-1989-003``
revision ``-C``, four 1 GHz R16000 revision 3.0 with 16 MiB caches, 8 GiB,
and IO9 ``030-1771-006`` revision ``-A`` below the ``2U_INT_53`` interface
board at widget 15 (:src:`irixnet-thread-2263-page-2`), *observed*. The
poster's first-page inventory shows the same processors and memory for
this module but prints the board only as an ``IP35`` node board, with no
part number (:src:`irixnet-thread-2263`). Module ``001c02``, the graphics
brick, reports a second ``IP59_4CPU`` of the same part at revision ``-D``.
The poster says a quad 1 GHz board was installed in the Onyx 4 G2N brick
after a trade, and the first page shows ``001c02`` with 800 MHz
processors, so ``001c02`` holds the fitted board, *inferred*. The poster
built the system in an Onyx 350 prototype chassis, so treating ``001c01``
as the Onyx 4 host is *inferred*.

The model maps this IP59 board onto the IP53 board path, its PIC and its
IO9 wiring, an *approximation*: no source describes the IP59 PIC, its
revision or its routes. ``onyx4`` builds only this board: no source
gives the Onyx 4 host an IP53 processor tuple, so no IP53 topology is
offered there. It builds no G2, G2N or NUMAlink peer. The
``onyx4-g2`` and ``onyx4-g2n`` compositions are reference
models that no machine builds.

IO9 and its PCI routes
~~~~~~~~~~~~~~~~~~~~~~

.. list-table::
   :header-rows: 1

   * - Function
     - PCI identity
     - Device
     - PCI revision
     - PIC input
   * - IOC4
     - ``10a9:100a``
     - 1
     - ``0x53``
     - 0
   * - ISP12160
     - ``1077:1216``
     - 3
     - ``0x06``
     - 2
   * - BCM5701
     - ``14e4:1645``
     - 4
     - ``0x00``
     - 3

Every captured IP53 inventory places these functions at IRIX PCI ids 1,
3 and 4, *observed*. PIC configuration devices are its internal slots
plus one (OpenBSD ``xbridge.c``), so these are the configuration devices
too, *inferred*. The revisions are the existing models' values, not read
from any IO9; one Tezro PROM prints a BCM570x revision of ``15``
(:src:`irixnet-thread-3613`). Each function's INTA goes to the PIC input
numbered one below its device, the linux-ip35 ``pci-sgipic.c``
convention (lines 51-100, 383-413), a *software expectation*. The
physical routes are *unknown*.

.. _sgi-ip53-pic:

PIC
~~~

Each PIC is one widget with two PCI-X heads, the second head's
registers ``0x800000`` above the first (OpenBSD ``xbridgereg.h`` lines
24-28 and ``xbowdevs``: part ``0xd102``, second head ``0xd112``,
manufacturer ``0x024``), a *software expectation*. The profiles select revision 3
behaviour and their direct-DMA settings as named compatibility profiles.
These do not establish the fitted PIC revision, its reset image or the
Bedrock-to-PIC wiring. :doc:`hardware/pic` describes the model and its
profiles.

.. _sgi-ip53-ioc4:

IOC4
~~~~

IO9 carries one IOC4 function, ``10a9:100a``, at the existing model's
revision ``0x53``, with serial DMA enabled. The clock is 33,333,333 Hz on
the Origin 350, Onyx 350 and Onyx 4 host profiles and 66,666,667 Hz on
the Tezro profiles, all choices; the board straps are *unknown*. The L1
console and the four IOC4 serial ports are separate endpoints, as the
Onyx 350 and Onyx 4 guides describe. :doc:`hardware/ioc4` describes the
model, including how its serial ring DMA differs from :term:`IOC3`'s.

.. _sgi-ip53-bcm570x:

BCM5701
~~~~~~~

IO9's Ethernet is the generic ``bcm570x`` model as a single-port BCM5701,
``14e4:1645``. The fitted IO9 Ethernet part and its revision are
*unknown*. :doc:`hardware/bcm570x` describes the model.

.. _sgi-ip53-ds1742:

.. _sgi-ip53-ds1744:

Timekeeper
~~~~~~~~~~

Every IP53 profile links a DS1744-compatible 32 KiB timekeeper
(:src:`analog-ds1744-rev-6-13`) to IOC4, mapped whole at IOC4 BAR0
offset ``0x80000`` with the clock in its last eight bytes, the span
OpenBSD's driver uses. A fresh or blank clock starts from the 1968 year
base. Its data and clock record are the ``nvram0`` and ``nvram0-clock``
stores. Fitting this part to IO9 is an *approximation*: the datasheet supports
the part's behaviour, not its presence on the board. The fitted IO9 part
and its address wiring are *unknown*. The model also has a DS1742
selection exposing only the clock bytes of a 2 KiB part; no profile uses
it. :doc:`hardware/timekeepers` describes both parts.

.. _sgi-ip53-io-profile:

Profile boundaries
~~~~~~~~~~~~~~~~~~

The Origin 350 and Onyx 350 captures are different boards in different
systems. Neither profile's topology or unmeasured behaviour is inferred
from the other, and the two-PIC Tezro layout is not inferred from an
Origin 350. A guest reaching the PROM menu or an IRIX login on one of
these profiles shows that the model runs that software, not that the
named product is wired that way.

.. _sgi-ip59-profiles:

IP59 node board profiles
------------------------

IP59 is the 1 GHz generation of the IP53 board (OpenBSD
``share/man/man4/man4.sgi/intro.4`` at ``2df91d80c104``, lines 113-114).
Two published inventories carry IP59 board records: the Onyx 4 above
(:src:`irixnet-thread-2263-page-2`) and a Tezro rack
(:src:`nekonomicon-16719032`). Both report a Bedrock, printed as ``HUB``
in the Tezro, at revision 2 and 200 MHz, and an IO9 of part ``030-1771``,
as the IP53 inventories do: ``-006`` revision ``-A`` in the Onyx 4 and
``-005`` revision B in the Tezro, *observed*. That IP59 was sold as an
upgrade for the Origin 350, Onyx 350 and Tezro is *inferred*; the Onyx 4
poster reports fitting a quad 1 GHz board into an Onyx 4 G2N brick.

The model builds each IP59 product from the IP53 assembly, PIC and IO9
and changes only the node-board record and the processors: 1.0 GHz
R16000 revision 3.0 with a 16 MiB secondary cache at one third of the
processor clock, which both captured IP59 inventories print as ``Speed
333 Mhz  Tap 0x15`` (:src:`irixnet-thread-2263-page-2`;
:src:`nekonomicon-16719032`), *observed*. Reusing the IP53
PIC and IO9 wiring is an *approximation*: no source describes them on
IP59.

Each IP53 topology also has an IP59 twin, named with ``-ip59`` in place
of ``-ip53``, at the same memory. The IP53 stays the default of
``origin350``. ``onyx4`` builds only the IP59, which is therefore
its default. The first column below names a topology without its
``-ip53`` or ``-ip59`` suffix.

.. list-table::
   :header-rows: 1

   * - Topology
     - Machine
     - Memory
     - Boards
   * - ``origin350``
     - ``origin350``
     - 2 GiB
     - ``ip53`` (default), ``ip59``
   * - ``onyx350``
     - ``onyx350``
     - 8 GiB
     - ``ip53`` (default), ``ip59``
   * - ``tezro``
     - ``tezro``
     - 4 GiB
     - ``ip53`` (default), ``ip59`` with two or four processors
   * - ``tezro-rack``
     - ``tezro``, first enclosure of a rack
     - 4 GiB
     - ``ip53`` (default), ``ip59`` with two or four processors
   * - ``onyx4``
     - ``onyx4``

     - ``ip59`` only
   * - ``origin3900``
     - ``origin3000``, one Cx-brick
     - 2 GiB per node board

The L1 serves the node board from its record, as on IP53. A
four-processor node reports ``IP59_4CPU``, part ``030-1989-003``,
revision ``-C`` (:src:`irixnet-thread-2263-page-2`), and a two-processor
node ``IP59_2CPU``, part ``030-2059-002``, revision ``A``
(:src:`nekonomicon-16719032`), both *observed*. The Onyx 4's second board
is revision ``-D``, which no profile serves. Neither inventory shows a
one-processor IP59 board, so its record is *unknown*, and the IP59
builds only on the Tezro two/four-processor board: there is no
one-processor IP59 topology, and the rack's first enclosure takes two or
four IP59 processors. Serial
numbers and barcodes are synthetic.

The reset mode word ``0x00edb385`` and the flash configuration word
``0x4aedb385`` are *inferred* inputs, not measured values. Neither word is a row
of the PROM's configuration table, which has no 1 GHz row, and no Config register or
processor revision register has been read from a 1 GHz module. The two
words agree in their low 25 bits. Those bits hold secondary cache size
code 5, which selects the 16 MiB the captures print (*observed*),
secondary clock divisor code 5, system clock divisor code 9 and bit 22.
That the divisor codes mean one third and one fifth of the processor
clock, giving the printed 333 MHz cache clock and a 200 MHz hub, and
that bit 22 yields tap ``0x15``, are *inferred*: the captures print only
the results, and 800 MHz boards in the cited threads print tap
``0xa``. A boot that printed the PROM's invalid-tap message would refute
that reading. Whether the part is an R16000A is *unknown*. The PROM
payload is the 6.210 image the IP53 profiles use.

The model builds an Origin 3900 Cx-brick with IP53 or IP59 node boards,
not a mix: ``origin3900-ip59`` fits four IP59 boards, the generator refuses a
record that mixes the two, and the Cx-brick's L1 reports
the ``IP59_4CPU`` record for each. No Cx-brick inventory is published,
so the composition is an *approximation*, and whether a Cx-brick's IP59
is the same board as the 2U one is *unknown*. The 16 MiB cache follows
the captured 2U boards.

The L1 model carries no IP59 fan, sensor or expander tables and produces
no environment readings for either board.

.. _sgi-ip53-firmware:

Firmware and boot
=================

Every machine boots the stock IP35 PROM, :src:`ip35-prom-6.210`, from the
``-bios`` payload or from a bound boot flash, as described in
:ref:`sgi-ip35-firmware`. The IO9 timekeeper's stores are ``nvram0`` and
``nvram0-clock`` (:ref:`sgi-ip53-ds1744`). The console is the L1's serial
line, the first ``-serial``. The next four serial lines are the IOC4
ports.

.. _sgi-ip53-running:

Running
=======

Each command below reaches the stock 6.210 PROM's "System Maintenance
Menu" on the L1 line. Create the stores once per machine, naming the
selection as ``qemu-sgi-machine-init --machine help`` spells it, then
start the machine on them. For the Origin 350:

.. code-block:: shell

   qemu-sgi-machine-init \
       --machine origin350,topology=origin350-ip53,nodes=1 \
       --boot-prom ip35prom.img state

   qemu-system-mips64 -M origin350,node0-flash=f,nvram0=n,nvram0-clock=c \
       -blockdev driver=file,filename=state/node0-flash.raw,node-name=f \
       -blockdev driver=file,filename=state/nvram0.raw,node-name=n \
       -blockdev driver=file,filename=state/nvram0-clock.raw,node-name=c \
       -display none -nodefaults -monitor none -serial file:console.txt

The PROM reports four processors and 2048 MB. The same pair of commands,
with each product's own state, runs the others; only the selection and
the start of ``-M`` change:

.. list-table::
   :header-rows: 1

   * - Product
     - ``qemu-sgi-machine-init --machine``
     - Start of ``-M``
     - PROM reports
   * - Origin 350
     - ``origin350,topology=origin350-ip53,nodes=1``
     - ``origin350``
     - four processors, 2048 MB
   * - Onyx 350
     - ``onyx350,topology=onyx350-ip53,nodes=1``
     - ``onyx350,topology=onyx350-ip53``
     - four processors, 8192 MB
   * - Tezro
     - ``tezro,topology=tezro-ip53,nodes=1``
     - ``tezro,topology=tezro-ip53``, with ``-smp 4``
     - four processors, 4096 MB
   * - Onyx 4 host
     - ``onyx4,topology=onyx4,nodes=1``
     - ``onyx4``
     - four processors, 8192 MB

Booting IRIX from here needs a disk on ``scsi.0``, the first onboard SCSI
controller, or a netboot through the BCM5701 where the profile names it.
:ref:`sgi-sn-launch-metadata` lists each product's launch hints.

.. _sgi-ip53-graphics:

Graphics
========

None of the IP53 machines fits a graphics pipe by default.
Both Tezro boards and ``onyx350``, on either node board, take an
optional V12 at
``widget-12``, ``-device sgi-odyssey,slot=widget-12,product=v12``.
The published 700 MHz Tezro inventory reports its V12, part ``030-1884-002`` revision D, at widget 12
(:src:`graphica-tezro-hinv`), *observed*. The same Onyx 350 module, 001c01, was also published with a V12, part
``030-1909-008`` revision B, at widget 12 (:src:`graphica-onyx350-hinv`,
section "Origin / Onyx O350, Numalink'ed, V12 & DMedia DM3 etc"),
*observed*. The InfiniteReality section of the same page lists the module
with that pipe instead. The pipe
links to that port of the crossbar of the PIC that owns widget 0, uses
the Bedrock's graphics-credit handling, and is marked alive once it
realizes. The route from either physical XIO connector to the Bedrock is
*unknown*. On the one-processor Tezro board the slot reuses the
two/four-processor board's widget 12 and route, *inferred*: the
Tezro guide gives that board one XIO connector for a VPro board
(:src:`007-4564-001 p. 29-30`) but names no widget. On the model, with a
V12 fitted to the four-processor Tezro, the stock PROM finds the Odyssey
board on nasid 0 and passes its diagnostics.

The other IP53 topologies have no graphics slot. :ref:`sgi-sn-graphics-pipes`
describes how slots, defaults and refusals work, and
:doc:`hardware/odyssey` describes the board.
