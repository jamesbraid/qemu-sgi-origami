.. _sgi-r10000:

=========================
R10000-family processors
=========================

The R10000, R12000, R14000 and R16000 are the 64-bit MIPS IV processors
of SGI's Octane, Origin and Onyx machines. QEMU models them as the
``R10000``, ``R12000``, ``R14000`` and ``R16000`` CPU types, defined in
``target/mips/cpu-defs.c.inc``. Their shared state and properties live in
``target/mips/r10k.h`` and ``target/mips/r10k_cpu.c``; the CACHE
instruction and family CP0 registers in
``target/mips/tcg/system/r10k_helper.c``; the timer in
``target/mips/system/cp0_timer.c``; the performance counters in
``target/mips/system/r10k_perf.c``; floating point in
``target/mips/tcg/r10k_fpu.c``; and migration in
``target/mips/system/r10k_migrate.c``. This page covers the R10000 and
R12000 in full and the R14000 and R16000 only where they share that code.
No single chip revision is modelled: each machine selects the identity
and reset inputs of the part it fits.

Facts below carry the ratings defined on :ref:`sgi-ip30`: *established*,
*observed*, *software expectation*, *inferred*, *approximation* or
*unknown*.

A machine creates its CPU from the catalogue's processor part. The SGI
machine code (``hw/mips/sgi/sgi-cpu.c``) applies that part's values
through the CPU's own properties, each only where ``-cpu`` or
``-global`` did not already name it, so ``-cpu R12000,r12000-prid=0xe24``
overrides one field and keeps the rest. Every one of these properties is
fixed at realize: a later ``qom-set`` fails with "cannot change after CPU
realization". The platform pages say which part each machine fits and at
what clock (:ref:`sgi-ip30-processors`,
:ref:`sgi-sn-origin200-processors`).

A bare ``-cpu R12000`` outside a machine that supplies the inputs refuses
to realize and names the first missing property ("R12000 requires
r12000-prid"). It never falls back to R10000 or R14000 values.

.. _sgi-r10000-identity:

Identity
========

PRId is CP0 register 15, 32 bits, read-only. Bits 31:16 read zero, bits
15:8 hold the implementation and bits 7:4 and 3:0 the major and minor
revision :src:`r10000-users-manual-2.0 p. 255`, *established*. The manual
warns that a revision number need not track a chip change, so identity
alone settles no execution, cache or erratum difference. Linux uses
implementation ``0x09`` for the R10000 and ``0x0e`` for the R12000, a
software expectation.

``r10000-prid``, ``r14000-prid`` and ``r12000-prid`` each take the whole
32-bit word and keep the revision byte the caller gives. Setting
``r10000-prid`` or ``r14000-prid`` fails unless bits 31:16 are zero and
the implementation byte is ``0x09`` for ``r10000-prid`` and ``0x0f`` for
``r14000-prid``. An R12000 fails to
realize unless bits 15:8 are ``0x0e``; its upper 16 bits are not
checked. Reset installs the configured word every time, and an ``MTC0``
to PRId leaves it unchanged.

The FPU implementation and revision register (CP1 control register 0) is
``0x00000900`` on the R10000, R14000 and R16000: implementation ``0x09``,
revision 0. The R12000 takes its word from ``r12000-fpu-id`` with no
check. The NEC manual labels its implementation-``0x09`` example as
R10000 and leaves the revision open
:src:`nec-vr10000-series-um-4 PDF p. 281`, so the R10000 value is not
imported into the R12000 by default.

The values each machine selects:

   * - ``octane``

       No raw PRId read was published. FPU word is the model default.
   * - ``octane2``

.. _sgi-r10000-config:

Config and the reset mode word
==============================

Config is CP0 register 16, 32 bits. Bits 31:29 (IC) and 28:26 (DC) encode
the primary cache sizes and read ``011``, 32 KiB each
:src:`nec-vr10000-series-um-4 PDF p. 230`, *established*. Cold reset
samples SysAD bits 24:0 into Config bits 24:0 when SysGnt* is asserted
during SysReset* :src:`nec-vr10000-series-um-4 PDF p. 180`
:src:`nec-vr10000-vr12000-um-3 p. 184-185`, *established*. Those bits
carry the Kseg0 cache algorithm (2:0), processor device number (4:3),
coherent request target (5), eliminate enable (6), outstanding request
limit (8:7), system clock divisor (12:9), secondary-cache block size SB
(13), error-correction mode SK (14), byte order BE (15), secondary-cache
size SS (18:16) and secondary clock divisor (21:19), and on the R12000
bit 24 selects delayed speculative dirty behaviour
:src:`r10000-users-manual-2.0 p. 162, 164`
:src:`nec-vr10000-series-um-4 PDF p. 181-182`. SS selects
``512 KiB << SS`` for codes 0 to 5; 6 and 7 are reserved. SB zero
selects 16-word blocks and one selects 32-word blocks. A write to Config
changes only the Kseg0 field; the model preserves bits 31:3.

The board, not the processor, chooses the word. The model reproduces that
with a per-CPU input:

- R10000 and R14000: ``reset-mode`` replaces bits 24:0 of the definition's
  Config at every reset. Without it the definition's own bits stand. For
  the R10000 those are SC=3, SS=1 (1 MiB), SB=1, EC=3 and Kseg0 algorithm
  3, a fallback value and not any machine's measured word.
- R12000: ``r12000-reset-mode`` is required. Realize rejects bits above
  24, reserved Kseg0 codes (0, 1 and 6), a system clock divisor below 3
  or above 11, a secondary clock divisor below 2 or equal to 6, bits
  23:22 set, and a BE bit that disagrees with the
  CPU's ``big-endian`` property. ``r12000-scache-bytes`` must equal the
  size SS selects, ``r12000-scache-block-words`` must be 16 or 32 and
  agree with SB, and 16-word blocks are accepted only up to 2 MiB. Which
  divisor codes the R12000 actually reserves is set out in the NEC manual
  :src:`nec-vr10000-vr12000-um-3 p. 366`; the model's accepted ranges
  are its own choice.
- In every case BE follows ``big-endian`` at reset.

The ``octane2`` catalogue supplies ``0x001aa683``, giving Config
``0x6c1aa683``: big-endian, SS=``010`` (2 MiB), SB=1 (32-word blocks),
Kseg0 algorithm 3, and divisor and mode fields chosen only to be valid
encodings. SS is *inferred* from the 2 MiB the inventory reports. The
rest of the word, including the block size, is an *approximation*: no
source gives the word the Octane2 processor module drives, and reading it
would need a Config read taken before software changes it. The
``octane`` machine passes no word, so its Config is the R10000 fallback
above with BE set, ``0x6c19a603``, an *approximation* with the same
limitation. The Origin 200 words are on :ref:`sgi-sn-origin200-processors`.

Cold reset also sets Status ERL and BEV, clears Wired, sets Random to its
upper bound and starts execution in unmapped uncached space
:src:`nec-vr10000-series-um-4 PDF p. 306`, *established*; the shared MIPS
reset does the same. Count is set to 1 and Compare to 0.

.. _sgi-r10000-caches:

Caches
======

The primary instruction and data caches are 32 KiB and two-way. The
instruction cache has 64-byte blocks holding predecoded 36-bit
instructions; the data cache has 32-byte blocks and is virtually indexed
and physically tagged. The secondary cache is external, two-way,
physically indexed and tagged, 512 KiB to 16 MiB in powers of two, with
64- or 128-byte blocks; primary data blocks are subsets of secondary
blocks :src:`r10000-users-manual-2.0 p. 48-51`, *established*. The
fitted secondary size and block are board facts.

The model keeps the cache arrays the CACHE instruction's index and hit
operations reach: primary tags, data and parity, and a secondary array
sized at realize from the configured capacity and block size. Index
operations take the way from address bit 0; the primary ones index by
virtual address and the secondary ones by physical address. Undefined
operation and cache combinations do nothing. Secondary Hit operations set
Status CH on a hit and clear it on a miss. Ordinary loads and stores do
not use these arrays (:ref:`sgi-r10000-cca`), so the arrays hold only
what software put there.

The branch prediction table the Diagnostic register (CP0 22) reads and
writes has 512 two-bit entries on the R10000 and 2,048 on the R12000
:src:`nec-vr10000-series-um-4 PDF p. 351`, *established*. The model
predicts no branches;
the entries hold what software wrote. The R12000 Diagnostic register also
makes bit 26 writable, which Linux sets during its R12000 probe.

The manual leaves cache and TLB contents undefined after cold reset
:src:`r10000-users-manual-2.0 p. 336`, *established*. The model clears
every array to
zero (invalid) at reset, an *approximation*: software that initialises the
caches before use, as the manual requires, cannot tell the difference.

.. _sgi-r10000-timer:

Count and Compare
=================

Count advances every other processor clock
:src:`r10000-users-manual-2.0 section 14.8`. Compare is compared with
Count continuously, equality sets Cause IP7, and a Compare write clears
that interrupt :src:`r10000-users-manual-2.0 p. 244`, *established*. The
timer and the performance counters share IP7. The manual does not say
what a Compare write behind Count does. In the model a Compare write
behind Count clears the timer's IP7 and arms the next equality a full
32-bit wrap away; a write that leaves Count equal to Compare raises IP7
at once. The timer's and the counters' contributions are kept apart, so
neither can clear what the other raised.

Without instruction counting, QEMU's virtual clock follows host time and
a vCPU can be held between two instructions. A guest that samples Count
and then writes Compare a short way ahead of it can then find Count
already past its target, and a strict comparator defers the tick for a
whole wrap: 44.05 s at the ``octane``'s 97.5 MHz Count, 23.86 s at the
``octane2``'s 180 MHz. On the processor the instructions between the two
take a few cycles, *inferred* from instruction timing. The model has two
recoveries for this host artefact. Both are *approximations*: after a
delayed arm the model raises IP7 at the Compare write, where silicon would
not have been late.

Adjacent-write recovery
-----------------------

Every family member applies it. It covers a Compare write (``MTC0`` or
``DMTC0``) that is the very next instruction executed after a Count write.
With ``forward`` the Compare value minus the Count value written and
``elapsed`` the unwrapped Count ticks since the Count write, the Compare
write raises IP7 if ``0 < forward < 2^31``, ``elapsed < 2^31`` and
``elapsed >= forward``. Any other instruction, an exception or interrupt
entry, a reset or another Count write in between cancels it; the next
instruction follows a branch delay slot to the one actually executed. The
IRIX 6.5.30 kernel resets its scheduler clock this way on the SN machines,
writing Count zero and then Compare at least 1000 ticks ahead, a software
expectation. An adjacent Count=1, Compare=0 pair has ``forward``
``0xffffffff`` and still arms a full wrap.

.. _sgi-r10000-count-sample-window:

Count-sample window
-------------------

The ``count-sample-window`` CPU property, off by default, selects a wider
rule. The ``octane`` and ``octane2`` machines set it; the SN machines do
not.

The IRIX 6.5.30 IP30 kernel arms its scheduler clock in two ways, both
with interrupts masked, a software expectation read from the shipped
kernel's instructions. Its rearm routine reads Compare and Count. When the
deadline has passed it writes Count zero and, up to eight register
instructions later, Compare at least 1000 ticks ahead (5.6 us at 180 MHz).
When it has not, it writes the Count it read back and either leaves
Compare alone or writes it to an absolute target. A second routine reads
Count and, up to sixteen register instructions after a Compare read,
writes Compare at least 1000 ticks ahead of the value read. Neither
need be an adjacent pair. When a host stall crosses the target, the
kernel reports that the CPU "hasn't seen a scheduler clock interrupt"
and loses the tick.

With the window selected, every guest Count read or write records the
value and the virtual clock. The next Compare write raises IP7 when its
target is more than zero ticks ahead of that recorded value, fewer than
2^31 ticks have elapsed since the sample, and Count has already reached
the target. That the target lies less than 2^31 ticks ahead follows and
is not a separate test. Otherwise the ordinary rule applies. Exception or
interrupt entry and reset close the window, and a later Count access opens
a new one. No limit applies to the number of instructions between the
sample and the Compare write.

A window open at migration is dropped (:ref:`sgi-r10000-migration`).

A target behind the sample, or equal to it, keeps the ordinary rule. That
covers the read-Count-minus-one disarm public drivers use (OpenBSD writes
Compare to the Count it read minus one), the kernel's Count=1, Compare=0
disarm, and a stale target behind a later Count read. In the rearm
routine's not-passed branch the sample is the Count written back, so an
absolute target behind it is left alone and one ahead is recovered only
once Count has really passed it.

The cost of the wider rule: a guest that read Count, waited with
interrupts masked until Count passed a target ahead of that value, and
then wrote that target meaning a full-wrap wait would be served early. No
supported guest is known to do that.

.. _sgi-r10000-perf:

Performance counters
====================

The R10000 has two 32-bit counters and the R12000 four, each with a
control register, reached through CP0 register 25: even selectors are
control registers and odd selectors counters. A control register selects
an event and enables counting per mode: user, supervisor and kernel each
with EXL and ERL clear, and EXL set with ERL clear; ERL set stops all
counting. An enabled counter asserts IP7 while its bit 31 is set
:src:`nec-vr10000-series-um-4 PDF p. 247-250`, *established*. The event
field is four bits (8:5) on the R10000 and five (9:5) on the R12000.

Only event 0, Cycles, counts. It counts processor clocks of virtual time,
the clock Count is derived from. A counter selecting any other event holds
the value written, because the model has none of the microarchitecture
the other events measure. This is a functional *approximation* of cycle
counting. The manual describes a two-cycle delay between an event and the
counter update and requires an instruction between writing a control
register and initialising its counter
:src:`nec-vr10000-series-um-4 PDF p. 247, 250`, *established*. The
model updates at
once and does not model events in flight when software changes a
counter, a control register or the processor mode.

.. _sgi-r10000-cca:

Cache algorithms and coherence
==============================

A mapped access takes its cache algorithm from EntryLo C, kseg0 from
Config K0 and xkphys from address bits 61:59. Algorithm 2 is uncached, 3
cacheable noncoherent and 5 cacheable coherent exclusive on write
:src:`r10000-users-manual-2.0 p. 53`, *established*. Under algorithm 3 a
secondary miss is a noncoherent block read; under 5 a load miss is a
coherent read shared and a store miss a coherent read exclusive
:src:`r10000-users-manual-2.0 p. 57`, *established*.

EntryLo carries a two-bit uncached attribute beside the cache algorithm
:src:`r10000-users-manual-2.0 p. 239-240`, *established*. The model
drives it for uncached references (algorithm 2, and 7, uncached
accelerated) from EntryLo UC for a mapped page and from address bits
58:57 for xkphys, where those two bits are then not part of the physical
address.

The model has no functional cache on the default CPU. Every load, store
and fetch goes to the machine's memory directly, whatever the algorithm.
It carries the algorithm, an uncached flag, the uncached attribute (as an
address window above the physical address) and the CPU's requester
identity with each reference, so a board can tell a coherent request
from a noncoherent one and an uncached register access from memory. The
SN1 Bedrock memory directory uses that. A ``PREF`` with a load or store
hint to an algorithm 4 (cacheable coherent exclusive) or 5 address is
passed to the board as a coherent prefetch request; a prefetch with
another hint or algorithm does nothing. The secondary Index Writeback
Invalidate and Hit operations are passed on as system requests. None of
the manual's coherence transactions, interventions, state responses or
conflict rules :src:`r10000-users-manual-2.0 p. 127-145` are modelled.
On the Octane, HEART is the external agent that keeps processor caches
coherent with I/O :src:`octane-technical-report p. 2-16-2-17`; the
exact rules it uses are *unknown*, and the model needs none because
nothing is cached.

``cache-data-visibility=on``, R10000 only and off by default, routes
xkphys algorithm 3 loads and stores to RAM through the primary data and
secondary arrays, with fills, dirty writeback, and writeback by the index
and hit CACHE operations. It is a diagnostic aid, not a coherence model:
a cached instruction fetch, an algorithm-3 access outside xkphys and
any access under another cached algorithm each log ``LOG_UNIMP`` and
raise an address error, and a machine with it on cannot migrate.

TLB remapping
-------------

Because nothing is cached, rewriting a TLB entry's PFN takes effect on
the next access through it, under algorithm 2 or 3, and rewriting only
its C field is honoured at once. Diagnostic CACHE operations on the
arrays leave memory unchanged. A 32-bit load through a remapped page
sign-extends bit 31 into the upper half. These are model behaviours. The
manual facts the test relies on are the cache algorithms
:src:`r10000-users-manual-2.0 p. 53-54`, the EntryLo and PageMask fields
:src:`r10000-users-manual-2.0 p. 239-242` and the primary-data index
operations :src:`r10000-users-manual-2.0 p. 283, 287-288`.

.. _sgi-r10000-ecc:

Secondary-cache ECC
===================

Each 128-bit secondary data quadword carries nine ECC bits and an even
parity bit, and each 26-bit tag seven ECC bits. CP0 register 26, ECC, is
ten bits: bit 9 the quadword parity bit and bits 8:0 its ECC bits, with
the primary caches' parity bits at the low end. Reset input SCCorEn (mode
bit 14) chooses whether every secondary data read passes through the
corrector or only one whose parity fails. An uncorrectable error posts a
Cache Error, records the unit and index in CacheErr (CP0 27), sets
Status ERL and enters the Cache Error vector; Status DE suppresses posting
:src:`r10000-users-manual-2.0 p. 165, 171-172, 176-179, 274-276`,
*established*.

The model stores and returns check bits but never computes or checks
them. Index Store Data (S) writes one doubleword from TagHi and TagLo,
zeroes the other half of the quadword, and stores the ten bits from CP0
ECC; Index Load Data (S) returns them. ECC keeps bits 9:0 and reads bits
31:10 as zero. Invalidation stores zero tag check bits, and fills under
``cache-data-visibility`` leave the stored check bits unchanged. No
access raises a Cache Error, and CacheErr reads zero.

.. _sgi-r10000-fpu:

Floating point
==============

With FCSR FS clear, R10000 and R12000 scalar ``ADD.S`` and ``DIV.S``
with a denormalized operand take an Unimplemented Operation exception:
FCSR Cause E (bit 17), which has no enable and always traps. The
rejected instruction writes neither its destination nor new sticky flags.
A denormalized result with FS clear takes the same exception
:src:`nec-vr10000-series-um-4 p. 282-284, 349`, *established*. ``MOV``
and conditional ``MOV`` take no denormal-input exception.

The model applies the input check to ``ADD.S`` and ``DIV.S`` only. It
applies the result check to ``ADD``, ``SUB``, ``MUL``, ``DIV``, the four
multiply-add forms and ``RECIP`` in both precisions, to ``CVT.S.D`` and
to ``ABS`` and ``NEG``, raising E alone and discarding the operation's
other flags. With FS set, denormal results are flushed to zero.

``CVT.L`` of a result wider than 51 bits takes Unimplemented Operation
:src:`r10000-users-manual-2.0 section 15.5`, *established*. The model
also traps a NaN, an infinity or an out-of-range source in place of the
architectural Invalid result, an *approximation*: the manual gives no
result for them. The model treats ``ABS`` and ``NEG`` as arithmetic, so a
NaN operand signals Invalid, an *approximation* that follows NEC's
*VR10000 Instruction Set User's Manual*. The
R12000 changes FS handling of input denormals and quiet NaNs
:src:`nec-vr10000-series-um-4 PDF p. 349-351, 353`, *established*; the
model does not separate it.

.. _sgi-r10000-lwr:

Unaligned word loads
====================

``LWL`` always supplies bit 31 and sign-extends it through bits 63:32.
A full four-byte ``LWR`` does too. A partial ``LWR`` leaves bit 31 from
the old register, and MIPS IV permits two results for bits 63:32: keep
the old upper half, or fill it from the unchanged bit 31
:src:`007-2597-001 p. A-101-A-106`, *established*. No processor manual
found narrows the choice.

In big-endian 64-bit mode the model keeps the old upper half on a partial
``LWR``, for every family member; other MIPS CPUs keep QEMU's generic
sign fill. This follows a software expectation: SGI's online processor
random-instruction diagnostic for IRIX 6.5.30m on IP27 expects the upper
half kept, and Linux's pre-Release-6 instruction emulator keeps it too.
Neither is a measurement of R10000 silicon.

.. _sgi-r10000-migration:

Migration
=========

Migration works only between identical builds. The family state travels
behind the CPU in its own subsections:

- ``cpu/r10k``: the first megabyte of secondary-cache arrays, the primary
  caches, CacheErr, the full 64-bit Diagnostic register, the first 512
  branch prediction entries and a postponed Watch exception.
- Capacity subsections for the secondary cache above 1, 2, 4 and 8 MiB,
  present only when the configured capacity needs them.
- ``cpu/r12000-extra`` and ``cpu/r12000-profile`` on the R12000: the
  secondary arrays the profile's geometry adds, branch prediction entries
  512 to 2,047, and the five profile values. Loading fails unless the
  destination was configured with the same five values, so a destination
  with the same capacity but another block size or FPU word refuses the
  stream.
- On the R10000 and R14000, loading fails if the incoming PRId differs
  from the destination's configured PRId, so its next reset cannot
  restore another identity.
- On every family member, loading fails if Config SS differs.
- A pending adjacent-write candidate travels with its age. An open
  Count-sample window does not: the destination applies the ordinary rule
  to the next Compare write. The virtual clock is frozen while the
  machine is stopped, so the drop costs at most one tick, and only if a
  host stall after the resume crosses the target.
- R10000 counters travel as their running clock offsets; the four-pair
  CPUs carry the counter values and re-anchor them to the destination's
  clock.

PRId or CP1 register 0, and no read was taken at reset. None of these
establishes the reset mode word, the secondary block size, the die
variant or any revision's errata.

.. _sgi-r10000-r14000:

R14000
======

The ``R14000`` type is the processor of the ``origin300`` and ``fuel``
machines. It shares the family code above: the cache arrays and CACHE
operations, Count and Compare with the adjacent-write recovery, the
partial ``LWR`` rule, the denormal-result and ``CVT.L`` traps,
``reset-mode`` and PRId through ``r14000-prid`` (implementation
``0x0f``). Unlike the R10000 and R12000 it has no input-denormal trap,
and it has four counters without counter interrupts. Its
machine-specific detail belongs with the SN1 machines.

.. _sgi-r10000-r16000:

R16000
======

The ``R16000`` type is the processor of the IP53 machines. It shares the
same family code and requires ``r16000-experimental=on``,
``r16000-reset-mode`` and ``r16000-scache-bytes`` (4, 8 or 16 MiB, with
SB=1); its counters log ``LOG_UNIMP`` for any event but Cycles and for
an interrupt enable. Its machine-specific detail belongs with the IP53
machines.

.. _sgi-r10000-limits:

Model limits
============

- No functional cache on the default CPU, no coherence transactions, no
  speculative execution and no instruction-cache coherence. Board
  coherence works only from the algorithm and requester carried with
  each reference.
- Cache arrays read zero after reset; the hardware leaves them undefined.
- The ``octane`` Config low bits are the R10000 definition's fallback,
  and the ``octane2`` reset mode word is chosen, not measured.
- Secondary-cache check bits are stored, never generated or checked; no
  Cache Error is ever posted.
- Performance counters count only Cycles, with no update delay.
- The Count-sample window and the adjacent-write recovery can raise IP7
  at a Compare write that silicon would have deferred a full wrap.
- R12000 FS-set denormal and quiet-NaN handling and R12000A features,
  such as the secondary ECC syndrome in performance control 0
  :src:`nec-vr10000-series-um-4 PDF p. 247, 358`, are not modelled.
- Cold and soft reset differ only in the generic MIPS way: a QEMU system
  reset is a cold reset. A Soft Reset exception keeps WatchLo on the
  R10000 and R16000 and clears it on the R12000 and R14000, a model
  choice; whether the R12000 and R14000 keep WatchLo is *unknown*.
- On the R10000 the secondary arrays follow a reset-mode SS of 1 to 5
  (1 to 16 MiB); SS 0, 6 and 7 leave 1 MiB. The R14000's arrays stay at
  2 MiB whatever SS says. Config SS then disagrees with the arrays.
- An unhandled CP0 register 25 selector logs ``LOG_UNIMP`` and reads
  zero. Setting Status RE logs ``LOG_UNIMP``.
- Migration works only between identical builds.

Tests
=====

- ``tests/qtest/r10000-identity-test.c``: PRId through an executed
  ``MFC0`` on ``octane``, ``octane2``, ``origin200``, ``origin300``,
  ``fuel`` and a bare R10000 and R14000; overrides; a rejected PRId
  write; repeated resets; immutable properties; rejected implementation
  numbers; and migration with matching and mismatched identities. It also
  checks the ``octane2`` catalogue's five R12000 values.

  (``/sn0/qtest/r10000-timer``, ``r14000-timer``); the adjacent-write
  recovery on all four types; partial ``LWR`` on the R10000, R14000 and
  R16000; R12000 profile validation, both block sizes and 4 MiB; R12000
  migration, including refused block-size and FPU-word mismatches; and
  R12000 counter selectors and counter IP7 apart from Count/Compare IP7.
- ``tests/qtest/octane-timer-test.c``: the Count-sample window on
  ``octane`` and ``octane2`` under ``-icount shift=10``, with crossed
  targets after a Count read and a Count write and the six controls the
  window must leave alone.
- ``tests/qtest/sn0-mttcg-test.c``: the adjacent-write recovery with a
  vCPU held from a debugger between the two writes, across interrupts,
  delay slots, single stepping, resets, migration and holds past half
  the counter range.
- ``tests/qtest/sn0-r10k-test.c``: the R10000 secondary capacity a
  reset mode word selects, secondary block sizes, soft-reset state, coherent
  prefetch hints and Status RE logging.
- ``tests/qtest/sn0-r10k-perf-migration-test.c``: counter migration, the
  secondary-cache arrays across migration and Index Store Data padding.
- ``tests/qtest/o2-r10k-cache-test.c``: ``cache-data-visibility`` dirty
  data, writeback by CACHE operations and the address errors for the
  unsupported paths.
- ``tests/functional/mips64/test_r10k_fpu.py``: the denormal input and
  result vectors on the R10000, R12000 and R16000.
- ``tests/functional/mips64/test_r10000_tlb_cache.py``: TLB remapping
  under algorithms 2 and 3, sign extension and the separation of
  diagnostic arrays from memory.
- ``tests/functional/mips64/roms/``: bare-metal ROMs for CACHE
  operations, tags, ECC register bits, the timer and the performance
  counters, run by ``test_sgi_roms.py`` in the thorough set.
