.. _sgi-l1:

===============================================================
SGI L1 system controller (Origin 300, Fuel, Origin 350 family)
===============================================================

The L1 is the per-chassis system controller of the Origin 300, Fuel and
the Origin 350 family (Origin 350, Onyx 350, Tezro and Onyx4). QEMU models the node-facing side in ``hw/misc/sgi-l1.c``: a
16550-style UART in the Bedrock's Hub special space speaking a framed
request and response protocol, which the PROM, IRIX and the other
guests use to read board records, drive the display and carry the
operator console. The controller's board-side interfaces (environmental
monitoring, JTAG scan, USB to an upstream controller, the RS-422
peer links) are not modelled. This page states what public sources
establish, what the model chose, and what has no public source.
Ratings follow :ref:`sgi-ip30`.

Sources: OpenBSD sgi at
``openbsd-sgi:2df91d80c104636deeef8124252ddd5951b55fbf``
(``sys/arch/sgi/sgi/l1.c``, ``l1.h``, ``sys/arch/sgi/xbow/hub.h``); SGI's
Linux SN1 port at ``linux-history:7570df54ef8c`` (tag v2.5.40,
``arch/ia64/sn/io/l1.c``, ``l1_command.c``, ``include/asm-ia64/sn/ksys/l1.h``);
the out-of-tree MIPS port ``linux-ip35:9f613a321ea0``
(``arch/mips/sgi-ip35/ip35-l1.c``); *SGI L1 and L2 Controller Software
User's Guide* (007-3938-001 and -006, printed pages cited below); *Origin
300 User's Guide* (007-4365-002); *Origin 300 System with NUMAlink Module
User's Guide* (007-4498-002); *Origin 3000 System Architecture*
(108-0240-002); *PCI Expansion Module User's Guide* (007-4499-002);
*Fuel Visual Workstation Hardware User's Guide* (007-4480-001).

.. _sgi-l1-uart:

UART window
===========

The UART is reached in Hub special space at the node's remote register
window plus ``0x80``, that is the node's Hub special base plus
``0x3000_0080``, one 16550 register per 8 bytes, accessed as 64-bit loads
and stores of which only the low byte is significant (established: OpenBSD
``hub.h`` lines 68-73 and ``l1.c`` lines 97-142; Linux SN1 ``l1.c`` lines
61-77; ``ip35-l1.c`` lines 28-50). All three consumers use the remote form;
none uses the local form. What no public source states is whether the
Bedrock's memory and directory unit decodes this window or another unit
forwards it (unknown; the unit's junk-bus timing register carries setup and
hold fields for the UART, Linux SN1 ``hubmd.h`` lines 1059-1097).

.. list-table::
   :header-rows: 1
   :widths: 14 30 56

   * - Offset
     - 16550 register
     - What the consumers require
   * - ``0x00``
     - receive and transmit data
     - A write hands a byte to the frame parser; a read pops the next
       byte the L1 has for the processor.
   * - ``0x08``
     - interrupt enable
     - Accepts writes; the SN1 port writes 0.
   * - ``0x10``
     - interrupt identification, FIFO control
     - The SN1 port writes ``0x01`` then ``0x07``; read ``0x01`` (none
       pending) in polled operation.
   * - ``0x18``
     - line control
     - Read-write latch; the SN1 port writes ``0x80`` for the divisor then
       ``0x03``.
   * - ``0x20``
     - modem control
     - Accepts writes; the SN1 port writes ``0x22``.
   * - ``0x28``
     - line status
     - Bits 5 and 6 set whenever a byte can be accepted; bit 0 set
       exactly while a received byte waits; bits 2 and 3 clear.
   * - ``0x30``
     - modem status
     - Bit 4 (clear to send) set; the SN1 early path and the MIPS port
       spin forever without it (``l1.c`` line 1973; ``ip35-l1.c`` lines
       56-57).
   * - ``0x38``
     - scratch
     - Unused.

The SN1 port programs a divisor of 13 against a 12 MHz clock for 57,600
baud, and the L1's own ``uart`` command reports the Bedrock-side port at
57,692 baud, exactly that divisor (007-3938-006 printed pages 110-111);
the SN1 port's raw-byte configuration uses a baud base of 124,800
(``kernel/setup.c`` lines 236-259), so the model enforces no divisor. OpenBSD
never programs the UART and polls line status up to a million times per
byte with no wall-clock bound (``l1.c`` lines 100-144), so a silent UART
costs it nine such waits per node (established). The model also decodes the
same eight registers at the local form's ``+0x80`` (node Hub special base
plus ``0x1000_0080``), sharing state: an *approximation* with no public
consumer, kept because the vendor field-diagnostic monitor sMDK writes its
console there when booted headless under the stock PROM (observed on the
model; no public source documents it). A read of Hub special
local offset ``0x80`` on a physical Origin 300 or 350 would settle whether
real silicon answers there.

.. _sgi-l1-framing:

Framing and packets
===================

.. list-table::
   :header-rows: 1
   :widths: 46 12 42

   * - Fact
     - Rating
     - Source
   * - Frames are HDLC-like, as in PPP: a ``0x7e`` flag on each end, ``0x7d``
       escaping ``0x7e`` and ``0x7d`` by exclusive-or ``0x20``, and a
       16-bit frame check initialised ``0xffff``, complemented and sent low
       byte first over every payload byte from the header to the last
       argument; a receiver's running check over payload plus the two check
       bytes equals ``0xf0b8``. Frames shorter than two bytes are dropped.
     - established
     - All three consumers agree: OpenBSD ``l1.c`` lines 156-306 with
       ``ppp_defs.h``; Linux SN1 ``l1.c`` lines 737-1006 and 1186-1474;
       ``ip35-l1.c`` lines 99-238.
   * - Only the SN1 receiver tolerates repeated flags between frames
       (``l1.c`` lines 1239-1242, 1327); OpenBSD reads to the next flag
       and the MIPS port loses the next frame after a doubled or shared
       flag (``l1.c`` lines 266-293, 525-526; ``ip35-l1.c`` lines
       193-217). The model therefore sends exactly one opening and one
       closing flag per frame and never shares a flag.
     - established
     - The same lines.
   * - Payloads are at most 127 bytes (the SN1 send-side clamp and the
       seven-bit binary length).
     - established
     - Linux SN1 ``l1.c``.
   * - The header byte carries the packet type in bits 7:5 and the
       subchannel in 4:0: request ``0x00``, response ``0x20``, event
       ``0x40``. Subchannels 0 to 3 are per-processor consoles, 4 the
       system console, 16 to 31 operating-system requests (OpenBSD uses
       16 for everything). A response returns on the request's
       subchannel.
     - established
     - OpenBSD ``l1.h``; Linux SN1 ``ksys/l1.h``.
   * - A request payload after the header is a four-byte big-endian
       destination, a two-byte request code, an argument count byte, then
       typed arguments (``0x00`` plus four bytes an integer, ``0x01`` plus
       text and a zero a string, ``0x80`` with the low seven bits the
       length a binary). The SN1 port omits the count byte on
       zero-argument requests, OpenBSD always includes it, and a
       responder must accept both.
     - established
     - OpenBSD ``l1.c``; Linux SN1 ``l1.c``.
   * - A response payload is a four-byte signed code, a field count, then
       typed fields. Codes: 0 success, minus 100 wrong argument count,
       minus 101 unknown request, minus 104 data not available, minus 105
       argument out of range, minus 107 data invalid. OpenBSD decodes the
       whole word; the SN1 port keeps only the low byte and tests for a
       negative result, so it never sees a negative code (``l1.c`` lines
       133-139, 2467-2471).
     - established
     - OpenBSD ``l1.h``; Linux SN1 ``ksys/l1.h`` and ``l1.c``. The
       firmware also sends minus 1 (router error), minus 102, minus 106
       and minus 108: known only from the stock L1 firmware image, not a
       registered source, so unknown here as a public fact.
   * - The 32-bit destination: bits 31:28 controller type (0 L1, 1 L2, 2
       L3, 3 attached C-brick, 4 attached I/O brick), 27:18 rack with
       ``0x3ff`` meaning local, 17:12 bay with ``0x3f`` meaning local,
       4:0 task (3 command interpreter, 4 environmental monitor, 5
       Bedrock console, 6 general). The local general address is
       ``0x0ffff006``, the command interpreter ``0x0ffff003``, the
       attached I/O brick's general task ``0x4ffff006``.
     - established
     - Linux SN1 ``ksys/l1.h``; OpenBSD ``l1.h``;
       linux-ip35 ``sn/l1.h``.
   * - The prompt names the chassis as rack, type letter and slot,
       ``001c01`` for a stock single chassis; the letter is one of c, i,
       p, r, x, n, g, or ``?``. A second chassis is given slot 02 before
       cabling and the pair appears in the PROM inventory as ``Module
       001c01`` and ``Module 001c02``.
     - established
     - 007-3938-006 printed page 60 ("Valid Brick Types");
       007-4365-002 printed page 38; the 2014 two-chassis OpenBSD
       capture ``web:marc-openbsd-sgi-139223952727384``.

.. _sgi-l1-routing:

Routing outcomes
================

No public source states how the firmware handles destination forms that
are not local (a foreign rack or bay, a mixed local sentinel, controller
types 1 to 4 and above, unregistered tasks). These outcomes are *unknown*
and are the model's choice; a reply capture from a real controller would
settle them,
recorded in the checks of ``hw/misc/sgi-l1.c``: a local key (type 0 with the
own rack and bay, or both sentinels) is delivered to the addressed task; a
foreign or mixed key gets a router error reply (code minus 1 with a
detail number); an unregistered local task gets no reply. What a real
standalone Origin 300 answers to a type-4 (attached I/O brick) request is
open: the IO-8 is not an attached I/O brick to the firmware and real
``cfg`` output lists those positions as ``not connected``. A matching
stock-PROM request, L1 handle status and Bedrock reply capture would settle
it.

.. _sgi-l1-model:

Emulator choices
================

- The device answers reviewed node-facing requests for one chassis; the
  M-Bus environmental monitoring, JTAG scan, flash programming, USB device
  to an L2 and RS-422 peer routing are not modelled
  (approximation: the controller has them, no revision-matched contract is
  public).
- The two-chassis pair relies on the operator procedure of 007-4365-002
  printed pages 34-41 and 007-4498-002 (system ids, cabling with both
  servers off); the model's inter-L1 link is an emulator construction.
- Console multiplexing, the management console and the power and reset
  lifecycle are approximations built from the stock PROM's and IRIX's
  observed requests; no public document describes them beyond the user
  guides' operator-side commands (007-3938-006 printed pages 9-12, 19, 28,
  46-48, 63-64, 77-79, 100-103 and 110-111).

.. _sgi-l1-origin3000:

Origin 3000 C-brick, I-brick and V-brick profiles
=================================================

``brick-type=cbrick`` and ``brick-type=ibrick`` model the L1 of the Origin
3000 compute brick and system I/O brick; ``brick-type=vbrick`` models the
Onyx 3000 V-brick's, described after the table. Each brick has its own controller
with its own rack, slot, type and records (007-4240-002 printed pages 69,
72, 118 and 128). The profiles reuse this page's request encoding, framing
and task-6 request codes, which the public Linux and OpenBSD headers name
for the Origin 3000 products; that a fitted C-brick frames bytes the same
way is *unknown*. ``brick-type-code`` is refused. The C-brick, I-brick and
N-brick profiles answer request ``0x0005`` with the firmware revision
``revision-*`` configures and minus 104 without one; the V-brick profile
refuses ``revision-*``.

captured controller output.

The V-brick profile (``brick-type=vbrick``) is reached from the C-brick
its XIO cable joins, as an I-brick's is, and knows only that C-brick. The
V-brick has its own L1 (007-4264-002 printed pages 52 and 128 to 129). It
is the X-brick's chassis and midplane XBridge with V12 boards in the slots,
and the Origin 3000 L1 firmware has no personality of its own for it: the
firmware picks a brick's type letter from the name field of its power and
logic board EEPROMs and installs that letter's personality. A logic board
named ``XBRICK`` gives ``X``. The firmware's only ``V`` belongs to a
PIC-based graphics brick of a later family, which IRIX 6.5.30 and the stock
PROM name ``CGbrick``, and no firmware command can store ``V``. So the
profile answers as the X-brick personality. No V-brick L1 reply has been
captured, and its address and ID PROM contents are unknown:

What the model chooses, and the limit of each choice:

- A brick with no rack and slot answers an identity request with the
  router's error reply, because the integer a real one returns is unknown.
  Rack and slot are supplied with ``named=on``, ``rack`` and ``bay``.
- All records are synthetic and marked as such; the SPD records set only
  the length, size and checksum bytes and a position marker. An unfitted
  PIMM or DIMM (``pimm-mask``, ``dimm-mask``) has no record and answers
  minus 104, where a real controller's wire form is unknown.
- The C-to-C and C-to-I links are in-process calls and carry no wire
  format, baud rate or detection. A C-brick has two links: ``peer`` for the
  other C-brick and ``io-peer`` for its I-brick. Both are checked against the
  two profiles: a C-brick pairs only with a C-brick, and ``io-peer`` joins a
  C-brick to an I-brick or N-brick. The check holds whether the link is
  given with the device (it runs when the device realizes) or set afterwards
  (it runs when the link is set). An I-brick takes one C-brick: the fitted system's cabling
  of a second is unknown, so a second is refused with an error, and the first
  link stays. An N-brick takes several; the model does not count its
  connectors. After ``reboot_l1`` a brick answers no peer for one second of
  virtual time.
- ``power`` and ``reset`` on an I-brick act on that brick only; a C-brick
  keeps the single-node power and reset behaviour above. ``*`` runs a
  command on this brick, the other C-brick and the I-brick in turn, each
  result headed by that brick's name. Which of two C-bricks is master is
  not modelled.
- ``select``, ``nmi``, ``softreset``, ``cpu``, ``pimm``, ``autopower``,
  ``ctc``, ``cti``, ``debug``, ``leds``, ``junkbus`` and ``*`` are refused
  on an I-brick, ``pci`` on a C-brick and ``router`` on both, with
  ``INFO: command not supported on this brick type``; other commands the
  guide lists but this model does not run are reported as unimplemented.
  The refusal text and the ``config`` line format are the model's choices.

The exact text and layout of each reply below are the model's own, whether
or not a manual prints a similar form. All are approximations. A console
ends each line with CR LF. A reply to a command interpreter request (task 3)
carries each line as its own field with no line ending; a line the model
ends with LF, as the Origin 300 profile's text does, keeps that LF inside
its field. The Origin 3000 refusals and the ``no response`` line below are
written CR LF-ended, so on a console, or relayed, they do not run into the
next brick's name line, and on task 3 they arrive as separate fields.

     - None.
   * - A ``cti``, ``ctc`` or ``*`` run on a brick that was itself reached by
       a relay is refused: ``INFO: nested cti is unsupported.``, ``INFO:
       nested ctc is unsupported.`` or ``INFO: nested * is unsupported.``.
       A ``*`` that names another ``*`` is refused the same way. Nothing
       runs, and the relay depth is one.
     - Whether a real L1 relays a command back through its peer is not
       published. Without the bound, each extra ``*`` doubled the work. The
       refusals carry no brick-name prefix, where the guide prints one for
       a remote reply (007-3938-001 printed page 18).
     - None.
   * - A relay to a restarting brick prints its name, then ``no response``.
     - The interval is one second of virtual time, chosen by the model;
       the layout and words differ from the printed form.
     - ``003c01 ERROR: no response from ---i--`` answers the restart
       command itself (007-3938-001 printed page 24).

.. _sgi-l1-cxbrick:

Origin 3900 Cx-brick profile
============================

``brick-type=cxbrick`` models the one L1 of a Cx-brick, the Origin 3900
and Onyx 3000 brick that holds one to four IP53 node boards behind a single
controller on its router board (*SGI Origin 3900 Server User's Guide*
007-4653-001 printed pages 52-60; *Cx-brick Addendum* 007-4572-001 printed
pages 2-18). ``boards`` names the fitted node boards and ``compute-boards``
those with processors, one bit per board 0 to 3. Each fitted board reaches
the controller through its own UART window, ``sgi-l1-uart`` with
``transport-index`` the board number. Identity, naming and restart follow
the C-brick profile above: a brick starts unnamed and prints ``---c--``
(007-4653-001 printed page 144).

Request codes, the request layout and the framing follow the C-brick rule.
The profile serves the codes the Linux v2.6.0 ``ksys/l1.h`` header names
with the Origin 300 meaning (``0x0001`` to ``0x0009``, ``0x1002`` to
``0x1007``) and the Origin 300 codes ``0x000e``, ``0x2001``, ``0x2005`` and
``0x2006``. Every other code answers the unknown-request code and is logged
as unimplemented, the attached-brick requests ``0x000c`` and ``0x000d``
among them. ``0x2001`` resets, as on the Origin 300; the public header gives
``0x2001`` to PCI power-up and ``0x2000`` to the full reset, so which a
fitted Cx-brick uses is *unknown*, and each ``0x2001`` is logged as such.

What the model chooses, and the limit of each choice:

- Each board's window is the Origin 300 UART and packet path. A reply goes
  back only on the window that asked, and on each window subchannels 0 to 3
  are that board's processors A to D and 4 its console. A shared line or a
  path through the router could interleave traffic in ways this does not
  show.
- Each window keeps its own port field: ``0x000e`` answers the board number
  after L1 power-on and ``0x1002`` rewrites only the asking window's field,
  by the Origin 300 rule. A real L1 may keep one value per brick.
- The console selection is the brick's: a board and a subchannel, changed
  by ``select`` and by ``0x1003``, which moves it to the volunteer's console
  subchannel. Console output on a window does not move it, as it does on the
  Origin 300. It starts on board 0's console, or on the lowest board with
  processors when board 0 has none; a real L1 may keep ``console0`` and time
  out. The filter is cleared at L1 power-on.
- ``select`` refuses a board that is not fitted with ``ERROR: bad subchanel
  selection.`` and accepts one without processors. Console mode toward a
  board without processors prints the guide's ``no response from 001c07
  junk bus console UART:UART_TIMEOUT``, or for a processor subchannel
  ``no response from 001c07 Junk bus CPU2B system not responding``
  (007-4653-001 printed pages 115 and 141), and stays in L1 mode.
- Power, reset and NMI requests from any window, and from the prompt, act on
  every board at once and log one entry. The machine's own reset carries
  them out, so the router is reset with the rest, where the profile's
  contract keeps the router's state; per-board power and reset are not
  offered. ``nmi`` pulses one ``nmi`` line per board, and only boards with
  processors are wired to them.
- Board ``n``'s window reads board ``n``'s synthetic node board record at
  component 0; every other component answers minus 104. The DIMM, router
  board and power entry module records are not modelled. With
  ``cpu-context-present`` each board's record carries the CPU context the
  Origin 350's carries, which the stock PROM compares with its flash.
- Board ``n``'s window answers the identity requests with the brick's slot
  plus ``n``, and the serial request with the brick's serial and ``.n``,
  because the stock PROM refuses two modules at one slot and tells hubs apart
  by the serial. No source says how a Cx-brick numbers its boards or what it
  returns; this is an approximation.
- The brick has no default type character: ``0x0003`` answers minus 104
  until ``brick-type-code`` supplies one, and ``brick`` prints the type as
  ``?``. The firmware revision is unknown, so ``revision-*`` is refused.
- A neighbouring Cx-brick link is refused. The L2, the neighbouring Cx-brick
  and the ``iia`` to ``iid``, ``nia`` and ``nib`` commands are not modelled.
  One I-brick may be named as ``io-peer``: the attached I/O brick request
  then goes to it in the C-brick's request form, because the addressing of a
  Cx-brick's four I/O ports is unknown. Without a peer an attached-brick
  destination answers the router's error reply.
