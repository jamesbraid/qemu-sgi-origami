.. _sgi-l1:

=====================
L1: system controller
=====================

Used in :ref:`sgi-ip35` (Origin 300 and Fuel), :ref:`sgi-ip53` (Origin
350, Onyx 350, Tezro and the Onyx4 host), the Origin 300 PCI expansion
module (:doc:`pci-expansion`) and :term:`NUMAlink` module
(:ref:`sgi-bricks-numalink-module`), and the Origin 3000 and Onyx 3000
C-, I-, N-, V-, R- and CX-bricks (:ref:`sgi-bricks`), which the
``origin3000`` machine's topologies build.

.. seealso::

   Platform pages: :ref:`sgi-ip35`, :ref:`sgi-ip53`.

.. seealso::

   - :term:`ELSC` (:doc:`elsc`): the module system controller of the :term:`SN0` machines.

The L1 is the per-chassis system controller of :term:`SN1` systems. It runs
from standby power, keeps the chassis identity, watches fans, supplies and temperatures, drives node power, reset and NMI, and
carries the operator console. The node's :term:`Bedrock` reaches it through a
16550-style UART and a framed request and response protocol, which the
IP35 :term:`PROM`, IRIX and the public kernels use to read board records, write
the display and pass console text.

QEMU models the node-facing side as two objects in
``hw/misc/sgi-l1.c``: ``sgi-l1``, the controller (frame parser, request
dispatch, operator console, display, log and power state), and
``sgi-l1-uart``, the eight-register UART window a Bedrock or router
maps. The controller's own processor, its environmental bus, JTAG scan,
flash and management USB are not modelled. No controller board or
firmware revision is modelled. Where this page says what "the 1.44.0
image" does, it states what the shipped L1 firmware image version 1.44.0
for the Origin 300 product group, :src:`l1-firmware-1.44.0`, was read to
do. Those statements are rated *inferred*: the image is the controller's
software, and its behaviour on a fitted chassis follows only if that
image runs there. Captures show Origin 300s running L1 1.18.5
(:src:`irixnet-thread-2737`) and 1.48.1 (:src:`nekonomicon-16724335`),
and other versions may differ. Facts are rated as described in
:ref:`sgi-ratings`.

(:doc:`pci-expansion`). The ``brick-type`` property picks a profile:

without compute services refuses ``power``, ``reset``, ``softreset``,
``nmi`` and ``select`` with an ``INFO:`` line and ``LOG_UNIMP``, and
answers the compute requests (``0x1002``, ``0x1003``, ``0x100b``,
``0x100c``, ``0x2001``, ``0x2005`` to ``0x2008``) with minus 101.

.. _sgi-l1-identity:

Identity
========

The identity request ``0x0003`` returns the rack and bay packed as rack
shifted left 6 or-ed with bay, then the brick-type character. The 1.44.0
image keeps the character in non-volatile memory and answers ``0x34``
(``4``) for an IP45 chassis, *inferred*. The machines select these
characters:

.. list-table::
   :header-rows: 1
   :widths: 30 12 58

   * - Machine
     - Character
     - Basis
   * - Origin 300
     - ``0x34``
     - The 1.44.0 image, *inferred*; the Linux header's IP45 code and
       :src:`lore-kaloz-ip35-35`, a *software expectation*.
   * - Fuel
     - ``0x41`` (``A``)
     - :src:`lore-kaloz-ip35-35`, a *software expectation*. The IP35
       PROM accepts ``4`` or ``A`` here. No Fuel L1 reply is captured.
   * - Origin 350, Onyx 350, Onyx 4 host
     - ``0x37``
     - A retained L1 firmware image selects ``0x37`` when the integrated
       board's record names the Origin 350 interconnect board,
       *inferred*; published Origin 350 inventories show that board,
       :src:`nekonomicon-16724207`. The Onyx 350 and Onyx 4 reuse the
       value, an *approximation*.
   * - Tezro deskside
     - ``0x39`` (``9``)
     - :src:`lore-kaloz-ip35-35`, a *software expectation*.
   * - Tezro rack
     - ``0x51`` (``Q``)
     - :src:`lore-kaloz-ip35-35`, a *software expectation*.
   * - Router module
     - ``0x52`` (``R``)
     - The Linux SN1 header's router character, a *software
       expectation*.
   * - PCI expansion module
     - ``0x25``
     - The 1.44.0 image, *inferred*.

No physical L1 identity reply has been captured for any of these
products, so each value is the model's choice from the basis given.

The prompt names the chassis as rack, type letter and slot, ``001c01``
for a stock single chassis. The letter is one of c, i, p, r, x, n, g, or
``?`` :src:`007-3938-006 p. 60`. Rack and slot are kept in non-volatile
memory and a change takes effect at the next L1 boot
:src:`007-3938-001 p. 23`, *established*. A second chassis is given slot
02 before cabling :src:`007-4365-002 p. 38`, and a cabled pair appears as
``Module 001c01`` and ``Module 001c02``
:src:`marc-openbsd-sgi-139223952727384 lines 17-62`, *observed*.

The model takes rack and bay from the ``rack`` and ``bay`` properties
(both default 1; rack below ``0x3ff``, bay below ``0x3f``). ``brick rack``
and ``brick slot`` store a pending value applied at the next controller
restart. The brick serial (``0x0004``) comes from ``brick-serial`` and
the system serial (``0x0008``) from ``system-serial``, or from a station
address (see :ref:`sgi-l1-records`). Without them both requests answer
minus 104, except that the Fuel's brick serial defaults to ``EMUN`` and a
hex byte of the machine's identity seed (the system disk's path or the
machine name, hashed as for the default station address), the synthetic
text serial of the node's system board, a model choice that
``brick-serial`` replaces. The firmware revision (``0x0005``) comes from
``revision-major``, ``-minor`` and ``-patch``. All three must be set or
none; on a machine that selects none the request answers minus 104 and
logs ``LOG_UNIMP``.
The Origin 300, Origin 350, Onyx 350 and Onyx 4 machines select 1.18.5,
the version an Origin 300 capture shows (:src:`irixnet-thread-2737`). The Tezro profiles select 1.48.1,
the version in :src:`ip35-patch-sg0007149`. The Fuel selects 1.48.1 too,
the version one public Fuel capture reports; no capture ties it to the
modelled board, and the machine's ``l1-revision`` replaces it. These
are compatibility choices, not measured factory values.

.. _sgi-l1-uart:

Register map
============

The UART sits in :term:`Hub` special space at the node's remote register window
plus ``0x80``: the node's Hub special base plus ``0x3000_0080``. Each
16550 register occupies eight bytes and is reached with 64-bit loads and
stores whose low byte carries the data (OpenBSD ``hub.h`` lines 68-73
and ``l1.c`` lines 97-142; Linux SN1 ``l1.c`` lines 61-77;
``ip35-l1.c`` lines 28-50), a *software expectation*. All three
consumers use the remote form. The stock IP35 PROM's L1 client uses it
too. Which Bedrock unit decodes the window is *unknown*; the
memory-directory unit's junk-bus timing register carries UART setup and
hold fields (Linux SN1 ``hubmd.h`` lines 1059-1097).

The model also decodes the same eight registers at the local form's
``+0x80`` (the node's Hub special base plus ``0x1000_0080``), sharing
one state. No public consumer reads the UART there. The Origin 300
field diagnostic monitor writes its console there when booted headless
under the stock PROM, observed on the model only. The local decode is
an *approximation*. A read of Hub special local offset ``0x80`` on a
physical Origin 300 or 350 would settle whether real silicon answers.
A router module maps the same window in its own register space
(:doc:`sn1-router`).

``sgi-l1-uart`` accepts only eight-byte accesses, big-endian, with the
register in the low byte. A narrower access is refused by QEMU's memory
core and logged under ``LOG_GUEST_ERROR``; through the Hub windows the
processor sees a decode error. The Hub's region protection applies to
both forms.

   :header-rows: 1
   :widths: 9 22 9 60

   * - Offset
     - Register
     - Reset
     - Model
   * - ``0x00``
     - receive / transmit; divisor low with DLAB
     - ``0``
     - A write hands one byte to the frame parser. A read pops the next
       byte queued for the processor, or returns 0 when the queue is
       empty.
   * - ``0x08``
     - interrupt enable; divisor high with DLAB
     - ``0``
     - Bits 0 and 1 are honoured. Setting bits 7-2 logs ``LOG_UNIMP``.
   * - ``0x10``

     - ``0x01``
     - Reads ``0x04`` (received data), ``0x02`` (transmitter empty) or
       ``0x01`` (none). A write with bit 1 set empties the queue toward
       the processor. No FIFO identification bits.
   * - ``0x18``

     - ``0``

   * - ``0x28``

The register set and the consumers' demands on it are each a *software
expectation*: line status bits 5 and 6 whenever a byte can be accepted,
bit 0 exactly while a byte waits, and clear-to-send, without which the
SN1 early path and the MIPS port spin forever (``l1.c`` line 1973;
``ip35-l1.c`` lines 56-57). The constant values are an *approximation*:
the window accepts every byte at once and has no transmit delay.

Divisor
-------

The SN1 port programs divisor 13 against a 12 MHz clock for 57,600 baud.
The L1's ``uart`` command reports the Bedrock-side port at 57,692 baud,
exactly that divisor :src:`007-3938-006 p. 110-111`, *established*. The
stock PROM programs the same divisor and eight data bits, no parity, one
stop bit, a *software expectation*. Another SN1 build drives the same
window as a raw 8250 with a baud base of 124,800 (``kernel/setup.c``
lines 236-259), so the model stores the divisor and enforces nothing.

Interrupt
---------

The window's ``uart`` output follows the PC16550D rules for the two
causes it implements :src:`ns-pc16550d-1995 p. 11, 13-18`,
*established* for that part:

- Interrupt-enable bit 0 with a byte waiting selects cause ``0x04``,
  ahead of transmitter-empty. Reading the last byte clears it. Reading
  identification does not.
- Setting interrupt-enable bit 1 while it was clear raises a
  transmitter-empty occurrence. Reading identification while it is the
  selected cause acknowledges it. A data write clears it and, once the
  parser has taken the byte, raises one new occurrence if bit 1 is set.
- The output is high while an enabled cause remains.

The immediate re-arm after each written byte is an *approximation*: no
character time passes. Line errors, receive timeouts and modem-status
interrupts are not modelled. The node wires the output to Bedrock
interrupt pending bank 0 bit 4 on both processor interfaces. The bit is
the SN1 header's UART bit, a *software expectation*; delivery to both
interfaces is an *approximation*, since no source says which interface
real silicon targets. OpenBSD, the SN1 port and the stock PROM poll and
never enable the interrupt.

.. _sgi-l1-framing:

Framing and packets
===================

.. list-table::
   :header-rows: 1
   :widths: 46 14 40

   * - Fact
     - Rating
     - Source
   * - Frames are HDLC-like, as in PPP: a ``0x7e`` flag at each end,
       ``0x7d`` escaping ``0x7e`` and ``0x7d`` by exclusive-or ``0x20``,
       and a 16-bit check (reflected polynomial ``0x8408``) initialised
       ``0xffff``, complemented and sent low byte first, over every byte
       from the header to the last argument. A receiver's running check
       over payload and check bytes equals ``0xf0b8``.
     - software expectation
     - All three consumers agree: OpenBSD ``l1.c`` lines 156-306 with
       ``ppp_defs.h``; Linux SN1 ``l1.c`` lines 737-1006 and 1186-1474;
       ``ip35-l1.c`` lines 99-238.
   * - Only the SN1 receiver tolerates repeated flags. OpenBSD and the
       MIPS port lose the next frame after a doubled or shared flag.
     - software expectation
     - OpenBSD ``l1.c`` lines 266-293, 525-526; ``ip35-l1.c`` lines
       193-217; SN1 ``l1.c`` lines 1239-1242.
   * - The header byte carries the packet type in bits 7:5 and the
       subchannel in 4:0: request ``0x00``, response ``0x20``, event
       ``0x40``. Subchannels 0 to 3 are per-processor consoles, 4 the
       system console, 16 to 31 operating-system requests. A response
       returns on the request's subchannel.
     - software expectation
     - OpenBSD ``l1.h``; Linux SN1 ``ksys/l1.h``.
   * - A request payload is a four-byte big-endian destination, a
       two-byte code, a count byte and typed arguments: ``0x00`` and four
       bytes an integer, ``0x01`` and text ending in a zero, ``0x80`` with
       the length in the low seven bits a binary field. The SN1 port and
       the stock PROM omit the count byte on zero-argument requests;
       OpenBSD always sends it.
     - software expectation
     - OpenBSD ``l1.c``; Linux SN1 ``l1.c``; :src:`ip35-prom-6.210 L1
       request builder`.
   * - A response payload is a four-byte signed code, a field count and
       typed fields. OpenBSD and the stock PROM decode the whole word. The
       SN1 port keeps only the low byte, so it never sees a negative
       code.
     - software expectation
     - OpenBSD ``l1.h``; SN1 ``l1.c`` lines 133-139, 2467-2471.
   * - The receiver accepts up to 256 payload bytes plus the check, drops
       one- and two-byte frames, resynchronises after a bad check,
       ``0x7d`` before a flag, or overflow without losing the next frame,
       and treats ``0x7d 0x7d`` as one escape.
     - inferred
     - :src:`l1-firmware-1.44.0 link frame reader`
   * - A reply field is written only while its offset plus its length
       stays below 128, counting the header but not the tag. The largest
       binary field is therefore 116 bytes.
     - inferred
     - :src:`l1-firmware-1.44.0 reply serializer`

The model's receiver follows the 1.44.0 reading: bytes before the first
flag are discarded, a frame of three bytes or more whose check passes is
delivered, and anything else is dropped silently with no reply. Frames
over 258 bytes are discarded up to the next flag. Its emitter sends one
opening and one closing flag per frame and never shares a flag, because
the consumers are less tolerant than the controller. It escapes
``0x7e``, ``0x7d`` and carriage return (``0x0d``); it does not escape
``0x11`` or ``0x13``. The 1.44.0 image escapes carriage return only when
the port's carriage-return option is on; the image's serial start-up
selects that option, *inferred*. Frames from the processor typed
response (``0x20``) or ``0x60`` to ``0xe0``, and requests shorter than
seven bytes, are discarded without a reply. Malformed typed arguments
(a count that runs past the frame, an unknown tag) answer minus 100. The
1.44.0 image does not check them and reads stale bytes instead, so that
answer is an *approximation*.

``0x000e`` and the console field
--------------------------------

The 1.44.0 image keeps a seven-bit field per Bedrock port: node position
in bits 6:5 and console subchannel in 4:0. It stamps every request with a
source address whose bits 11:5 hold that position and the request's
subchannel, and ``0x000e`` returns the position, *inferred*. On a
single-node Origin 300 the position is 0. The stock PROM discards the
value on an Origin 300 and uses it only for type ``6``, a *software
expectation*. The model starts the field at ``node-position`` shifted
left five (0 to 3, default 0), at every controller restart. ``0x1002``
updates it without masking its argument, as the image does, so an
argument of 32 or more lands in the position bits.

Port speeds
-----------

The stock PROM shows the first ``0x000a`` integer as the I/O link rate:
zero is 400 MHz and any other value 600 MHz. It ignores the second, a
*software expectation*. The model answers ``(0, 0)`` by default. The
Origin 350, Onyx 350, Tezro and Onyx 4 profiles set ``port-speed-first``
to 1, which removes the PROM's "set to 400Mhz. Expected 600Mhz" warning.
Each is an *approximation*; no physical reply is captured.

.. _sgi-l1-records:

EEPROM records
==============

The 1.44.0 image registers six records on an Origin 300: 0 the node
board, 1 the I/O-8 board, then memory modules 0, 2, 1 and 3 as
components 2 to 5, *inferred*. An index of 6 or more answers minus 104.
A board record has area 0 (the eight-byte common header), 1 (chassis),
2 (board) and 3 (internal use); a memory-module record has area 4 (SPD).
``0x0006`` answers a size probe (length 0) with the remaining count, and
a read with the remaining count after the chunk and one binary field.
The image validates each board area by a zero byte sum and each SPD by
byte 63 equalling the sum of bytes 0 to 62, and marks a failing area
invalid, *inferred*. The stock PROM and IRIX read components 0 and 1 in
64-byte chunks; OpenBSD reads SPD records and the I/O board's area for
its Ethernet address, each a *software expectation*. OpenBSD's Origin 300 arm
numbers memory modules differently from the image (``l1.c`` lines
996-1015).

The model takes records three ways, and never more than one way per
component.

Raw area files
  ``chassis-eeprom``, ``board-eeprom`` and ``spd-eeprom`` are arrays of
  file paths by component (0 to 15) serving areas 1, 2 and 4. A chassis
  or board file is invalid when its byte sum is not zero, an SPD file
  (at least 64 bytes) when byte 63 is not the sum of bytes 0 to 62. Areas
  0 and 3 answer minus 104. A chunk above 116 bytes answers minus 105
  and logs ``LOG_UNIMP``.

Whole-image records
  ``board-record-eeprom`` and ``spd-record-eeprom`` take a whole EEPROM
  image per component (0 to 5). A board image's header bytes 1, 2 and 3,
  times eight, locate areas 3, 1 and 2. Each area must sum to zero and
  end below the configured capacity. A missing or failing area answers
  minus 107. An SPD image is exactly 160 bytes. A chunk above 116 bytes
  answers with the count 2 and the remaining-count integer only, as the
  1.44.0 serializer does. The expansion profile takes four board images
  of at most 512 bytes (power board, PCI logic board, two interface
  boards) and no SPD.

Built identity records
  When no file names component 0, and ``node-board-name``,
  ``node-board-part`` and ``node-board-revision`` (or
  ``cpu-context-present``) are set, the controller builds a chassis
  area and a board area. The board area carries the given name, part
  and revision, the manufacturer ``SYNTHETIC``, a marked synthetic
  serial, ``board-serial`` when set (the machine sets ``EMUN`` and a hex byte
  of the identity seed, plus the node index, on the Fuel and the Origin 300
  family), else such as ``EMUN00`` (``N`` and the ``identity-index``), and zero
  placeholder fields, and sums to zero. ``cpu-context-present`` adds the
  processor and hub clocks and a mode word for the Origin 350 family.
  ``mac-record`` adds the station address (``mac``): ``io8-board``
  builds component 1 as an ``IO8`` board with serial ``EMUI00`` and the
  address as twelve hex digits; ``mac-text`` makes the system serial the
  address text; ``system-board`` does both for the Fuel's single board.
  ``fuel-mac-eeprom`` instead reads a 512-byte Fuel record image and
  takes the address from its ``MAC`` field. The address is handed to
  the node's Ethernet model.

The built records are each an *approximation*: names, parts and revisions come
from published inventories (``IP45_2CPU``, ``030-1780-001`` revision C,
:src:`nekonomicon-16726611`), everything else is a placeholder. With
the marked serial the model keeps the stock PROM's NVRAM across
resets. With the serial ``000000`` the stock PROM reinitialises its
NVRAM on every boot. That is model behaviour, not a statement about
hardware. The Origin 300 machine supplies no
SPD records, so the PROM's SPD reads answer minus 104, an
*approximation* that OpenBSD sees as absent memory modules.

.. _sgi-l1-console:

Console, display and operator commands
======================================

The L1 has two modes. In L1 mode its console shows the prompt and input
goes to the command processor. In console mode system output is shown
and input goes to the system :src:`007-4365-002 p. 41`, *established*.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Operator input
     - Model
   * - Ctrl-D (``0x04``) at the prompt
     - Prints ``entering console mode  001c01 CPU0, <CTRL_T> to escape
       to L1`` and enters console mode.
   * - Ctrl-T (``0x14``) in console mode
     - Prints ``escaping to L1 system controller`` and the prompt. The
       next command runs, then the L1 prints ``returning to console mode
       ...`` and returns.
   * - ``l1`` when escaped
     - Holds L1 mode until the next Ctrl-D.
   * - Any byte in console mode, node on
     - Sent to the processor as a two-byte request frame on the
       selected subchannel: header, then the byte.
   * - Any byte in console mode, node off
     - ``WARNING: power appears off, console unavailable`` once per entry
       into console mode; the byte is dropped.
   * - Return or line feed in L1 mode
     - Runs the line (at most 127 characters; more logs
       ``LOG_GUEST_ERROR``). Backspace and delete edit.

The texts are those real firmware prints: two spaces before the brick
id, ``<CTRL_T>`` with an underscore, ``returning`` after an escape
(:src:`graphica-o350-notes lines 1792, 2030`), *observed*. The
manuals print ``re-entering`` and ``<CTRL-T>``
:src:`007-4365-002 p. 41`. The designation after the id is ``CPU0`` to
``CPU3`` or ``console`` for subchannel 4.

Console output from the processor is an event-type (``0x40``) frame on
any subchannel. Its bytes go to the operator console in console mode
with the node on. Its subchannel becomes the console-input subchannel,
as in the 1.44.0 image, *inferred*. Output that arrives while the
operator is at the prompt is discarded with ``LOG_UNIMP``. What real
firmware does with it is *unknown*; escaping during PROM output and
watching what appears on return would settle it.

The model implements this command subset of the 2001-2002 vocabulary
:src:`007-4498-002 p. 177-206`. ``*`` before a command broadcasts it to
the cabled peer; ``ctc`` runs it on the peer (see :ref:`sgi-l1-routing`).

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Command
     - Model
   * - ``power`` / ``pwr`` ``up``\|``u``, ``down``\|``d``, ``check``
     - See :ref:`sgi-l1-power`.
   * - ``reset`` / ``rst``, ``softreset`` / ``softrst``, ``nmi``
     - See :ref:`sgi-l1-power`.
   * - ``reboot_l1``
     - Controller restart.
   * - ``select`` / ``sel`` [``subchannel``\|``sub``\|``s``]
       ``console``\|``0``-``4``\|``a``-``d``
     - Sets the console subchannel. Alone, prints the selection. Other
       forms print ``ERROR: bad subchanel selection.``
   * - ``display`` / ``dsp`` [``1``\|``2`` *text*]
     - Prints or writes a display line.
   * - ``log`` [``clear``\|``reset``\|``insert`` *text*]
     - Prints, clears or appends to the log.
   * - ``brick`` [``rack`` *n*\|``slot`` *n*]
     - Prints the identity line, or sets the pending rack (below
       ``0x3ff``) or slot (1 to 39).
   * - ``version`` / ``ver``
     - ``L1 x.y.z (Image A) [Fuel/PE/O300 1MB image]``, or a line saying
       the revision is unavailable.
   * - ``debug`` [*value*]
     - Prints or sets the debug switches.
   * - ``l1dbg`` [``promreq``\|``req`` ``on``\|``off``]
     - Prints or sets request logging.
   * - ``l1``, ``help`` / ``hlp``
     - As above; a fixed help list.
   * - anything else
     - ``ERROR: command not found.``, ``LOG_UNIMP``, status minus 1.

Through task 3 each output line becomes one text field and the reply
code is the command's status. A malformed ``debug`` value answers minus
1200 with a not-found line, the 1.44.0 image's unmodified path,
*inferred*. ``* pwr d``, which OpenBSD, the SN1 port and IRIX send at
power-off, powers the node down at once. ``display`` writes line 1 or
2 of a 12-character view; line 1 holds ``001c01     /``, where the
hardware spins a heartbeat in the last place, and line 2 the status
(``L1 running``, ``Powered Up``, ``Powered Down``, ``Reset done``,
``Sft rst done``, ``NMI done``) until software writes it. Both lines are
readable as the ``display-line-1`` and ``display-line-2`` properties.

The log is a ring of 128 entries of 47 characters stamped from QEMU's
clock as ``MM/DD/YY HH:MM:SS``, oldest dropped first. It records L1
boots, power and reset events with their reason, ``0x100b`` and
``log insert``. With ``l1dbg promreq on`` every task-6 request adds
``L1REQ: <source> - <code>`` with the source address built from the
console field, as :src:`007-3938-006 p. 102` describes, *established*
for the line's form. The real log lives in NVRAM and survives L1 boots
:src:`nekonomicon-16729141`, *observed*.

Events
------

The 1.44.0 image sends environmental events (supply, fan, temperature,
power-down countdown) to the processor only on the subchannel the
processor registered with ``0x1007``, as an event-type frame from task 4
with a code, an integer diagnostic number and a text line
``\r\n<id> ATTN: <message>\r\n``, *inferred*. The model generates one
event: the first ``power down`` while the node is up sends code
``0x8000``, diagnostic 0 and ``Power Down: issue 'pwr d' again to
immediately power down.``, and waits for the second. No environmental
event is generated. A registered event subchannel of 4 or more survives
a controller restart; a lower one is cleared, as in the image.

.. _sgi-l1-routing:

Routing
=======

The destination's bits 31:28 are the controller type (0 L1, 1 L2, 2 L3,
3 attached C-brick, 4 attached I/O brick), 27:18 the rack (``0x3ff``
local), 17:12 the bay (``0x3f`` local) and 4:0 the task (3 command
interpreter, 4 environment, 5 Bedrock console, 6 general). The local
general address is ``0x0ffff006`` (Linux SN1 ``ksys/l1.h``; OpenBSD
``l1.h``), a *software expectation*.

The 1.44.0 image routes on bits 31:12. A request is local when they
equal the controller's own type-0 rack and bay or ``0xffff``. Bits 11:5
are ignored. Anything else goes to a catch-all that tries the cabled
peer, the attached I/O port or an L2, and a failure there answers a
router error reply: ``0x20 | subchannel``, ``ff ff ff ff``, ``00 00 00
08``. A mixed form, one coordinate concrete and one the sentinel, is not
local, *inferred*. On a standalone Origin 300 a type-4 request is
forwarded toward a software peer slot; whether it gets an immediate
router error or no reply depends on handle state the image reading
could not settle, *unknown*. A matching stock-PROM type-4 request with
the L1's handle status and the Bedrock reply captured would settle it.
The stock PROM sends ``0x0003`` and ``0x000c`` to ``0x4ffff006``, a
*software expectation*.

The model:

- A local key goes to the addressed task.
- With a cabled peer (below), a type-0 request for the peer's rack and
  bay, or any type-3 request rewritten to type 0, is answered by the
  peer as if local there, on the requester's subchannel and UART.
- With a query router (below), type-0 requests and, when an attached
  owner is configured, ``0x4ffff006`` requests go to it.
- With an L2 link (:ref:`below <sgi-l1-l2-link>`) connected, a type-1
  or type-2 request leaves on the link.
- Everything else gets the router error reply with detail 8 and logs
  ``LOG_UNIMP``. This includes type 4 on a standalone chassis, a
  type-1 or type-2 request with no L2 link connected, and a type-1 or
  type-2 request the link cannot carry. Type 4 on a standalone chassis
  is an *approximation* of the unknown above.

Two-chassis peer
----------------

A two-chassis Origin 300 links its two controllers through the ``peer``
property, standing for the RS-422 pair in the NUMAlink cable. The link
works only while both have compute services and ``network-422`` set
(default on, the mode the manual requires for a pair,
:src:`007-4365-002 p. 38`). The link carries no wire format: a forwarded
request is an in-process call, an *approximation*, since nothing public
describes what the two L1s exchange. ``* power up`` and ``* power down``
act locally and then on the peer :src:`007-4365-002 p. 36-37`,
*established*; ``* reset`` doing the same is a model choice. Both chassis
are one QEMU machine, so the peer only records its power state, display
and log entry. A power-down reaches the peer only once the requesting
chassis is down. ``ctc <command>`` runs the command on the peer and
prints the peer's id line first; a nested ``ctc`` is refused with
``INFO: nested ctc is unsupported.`` and ``LOG_UNIMP``. ``* debug``,
``ctc debug``, ``* nmi`` and console forwarding from the second chassis
are not modelled.

Query router
------------

For the Origin 300 PCI expansion topologies the machine registers each
controller with a synthetic owner registry and declares which owners can
reach which. A type-0 request with concrete coordinates that match
exactly one reachable associated owner is served by that owner and the
reply returns through the issuer's UART. An issuer may also have one
attached owner that serves ``0x4ffff006``; the request reaches it as
``0x0ffff006``. Only read-only task-6 requests pass: ``0x0003``,
``0x0006``, ``0x0007``, and ``0x0004`` for concrete addresses or
``0x000c`` for the attached address. Everything else, a missing,
disconnected or ambiguous owner, mixed sentinels and nested routing gets
the router error reply with detail 8 and ``LOG_UNIMP``. The registry is
an *approximation* standing for the controllers' configuration
exchange, which is not modelled; it does not claim a physical cable
pairing.

The ``vbrick-discovery-reference`` profile answers every well-formed
task-6 request with minus 104 and other tasks with minus 101, refuses
operator commands, and logs ``LOG_UNIMP``.

Multi-frame transport
---------------------

Codes ``0x3001`` to ``0x3003`` behind a zero destination word are a
multi-frame transport: ``0x3001`` starts a message with a fragment
count and length, ``0x3002`` starts another fragment and ``0x3003``
continues one. The inner message has a 20-byte header (length, version
2, status, sequence, fragment count, type, source metadata, destination,
source, descriptor count, command field) and eight-byte descriptors,
and replies go back in pieces of at most 113 inner bytes, *inferred*
from the 1.48.1 image in :src:`ip35-patch-sg0007149`. IRIX 6.5.30
``l1cmd`` uses it, a *software expectation*.

The model assembles one inner fragment per UART and subchannel and
answers only when a profile selects it:

- ``irouter-compat`` (Origin 350 family profiles): types ``0x37``,
  ``0x39`` and ``0x51`` answer the local commands ``brick`` and
  ``brick`` with a trailing space with ``rack: <rack>, slot: <slot>,
  partition: none|<n>, type: <label> [?MB flash], serial:<serial>,
  source: OTHER``. Rack, slot and partition are the configured values.
- ``o300-l1cmd-compat`` (the ``origin300-l1cmd-compat`` machine option):
  type ``0x34`` answers ``brick``, ``version`` and ``serial all``, each
  with a trailing space, with text whose missing fields read
  ``EMU-UNKNOWN``.

The reply address packs the UART index and subchannel into bits 11:5
with task 21. The 1.48.1 image does so for the Origin 350 family types;
for type ``0x34`` it is an *approximation*. All reply text beyond the
configured identity is model policy, not firmware output. Multi-fragment
messages, other commands and malformed chunks are dropped with
``LOG_UNIMP`` or ``LOG_GUEST_ERROR`` and get no reply.

.. _sgi-l1-l2-link:

L2 link
=======

An L2 is the rack controller that reaches every brick's L1 over USB. The
model has none. The optional ``l2`` property is a chardev that stands for
the USB bulk pair toward whatever plays the L2: the project's own
stand-in for a test or a companion process, not a hardware wire. With
the property unset, or while no peer is connected, nothing changes: a
request for controller type 1 or 2 gets the router error reply with
detail 8, and request ``0x000b`` answers the stored setting. The
read-only ``l2-link-up`` property says whether a peer is connected.

``l2-partition-flag`` (0 to 3, default 0) is the initial value of the
two-bit setting that request ``0x000b`` returns and ``0x1008`` writes.
The stock PROM fetches a partition record from an L2 only after a
nonzero answer, so a test starts that fetch by setting it. It is not the
partition ID that ``0x0009`` returns. What the setting means on a real
controller is *unknown*.

Link format
-----------

The real link carries one router segment per USB transfer. A stream
socket has no transfer boundary, so each message on the chardev is a
one-byte kind followed by its body. Kind 1 is a segment, and its first
two bytes (big endian, counting themselves, at least 6 and at most
1,024) delimit it. Other kinds are reserved: the L1 logs one with
``LOG_GUEST_ERROR`` and skips the byte. The format is the project's own
(``include/hw/misc/sgi-l1-l2-link.h``); the segment inside it is the
field map of the controller's management USB stream, *established* for
the L1 side and *inferred* for what the L2 expects:

.. list-table::
   :header-rows: 1
   :widths: 12 12 76

   * - Offset
     - Width
     - Field
   * - 0
     - 2
     - Segment length, including itself.
   * - 2
     - 1
     - Format byte, 2 as the L1 builds it.
   * - 3
     - 1
     - Flag byte, meaning *unknown*; the model sends 0.
   * - 4
     - 1
     - Low byte of the sequence number.
   * - 5
     - 1
     - Bit 7 set on the first segment of a packet; bits 6:0 the segments
       left, counting this one on the first. A packet is up to 127
       segments, each carrying one less than the last.
   * - 6
     - 1
     - Class: request 0, response 1, event 2.
   * - 7
     - 1
     - Source port, meaning *unknown*; the model sends 0.
   * - 8
     - 4
     - Destination router address.
   * - 12
     - 4
     - Source router address.
   * - 16
     - 1
     - Descriptor count.
   * - 17
     - 1
     - High byte of the sequence number.
   * - 18
     - 2
     - Request or response code.
   * - 20
     - 8 each
     - Descriptors. A scalar is ``00 00 0000`` and a 32-bit value.

Every segment that crosses the link in either direction is the trace
event ``sgi_l1_l2_segment`` with its bytes, so a run's traffic can be
read from the trace.

Requests toward the L2
----------------------

A plain request from the node for type 1 or 2 is forwarded as one
request segment when every argument is an integer, because no other
descriptor form is established. A request with another argument type
keeps the router error reply. The stock PROM sends its partition-record
fetch another way, as the multi-frame transport (below) carrying a
complete inner message for controller type 1, task ``0xa``; the inner
message already has the segment layout, so the model forwards it as it
arrived. In a boot run of the stock firmware it was a 28-byte request
segment with code 1 and one integer argument, 4 on the C-brick in bay 4,
which the firmware sent after asking ``0x000b`` and followed with
``0x1006`` once the reply came. What the argument means is *inferred*:
an L2's partition service reads it as a brick identifier.
While a peer is connected every profile accepts that transport for a
request whose inner destination is controller type 1 or 2. On a profile
without an IRouter of its own, any other chunk frame is handled as it is
with no peer. A packet of more than one fragment is not forwarded.

In both forms the source word is rewritten to the controller's own
rack and bay key in bits 31:12, the requester's UART index and
subchannel in bits 11:5 and task 21 in bits 4:0, the packing the
multi-frame transport uses for its replies. That the controller's key
fills the rest is an *approximation*; the real base is not established.
The peer addresses its response to that word, which is how the model finds
the requester.

Responses from the L2
---------------------

A response segment whose destination names a requester with a request
pending is returned to it.

- To a plain request, the first descriptor is the reply code and every
  further integer descriptor is one integer field of the ordinary reply.
  A response of more than one segment, or with a descriptor that is not
  a scalar, is logged with ``LOG_UNIMP`` and the requester gets the
  router error reply.
- To a chunk-transport request, each segment returns as frames of at most
  113 payload bytes. The first frame of a segment is ``0x3001`` and
  carries the segment's remaining-segment count in its count byte and the
  frame's own payload length in its length field. Each later frame is
  ``0x3003`` while the segment has more, and ``0x3002`` on the frame that
  exhausts it; their count and length fields are zero. A segment that fits
  one frame is a single ``0x3001``.

  The stock boot firmware was run against this (a stand-in peer, the
  two-partition Origin 3400, a nonzero ``l2-partition-flag`` on the first
  C-brick). A 36-byte segment in one ``0x3001`` frame was accepted and its
  integer used. A 300-byte segment in three frames, with the length field
  of the ``0x3001`` frame holding the whole 300, made the firmware reject
  the frame as shorter than that length; with that field holding the
  frame's own 113 bytes it was accepted, whether the later frames carried a zero length or
  their own. That is the reader's behavior in a model run, for this
  firmware version only, not a capture of an L2. A reply of two segments was accepted with each segment's
  first frame ``0x3001`` and also with only the first, so which the
  firmware expects of a second segment, and whether it reads one, is
  *unknown*. The firmware's wait of about four seconds for a reply is
  *inferred*: with no reply it reported that the wait had failed and went
  on with the partition ID its controller holds.

Segments that are not responses (requests and events from the L2),
responses that name no requester or one with nothing pending, and
continuations out of order are logged and dropped. The L2's own
housekeeping requests are not served, because nothing published says what
the L1 answers.

No timeout is modelled: the PROM's own wait for the reply is its
concern. If the peer disconnects, a plain request still waiting gets the
router error reply and pending state is cleared.

Limits
------

- There is no USB device: no descriptors, endpoint halt clearing,
  zero-length packets or 64-byte packetisation. Those are the L1's
  firmware behaviour and wait for the firmware L1.
- Attach, device-reset and endpoint-reset control messages are not
  defined; the peer learns of the L1 by the connection.
- Setting ``l2`` blocks migration and snapshots, whether or not a peer is
  connected, because the peer's state is outside the machine.
- The link state is not part of the saved device state.

Board-side interfaces
=====================

The 1.44.0 image drives an M-Bus (the ColdFire's I2C-style bus) through
the MCF5206e registers at ``MBAR+0x1e0`` to ``+0x1f0``
:src:`nxp-mcf5206eum-1 p. 13-6-13-11`, with divider selector ``0x13``,
which the manual maps to 480 :src:`nxp-mcf5206eum-1 p. 13-7`. It polls
monitors at bus addresses ``0x58``, ``0x5a`` and ``0x5c``, I/O
expanders, supplies, fans and temperatures, and reads the board
EEPROMs into RAM at start, *inferred*. ``0x0006`` serves that RAM copy.
The SCL rate, fitted parts and bus topology are *unknown*.

The model has none of this. Its only board-side action is
for the PCI expansion module: when the machine binds an
interface board, each controller restart writes the packed rack and bay
to that board through two operations (bus 0, address ``0x8c`` for
position 0 or ``0x8e`` for position 1, command ``0x13`` with the high
byte and ``0x12`` with the low). A failed operation logs
``LOG_GUEST_ERROR`` and the other still runs. This is an
*approximation*; the operation is a function call, not an M-Bus
transaction.

The management USB port is a USB 1.0 device toward an optional L2. The
1.44.0 image declares one interface with 64-byte bulk endpoints OUT 1
and IN 2, *inferred*. The model has no USB device. Test-only properties
under qtest compute the image's ``GET_STATUS`` and ``GET_DESCRIPTOR``
bytes for cached endpoint states; no transfer takes place.

.. _sgi-l1-power:

Power, reset and NMI
====================

The L1 runs whenever the chassis has mains power, before the node is
powered :src:`007-4365-002 p. 35`, and drives reset, soft reset and NMI
to the node on its commands and the front-panel buttons
:src:`007-3938-006 p. 80, 91, 94`, *established*. No public guest asks
it to reset; OpenBSD reboots through the Bedrock and uses the L1 only to
power off.

.. list-table::
   :header-rows: 1
   :widths: 26 74

   * - Event
     - Model
   * - Realize (mains applied)
     - Controller boot. With ``auto-power`` (default on) the node is
       powered at once with no countdown, logging ``auto power up
       initiated`` and printing ``INFO: 001c01 powering up the system.``
   * - ``power up``
     - With the node off: node power on, console selection back to CPU
       0, ``Powered Up``, a log entry, the console-mode text, then a
       QEMU system reset; the machine resumes once that reset has run.
       With the node on: ``Power is already on``.
   * - ``power down``
     - First request while up: the ``0x8000`` event and nothing else.
       Second: node power off, ``Powered Down``, a log entry and a QEMU
       shutdown request. Through task 3 or ``0x2005`` it acts at once.
       With the node off it does nothing.
   * - ``0x2006``
     - Power-off without shutdown when the node is on, then power-on as
       for ``power up``, both with reason 3.
   * - ``reset``, ``0x2001``
     - With the node on: ``Reset done``, a log entry, a pulse on
       ``node-reset`` and a QEMU system reset.
   * - ``softreset``
     - With the node on: ``Sft rst done``, a log entry and a pulse on
       ``soft-reset``.
   * - ``nmi``
     - With the node on: ``NMI done``, a log entry and a pulse on
       ``nmi``, which the node routes to every fitted processor's NMI
       input.

Each machine action is queued on the processor whose write reached the
UART and every processor is paused before QEMU handles it; from the
host console the main thread pauses all processors first. A reply queued
before a reset may be cleared with the UART before the guest reads it.
Resetting the whole machine, keeping the QEMU process alive for a power
cycle, the hold times and the missing countdown are each an *approximation*.
The ``node-power``, ``node-reset`` and ``soft-reset`` outputs report
what the L1 did and drive nothing; no source says what a soft reset
reaches in the node. The front-panel buttons are not modelled.

Reset
=====

A controller restart (realize, ``reboot_l1``, ``0x4002``) applies the
pending rack and slot, leaves console mode, clears the command line,
the frame parsers and request logging, sets the console field from
``node-position``, clears a registered event subchannel below 4, clears a pending
power-down, writes
``001c01     /`` and ``L1 running`` and logs ``L1 booting x.y.z``. It
keeps node power, the log, the debug switches, partition and the
records. The router, expansion and reference controllers are on the
machine's reset tree and restart on a system reset. A compute node's
controller is not: a node reset leaves it running, as the manuals
describe :src:`007-3938-006 p. 91`, *inferred*.

A device reset of ``sgi-l1`` also clears every multi-frame assembly and
the USB test state. A reset of ``sgi-l1-uart`` clears its registers, divisor and queue,
lowers its interrupt and discards the controller's partial frame and
multi-frame assembly for that UART.

Migration
=========

``sgi-l1`` migrates its power and console state, settings, rack and bay,
pending values, console field, event subchannel, log, display, partial
frames, multi-frame assemblies and record bytes. Loading checks that the
destination has the same profile, port-speed value, multi-frame
selection, power and interface-board bindings and query owner identity,
and rejects a stream whose records or indices are out of range. The
records travel in the stream, so the destination's files are not read.
Saving is refused while a routed or bound call is in progress.
``sgi-l1-uart`` migrates its registers, transmitter-empty occurrence and
queue, checks its UART index and recomputes the interrupt line. The peer
link, ``network-422`` and ``auto-power`` are configuration and are not
migrated. Migration works only between identical builds. An ``l2`` link
blocks migration and snapshots.

Origin 3900 Cx-brick profile
============================

``brick-type=cxbrick`` models the one L1 of a Cx-brick, the Origin 3900
and Onyx 3000 brick that holds one to four IP53 node boards behind a single
controller on its router board (*SGI Origin 3900 Server User's Guide*
:src:`007-4653-001 p. 52-60`; *Cx-brick Addendum*
:src:`007-4572-001 p. 2-18`). ``boards`` names the fitted node boards
and ``compute-boards`` those with processors, one bit per board 0 to 3. Each fitted board reaches
the controller through its own UART window, ``sgi-l1-uart`` with
``transport-index`` the board number. Identity, naming and restart follow
the C-brick profile above: a brick starts unnamed and prints ``---c--``
(:src:`007-4653-001 p. 144`).

Request codes, the request layout and the framing follow the C-brick rule.
The profile serves the codes the Linux v2.6.0 ``ksys/l1.h`` header names
with the Origin 300 meaning (``0x0001`` to ``0x0009``, ``0x1002`` to
``0x1007``), the I/O link speed ``0x000a`` that the stock PROM reads from
its node's own L1, and the Origin 300 codes ``0x000e``, ``0x2001``,
``0x2005`` and ``0x2006``. Every other code answers the unknown-request code and is logged
as unimplemented, the attached-brick requests ``0x000c`` and ``0x000d``
among them. ``0x2001`` resets, as on the Origin 300; the public header gives
``0x2001`` to PCI power-up and ``0x2000`` to the full reset, so which a
fitted Cx-brick uses is *unknown*, and each ``0x2001`` is logged as such.

  by ``select`` and by ``0x1003``, which moves it to the volunteer's console
  subchannel. Console output on a window does not move it, as it does on the
  Origin 300. It starts on board 0's console, or on the lowest board with
  processors when board 0 has none; a real L1 may keep ``console0`` and time
  out. The filter is cleared at L1 power-on.
- ``select`` refuses a board that is not fitted with ``ERROR: bad subchanel
  selection.`` and accepts one without processors. Console mode toward a
  board without processors prints the guide's ``no response from 001c07
  junk bus console UART:UART_TIMEOUT``, or for a processor subchannel
  ``no response from 001c07 Junk bus CPU2B system not responding``
  (:src:`007-4653-001 p. 115, 141`), and stays in L1 mode.
- Power, reset and NMI requests from any window, and from the prompt, act on
  every board at once and log one entry. The machine's own reset carries
  them out, so the router is reset with the rest, where the profile's
  contract keeps the router's state; per-board power and reset are not
  offered. ``nmi`` pulses one ``nmi`` line per board, and only boards with
  processors are wired to them.
- Request ``0x0006`` follows the 38-entry component table of the L1
  firmware's Cx-brick personality: component 0 the power entry module's
  inlet board, 1 the router board, then a node board at 2, 11, 20 and 29,
  each followed by its eight DIMM SPDs in the order 0, 2, 4, 6, 1, 3, 5, 7.
  The firmware numbers a request by the port it arrived on. On board ``n``'s
  window component 0 is table entry 2 + 9n (its node board), 1 is 3 + 9n (its
  DIMM 0 SPD, not the router), and ``c`` of 2 or more is ``c`` + 9n, so 3 to
  10 are its own DIMMs and larger numbers reach other boards; 38 and up
  answer minus 104, as do the entries of an unfitted board. With
  ``cpu-context-present`` each node board's record carries the CPU context
  the Origin 350's carries, which the stock PROM compares with its flash.
  Approximations:

  - Link ``n`` is node board ``n``'s port. The numbering is established for
    the firmware; the port to board mapping is inferred.
  - The router's own port is the router window: a router-profile L1 behind
    the window answers component 1 with the ``ROUTER`` record (name
    inferred, part ``NOTOBSERVED0`` and revision ``00`` not observed,
    synthetic serial) and components 0 and 2 up with minus 104. The brick's
    own L1 has no router port, so it serves neither the router record nor
    the power inlet.
  - The power inlet is absent: its record's contents are unknown and the
    stock PROM never asks for it.
  - SPDs exist only for the DIMMs the catalogue's 2048 MiB per node needs,
    the two 1 GiB DIMMs in slots 0 and 1. Each has a valid checksum, byte 13
    zero (the PROM's memory self-test decides the width) and byte 31 the
    1 GiB rank density, which the PROM uses only when its memory probe finds
    nothing. Type and timing bytes stay zero and are not interpreted. The
    population of a real Cx-brick is unknown. Byte 99 marks the board.
- Board ``n``'s window answers the identity requests with the brick's slot
  plus ``n``, because the stock PROM refuses two modules at one slot. Request
  ``0x0003`` returns the personality letter ``6`` (``brick-type-code``
  overrides it), and ``brick`` prints it. Request ``0x0004`` returns the
  serial of the board record the port names: node ``n``'s synthetic serial
  on link ``n`` and the ``ROUTER`` record's on the router window, which is
  also the brick's serial; the ``brick-serial`` property does not reach the
  guest. The serials are the model's synthetic ones.
- Request ``0x0005`` answers the firmware revision ``revision-*``
  configures, 1.44.0 in the Origin 3900 catalogue entries as on the other
  brick profiles, and minus 104 without one. ``version`` prints it as
  ``L1 1.44.0 (Image EMU-UNKNOWN)``. That a fitted Cx-brick runs 1.44.0
  is *inferred*, as for the other bricks.
- Request ``0x000a`` answers as on the C-brick profile, 400 MHz unless
  ``port-speed-first`` says otherwise, which matches the I-brick the
  Cx-brick's L1 reaches. What a fitted Cx-brick answers is *unknown*.
- A neighbouring Cx-brick link is refused. The L2, the neighbouring
  Cx-brick and the ``iia`` to ``iid``, ``nia`` and ``nib`` commands are not
  modelled. One I-brick may be named as ``io-peer``: the attached I/O
  brick request then goes to it in the C-brick's request form, because the
  addressing of a Cx-brick's four I/O ports is unknown. Without a peer an
  attached-brick destination answers the router's error reply.

Measurements
============

No L1 has been measured for this model. The captures named under
:ref:`sgi-l1-sources` are published sessions; none records a framed
exchange on the Bedrock UART.

.. _sgi-l1-model:

Model limits
============

- The controller does not run L1 firmware. Its replies are a responder
  built from the readings above; a reply or a version line does not mean
  firmware ran.
- No M-Bus, environmental monitoring, events other than the deferred
  power-down, JTAG scan, flash, management USB device, task-14
  configuration exchange or RS-422 wire protocol. The L2 link carries
  segments only; nothing the L2 sends on its own is served.
- The operator commands ``env``, ``date``, ``config``, ``uart``,
  ``flash``, ``network``, ``cpu``, ``port``, ``serial``, ``autopower``,
  ``history``, ``l1dbg console`` and ``select filter`` are not modelled.
  Unknown commands log ``LOG_UNIMP``.
- The prompt, display and ``brick`` line always use the letter ``c``,
  and ``brick`` always prints ``type: C (IP45) [1MB flash], serial:
  unavailable, source: EEPROM``, whatever the profile.
- Display hardware, LEDs and the heartbeat are not modelled; ``display``
  reports fixed LED texts.
- Malformed frames, bad checks and unrouted local tasks are dropped with
  no entry in the L1 log, where the 1.44.0 image logs them.
- The UART has no character timing, line errors or FIFO identification.
- Accesses: unsupported interrupt-enable bits and unrouted tasks log
  ``LOG_UNIMP``; writes to the status registers, a full queue toward the
  processor (4096 bytes; the frame is dropped) and an over-long command
  line log ``LOG_GUEST_ERROR``; a narrower access to the window is a
  decode error.

Tests
=====

``tests/qtest/sn1-l1-test.c`` covers the UART registers, interrupts and
their migration, framing and receive tolerance, output escaping, every
general request and reply code, the command interpreter, console mode,
retargeting and short frames, the power, reset, NMI and power-cycle
paths, controller restart and node position, raw, whole-image and built
EEPROM records, the Fuel station-address record, the peer pair, the
query and attached routing models (with
``tests/qtest/l1-query-routing-fixture.c``), the expansion, router and
reference profiles, the interface-board start-up (with
``tests/qtest/l1-bic-startup-fixture.c``), the multi-frame transport for
both selections, the management USB byte calculations and migration of
each. ``tests/qtest/sn1-address-map-test.c`` checks the window at both
Hub forms, the interrupt reaching the processor, the operator console,
revisions, type codes and built records on the machines.
``tests/qtest/sn1-bedrock-test.c`` checks the Bedrock's refusals and
protection for the window, ``tests/qtest/sn1-cross-node-test.c`` the
local form on a second node, ``tests/qtest/sn1-fuel-test.c`` the Fuel
type code and NMI routing, ``tests/qtest/sn-builder-test.c`` the peer
wiring and the Origin 350 family type selection, and
``tests/qtest/sgi-sn1-router-test.c`` the router module's window.
``tests/functional/mips64/test_sn1_l1_reset.py`` runs real guest code:
one processor sends a framed ``0x2001`` while another spins, across
repeated resets, and power cycles through the host console stop every
processor. It needs the stock IP35 PROM image.

``tests/qtest/sgi-l1-o3k-test.c`` covers the L2 link with a stub peer in
``tests/qtest/sgi-l1-l2-stub.h``: the no-route reply with no peer, the
forwarded segment bytes, the partition-record fetch and its single- and
multi-frame replies, tolerance of junk on the link, the stored setting
behind ``0x000b`` and the migration blocker. The stub answers one
request and is a fixture, not an L2 model.
