.. _sgi-l1:

=====================
L1: system controller
=====================

Used in :ref:`sgi-ip35` (Origin 300 and Fuel), :ref:`sgi-ip53` (Origin
350, Onyx 350, Tezro and the Onyx4 host), the Origin 300 PCI expansion
module (:doc:`pci-expansion`) and :term:`NUMAlink` module
(:ref:`sgi-bricks-numalink-module`), and the Origin 3000 and Onyx 3000
C-, I-, N-, V-, R- and CX-bricks (:ref:`sgi-bricks`), which the
``origin3000`` machine's topologies build.

.. seealso::

   Platform pages: :ref:`sgi-ip35`, :ref:`sgi-ip53`.

.. seealso::

   - :term:`ELSC` (:doc:`elsc`): the module system controller of the :term:`SN0` machines.

The L1 is the per-chassis system controller of :term:`SN1` systems. It runs
from standby power, keeps the chassis identity, watches fans, supplies and temperatures, drives node power, reset and NMI, and
carries the operator console. The node's :term:`Bedrock` reaches it through a
16550-style UART and a framed request and response protocol, which the
IP35 :term:`PROM`, IRIX and the public kernels use to read board records, write
the display and pass console text.

QEMU models the node-facing side as two objects in
``hw/misc/sgi-l1.c``: ``sgi-l1``, the controller (frame parser, request
dispatch, operator console, display, log and power state), and
``sgi-l1-uart``, the eight-register UART window a Bedrock or router
maps. The controller's own processor, its environmental bus, JTAG scan,
flash and management USB are not modelled. No controller board or
firmware revision is modelled. Where this page says what "the 1.44.0
image" does, it states what the shipped L1 firmware image version 1.44.0
for the Origin 300 product group, :src:`l1-firmware-1.44.0`, was read to
do. Those statements are each a *software expectation*: the image is the
controller's software, and its behaviour on a fitted chassis follows only
if that image runs there, which is *inferred*. Captures show Origin 300s running L1 1.18.5
(:src:`irixnet-thread-2737`) and 1.48.1 (:src:`nekonomicon-16724335`),
and other versions may differ. Facts are rated as described in
:ref:`sgi-ratings`.

(:doc:`sn1-router`) and one in each PCI expansion module
(:doc:`pci-expansion`). The ``brick-type`` property picks a profile:

     - Profile
   * - ``ip45`` (default)

       positions.
   * - ``ip34``
     - none
     - Compute chassis with no default type. The machine supplies one.
   * - ``ip35``

       bytes, no console, power or reset of a node.
   * - ``router``
     - ``0x52``

       topology. It refuses every request (see
       :ref:`sgi-l1-routing`).

A non-zero ``brick-type-code`` overrides the profile's code. A profile
without compute services refuses ``power``, ``reset``, ``softreset``,
``nmi`` and ``select`` with an ``INFO:`` line and ``LOG_UNIMP``, and
answers the compute requests (``0x1002``, ``0x1003``, ``0x100b``,
``0x100c``, ``0x2001``, ``0x2005`` to ``0x2008``) with minus 101.

.. _sgi-l1-identity:

Identity
========

The identity request ``0x0003`` returns the rack and bay packed as rack
shifted left 6 or-ed with bay, then the brick-type character. The 1.44.0
image keeps the character in non-volatile memory and answers ``0x34``
(``4``) for an IP45 chassis, *inferred*. The machines select these
characters:

.. list-table::
   :header-rows: 1
   :widths: 30 12 58

   * - Machine
     - Character
     - Basis
   * - Origin 300
     - ``0x34``
     - The 1.44.0 image, *inferred*; the Linux header's IP45 code and
       :src:`lore-kaloz-ip35-35`, a *software expectation*.
   * - Fuel
     - ``0x41`` (``A``)
     - :src:`lore-kaloz-ip35-35`, a *software expectation*. The IP35
       PROM accepts ``4`` or ``A`` here. No Fuel L1 reply is captured.
   * - Origin 350, Onyx 350, Onyx 4 host
     - ``0x37``
     - A retained L1 firmware image selects ``0x37`` when the integrated
       board's record names the Origin 350 interconnect board,
       *inferred*; published Origin 350 inventories show that board,
       :src:`nekonomicon-16724207`. The Onyx 350 and Onyx 4 reuse the
       value, an *approximation*.
   * - Tezro deskside
     - ``0x39`` (``9``)
     - :src:`lore-kaloz-ip35-35`, a *software expectation*.
   * - Tezro rack
     - ``0x51`` (``Q``)
     - :src:`lore-kaloz-ip35-35`, a *software expectation*.
   * - Router module
     - ``0x52`` (``R``)
     - The Linux SN1 header's router character, a *software
       expectation*.
   * - PCI expansion module
     - ``0x25``
     - The 1.44.0 image, *inferred*.

No physical L1 identity reply has been captured for any of these
products, so each value is the model's choice from the basis given.

The prompt names the chassis as rack, type letter and slot, ``001c01``
for a stock single chassis. The letter is one of c, i, p, r, x, n, g, or
``?`` :src:`007-3938-006 p. 60`. Rack and slot are kept in non-volatile
memory and a change takes effect at the next L1 boot
:src:`007-3938-001 p. 23`, *established*. A second chassis is given slot
02 before cabling :src:`007-4365-002 p. 38`, and a cabled pair appears as
``Module 001c01`` and ``Module 001c02``
:src:`marc-openbsd-sgi-139223952727384 lines 17-62`, *observed*.

The model takes rack and bay from the ``rack`` and ``bay`` properties
(both default 1; rack below ``0x3ff``, bay below ``0x3f``). ``brick rack``
and ``brick slot`` store a pending value applied at the next controller
restart. The brick serial (``0x0004``) comes from ``brick-serial`` and
the system serial (``0x0008``) from ``system-serial``, or from a station
address (see :ref:`sgi-l1-records`). Without them both requests answer
minus 104, except that the Fuel's brick serial defaults to ``EMUN`` and
the node number as a hex byte, the synthetic text serial of the node's
system board, a model choice that ``brick-serial`` replaces; it does not
follow any identity input, because the PROM ties its NVRAM to it.
Every machine except the Fuel sets each of its L1s' system serial to
``LEMU``, the kind digit, the machine's ``emu-id`` as four digits and ``0``,
or the text ``serial=`` or ``hostid=`` gives (:ref:`sgi-identity`), another
model choice that ``system-serial`` replaces. All of a machine's L1s hold the one
value, because the serial belongs to the system and the guest sends the
request to whichever L1 its node reaches (on a C-brick, the attached I/O
brick's). A bare L1 device with no machine around it has none, so the
guest's system id, and FLEXlm's host id, would be empty. The firmware
revision (``0x0005``) comes from ``revision-major``, ``-minor`` and
``-patch``. All three must be set or none; on a machine that selects none the request answers minus 104 and
logs ``LOG_UNIMP``.
The Origin 300, Origin 350, Onyx 350 and Onyx 4 machines select 1.18.5,
the version an Origin 300 capture shows (:src:`irixnet-thread-2737`). The Tezro profiles select 1.48.1,
the version in :src:`ip35-patch-sg0007149`. The Fuel selects 1.48.1 too,
the version one public Fuel capture reports; no capture ties it to the
modelled board, and the machine's ``l1-revision`` replaces it. These
are compatibility choices, not measured factory values.

.. _sgi-l1-uart:

Register map
============

The UART sits in :term:`Hub` special space at the node's remote register window
plus ``0x80``: the node's Hub special base plus ``0x3000_0080``. Each
16550 register occupies eight bytes and is reached with 64-bit loads and
stores whose low byte carries the data (OpenBSD ``hub.h`` lines 68-73
and ``l1.c`` lines 97-142; Linux SN1 ``l1.c`` lines 61-77;
``ip35-l1.c`` lines 28-50), a *software expectation*. All three
consumers use the remote form. The stock IP35 PROM's L1 client uses it
too. Which Bedrock unit decodes the window is *unknown*; the
memory-directory unit's junk-bus timing register carries UART setup and
hold fields (Linux SN1 ``hubmd.h`` lines 1059-1097).

The model also decodes the same eight registers at the local form's
``+0x80`` (the node's Hub special base plus ``0x1000_0080``), sharing
one state. No public consumer reads the UART there. The Origin 300
field diagnostic monitor writes its console there when booted headless
under the stock PROM, observed on the model only. The local decode is
an *approximation*. A read of Hub special local offset ``0x80`` on a
physical Origin 300 or 350 would settle whether real silicon answers.
A router module maps the same window in its own register space
(:doc:`sn1-router`).

``sgi-l1-uart`` accepts only eight-byte accesses, big-endian, with the
register in the low byte. A narrower access is refused by QEMU's memory
core and logged under ``LOG_GUEST_ERROR``; through the Hub windows the
processor sees a decode error. The Hub's region protection applies to
both forms.

   * - ``0x00``
     - receive / transmit; divisor low with DLAB

       byte queued for the processor, or returns 0 when the queue is
       empty.
   * - ``0x08``

   * - ``0x10``

The register set and the consumers' demands on it are each a *software
expectation*: line status bits 5 and 6 whenever a byte can be accepted,
bit 0 exactly while a byte waits, and clear-to-send, without which the
SN1 early path and the MIPS port spin forever (``l1.c`` line 1973;
``ip35-l1.c`` lines 56-57). The constant values are an *approximation*:
the window accepts every byte at once and has no transmit delay.

Divisor
-------

The SN1 port programs divisor 13 against a 12 MHz clock for 57,600 baud.
The L1's ``uart`` command reports the Bedrock-side port at 57,692 baud,
exactly that divisor :src:`007-3938-006 p. 110-111`, *established*. The
stock PROM programs the same divisor and eight data bits, no parity, one
stop bit, a *software expectation*. Another SN1 build drives the same
window as a raw 8250 with a baud base of 124,800 (``kernel/setup.c``
lines 236-259), so the model stores the divisor and enforces nothing.

Interrupt
---------

The window's ``uart`` output follows the PC16550D rules for the two
causes it implements :src:`ns-pc16550d-1995 p. 11, 13-18`,
*established* for that part:

- Interrupt-enable bit 0 with a byte waiting selects cause ``0x04``,
  ahead of transmitter-empty. Reading the last byte clears it. Reading
  identification does not.
- Setting interrupt-enable bit 1 while it was clear raises a
  transmitter-empty occurrence. Reading identification while it is the
  selected cause acknowledges it. A data write clears it and, once the
  parser has taken the byte, raises one new occurrence if bit 1 is set.
- The output is high while an enabled cause remains.

The immediate re-arm after each written byte is an *approximation*: no
character time passes. Line errors, receive timeouts and modem-status
interrupts are not modelled. The node wires the output to Bedrock
interrupt pending bank 0 bit 4 on both processor interfaces. The bit is
the SN1 header's UART bit, a *software expectation*; delivery to both
interfaces is an *approximation*, since no source says which interface
real silicon targets. OpenBSD, the SN1 port and the stock PROM poll and
never enable the interrupt.

.. _sgi-l1-framing:

Framing and packets
===================

.. list-table::
   :header-rows: 1
   :widths: 46 14 40

   * - Fact
     - Rating
     - Source
   * - Frames are HDLC-like, as in PPP: a ``0x7e`` flag at each end,
       ``0x7d`` escaping ``0x7e`` and ``0x7d`` by exclusive-or ``0x20``,
       and a 16-bit check (reflected polynomial ``0x8408``) initialised
       ``0xffff``, complemented and sent low byte first, over every byte
       from the header to the last argument. A receiver's running check
       over payload and check bytes equals ``0xf0b8``.
     - software expectation
     - All three consumers agree: OpenBSD ``l1.c`` lines 156-306 with
       ``ppp_defs.h``; Linux SN1 ``l1.c`` lines 737-1006 and 1186-1474;
       ``ip35-l1.c`` lines 99-238.
   * - Only the SN1 receiver tolerates repeated flags. OpenBSD and the
       MIPS port lose the next frame after a doubled or shared flag.
     - software expectation
     - OpenBSD ``l1.c`` lines 266-293, 525-526; ``ip35-l1.c`` lines
       193-217; SN1 ``l1.c`` lines 1239-1242.
   * - The header byte carries the packet type in bits 7:5 and the
       subchannel in 4:0: request ``0x00``, response ``0x20``, event
       ``0x40``. Subchannels 0 to 3 are per-processor consoles, 4 the
       system console, 16 to 31 operating-system requests. A response
       returns on the request's subchannel.
     - software expectation
     - OpenBSD ``l1.h``; Linux SN1 ``ksys/l1.h``.
   * - A request payload is a four-byte big-endian destination, a
       two-byte code, a count byte and typed arguments: ``0x00`` and four
       bytes an integer, ``0x01`` and text ending in a zero, ``0x80`` with
       the length in the low seven bits a binary field. The SN1 port and
       the stock PROM omit the count byte on zero-argument requests;
       OpenBSD always sends it.
     - software expectation
     - OpenBSD ``l1.c``; Linux SN1 ``l1.c``; :src:`ip35-prom-6.210 L1
       request builder`.
   * - A response payload is a four-byte signed code, a field count and
       typed fields. OpenBSD and the stock PROM decode the whole word. The
       SN1 port keeps only the low byte, so it never sees a negative
       code.
     - software expectation
     - OpenBSD ``l1.h``; SN1 ``l1.c`` lines 133-139, 2467-2471.
   * - The receiver accepts up to 256 payload bytes plus the check, drops
       one- and two-byte frames, resynchronises after a bad check,
       ``0x7d`` before a flag, or overflow without losing the next frame,
       and treats ``0x7d 0x7d`` as one escape.
     - inferred
     - :src:`l1-firmware-1.44.0 link frame reader`
   * - A reply field is written only while its offset plus its length
       stays below 128, counting the header but not the tag. The largest
       binary field is therefore 116 bytes.
     - inferred
     - :src:`l1-firmware-1.44.0 reply serializer`

The model's receiver follows the 1.44.0 reading: bytes before the first
flag are discarded, a frame of three bytes or more whose check passes is
delivered, and anything else is dropped silently with no reply. Frames
over 258 bytes are discarded up to the next flag. Its emitter sends one
opening and one closing flag per frame and never shares a flag, because
the consumers are less tolerant than the controller. It escapes
``0x7e``, ``0x7d`` and carriage return (``0x0d``); it does not escape
``0x11`` or ``0x13``. The 1.44.0 image escapes carriage return only when
the port's carriage-return option is on; the image's serial start-up
selects that option, *inferred*. Frames from the processor typed
response (``0x20``) or ``0x60`` to ``0xe0``, and requests shorter than
seven bytes, are discarded without a reply. Malformed typed arguments
(a count that runs past the frame, an unknown tag) answer minus 100. The
1.44.0 image does not check them and reads stale bytes instead, so that
answer is an *approximation*.

========

The model routes each request by its destination (see
:ref:`sgi-l1-routing`). A local request goes to the task in bits 4:0.

     - 1.44.0 image (*inferred*)

   * - 3

-------------------------

Extra arguments are accepted. "Sent by" names the known senders, each
a *software expectation*.

``0x000e`` and the console field
--------------------------------

The 1.44.0 image keeps a seven-bit field per Bedrock port: node position
in bits 6:5 and console subchannel in 4:0. It stamps every request with a
source address whose bits 11:5 hold that position and the request's
subchannel, and ``0x000e`` returns the position, *inferred*. On a
single-node Origin 300 the position is 0. The stock PROM discards the
value on an Origin 300 and uses it only for type ``6``, a *software
expectation*. The model starts the field at ``node-position`` shifted
left five (0 to 3, default 0), at every controller restart. ``0x1002``
updates it without masking its argument, as the image does, so an
argument of 32 or more lands in the position bits.

Port speeds
-----------

The stock PROM shows the first ``0x000a`` integer as the I/O link rate:
zero is 400 MHz and any other value 600 MHz. It ignores the second, a
*software expectation*. The model answers ``(0, 0)`` by default. The
Origin 350, Onyx 350, Tezro and Onyx 4 profiles set ``port-speed-first``
to 1, which removes the PROM's "set to 400Mhz. Expected 600Mhz" warning.
Each is an *approximation*; no physical reply is captured.

.. _sgi-l1-records:

EEPROM records
==============

The 1.44.0 image registers six records on an Origin 300: 0 the node
board, 1 the I/O-8 board, then memory modules 0, 2, 1 and 3 as
components 2 to 5, *inferred*. An index of 6 or more answers minus 104.
A board record has area 0 (the eight-byte common header), 1 (chassis),
2 (board) and 3 (internal use); a memory-module record has area 4 (SPD).
``0x0006`` answers a size probe (length 0) with the remaining count, and
a read with the remaining count after the chunk and one binary field.
The image validates each board area by a zero byte sum and each SPD by
byte 63 equalling the sum of bytes 0 to 62, and marks a failing area
invalid, *inferred*. The stock PROM and IRIX read components 0 and 1 in
64-byte chunks; OpenBSD reads SPD records and the I/O board's area for
its Ethernet address, each a *software expectation*. OpenBSD's Origin 300 arm
numbers memory modules differently from the image (``l1.c`` lines
996-1015).

The model takes records three ways, and never more than one way per
component.

Raw area files
  ``chassis-eeprom``, ``board-eeprom`` and ``spd-eeprom`` are arrays of
  file paths by component (0 to 15) serving areas 1, 2 and 4. A chassis
  or board file is invalid when its byte sum is not zero, an SPD file
  (at least 64 bytes) when byte 63 is not the sum of bytes 0 to 62. Areas
  0 and 3 answer minus 104. A chunk above 116 bytes answers minus 105
  and logs ``LOG_UNIMP``.

Whole-image records
  ``board-record-eeprom`` and ``spd-record-eeprom`` take a whole EEPROM
  image per component (0 to 5). A board image's header bytes 1, 2 and 3,
  times eight, locate areas 3, 1 and 2. Each area must sum to zero and
  end below the configured capacity. A missing or failing area answers
  minus 107. An SPD image is exactly 160 bytes. A chunk above 116 bytes
  answers with the count 2 and the remaining-count integer only, as the
  1.44.0 serializer does. The expansion profile takes four board images
  of at most 512 bytes (power board, PCI logic board, two interface
  boards) and no SPD.

Built identity records
  When no file names component 0, and ``node-board-name``,
  ``node-board-part`` and ``node-board-revision`` (or
  ``cpu-context-present``) are set, the controller builds a chassis
  area and a board area. The board area carries the given name, part
  and revision, the manufacturer ``SYNTHETIC``, a marked synthetic
  serial, ``board-serial`` when set (the machine sets ``EMUN`` and the node
  index as a hex byte on the Fuel and the Origin 300 family), else such as
  ``EMUN00`` (``N`` and the ``identity-index``), and zero
  placeholder fields, and sums to zero. ``cpu-context-present`` adds the
  processor and hub clocks and a mode word for the Origin 350 family.
  ``mac-record`` adds the station address (``mac``): ``io8-board``
  builds component 1 as an ``IO8`` board with serial ``EMUI00`` and the
  address as twelve hex digits; ``mac-text`` makes the system serial the
  address text; ``system-board`` does both for the Fuel's single board.
  ``fuel-mac-eeprom`` instead reads a 512-byte Fuel record image and
  takes the address from its ``MAC`` field. The address is handed to
  the node's Ethernet model.

The built records are each an *approximation*: names, parts and revisions come
from published inventories (``IP45_2CPU``, ``030-1780-001`` revision C,
:src:`nekonomicon-16726611`), everything else is a placeholder. With
the marked serial the model keeps the stock PROM's NVRAM across
resets. With the serial ``000000`` the stock PROM reinitialises its
NVRAM on every boot. That is model behaviour, not a statement about
hardware. The Origin 300 machine supplies no
SPD records, so the PROM's SPD reads answer minus 104, an
*approximation* that OpenBSD sees as absent memory modules.

.. _sgi-l1-console:

Console, display and operator commands
======================================

The L1 has two modes. In L1 mode its console shows the prompt and input
goes to the command processor. In console mode system output is shown
and input goes to the system :src:`007-4365-002 p. 41`, *established*.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Operator input
     - Model
   * - Ctrl-D (``0x04``) at the prompt
     - Prints ``entering console mode  001c01 CPU0, <CTRL_T> to escape
       to L1`` and enters console mode.
   * - Ctrl-T (``0x14``) in console mode
     - Prints ``escaping to L1 system controller`` and the prompt. The
       next command runs, then the L1 prints ``returning to console mode
       ...`` and returns.
   * - ``l1`` when escaped
     - Holds L1 mode until the next Ctrl-D.
   * - Any byte in console mode, node on
     - Sent to the processor as a two-byte request frame on the
       selected subchannel: header, then the byte.
   * - Any byte in console mode, node off
     - ``WARNING: power appears off, console unavailable`` once per entry
       into console mode; the byte is dropped.
   * - Return or line feed in L1 mode
     - Runs the line (at most 127 characters; more logs
       ``LOG_GUEST_ERROR``). Backspace and delete edit.

The texts are those real firmware prints: two spaces before the brick
id, ``<CTRL_T>`` with an underscore, ``returning`` after an escape
(:src:`graphica-o350-notes lines 1792, 2030`), *observed*. The
manuals print ``re-entering`` and ``<CTRL-T>``
:src:`007-4365-002 p. 41`. The designation after the id is ``CPU0`` to
``CPU3`` or ``console`` for subchannel 4.

Console output from the processor is an event-type (``0x40``) frame on
any subchannel. Its bytes go to the operator console in console mode
with the node on. Its subchannel becomes the console-input subchannel,
as in the 1.44.0 image, *inferred*. Output that arrives while the
operator is at the prompt is discarded with ``LOG_UNIMP``. What real
firmware does with it is *unknown*; escaping during PROM output and
watching what appears on return would settle it.

The model implements this command subset of the 2001-2002 vocabulary
:src:`007-4498-002 p. 177-206`. ``*`` before a command broadcasts it to
the cabled peer; ``ctc`` runs it on the peer (see :ref:`sgi-l1-routing`).

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Command
     - Model
   * - ``power`` / ``pwr`` ``up``\|``u``, ``down``\|``d``, ``check``
     - See :ref:`sgi-l1-power`.
   * - ``reset`` / ``rst``, ``softreset`` / ``softrst``, ``nmi``
     - See :ref:`sgi-l1-power`.
   * - ``reboot_l1``
     - Controller restart.
   * - ``select`` / ``sel`` [``subchannel``\|``sub``\|``s``]
       ``console``\|``0``-``4``\|``a``-``d``
     - Sets the console subchannel. Alone, prints the selection. Other
       forms print ``ERROR: bad subchanel selection.``
   * - ``display`` / ``dsp`` [``1``\|``2`` *text*]
     - Prints or writes a display line.
   * - ``log`` [``clear``\|``reset``\|``insert`` *text*]
     - Prints, clears or appends to the log.
   * - ``brick`` [``rack`` *n*\|``slot`` *n*]
     - Prints the identity line, or sets the pending rack (below
       ``0x3ff``) or slot (1 to 39).
   * - ``version`` / ``ver``
     - ``L1 x.y.z (Image A) [Fuel/PE/O300 1MB image]``, or a line saying
       the revision is unavailable.
   * - ``debug`` [*value*]
     - Prints or sets the debug switches.
   * - ``l1dbg`` [``promreq``\|``req`` ``on``\|``off``]
     - Prints or sets request logging.
   * - ``l1``, ``help`` / ``hlp``
     - As above; a fixed help list.
   * - anything else
     - ``ERROR: command not found.``, ``LOG_UNIMP``, status minus 1.

Through task 3 each output line becomes one text field and the reply
code is the command's status. A malformed ``debug`` value answers minus
1200 with a not-found line, the 1.44.0 image's unmodified path,
*inferred*. ``* pwr d``, which OpenBSD, the SN1 port and IRIX send at
power-off, powers the node down at once. ``display`` writes line 1 or
2 of a 12-character view; line 1 holds ``001c01     /``, where the
hardware spins a heartbeat in the last place, and line 2 the status
(``L1 running``, ``Powered Up``, ``Powered Down``, ``Reset done``,
``Sft rst done``, ``NMI done``) until software writes it. Both lines are
readable as the ``display-line-1`` and ``display-line-2`` properties.

The log is a ring of 128 entries of 47 characters stamped from QEMU's
clock as ``MM/DD/YY HH:MM:SS``, oldest dropped first. It records L1
boots, power and reset events with their reason, ``0x100b`` and
``log insert``. With ``l1dbg promreq on`` every task-6 request adds
``L1REQ: <source> - <code>`` with the source address built from the
console field, as :src:`007-3938-006 p. 102` describes, *established*
for the line's form. The real log lives in NVRAM and survives L1 boots
:src:`nekonomicon-16729141`, *observed*.

Events
------

The 1.44.0 image sends environmental events (supply, fan, temperature,
power-down countdown) to the processor only on the subchannel the
processor registered with ``0x1007``, as an event-type frame from task 4
with a code, an integer diagnostic number and a text line
``\r\n<id> ATTN: <message>\r\n``, *inferred*. The model generates one
event: the first ``power down`` of a brick whose type letter is ``9``,
``A`` or ``Q``, with an event subchannel registered, sends code
``0x8000``, diagnostic 0 and ``Power Down: issue 'pwr d' again to
immediately power down.``, and waits for the second (*software expectation*). An
Origin 300 (``4``), C-brick (``C``) or I-brick (``I``) never defers: its
first request acts and prints nothing on the console, and every
power-down clears the registered event subchannel, so a later event
needs a new ``0x1007`` (*software expectation*). No environmental event is
generated. A registered event subchannel of 4 or more survives
a controller restart; a lower one is cleared, as in the image.

.. _sgi-l1-routing:

Routing
=======

The destination's bits 31:28 are the controller type (0 L1, 1 L2, 2 L3,
3 attached C-brick, 4 attached I/O brick), 27:18 the rack (``0x3ff``
local), 17:12 the bay (``0x3f`` local) and 4:0 the task (3 command
interpreter, 4 environment, 5 Bedrock console, 6 general). The local
general address is ``0x0ffff006`` (Linux SN1 ``ksys/l1.h``; OpenBSD
``l1.h``), a *software expectation*.

The 1.44.0 image routes on bits 31:12. A request is local when they
equal the controller's own type-0 rack and bay or ``0xffff``. Bits 11:5
are ignored. Anything else goes to a catch-all that tries the cabled
peer, the attached I/O port or an L2, and a failure there answers a
router error reply: ``0x20 | subchannel``, ``ff ff ff ff``, ``00 00 00
08``. A mixed form, one coordinate concrete and one the sentinel, is not
local, *inferred*. On a standalone Origin 300 a type-4 request is
forwarded toward a software peer slot; whether it gets an immediate
router error or no reply depends on handle state the image reading
could not settle, *unknown*. A matching stock-PROM type-4 request with
the L1's handle status and the Bedrock reply captured would settle it.
The stock PROM sends ``0x0003`` and ``0x000c`` to ``0x4ffff006``, a
*software expectation*.

The model:

- A local key goes to the addressed task.
- With a cabled peer (below), a type-0 request for the peer's rack and
  bay, or any type-3 request rewritten to type 0, is answered by the
  peer as if local there, on the requester's subchannel and UART.
- With a query router (below), type-0 requests and, when an attached
  owner is configured, ``0x4ffff006`` requests go to it.
- With an L2 link (:ref:`below <sgi-l1-l2-link>`) connected, a type-1
  or type-2 request leaves on the link.
- Everything else gets the router error reply with detail 8 and logs
  ``LOG_UNIMP``. This includes type 4 on a standalone chassis, a
  type-1 or type-2 request with no L2 link connected, and a type-1 or
  type-2 request the link cannot carry. Type 4 on a standalone chassis
  is an *approximation* of the unknown above.

Two-chassis peer
----------------

A two-chassis Origin 300 links its two controllers through the ``peer``
property, standing for the RS-422 pair in the NUMAlink cable. The link
works only while both have compute services and ``network-422`` set
(default on, the mode the manual requires for a pair,
:src:`007-4365-002 p. 38`). The link carries no wire format: a forwarded
request is an in-process call, an *approximation*, since nothing public
describes what the two L1s exchange. ``* power up`` and ``* power down``
act locally and then on the peer :src:`007-4365-002 p. 36-37`,
*established*; ``* reset`` doing the same is an *approximation*. Both chassis
are one QEMU machine, so the peer only records its power state, display
and log entry. A plain ``power up`` or ``power down`` publishes a
power-state notice to the peer (*software expectation* for the sender, the
configuration event carrying rack, bay and power word); a plain ``reset``
publishes none. What the peer does with a notice is *unknown*, so it
only records the last one, readable as the ``peer-power-notice``
property. ``ctc <command>`` runs the command on the peer and
prints the peer's id line first; a nested ``ctc`` is refused with
``INFO: nested ctc is unsupported.`` and ``LOG_UNIMP``. ``* debug``,
``ctc debug``, ``* nmi`` and console forwarding from the second chassis
are not modelled.

Query router
------------

For the Origin 300 PCI expansion topologies the machine registers each
controller with a synthetic owner registry and declares which owners can
reach which. A type-0 request with concrete coordinates that match
exactly one reachable associated owner is served by that owner and the
reply returns through the issuer's UART. An issuer may also have one
attached owner that serves ``0x4ffff006``; the request reaches it as
``0x0ffff006``. Only read-only task-6 requests pass: ``0x0003``,
``0x0006``, ``0x0007``, and ``0x0004`` for concrete addresses or
``0x000c`` for the attached address. Everything else, a missing,
disconnected or ambiguous owner, mixed sentinels and nested routing gets
the router error reply with detail 8 and ``LOG_UNIMP``. The registry is
an *approximation* standing for the controllers' configuration
exchange, which is not modelled; it does not claim a physical cable
pairing.

The ``vbrick-discovery-reference`` profile answers every well-formed
task-6 request with minus 104 and other tasks with minus 101, refuses
operator commands, and logs ``LOG_UNIMP``.

Multi-frame transport
---------------------

Codes ``0x3001`` to ``0x3003`` behind a zero destination word are a
multi-frame transport: ``0x3001`` starts a message with a fragment
count and length, ``0x3002`` starts another fragment and ``0x3003``
continues one. The inner message has a 20-byte header (length, version
2, status, sequence, fragment count, type, source metadata, destination,
source, descriptor count, command field) and eight-byte descriptors,
and replies go back in pieces of at most 113 inner bytes, *inferred*
from the 1.48.1 image in :src:`ip35-patch-sg0007149`. IRIX 6.5.30
``l1cmd`` uses it, a *software expectation*.

The model assembles one inner fragment per UART and subchannel and
answers only when a profile selects it:

- ``irouter-compat`` (Origin 350 family profiles): types ``0x37``,
  ``0x39`` and ``0x51`` answer the local commands ``brick`` and
  ``brick`` with a trailing space with ``rack: <rack>, slot: <slot>,
  partition: none|<n>, type: <label> [?MB flash], serial:<serial>,
  source: OTHER``. Rack, slot and partition are the configured values.
- ``o300-l1cmd-compat`` (the ``origin300-l1cmd-compat`` machine option):
  type ``0x34`` answers ``brick``, ``version`` and ``serial all``, each
  with a trailing space, with text whose missing fields read
  ``EMU-UNKNOWN``.

The reply address packs the UART index and subchannel into bits 11:5
with task 21. The 1.48.1 image does so for the Origin 350 family types;
for type ``0x34`` it is an *approximation*. All reply text beyond the
configured identity is model policy, not firmware output. Multi-fragment
messages, other commands and malformed chunks are dropped with
``LOG_UNIMP`` or ``LOG_GUEST_ERROR`` and get no reply.

.. _sgi-l1-l2-link:

L2 link
=======

An L2 is the rack controller that reaches every brick's L1 over USB. The
model has none. The optional ``l2`` property is a chardev that stands for
the USB bulk pair toward whatever plays the L2: the project's own
stand-in for a test or a companion process, not a hardware wire. With
the property unset, or while no peer is connected, nothing changes: a
request for controller type 1 or 2 gets the router error reply with
detail 8, and request ``0x000b`` answers the stored setting. The
read-only ``l2-link-up`` property says whether a peer is connected.

``l2-partition-flag`` (0 to 3, default 0) is the initial value of the
two-bit setting that request ``0x000b`` returns and ``0x1008`` writes.
The stock PROM fetches a partition record from an L2 only after a
nonzero answer, so a test starts that fetch by setting it. It is not the
partition ID that ``0x0009`` returns. What the setting means on a real
controller is *unknown*.

Machine options
---------------

A machine reaches a controller's L1 with three list options, each entry
``<index>=<value>`` where *index* is the zero-based position of the
controller in the selected topology, the same numbering as
``controller-chardev`` (:ref:`sgi-pci-expansion-controller-inputs`):

``controller-l2-chardev.N=<index>=<chardev-id>``
  Sets the ``l2`` property of that controller's L1 to an existing
  chardev. Each chardev serves one controller; a second entry for the
  same controller or the same chardev id, a chardev that does not
  exist, or one that ``controller-chardev`` already uses is refused.

``controller-l2-partition-flag.N=<index>=<0 to 3>``
  Sets ``l2-partition-flag`` on that controller's L1. It needs no
  chardev, and a value outside 0 to 3 is refused.

``controller-pbay-chardev.N=<index>=<chardev-id>``
  Sets the ``pbay`` property of that controller's L1 to an existing
  chardev, joining it to a power bay (:ref:`sgi-l1-pbay`; the bay end is
  the ``sgi-pbay`` device). The same rules as the L2 link apply, and a
  chardev that ``controller-chardev`` or ``controller-l2-chardev`` uses is
  refused too. The L1 refuses to start on a brick type that does not run the
  power-bay task. The option sets no timing: the ``pbay-tick-us`` and
  ``pbay-poll-ms`` properties are reached with ``-global sgi-l1.<property>``.

All accept an expansion controller and a controller that no module owns
and exactly one compute node names, which is a C-brick's L1 in the
Origin 3000 topologies. A module-owned L1 serves several boards, so an
entry for one, or for an index beyond the topology, is refused. For
example, the two-partition Origin 3400 gives its first partition a link
and a nonzero setting with::

   -chardev socket,id=l2a,path=l2.sock \
   -M origin3000,topology=origin3400-two-partitions,controller-l2-chardev.0=0=l2a,controller-l2-partition-flag.0=0=1

Setting ``controller-l2-chardev`` blocks migration for the reason given
under Limits; ``controller-pbay-chardev`` blocks it because the bay's state
lies outside the machine.

Link format
-----------

The real link carries one router segment per USB transfer. A stream
socket has no transfer boundary, so each message on the chardev is a
one-byte kind followed by its body. Kind 1 is a segment, and its first
two bytes (big endian, counting themselves, at least 6 and at most
1,024) delimit it. Other kinds are reserved: the L1 logs one with
``LOG_GUEST_ERROR`` and skips the byte. The format is the project's own
(``include/hw/misc/sgi-l1-l2-link.h``); the segment inside it is the
field map of the controller's management USB stream, *software expectation* for
the L1 side and *inferred* for what the L2 expects:

.. list-table::
   :header-rows: 1
   :widths: 12 12 76

   * - Offset
     - Width
     - Field
   * - 0
     - 2
     - Segment length, including itself.
   * - 2
     - 1
     - Format byte, 2 as the L1 builds it.
   * - 3
     - 1
     - Flag byte, meaning *unknown*; the model sends 0.
   * - 4
     - 1
     - Low byte of the sequence number.
   * - 5
     - 1
     - Bit 7 set on the first segment of a packet; bits 6:0 the segments
       left, counting this one on the first. A packet is up to 127
       segments, each carrying one less than the last.
   * - 6
     - 1
     - Class: request 0, response 1, event 2.
   * - 7
     - 1
     - Source port, meaning *unknown*; the model sends 0.
   * - 8
     - 4
     - Destination router address.
   * - 12
     - 4
     - Source router address.
   * - 16
     - 1
     - Descriptor count.
   * - 17
     - 1
     - High byte of the sequence number.
   * - 18
     - 2
     - Request or response code.
   * - 20
     - 8 each
     - Descriptors. A scalar is ``00 00 0000`` and a 32-bit value.

Every segment that crosses the link in either direction is the trace
event ``sgi_l1_l2_segment`` with its bytes, so a run's traffic can be
read from the trace.

.. _sgi-l1-l2-user-space:

Running the L2's own programs
-----------------------------

The L2's own programs, taken from the shipped controller image, run under
the PowerPC Linux user-mode emulator (``qemu-ppc``, built with the
``ppc-linux-user`` target) against the unpacked image as ``-L`` root with
``-r 2.4.7``. Two pieces of this tree replace what their kernel gave
them. Neither changes the emulator itself.

``qemu-sgi-l2-hub`` is the host end of the L1 device nodes. It stands for the
L2's USB host controller and hubs, owns the links to the L1 models and
logs everything that crosses them with a timestamp::

   qemu-sgi-l2-hub --dir DIR [--log FILE]

It listens on ``DIR/l1.sock`` (a stream socket) for L1 models and on
``DIR/dev.sock`` (sequenced packets) for the plugin. An L1 connects with
its ``l2`` chardev as a client, for example ``-chardev
socket,id=l2a,path=DIR/l1.sock,reconnect-ms=1000``. Each link gets the lowest
free slot from 0 to 39, which is a USB attach, and a close is a detach. A
slot's 9-byte device record is synthetic (bus 1, two hub ports, device
address slot + 2, ports 1 and slot + 1): its layout is a *software expectation*, the
values the real L2 would show are *unknown* until a rack topology supplies
them. A segment that reaches the hub before the program has opened the
slot's node is queued, up to 256 segments, and delivered in order on open.
Links and nodes are served independently: a program that stops reading a
node, or an L1 that stops reading its link, delays only that slot, and
traffic from several L1s interleaves freely, as in the two-partition
Origin 3400 with both C-brick L1s linked.
A segment the program writes goes to the L1 with the length field set to
the transfer's length, as the kernel driver does. Closing a node resets the
device, which the hub logs; the link has no message for a reset, so the L1
does not see it. The messages between the hub and the plugin are in
``include/hw/misc/sgi-l2-hub.h``.

``sgi-l2-shim`` (``contrib/plugins``) is a TCG plugin for ``qemu-ppc``. With
``hub=DIR`` it serves the programs' system calls on the L1 nodes:

- ``open`` of ``/dev/sgil1_cs`` and ``/dev/sgil1_N`` returns a socket
  connected to the hub, so ``read``, ``write`` and ``poll`` run on the host
  with one message per transfer. A slot with no L1 is ``ENODEV`` and one
  already open is ``EBUSY``.
- The driver's ioctls are answered: revision 2 (``0x40045306``), the device
  record by slot or by node (``0xc0095307``, ``0x40095304``), and the four
  resets (``0x20005301`` to ``0x20005303``, ``0x20005305``), which the hub
  logs. Any other ioctl on a node is ``ENOTTY``.
- ``/dev/mem`` is a regular file in the root. The programs map the flash
  at physical ``0xfe000000`` (``0xfc000000`` first). The emulator cannot pass
  those offsets to the host, because 32-bit PowerPC hands it the offset
  as a signed number, so the plugin has the guest repeat the call with an
  offset into the file. The file holds 36 MiB: the first 4 MiB stand for
  the empty bus at ``0xfc000000`` and the flash is the 4 MiB at file offset
  ``0x2000000``. A fresh flash is all ones. The daemon reads the flashed
  version from the window, and only the controller image's payload (the
  file without its 0x2c-byte file header) placed at window offset 0 passes
  its header check; the sizes and checksums are a *software expectation*, that the
  flash holds the payload there is *inferred*. The plugin does not fill the
  flash: whoever prepares the file writes the payload.
- Stores into the flash window are decoded after they happen and the plugin
  corrects guest memory: auto-select presents manufacturer ``0x00010001``
  and device ``0x22282228`` at offsets 0 and 4 until a reset command,
  program clears bits only, sector erase fills the sector with ones
  (31 sectors of 128 KiB, then 8 of 16 KiB) and chip erase fills the
  window, and the command cycles leave nothing behind. All operations
  complete at once. The command addresses, the doubled halfwords and the
  sector map are *inferred*; the plugin does
  not model the toggle bits the real chip shows during an operation.

Without ``hub`` the plugin only logs the opens and ioctls on ``/dev``
descriptors, which is how the system calls a program needs are collected.
``log=FILE`` redirects the log, ``flash-log=on`` logs each store into the
window and ``trace=on`` logs every ``/dev`` open and the ioctl results.

Limits. A sequenced-packet socket does not behave exactly as the driver
does: a read into a short buffer truncates instead of failing, an empty
non-blocking read is ``EAGAIN``, and a second write does not wait for the
first. The programs read with a buffer larger than any segment and only
when ``poll`` reports data, so none of these paths is expected to run.
Each program that maps the flash keeps its own copy of the window for
restoring command words and for the program step, so two programs that
program the same words see each other's results in the shared file but
not in that copy. The plugin instruments every store, which slows the
programs: a loop of 200 million stores took 2.2 times as long with the
plugin loaded (0.65 s to 1.44 s on the development host). The USB-level
rules of the real link (descriptors, endpoint halts, zero-length packets)
are not exercised.

Requests toward the L2
----------------------

A plain request from the node for type 1 or 2 is forwarded as one
request segment when every argument is an integer, because no other
descriptor form is known. A request with another argument type
keeps the router error reply. The stock PROM sends its partition-record
fetch another way, as the multi-frame transport (below) carrying a
complete inner message for controller type 1, task ``0xa``; the inner
message already has the segment layout, so the model forwards it as it
arrived. In a boot run of the stock firmware it was a 28-byte request
segment with code 1 and one integer argument, 4 on the C-brick in bay 4,
which the firmware sent after asking ``0x000b`` and followed with
``0x1006`` once the reply came. What the argument means is *inferred*:
an L2's partition service reads it as a brick identifier.
While a peer is connected every profile accepts that transport for a
request whose inner destination is controller type 1 or 2. On a profile
without an IRouter of its own, any other chunk frame is handled as it is
with no peer. A packet of more than one fragment is not forwarded.

In both forms the source word is rewritten to the controller's own
rack and bay key in bits 31:12, the requester's UART index and
subchannel in bits 11:5 and task 21 in bits 4:0, the packing the
multi-frame transport uses for its replies. That the controller's key
fills the rest is an *approximation*; the real base is *unknown*.
The peer addresses its response to that word, which is how the model finds
the requester.

Responses from the L2
---------------------

A response segment whose destination names a requester with a request
pending is returned to it.

- To a plain request, the first descriptor is the reply code and every
  further integer descriptor is one integer field of the ordinary reply.
  A response of more than one segment, or with a descriptor that is not
  a scalar, is logged with ``LOG_UNIMP`` and the requester gets the
  router error reply.
- To a chunk-transport request, each segment returns as frames of at most
  113 payload bytes. The first frame of a segment is ``0x3001`` and
  carries the segment's remaining-segment count in its count byte and the
  frame's own payload length in its length field. Each later frame is
  ``0x3003`` while the segment has more, and ``0x3002`` on the frame that
  exhausts it; their count and length fields are zero. A segment that fits
  one frame is a single ``0x3001``.

  The stock boot firmware was run against this (a stand-in peer, the
  two-partition Origin 3400, a nonzero ``l2-partition-flag`` on the first
  C-brick). A 36-byte segment in one ``0x3001`` frame was accepted and its
  integer used. A 300-byte segment in three frames, with the length field
  of the ``0x3001`` frame holding the whole 300, made the firmware reject
  the frame as shorter than that length; with that field holding the
  frame's own 113 bytes it was accepted, whether the later frames carried a zero length or
  their own. That is the reader's behavior in a model run, for this
  firmware version only, not a capture of an L2. A reply of two segments was accepted with each segment's
  first frame ``0x3001`` and also with only the first, so which the
  firmware expects of a second segment, and whether it reads one, is
  *unknown*. The firmware's wait of about four seconds for a reply is
  *inferred*: with no reply it reported that the wait had failed and went
  on with the partition ID its controller holds.

Segments that are not responses (requests and events from the L2),
responses that name no requester or one with nothing pending, and
continuations out of order are logged and dropped, except the one
request described next. The L2's other housekeeping requests are not
served, because nothing published says what the L1 answers.

.. _sgi-l1-l2-config:

The L2's configuration request
------------------------------

The L2 daemon sends each attached L1 a recurring request to destination
``0x0ffff00e``: class request, code 0, three descriptors, the integer 6,
the L2's serial setting as a string (or the integer 0 when it has none)
and an integer (*software expectation* for the shipped 1.44.0 daemon). Attaching
gives the L2 no route to an L1. The L1 becomes routable at the L2 only
when it answers this request, because the daemon registers it from the
reply. With the link up, the model answers a request with exactly these
three descriptors, the first the integer 6 and the third an integer.
Anything else is logged with ``LOG_UNIMP`` and not answered, except a
six-descriptor selector 2 or 13 request (:ref:`sgi-l1-table-exchange`). A controller
whose rack or bay is unset does not answer either, because nothing says
what a real one reports. A request cut short of its three descriptors is
not answered. A string descriptor whose offset or length lies outside the
segment, or whose text is not terminated inside it, is read as no serial
text and the reply goes out without one; what a real L1 does with such a
request is *unknown*, so each is an *approximation*.

Before it builds the reply, on every selector 6 request that is answered, the
controller starts the L1-to-peer-L1 table exchange of selectors 2 and 13
(next section). Neither selector is a request to the L2 and neither crosses
the L2 link.

The reply is one segment: class response, destination the request's
source word, status byte 0, the request's code, and these descriptors
(*software expectation*): the integer 7; the request's third
descriptor, echoed; the record count ``N``; the record size 0x70; a bytes
descriptor holding ``N`` index bytes, each a record's position; a bytes
descriptor holding ``N`` records of 0x70 bytes. A nonzero third request
descriptor makes the reply the single integer 7 (*software expectation*). The reply
carries the request's two sequence bytes unchanged; that a real L1 copies
them is *inferred*, and what it puts there otherwise is *unknown*, so the
copy is an *approximation*.

The source word is ``(identity << 12) | 0x0e`` with the identity the rack
in bits 15:6 and the bay in bits 5:0; that these are the controller's own
settings is *inferred*. The records come from the controller's module table
of fifteen entries of 0x70 bytes: its own entries at 0 to 4, the entries
learned from the peer on serial port 1 at 5 to 9 and from port 2 at 10 to 14
(*software expectation* for the stores; the naming is *inferred*). An entry is listed
when its word at +0x60 is nonzero (*software expectation*), and a group of five whose
first entry's string at +0x40 repeats an earlier group's is left out
(*software expectation* for the omission; that the L2 is the consumer of the
entries learned from a peer is *inferred*). The index array holds each
listed entry's table index. A record has a nonzero word at +0x00, the rack
in the word at +0x08 and the bay in the word at +0x0c, big endian
(*software expectation* as the fields the L2 routes by); the word at +0x60 is 1, an
*approximation* since its meaning is *unknown*. Every other field is zero
except two the model chooses: the text at +0x40, which holds the brick's
module name so the repeat test has something to compare, and the serial
text at +0x64 of the controller's own entry 0, the request's text cut to 11
characters (its role is *inferred*). A request whose text cannot be read
leaves the stored text unchanged, an *approximation*. The controller's own
entries are itself at 0 and, at 1, its I-brick (or, for an I-brick, its
host C-brick), with the rest empty. What fills the real table is *unknown*,
so those entries are an *approximation*.

The reply's descriptors are built the way the L1's packet builder builds
them. The integers have type ``0x00``. The index array (descriptor 4) is
referenced in place, type ``0x01``, and the record block (descriptor 5) is a
copy, type ``0x09``; the two are different bytes in one packet
(*software expectation* for the values the L1 builds, *inferred* that they reach the
wire unchanged, because the L1's USB path was not traced for a rewrite). The
low three bits of a type are the kind (0 integer, 1 bytes, 2 string); bit 3
(``0x08``) is a construction flag, "free the caller's buffer", that stays in
the type byte, and readers test the kind bits only. A data descriptor is
eight bytes: type, segment byte, 16-bit length and a 32-bit offset from the
start of the segment record, which sits 0x10 bytes before the first wire
byte. The segment byte is the 1-based number of the segment that holds the
payload, so it is 1 on both blobs of this single-segment reply
(*software expectation*: the L1's own reader returns nothing for a data descriptor
whose segment byte is 0). A reply of more than eight records would continue
into a second segment whose descriptors carry 2 (*inferred*); the model's
table never reaches that size. The reply follows the sheets' reading of the
1.44.0 package for one controller type and is not claimed to reproduce a
real L1's.

No timeout is modelled: the PROM's own wait for the reply is its
concern. If the peer disconnects, a plain request still waiting gets the
router error reply and pending state is cleared.

.. _sgi-l1-table-exchange:

The table exchange with a peer L1
---------------------------------

Selectors 2 and 13 are the L1's exchange of module-table entries with a
peer L1 over a peer serial port, not requests to the L2: selector 2 goes to
port 1 and selector 13 to port 2, posted to that port's writer only when its
handles are open (*software expectation* from one reading of the 1.44.0 package for
the Fuel, Origin 300 and PE builds; which package a C-brick ships is
*inferred*). A C-brick opens ports 1 and 9, so a paired C-brick is port 1,
selector 13 is never sent, and selector 2 is sent only while the pair's
``peer`` link is set on both controllers and ``network-422`` is up on both
(*inferred*: the receiver gets a packet only through a port of its own that
is open). A controller that is not named, or is restarting, does not
answer, as for selector 6. The
peer is a direct call between the paired controllers; the RS-422 framing is
not modelled. ``sgi_l1_peer_segment`` traces each packet.

The request is one 628-byte segment: class 0 (*inferred*, the
builder's class argument), code 0, destination ``0x0ffff00e``, the sender's
task 14 word as source, six descriptors (*software expectation*): the selector as an
integer, then five byte copies, type ``0x09``, segment byte 1, length 0x70,
the sender's own entries 0 to 4. The receiver clears the five entries of the
arrival port's group, copies descriptors 1 to 5 into them, each the smaller
of 0x70 and descriptor 1's length, and sets the first entry's +0x60 to 1
(*software expectation*). Nothing is stored when the status byte is nonzero or the
arrival is not a peer port. It then answers with a response, class 1,
status 0, to the request's source word, the same selector and its own entries
0 to 4, also when it stored nothing (*software expectation* from the branch order).
The sender stores the response's entries as the group for the selector it
sent. A selector 2 or 13 request that arrives on the L2 link is answered the
same way and stores nothing; no sender of one is known (*software expectation* for the
branch, *unknown* whether any L2 sends it).

Not modelled: the follow-up that sends the opposite selector to the other
peer port after a store (what it is for is *inferred*), a second peer port,
the two-descriptor form of selector 6 (the daemon never sends it; such a
request is logged and not answered) and a reply of more than eight records,
which would need a second segment. Whether a port that is initialised but
uncabled counts as open is *unknown*; a controller with no ``peer`` sends
nothing.

The learned entries and the serial text are not migrated. Only a request
that arrived on an L2 link, or the exchange that request starts, fills them,
and a controller with an L2 link blocks migration, as does a machine that
holds one for its peer; they are cleared when the controller itself starts.

Limits
------

- There is no USB device: no descriptors, endpoint halt clearing,
  zero-length packets or 64-byte packetisation. Those are the L1's
  firmware behaviour and wait for the firmware L1.
- Attach, device-reset and endpoint-reset control messages are not
  defined; the peer learns of the L1 by the connection.
- Setting ``l2`` blocks migration and snapshots, whether or not a peer is
  connected, because the peer's state is outside the machine. The blocker
  is process-wide, so it also covers a paired L1 that has no ``l2`` chardev.
- The link state is not part of the saved device state.

Board-side interfaces
=====================

The 1.44.0 image drives an M-Bus (the ColdFire's I2C-style bus) through
the MCF5206e registers at ``MBAR+0x1e0`` to ``+0x1f0``
:src:`nxp-mcf5206eum-1 p. 13-6-13-11`, with divider selector ``0x13``,
which the manual maps to 480 :src:`nxp-mcf5206eum-1 p. 13-7`. It polls
monitors at bus addresses ``0x58``, ``0x5a`` and ``0x5c``, I/O
expanders, supplies, fans and temperatures, and reads the board
EEPROMs into RAM at start, *inferred*. ``0x0006`` serves that RAM copy.
The SCL rate, fitted parts and bus topology are *unknown*.

The model has none of this. Its only board-side action is
for the PCI expansion module: when the machine binds an
interface board, each controller restart writes the packed rack and bay
to that board through two operations (bus 0, address ``0x8c`` for
position 0 or ``0x8e`` for position 1, command ``0x13`` with the high
byte and ``0x12`` with the low). A failed operation logs
``LOG_GUEST_ERROR`` and the other still runs. This is an
*approximation*; the operation is a function call, not an M-Bus
transaction.

The management USB port is a USB 1.0 device toward an optional L2. The
1.44.0 image declares one interface with 64-byte bulk endpoints OUT 1
and IN 2, *inferred*. The model has no USB device. Test-only properties
under qtest compute the image's ``GET_STATUS`` and ``GET_DESCRIPTOR``
bytes for cached endpoint states; no transfer takes place.

.. _sgi-l1-power:

Power, reset and NMI
====================

The L1 runs whenever the chassis has mains power, before the node is
powered :src:`007-4365-002 p. 35`, and drives reset, soft reset and NMI
to the node on its commands and the front-panel buttons
:src:`007-3938-006 p. 80, 91, 94`, *established*. No public guest asks
it to reset; OpenBSD reboots through the Bedrock and uses the L1 only to
power off.

.. list-table::
   :header-rows: 1
   :widths: 26 74

   * - Event
     - Model
   * - Realize (mains applied)
     - Controller boot. With ``auto-power`` (default on) the node is
       powered at once with no countdown, logging ``auto power up
       initiated`` and printing ``INFO: 001c01 powering up the system.``
   * - ``power up``
     - With the node off: node power on, console selection back to CPU
       0, ``Powered Up``, a log entry and the console-mode text. In a
       machine the ``node-power`` output switches that node on alone; if
       the machine had ended because its last compute node went off
       (``-no-shutdown``), it resumes through a QEMU system reset after
       which only the nodes whose controllers are on run. A controller
       with no node attached, a bare ``sgi-l1`` device, requests that
       system reset itself and resumes the machine after it.
       With the node on: ``Power is already on``.
   * - ``power down``
     - Node power off, ``Powered Down``, a log entry, the event
       subchannel cleared. In a machine the ``node-power`` output removes
       that node's supply and the machine shuts down only when no compute
       node is on and none has a power-up to come; a bare ``sgi-l1``
       device requests the QEMU shutdown itself. Only the type
       letters ``9``, ``A`` and ``Q`` with a registered event subchannel
       defer the first request (the ``0x8000`` event and nothing else;
       the second acts). Through task 3 or ``0x2005`` it acts at once.
       With the node off it does nothing.
   * - ``0x2006``
     - Power-off without shutdown when the node is on, then power-on as
       for ``power up``, both with reason 3.
   * - ``reset``, ``0x2001``
     - With the node on: ``Reset done``, a log entry and a pulse on
       ``node-reset``. In a machine the pulse restarts that brick's node
       alone, or resets the machine as a whole when that node is every
       powered compute node (below); a bare ``sgi-l1`` device requests a QEMU
       system reset itself. With the node off the L1 does nothing.
   * - ``softreset``
     - With the node on: ``Sft rst done``, a log entry and a pulse on
       ``soft-reset``.
   * - ``nmi``
     - With the node on: ``NMI done``, a log entry and a pulse on
       ``nmi``, which the node routes to every fitted processor's NMI
       input.

A bare ``sgi-l1`` device with no node still stands for the machine: its
reset is queued on the processor whose write reached the UART and every
processor is paused before QEMU handles it; from the host console the
main thread pauses all processors first. A reply queued before a reset may
be cleared with the UART before the guest reads it. The hold time of a
reset and the missing countdown are each an *approximation*.

On a C-brick, an Origin 300 and any other compute controller, the
``node-power`` output is the power input of the node it serves, so a
power change acts on that node alone and not on the machine (the
Bedrock page's Main power section describes what the node does). The
machine hands the node the controller's level when it joins them, so a
controller that starts off, with ``auto-power`` off, leaves its node
stopped until ``power up``. A Cx-brick's one controller serves all its
boards' nodes and powers them together, an *approximation*: the wiring
from the controller to the node boards is unknown. A broadcast
``* power up`` or ``* power down`` reaches the peer's controller as well,
which then moves its own node. The machine ends when the last compute
node, in any partition, is off, an *approximation*: no source gives the
rule. An I-brick or R-brick never keeps it alive, because its
controller serves no processor. A system reset of the machine is a mains
cycle: a controller whose node is off applies its start-up power decision
again, so with ``auto-power`` set it switches its node back on. The
``reset`` command and the ``0x2001`` request restart the controller's own
node and nothing else (*software expectation* for the controller, which acts on its
brick only; that a front-panel reset switch takes the same path is
*inferred*, and the switch is not modelled): ``node-reset`` is the
first node's ``reset`` input, and the machine restarts every board's
node of a Cx-brick for it. A node whose supply is off is never reached, so a
``reset`` does not switch it on. ``* reset`` runs the same on the peer's
controller first and then on this one, as ``* power`` does; ``ctc reset``
reaches the peer alone, and a peer whose node is off ignores it. When a
``reset`` reaches every powered compute node, as on a one-node machine such
as a Fuel or an Origin 300, or when the peer is off, the machine resets as
a whole with each controller keeping its power state, and the ``RESET`` event
is emitted. This whole-machine reset is an *approximation*: it also
restarts the routers and every controller, which a node reset does not, and
it applies because an unpartitioned guest cannot survive one brick
restarting (*inferred*). When another powered compute node is not reached,
only the named brick's node restarts and no ``RESET`` event is emitted. The
Bedrock resets that a guest writes reach nodes by registers (see the
Bedrock page) and use the same rule. The ``reset`` command, a ``reset hold`` and
release pair, the front-panel reset switch and ``0x2001`` all drive one
group of Bedrock control lines (*software expectation* for the L1 image; that the
switch input is the physical switch is *inferred*), while ``nmi`` drives one
other line and ``softreset`` a third. Which Bedrock input each line reaches
is *unknown*: the model sends the one pulse to the node's restart
(*approximation*), which cold-resets the Bedrock and the node's other
parts as a supply cycle does and leaves the kernel's restart word in local
block scratch 2. The L1 accepts ``0x2001`` from any processor of its node,
repeatedly, and restarts its own node only; the L1 does not reach an
I-brick's bridge. The C-brick controller never
asserts a reset hold, because ``reset hold``, ``reset release`` and ``power
up hold`` are not modelled on it, so its ``reset-hold`` line is not joined
to the node. The machine's own
record that it ended, and the queued check that decides it, are not
migrated, so a ``-no-shutdown`` machine that ended and was then migrated
does not resume when a node is powered up on the destination (see the
Bedrock page). The ``soft-reset`` output reports what the L1 did and
drives nothing on a C-brick; no source says what a soft reset reaches in the
node, so ``softreset`` stays unconnected. An I-brick's and an R-brick's
outputs drive their bridge and router, as described under their bricks.
The front-panel buttons are not modelled.

Reset
=====

A controller restart (realize, ``reboot_l1``, ``0x4002``) applies the
pending rack and slot, leaves console mode, clears the command line,
the frame parsers and request logging, sets the console field from
``node-position``, clears a registered event subchannel below 4, clears a pending
power-down, writes
``001c01     /`` and ``L1 running`` and logs ``L1 booting x.y.z``. It
keeps node power, the log, the debug switches, partition and the
records. The router, expansion and reference controllers are on the
machine's reset tree and restart on a system reset. A compute node's
controller is not: a node reset leaves it running, as the manuals
describe :src:`007-3938-006 p. 91`, *inferred*.

A device reset of ``sgi-l1`` also clears every multi-frame assembly and
the USB test state. A reset of ``sgi-l1-uart`` clears its registers, divisor and queue,
lowers its interrupt and discards the controller's partial frame and
multi-frame assembly for that UART.

Migration
=========

``sgi-l1`` migrates its power and console state, settings, rack and bay,
pending values, console field, event subchannel, log, display, partial
frames, multi-frame assemblies and record bytes. Loading checks that the
destination has the same profile, port-speed value, multi-frame
selection, power and interface-board bindings and query owner identity,
and rejects a stream whose records or indices are out of range. The
records travel in the stream, so the destination's files are not read.
Saving is refused while a routed or bound call is in progress.
``sgi-l1-uart`` migrates its registers, transmitter-empty occurrence and
queue, checks its UART index and recomputes the interrupt line. The peer
link, ``network-422`` and ``auto-power`` are configuration and are not
migrated. Migration works only between identical builds. An ``l2`` link
blocks migration and snapshots.

What the model chooses, and the limit of each choice:

- A brick with no rack and slot answers an identity request with the
  router's error reply, because the integer a real one returns is unknown.
  Rack and slot are supplied with ``named=on``, ``rack`` and ``bay``.
- All records are synthetic and marked as such; the SPD records set only
  the length, size and checksum bytes and a position marker. An unfitted
  PIMM or DIMM (``pimm-mask``, ``dimm-mask``) has no record and answers
  minus 104, where a real controller's wire form is unknown.
- The C-to-C and C-to-I links are in-process calls and carry no wire
  format, baud rate or detection. A C-brick has two links: ``peer`` for the
  other C-brick and ``io-peer`` for its I-brick. Both are checked against the
  two profiles: a C-brick pairs only with a C-brick, and ``io-peer`` joins a
  C-brick to an I-brick, N-brick or V-brick. The check holds whether the
  link is given with the device (it runs when the device realizes) or set
  afterwards (it runs when the link is set). An I-brick takes one C-brick:
  the fitted system's cabling of a second is unknown, so a second is
  refused with an error, and the first link stays. An N-brick takes
  several. The model does not count its connectors. After ``reboot_l1`` a brick answers no peer for one second of
  virtual time.
- An I-brick at mains is off with its bridges in reset, and has no
  power-up task of its own (*software expectation*, firmware reading). It powers
  on its own L1's ``power up`` or the front On/Off switch (the
  ``power-button`` input, a rising edge), unless setting 0x77 disables the
  switch, which the ``power-button-disabled`` property stands for
  (*software expectation* for the code path; that input bit 0 is the switch is
  *inferred*; the disabled switch's message is not modelled). In a
  machine its C-brick's auto power-up ends in ``* power up``,
  *inferred*, which reaches the I-brick, so it starts powered, logging
  ``power up (COMMAND)``. With ``auto-power`` off it starts unpowered.
  Its ``autopower`` command stays refused.
- An I-brick drives one ``reset-hold`` line, high while its bridges are
  held in reset (also the ``reset-hold`` property). Power-down raises
  it first; ``power up`` releases it after the supplies are on, ``power
  up hold`` leaves it raised; ``reset`` raises and releases it, ``reset
  hold`` leaves it raised, and ``reset`` is refused with ``power appears
  off`` while the brick is off (*software expectation*). The three bits are the
  bridges' resets by the expander's own label; which chip pins they reach
  is *unknown*, so in a machine the one line is the XBridge chip's
  ``reset-hold`` input and stands for all three (*approximation*). The
  L1's ``node-power`` output is the chip's ``main-power`` input, so a brick
  that is off or held leaves the bridge answering nothing and its C-brick's
  II link reading down, while the C-brick's processors and L1 run on. A
  ``reset`` raises the hold, which restarts the bridge cold, then releases
  it, so the ``node-reset`` pulse that follows reaches a held chip and does
  nothing more. The chip takes the L1's levels when the machine is built, so
  a brick the L1 starts off starts with the bridge held, and a restored
  machine takes them from the L1's saved state. The supplies'
  sequencing delays are not modelled.
- An R-brick L1 (``brick-type=router`` with ``router-board=rbrick``) is
  off at mains with its router in reset and accepts ``power up``,
  ``power up hold``, ``power down``, ``reset`` and ``reset hold`` from any
  request source, drives the same ``reset-hold`` line and takes the same
  front switch (*software expectation*, firmware reading). Its ``reset`` is not
  refused while off: it holds the router in reset and releases it only if
  a supply is on. It opens no RS-422 peer port, so ``peer`` and
  ``io-peer`` refuse it, and ``*``, ``ctc`` and ``cti`` are refused on it
  (*software expectation*: it cannot forward). Nothing in the stock protocol
  powers a router without an L2, so ``auto-power``, on by default,
  starts it powered as a declared *approximation* of a machine that has
  powered it; with ``auto-power`` off it starts off and in reset.
  In a machine its ``node-power`` and ``reset-hold`` outputs are the
  router's ``power`` and ``reset-hold`` inputs, so the router is offline
  whenever its brick is off or held: the pin-level join is *inferred* from
  the R-brick sheet, which records the order of the supply and the hold but
  not the pins.
- A machine reset, which a guest restart is on this machine, does not restart an I-brick, N-brick or V-brick L1: the L1
  runs on standby power, independent of brick power
  :src:`108-0240-002 p. 2-36`, and keeps its log in NVRAM
  :src:`007-3938-001 p. 3`, *established*; that a node reset leaves its
  other state alone is *inferred*. Only realize and ``reboot_l1`` start
  it.
- ``power`` and ``reset`` on an I-brick act on that brick only; a C-brick
  keeps the single-node power and reset behaviour above. ``*`` runs a
  command on this brick, the other C-brick and the I-brick in turn, each
  result headed by that brick's name. Which of two C-bricks is master is
  not modelled.
- ``select``, ``nmi``, ``softreset``, ``cpu``, ``pimm``, ``autopower``,
  ``ctc``, ``cti``, ``debug``, ``leds``, ``junkbus`` and ``*`` are refused
  on an I-brick, ``pci`` on a C-brick and ``router`` on both, with
  ``INFO: command not supported on this brick type``; other commands the
  guide lists but this model does not run are reported as unimplemented.
  The refusal text and the ``config`` line format are the model's choices.

Origin 3900 Cx-brick profile
============================

``brick-type=cxbrick`` models the one L1 of a Cx-brick, the Origin 3900
and Onyx 3000 brick that holds one to four IP53 node boards behind a single
controller on its router board (*SGI Origin 3900 Server User's Guide*
:src:`007-4653-001 p. 52-60`; *Cx-brick Addendum*
:src:`007-4572-001 p. 2-18`). ``boards`` names the fitted node boards
and ``compute-boards`` those with processors, one bit per board 0 to 3. Each fitted board reaches
the controller through its own UART window, ``sgi-l1-uart`` with
``transport-index`` the board number. Identity, naming and restart follow
the C-brick profile above: a brick starts unnamed and prints ``---c--``
(:src:`007-4653-001 p. 144`).

Request codes, the request layout and the framing follow the C-brick rule.
The profile serves the codes the Linux v2.6.0 ``ksys/l1.h`` header names
with the Origin 300 meaning (``0x0001`` to ``0x0009``, ``0x1002`` to
``0x1007``), the I/O link speed ``0x000a`` that the stock PROM reads from
its node's own L1, and the Origin 300 codes ``0x000e``, ``0x2001``,
``0x2005`` and ``0x2006``. Every other code answers the unknown-request code and is logged
as unimplemented, the attached-brick requests ``0x000c`` and ``0x000d``
among them. ``0x2001`` resets, as on the Origin 300; the public header gives
``0x2001`` to PCI power-up and ``0x2000`` to the full reset, so which a
fitted Cx-brick uses is *unknown*, and each ``0x2001`` is logged as such.

What the model chooses, and the limit of each choice:

- Each board's window is the Origin 300 UART and packet path. A reply goes
  back only on the window that asked, and on each window subchannels 0 to 3
  are that board's processors A to D and 4 its console. A shared line or a
  path through the router could interleave traffic in ways this does not
  show.
- Each window keeps its own port field: ``0x000e`` answers the board number
  after L1 power-on and ``0x1002`` rewrites only the asking window's field,
  by the Origin 300 rule. A real L1 may keep one value per brick.
- The console selection is the brick's: a board and a subchannel, changed
  by ``select`` and by ``0x1003``, which moves it to the volunteer's console
  subchannel. Console output on a window does not move it, as it does on the
  Origin 300. It starts on board 0's console, or on the lowest board with
  processors when board 0 has none; a real L1 may keep ``console0`` and time
  out. The filter is cleared at L1 power-on.
- ``select`` refuses a board that is not fitted with ``ERROR: bad subchanel
  selection.`` and accepts one without processors. Console mode toward a
  board without processors prints the guide's ``no response from 001c07
  junk bus console UART:UART_TIMEOUT``, or for a processor subchannel
  ``no response from 001c07 Junk bus CPU2B system not responding``
  (:src:`007-4653-001 p. 115, 141`), and stays in L1 mode.
- Power, reset and NMI requests from any window, and from the prompt, act on
  every board at once and log one entry. The machine's own reset carries
  them out, so the router is reset with the rest, where the profile's
  contract keeps the router's state; per-board power and reset are not
  offered. ``nmi`` pulses one ``nmi`` line per board, and only boards with
  processors are wired to them.
- Request ``0x0006`` follows the 38-entry component table of the L1
  firmware's Cx-brick personality: component 0 the power entry module's
  inlet board, 1 the router board, then a node board at 2, 11, 20 and 29,
  each followed by its eight DIMM SPDs in the order 0, 2, 4, 6, 1, 3, 5, 7.
  The firmware numbers a request by the port it arrived on. On board ``n``'s
  window component 0 is table entry 2 + 9n (its node board), 1 is 3 + 9n (its
  DIMM 0 SPD, not the router), and ``c`` of 2 or more is ``c`` + 9n, so 3 to
  10 are its own DIMMs and larger numbers reach other boards; 38 and up
  answer minus 104, as do the entries of an unfitted board. With
  ``cpu-context-present`` each node board's record carries the CPU context
  the Origin 350's carries, which the stock PROM compares with its flash.
  Approximations:

  - Link ``n`` is node board ``n``'s port. The numbering is a *software expectation* from
    the firmware; the port to board mapping is *inferred*.
  - The router's own port is the router window: a router-profile L1 behind
    the window answers component 1 with the ``ROUTER`` record (name
    inferred, part ``NOTOBSERVED0`` and revision ``00`` not observed,
    synthetic serial) and components 0 and 2 up with minus 104. The brick's
    own L1 has no router port, so it serves neither the router record nor
    the power inlet.
  - The power inlet is absent: its record's contents are unknown and the
    stock PROM never asks for it.
  - SPDs exist only for the DIMMs the catalogue's 2048 MiB per node needs,
    the two 1 GiB DIMMs in slots 0 and 1. Each has a valid checksum, byte 13
    zero (the PROM's memory self-test decides the width) and byte 31 the
    1 GiB rank density, which the PROM uses only when its memory probe finds
    nothing. Type and timing bytes stay zero and are not interpreted. The
    population of a real Cx-brick is unknown. Byte 99 marks the board.
- Board ``n``'s window answers the identity requests with the brick's slot
  plus ``n``, because the stock PROM refuses two modules at one slot. Request
  ``0x0003`` returns the personality letter ``6`` (``brick-type-code``
  overrides it), and ``brick`` prints it. Request ``0x0004`` returns the
  serial of the board record the port names: node ``n``'s synthetic serial
  on link ``n`` and the ``ROUTER`` record's on the router window, which is
  also the brick's serial; the ``brick-serial`` property does not reach the
  guest. The serials are the model's synthetic ones.
- Request ``0x0005`` answers the firmware revision ``revision-*``
  configures, 1.44.0 in the Origin 3900 catalogue entries as on the other
  brick profiles, and minus 104 without one. ``version`` prints it as
  ``L1 1.44.0 (Image EMU-UNKNOWN)``. That a fitted Cx-brick runs 1.44.0
  is *inferred*, as for the other bricks.
- Request ``0x000a`` answers as on the C-brick profile, 400 MHz unless
  ``port-speed-first`` says otherwise, which matches the I-brick the
  Cx-brick's L1 reaches. What a fitted Cx-brick answers is *unknown*.
- A neighbouring Cx-brick link is refused. The L2, the neighbouring
  Cx-brick and the ``iia`` to ``iid``, ``nia`` and ``nib`` commands are not
  modelled. One I-brick may be named as ``io-peer``: the attached I/O
  brick request then goes to it in the C-brick's request form, because the
  addressing of a Cx-brick's four I/O ports is unknown. Without a peer an
  attached-brick destination answers the router's error reply.

.. _sgi-l1-pbay:

Power-bay link
==============

The Origin 300 L1 package reads a power bay over its second serial port
(software port 1, the processor's on-chip UART 1, *inferred* from the
register block's address), at 19200 baud, 8 data bits, no parity and no
flow control, *software expectation*. The port's interrupt handler frames
the traffic in a mode the power-bay task selects: a transmission is a
start byte, the body with its checksum and the three framing bytes
stuffed, and a terminator; the transaction code above the handler works
on unframed bodies, *software expectation*. The link, its commands and the
bay's replies are described on :doc:`pbay`. The L1 starts the power-bay
task by the brick's type letter. In the package the Origin 3000 compute
brick uses it does not start it for ``0``, ``4``, ``7``, ``8``, ``9``,
``A``, ``E``, ``G``, ``O``, ``Q`` or ``V``, and the port is closed on all of
them but ``G`` and ``O``; on ``G`` the second port is a console at 38400
baud (setting word ``0x9600``, where 19200 is ``0x4b00``) instead of the bay
link, *software expectation*. Two other packages carry no letter table
and start the task for every letter except ``O``, ``G`` included although
port 1 holds the console there; neither lists ``G`` as a supported brick, so
the case does not arise, *inferred*. The model follows the first set.

The controller has an opt-in ``pbay`` character device property carrying the
framed bytes; ``pbay-address`` (default ``0x0001``) is the L1's own address
and ``pbay-poll-ms`` (default 0) overrides the poll period for tests. The
default period is the source material's, 6000 + 100 * bay ticks (:ref:`below
<sgi-l1-pbay-poll>`). ``pbay-tick-us`` is described under the receive path.
With the property unset, the controller behaves as it did before and the
link does not exist. With it set, the controller refuses to
start on a brick type that does not run the task, and blocks migration, because
the bay's state lies outside the machine.

Receive path
------------

The model follows the handler as read: it ignores every byte before a start
byte, drops a start byte inside a frame without restarting the frame,
unstuffs ``0xaa`` followed by ``0xb0``, ``0xb5`` or ``0xba`` and drops any
other byte after ``0xaa``, ends the frame at the terminator and discards
an empty one, *software expectation*. A frame whose first two body bytes
(little-endian) are neither ``0x0000`` nor the L1's address is dropped to
its terminator, and the checksum is not checked in this path but by the
transaction layer, *software expectation*. A stray ``0xaa`` before the
start byte puts the receiver in its escape state, which drops the next
start byte and everything up to a terminator, *software expectation*. A
terminator that ends a frame while an escape is pending clears the escape
as well, the same reset a terminator gives outside a frame; the handler's
treatment of that case is not read, so this is an *approximation*. The
handler does not act on UART line errors in this mode, *software
expectation*. Every request allows three transmissions with up to three
reads each. A read that times out goes to the next transmission, which waits
20 ticks first; a frame that fails the reply checks costs a read and the next
read is made without resending, *software expectation*. A read lasts 1 to 2
periods of 100 ticks, *software expectation*; the model gives each read 150
ticks, an *approximation* because the phase is *unknown*. A tick is 10 ms
(*inferred* from the 100 Hz timer); the ``pbay-tick-us`` property (default
10000, at least 1) sets it in microseconds, so tests can shorten every tick
timing at once. The first start-up request, command ``0x10``, has no reply
and is sent once: the source material does not say whether it is sent three
times, and no reply could be accepted for it, an *approximation*. A write that
finds a byte waiting in the UART is retried after a tick in the L1; the model's
receiver is never busy, so that retry is not modelled. The timers run on the
host's real-time clock, because the bay is a host peer that answers in real
time and the virtual clock is stopped while the guest is halted, so under
``-icount`` or record and replay the link's timing is not deterministic.

Initialisation and polling
--------------------------

The model starts the link when the controller starts, when it is reset and
when ``reboot_l1`` restarts it (a C-brick's L1 is not reset with the
machine, so only that command restarts its link). The task
sets the status to "busy initialising" and waits ``100 * bay + 300`` ticks,
``bay`` being the controller's ``bay`` property (L1 setting 2), before its
first request: 3 s plus 1 s per bay number at 10 ms a tick, *software
expectation* for the formula and *inferred* for the tick. It sends command ``0x10``
and then ``0x02`` to address 0 and takes the replied address, with zero or no
reply meaning a communication failure, then ``0x12`` with that address,
``0x13``, the ``0x00,0x00`` pair and the record loop from id 0, reading five
bytes of each record to learn its id and then the whole record, until the
next id is ``0xffff``, *software expectation*. It sets the status to
"busy initialising" while it runs, to "ready" when it finishes and to
"communication failure" when a transaction fails after its attempts. A reply
is accepted when its checksum holds, its control byte has the reply bit and
the request's tag, its command matches and its completion code is zero, and
for a tunnelled request when the inner command and completion code
match and the network function is the request's plus the response bit,
*software expectation*.

Of the three capability bytes, byte 1 when nonzero is stored as the fallback
FRU device of slot 0, used until a FRU locator for entity ``0xb0`` replaces
it; byte 2 when nonzero runs the record loop, *software expectation*. The
model reads the loop's records for what the L1 takes from them,
*software expectation* for the use and *inferred* for the field offsets in
the record (they follow the public IPMI sensor and FRU-locator record
layouts): a sensor record of entity ``0x0a`` and sensor type 8 maps its
sensors to supplies 1 to 6, one of entity ``0x15`` and type 9 to DC ports 1 to
8, and a FRU locator of entity ``0x0a`` (instances 1 to 6), ``0xb0`` or
``0x15`` gives the device of FRU slot 1 to 6, 0 or 7. The records do not say
how many sensors a record covers, so the model takes six and eight, an
*approximation*. The count of records read is exposed as ``pbay-records`` and slot 0's
device as ``pbay-fru-slot0``.

.. _sgi-l1-pbay-poll:

The polling task waits on its queue for ``6000 + 100 * bay`` ticks (60 s plus
1 s per bay number at 10 ms a tick, *software expectation* for the formula,
*inferred* for the tick). A request to the bay restarts the wait and a
timeout runs the poll. The model arms the wait when the link becomes ready
and after every command or pass that uses the bay; a change of the
monitoring setting is not a request to the bay. The poll does nothing, and
the wait starts again, unless the environment-monitoring setting (L1
setting 85, four bits) is nonzero, the status is ready and no other request
holds the bay; it sets the status to "busy" while it runs. The setting is
zero at power-on, so a controller with a bay polls nothing until ``pbay env
on`` stores ``0x0f`` (*software expectation* for the store, *inferred* that
nothing else sets it). Bit 0 of the setting enables the presence and AC-fail
tests, bit 1 the supply-fail test, bit 2 the predictive-fail test and bit 3
the DC ports, *software expectation*. ``pbay-poll-ms``, when nonzero,
replaces the period for tests; ``pbay-tick-us`` scales it otherwise.

A pass reads the supplies' sensors (when any of bits 0 to 2 is set) and the
ports' (bit 3), and each message goes to the L1 log, *software expectation*.
The line texts begin with ``Power Bay DPS n`` or ``Power Bay DCport n`` and
carry the words the polling task logs. The model keeps the last value of each
sensor, and nothing is stored at start, so a fault already present on the
first pass counts as new. For sensors 1 to 6 (``DPS`` 1 to 6) bit 0 set means
not inserted and clears the stored value, so a returning supply's faults are
new. Per supply the first matching test wins, so a pass logs at most one
fault for it: AC fail (bit 3 newly set), then fail (bit 1), then predictive
fail (bit 2). Fail and predictive fail are logged at once. An AC fail is
logged on the fourth consecutive sighting, with three immediate re-reads of
all six supplies between; a supply whose bit is gone at any re-read is not
logged. For sensors 7 to 14 (``DCport`` 1 to 8) a port whose bit 0 is set is
skipped and keeps its stored value, and bit 1 newly set on a port is logged
on the third consecutive sighting, with a re-read of the ports after 100
ticks. The source material does not say whether the two port re-reads are one
wait each or one wait in all, nor whether a supply with an AC candidate that
fails the debounce still lets the fail test run; the model waits 100 ticks
before each of two re-reads and lets the AC candidate take the supply's turn,
an *approximation*. A consequence of that choice: a supply with a new AC-fail
bit that then fails the debounce, and whose fail bit is also set, logs
neither fault on that pass, and the fail is new again only if its bit goes
from 0 to 1 later. The fail and predictive tests use the last reading.

The set of supplies with bit 0 clear is compared with L1 setting 105, the
expected-supply mask (bit n-1 for supply n; zero means no presence messages).
A supply that leaves it is logged as removed and one that arrives as
inserted, then the present set is written back when it differs. So the first
pass on a fresh record logs nothing and stores the baseline, and a pass that
finds no supply present is a failed read that skips the step, *software
expectation*. A supply whose single read fails (no answer after the retries)
is treated like one that is not present for that pass, so with the other
supplies answering it is logged as removed and as inserted when it answers
again; how the task treats one failed read is not in the source material, so
this is an *approximation*. Settings 85 and 105 are the L1's, so a restart of the
link keeps them; the previous readings are RAM and are cleared. The model does
not migrate any of this, because a configured link blocks migration.

Each message goes through the L1's event formatter, which adds two numbers
and sends an event; the wrapper's text and the numbers' meaning are *unknown*.
The model logs the bare message to the L1 log only, and logs ``LOG_UNIMP``
for the wrapper.

The ``pbay`` command
--------------------

The operator command is accepted on the brick types ``C356P%#=IXYRN&!``
(the link itself opens on more), *software expectation*; on another type the
model prints ``ERROR: command not found.``, because the refusal's text is
*unknown*. Its fourteen forms share one handler, *software expectation*.
The texts below paraphrase the source material, so the column heads and widths
are an *approximation*; the rows' words and their order are *software
expectation*.

- Whatever the form, a link that is not ready prints its state text
  (``PBay not initialized``, ``PBay busy initializing``, ``PBay busy try
  again later``, ``PBay busy flashing``, ``PBay communication failure`` or
  ``PBay state unknown``) and the command fails. A request that finds the
  bay held by a polling pass or another command prints the busy text. In
  state 5 ``pbay init`` runs the initialisation order again and prints ``PBay
  ready`` or the state text; in any other state it prints ``PBay already
  initialized``. The model does not repeat the task's start delay, an
  *approximation*.
- ``pbay version`` sends link command ``0xc0`` and prints ``PBay FW Version
  00.18, Built 09/29/2000 14:00:00``: the version bytes second then first,
  and the build time read as a Unix time in UTC (*inferred*). With no reply
  it prints ``PBay version unavailable``, an *approximation*: the source
  material gives no text.
- ``pbay dps [digits]`` and ``pbay dcport [digits]`` read the mapped sensors
  of the supplies 1 to 6 or the ports 1 to 8 (or the digits given) and print
  a header and one row each. A supply row is ``Ok`` or ``Low`` (bit 3),
  ``220Vac`` or ``110Vac`` (bit 4), ``Ok`` or ``Failing`` (bit 2) and ``Ok`` or
  ``Failed`` (bit 1), or ``Not_Present`` alone (bit 0). A port row is ``48V
  Off`` (bit 0) or ``48V On, `` with ``Ok`` or ``Failed`` (bit 1). An
  unmapped supply or port prints nothing and a failed read prints ``**read
  error**``. The string that follows a port's row when link command ``0x0b``
  returns the port's number is *unknown*: the model does not ask and logs
  ``LOG_UNIMP``.
- ``pbay fru [n]`` reads the FRU device of each slot (slot 0 the bay, 1 to 6
  the supplies; a negative ``n`` selects the seventh) with the streamed read
  and prints manufacturer, product name, part number, version, serial and
  the manufacturing date from the FRU's common header, product area and
  board area. A bad checksum prints ``**FRU checksum error**``. The
  source material does not say how the L1 addresses or sizes the reads,
  which area each column comes from, or the labels of the first column; the
  model reads 128 bytes from address 0, takes the columns from the product
  area and the date from the board area, labels slot 0 ``Bay`` and the
  seventh slot ``Card``, and prints the date as month, day and year. All of
  that is an *approximation*. The bay model returns zeros, so against it the rows read ``**FRU
  checksum error**``.
- ``pbay reset`` sends the pair ``0x18,0x03`` and prints ``Ok`` or
  ``Timeout``.
- ``pbay env`` prints ``Power Bay env monitoring enabled`` or ``disabled``, a
  blank line, and the ``dps`` and ``dcport`` tables; ``pbay env on`` and
  ``off`` print nothing and store ``0x0f`` or 0 in setting 85.
- ``pbay serial`` prints the serial in slot 0's product area (*inferred* to
  be the fifth field), nothing when there is no slot 0. The L1 caches it at
  start-up; the model reads it on first use, then keeps it until the link
  starts again, an *approximation* with the same output.
- Bare ``pbay`` prints a line per FRU device with a current in amps. Its
  arithmetic and record selection are *unknown*: the model prints nothing and
  logs ``LOG_UNIMP``.

A command that needs the bay finishes when the bay has answered, and the
prompt follows. Over task 3 the reply carries as many output lines as fit its
121 bytes of fields (each line takes its text plus two bytes), whole lines
only, and blank lines are dropped. A command relayed from another
controller (``ctc``) cannot wait for the bay and prints an error, logging
``LOG_UNIMP``. A request restarts the polling task's wait.

The flash task and its ``0x92`` to ``0x94`` requests are not modelled. The
read-only properties ``pbay-status``,
``pbay-records``, ``pbay-passes`` and ``pbay-fru-slot0`` expose the state for
tests.

.. _sgi-l1-model:

Model limits
============

- The controller does not run L1 firmware. Its replies are a responder
  built from the readings above; a reply or a version line does not mean
  firmware ran.
- No M-Bus, environmental monitoring, events other than the deferred
  power-down, JTAG scan, flash, management USB device or RS-422 wire
  protocol. The L2 link carries segments only; of what the L2 sends on its
  own, only its selector 6 configuration request is answered
  (:ref:`sgi-l1-l2-config`), and the peer table exchange it starts is a
  direct call between paired C-bricks (:ref:`sgi-l1-table-exchange`).
- The operator commands ``env``, ``date``, ``config``, ``uart``,
  ``flash``, ``network``, ``cpu``, ``port``, ``serial``, ``autopower``,
  ``history``, ``l1dbg console`` and ``select filter`` are not modelled.
  Unknown commands log ``LOG_UNIMP``.
- The prompt, display and ``brick`` line always use the letter ``c``,
  and ``brick`` always prints ``type: C (IP45) [1MB flash], serial:
  unavailable, source: EEPROM``, whatever the profile.
- Display hardware, LEDs and the heartbeat are not modelled; ``display``
  reports fixed LED texts.
- Malformed frames, bad checks and unrouted local tasks are dropped with
  no entry in the L1 log, where the 1.44.0 image logs them.
- The UART has no character timing, line errors or FIFO identification.
- Accesses: unsupported interrupt-enable bits and unrouted tasks log
  ``LOG_UNIMP``; writes to the status registers, a full queue toward the
  processor (4096 bytes; the frame is dropped) and an over-long command
  line log ``LOG_GUEST_ERROR``; a narrower access to the window is a
  decode error.

Tests
=====

``tests/qtest/sgi-l1-pbay-test.c`` plays the bay from a socket and joins
the controller to the bay model, covering the initialisation order, polling
and its log lines, the receive rules, a missing bay, the bricks that do not
run the task and the migration block.

``tests/qtest/sn1-l1-test.c`` covers the UART registers, interrupts and
their migration, framing and receive tolerance, output escaping, every
general request and reply code, the command interpreter, console mode,
retargeting and short frames, the power, reset, NMI and power-cycle
paths, controller restart and node position, raw, whole-image and built
EEPROM records, the Fuel station-address record, the peer pair, the
query and attached routing models (with
``tests/qtest/l1-query-routing-fixture.c``), the expansion, router and
reference profiles, the interface-board start-up (with
``tests/qtest/l1-bic-startup-fixture.c``), the multi-frame transport for
both selections, the management USB byte calculations and migration of
each. ``tests/qtest/sn1-address-map-test.c`` checks the window at both
Hub forms, the interrupt reaching the processor, the operator console,
revisions, type codes and built records on the machines.
``tests/qtest/sn1-bedrock-test.c`` checks the Bedrock's refusals and
protection for the window, ``tests/qtest/sn1-cross-node-test.c`` the
local form on a second node and, on an Origin 3200, each brick's power
acting on its own node, the machine ending with the last one and resuming
with only the brick switched on
(``sn1/cross-node/brick-power-ends-the-machine-last``,
``sn1/cross-node/broadcast-power-down-ends-the-machine``,
``sn1/cross-node/brick-power-stops-one-counter``,

type code and NMI routing, ``tests/qtest/sn-builder-test.c`` the peer

``tests/qtest/sgi-sn1-router-test.c`` the router module's window.

``tests/qtest/sgi-l1-o3k-test.c`` covers the L2 link with a stub peer in
