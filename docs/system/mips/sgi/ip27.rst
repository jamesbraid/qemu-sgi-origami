.. _sgi-ip27:

=======================================
IP27: Origin 200, Origin 2000 and Onyx2
=======================================

:term:`IP27 <IP number>` is the software platform of SGI's first Scalable Node generation,
built around the :term:`Hub` node controller. The ``origin200``, ``origin2000``
and ``onyx2`` machines (``hw/mips/sgi/sn-machine.c``, with the node in
``hw/mips/sgi/sn0.c``) build it on the shared Scalable Node base
described in :doc:`sn`. An Origin 200 is one or two IP29 system boards
in towers. The ``origin2000`` machine builds one Origin 2000 :term:`module`: one
to four IP27 :term:`node boards <node board>` joined by Routers, with two :term:`Crossbows <Crossbow>` and twelve
:term:`XIO` slots. Real systems join modules (:ref:`sgi-ip27-missing`). An Onyx2 is
the same IP27 silicon with an InfiniteReality graphics pipe, in a
deskside of its own or a rack built from the Origin 2000 module. Every
machine boots a stock IP27 :term:`PROM` that the user supplies.

This page is the hardware contract the machine models in
``hw/mips/sgi/models/`` cite for these products: what is fitted, how it
is wired, what the emulator chose where the hardware is not known, and
which sources back each statement. Chip registers are on the pages of
the parts (:ref:`sgi-ip27-devices`).

Facts are rated as described in :ref:`sgi-ratings`.

.. _sgi-ip27-topologies:

Topologies and node populations
-------------------------------

``topology=`` selects the wiring and ``nodes=`` the number of node boards
fitted, in SGI's fill order (:ref:`sgi-origin2000-module-nodes`). Each
topology's catalogue record has one row per accepted node count; the row
decides which Routers and cables exist and which XIO slots work. ``-smp``
and ``-m`` then select a population within that row.

.. list-table::
   :header-rows: 1

   * - Topology
     - ``nodes=``
     - Fabric
     - Processors per node
   * - ``origin200``
     - 1
     - none
     - 1 or 2
   * - ``origin200-dual``
     - 2
     - one CrayLink cable, Hub to Hub
     - 2 (fixed, 2+2)
   * - ``origin200-gigachannel``, ``origin200-gigachannel-loopback``
     - 1
     - none; a cabinet Crossbow or a loopback cable
       (:doc:`hardware/gigachannel`)
     - 1 or 2
   * - ``origin2000-rack``
     - 1 to 4
     - none for one node, two Standard Routers from two
     - 1 or 2
   * - ``origin2000-deskside``
     - 1 to 4
     - none for one node, a Null Router for two, two Standard Routers
       for three or four
     - 1 or 2
   * - ``onyx2-rack``
     - 1 to 4
     - as ``origin2000-rack``
     - 1 or 2
   * - ``onyx2-deskside``
     - 1 or 2
     - none for one node, the midplane's Null Router for two
     - 1 or 2

``nodes=`` defaults to the largest count the topology accepts. ``-smp``
keeps the product's default, which is the default topology's: the
machine cannot tell a default ``-smp`` from an explicit one, so a launch
with fewer node boards, or the Onyx2 deskside, names it
(``-M onyx2,topology=onyx2-deskside -smp 4``). ``-smp N`` picks the one
accepted population whose total is N, and ``population=4:2`` style
per-node counts choose between two that share a total; ``sockets=`` must
equal ``maxcpus`` (:ref:`sgi-sn-topology`). A count no row accepts is
refused with the counts that exist. ``nodes`` is part of the machine
configuration: a snapshot restores only into the same value. The
general rules for ``topology=``, ``-smp`` and ``-m`` are on
:ref:`sgi-sn-topology`.

.. _sgi-sn-gigachannel:

GIGAchannel expansion cabinet
-----------------------------

Two Origin 200 topologies fit the cabinet: ``origin200-gigachannel``,
where the cabinet's Crossbow sits between the Hub and the module's base
I/O :term:`Bridge`, and ``origin200-gigachannel-loopback``, the converted module
with a loopback cable instead of a cabinet. The cabinet's own I/O is the
``sgi-gigachannel`` board, which the machine places and which is not
``-device``-creatable. :doc:`hardware/gigachannel` describes both
topologies, the board, its BASEIO PROM flash and its status word.

Processor modules
-----------------

``origin2000`` and ``onyx2`` accept only the R10000 and fit one
composition, a 180 MHz R10000 with 1 MiB of secondary cache and a 90 MHz
Hub (:ref:`sgi-origin2000-reset-mode`). ``origin200`` accepts the R10000
and the R12000, and ``processor=`` selects the processor module (PIMM)
every node fits, by catalogue id. ``-cpu`` defaults to the module's part
and must name it when given; ``query-sgi-machines`` lists each topology's
choices as ``processor-options``.

.. list-table::
   :header-rows: 1

   * - ``processor=``
     - Part, PRId
     - Secondary cache
     - Processors a module
     - Mode word
   * - ``r10000-180mhz-1mb`` (default)
     - R10000 rev 2.6, ``0x0926``
     - 1 MiB at 120 MHz, tap 9
     - 1 or 2
     - ``0x1211a785``
   * - ``r10000-180mhz-2mb``
     - R10000 rev 2.6, ``0x0926``
     - 2 MiB at 180 MHz, tap 8
     - 1 or 2
     - ``0x100aa785``
   * - ``r10000-225mhz-2mb``
     - R10000 rev 3.4, ``0x0934``
     - 2 MiB at 225 MHz, tap 9
     - 2
     - ``0x120aa985``
   * - ``r12000-270mhz-4mb``
     - R12000 rev 2.3, ``0x0e23``
     - 4 MiB at 180 MHz, tap 9
     - 2
     - ``0x1213ab85``

An Origin 200 module carries an R10000 or R12000, one or two to a module
(*established*, :src:`007-3708-002 p. 5`). Published inventories show
each module's clock, cache size, cache clock, tap and chip revision, all
with a 90 MHz Hub (*observed*):

- 180 MHz with 1 MiB: one- and two-processor inventories (modules
  ``PIMM_1XT5_1MB`` 013-1895-001, :src:`usenet-6kd8bj`, and
  ``PIMM_2XT5_1MB`` 013-1896-001,
  :src:`ebbes-parallelrechner-dissertation p. 93`).
- 180 MHz with 2 MiB: a two-processor PROM inventory printing a 180 MHz
  R10000 revision 2.6 with a 2 MB, 180 MHz, tap 8 secondary cache
  (:src:`nekonomicon-16729597`); the single-processor module is
  ``PIMM_1XT5_2MB`` 013-2285-002 (:src:`usenet-3e2794b8`).
- 225 MHz: IRIX inventories print revision 3.4 and a 2 MB, 225 MHz,
  tap 9 cache, module ``PIMM_225_2M_2P`` 013-2382-002 revision B
  (:src:`nekonomicon-16731033`).
- 270 MHz: four-processor machines print an R12000 revision 2.3 with a
  4 MB, 180 MHz, tap 9 cache (:src:`nekonomicon-16726704`).

The stock PROM's own configuration block carries mode word
``0x1211a785`` and a 180 MHz clock, the same composition (*software
expectation*, :src:`ip27-prom-6.156 configuration block, mode word`;
:ref:`sgi-prom-image-config-block`). The remaining fields are *inferred*. The system clock divisor is the
processor clock over the Hub's 90 MHz and the cache divisor the
processor clock over the printed cache speed. The PRId's low byte is the
printed revision. The FPU identification is ``0x0900`` for every module.
Every other mode field is the 180 MHz, 1 MiB word's, and the R12000's
delayed speculative dirty bit is clear. The R12000 divisor codes are
NEC's (:src:`nec-vr10000-series-um-4 Table 8-1`). No source shows a
single-processor 225 or 270 MHz module, so those take two processors
only.

The machine writes each module's clock and mode word into every node's
flash configuration block (:ref:`sgi-prom-image-ip27-values`). The mode
word's bits 24:0 become each processor's Config at cold reset, the clock
drives CP0 Count, and the PRId and cache size are the CPU model's
(:doc:`hardware/r10000`). That a real node delivers the module's values
this way is *inferred*. The PROM's reconfiguration dialogue writes clock
and mode bits into the block, which supports it, but the stock image also
prints "Config values loaded from PIMM" from a path that reads another
source, so where a real Origin 200 node takes its configuration on every
boot is *unknown*.

Model limits, each an *approximation*:

- The Origin 200 node keeps Hub revision 3 and the IP29 board record
  030-1244-001 revision H for every module. Real 225 and 270 MHz
  inventories show Hub revision 5 and board 030-1389-001 (*observed*,
  :src:`nekonomicon-16731033`, :src:`nekonomicon-16726704`).
- A node flash that already exists, such as a bound ``node0-flash``,
  keeps the block it was written with: ``processor=`` does not rewrite
  it, as a module swap on real hardware needs the PROM's
  reconfiguration, and a mismatched block is not refused.
- The two module records the 180 MHz 2 MiB dual module and the R12000
  module would carry are not known, so their Hub one-wire part is left
  unprogrammed.

.. _sgi-ip27-memory:

Memory population rules
-----------------------

``-m`` splits evenly across nodes, and each node's share must be one of
its board's accepted sizes. The machine lays each share out in banks from
bank 0, with no empty bank between two populated ones. A refused size is
reported with the sizes that are accepted. Without ``-m`` every node gets
its topology's default kit.

**Origin 200 (IP29).** Four banks of two DIMMs, filled from the outer
pair, in pairs of matching DIMMs (*established*,
:src:`007-3709-002 p. 48`). The Origin technical
report lists 32, 64, 128 and 512 MB banks and no 256 MB bank
(*established*, :src:`origin-technical-report section 2.2.2.3, Table 2-1`).
The model builds no 32 MB bank (*approximation*). A 256 MB bank is
*observed* on a 270 MHz machine (:src:`nekonomicon-16726704`), and the
model builds it. The stock PROM 6.156 disables a 256 MB bank whenever the configuration
block gives a 180 or 195 MHz processor (*software expectation*: the
PROM prints "256 MB dimm banks not allowed on IP27 node boards" as it
does so, :src:`ip27-prom-6.156`). With a 180 MHz module the model
therefore builds 64, 128 and 512 MiB banks, 23 per-node sizes from 64 to
2048 MiB. With a 225 or 270 MHz module it adds 256 MiB banks, 27 sizes;
512 MiB is then two 256 MiB banks, as on a real 270 MHz machine
(*observed*, :src:`nekonomicon-16726704`).

**Origin 2000 and Onyx2 (IP27).** A node board has 16 main-memory DIMM
slots and 8 directory DIMM slots, filled as eight banks of DIMM pairs,
and bank 0 must be populated (*established*,
:src:`007-3439-002 pp. 35-36`). 16-Mb parts give 64 or 128 MB banks and
64-Mb parts 512 MB banks, up to 4 GB a node, intermixed as long as each
bank is a pair (*established*, :src:`007-3439-002 p. 35`). That page is the whole basis for the IP27
sizes. Inventories of 250 MHz and faster nodes show 256 MB banks, but
those are the later IP31 board on the same Hub. The model builds no 256
MiB IP27 bank, since the stock PROM disables one at 180 MHz, so every
Origin 2000 and Onyx2 topology accepts 55 per-node sizes from 64 to 4096
MiB.

Bank 0 stays at 128 MiB (256 MiB with a faster Origin 200 module)
whenever the other banks can hold the rest: 1664 MiB on an Origin 200 is
128, 512, 512 and 512 MiB, and 1024 MiB on an IP27 node is 128, 512, 128,
128 and 128 MiB. Only totals that need it get a 512 MiB bank 0: 1024,
1536 and 2048 MiB on a 180 MHz Origin 200, 2048 MiB with a faster
module, 3072, 3584 and 4096 MiB on IP27. This preference is the model's
choice (*approximation*); a real machine's banks follow the DIMMs fitted.
The default kits, one 64 MiB bank on the Origin 200 and two 128 MiB banks
on IP27, are also model choices; the IP27 one matches a published node
(*observed*, :src:`nekonomicon-16727716`).

.. _sgi-ip27-bank0-flash:

A 512 MiB bank 0 and the boot flash
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A 512 MiB bank 0 covers the boot flash's reset address, node offset
``0x1fc0_0000``. There a cached processor reference reaches the bank and
an uncached one the flash. The reset fetch through
``0xffff_ffff_bfc0_0000`` is an uncached memory reference, and the flash
is mapped into each processor's uncached space alone, at the node-less
address and at the node's own. That split is *inferred*: the stock
PROM's memory test covers the offset through cached space, and real
machines with a 512 MB bank 0 pass it, which they could not if a cached
reference reached the flash. A write and read-back through a cached
address at that offset, then an uncached read, on a machine with a
512 MB bank 0 would settle it.

Three further choices are the model's own, with the hardware *unknown*:
devices (inbound DMA, the block transfer engines) reach the bank; an
uncached reference from another node to this node's offset reaches the
bank; and the node-less address ``0x1fc0_0000`` names the reader's own
flash on every node. Smaller banks leave the reset address to the flash
in every view.

Missing devices
===============

- The Star Router: three- and four-node desksides are built with two
  Standard Routers instead (:ref:`sgi-origin2000-module-routers`).
- More than one Origin 2000 or Onyx2 module, Xpress links, the
  MetaRouter and the rack's multimodule system controller (MMSC). The
  two-module rack is a reference configuration only.
- IP31 node boards and Origin 2000 processors other than the 180 MHz,
  1 MiB R10000 (:ref:`sgi-ip27-cache`).
- More than one graphics pipe in a machine. The Onyx2 graphics module
  holds two pipes; the model fits one.
- The Onyx2 rack's Xtown and Ktown boards are not separate devices: the
  pipe widget answers on the Xtown's Crossbow port
  (:ref:`sgi-onyx2-pipe-link`).
- A GIGAchannel cabinet on the slave module of a two-module Origin 200,
  and a converted module with neither cabinet nor loopback.
- What drives the UST control port's pins
  (:ref:`sgi-origin2000-module-management`).

.. _sgi-origin2000-module:

Origin 2000 module
==================

An Origin 2000 module is the deskside chassis or one rack module: a
midplane with four node-board slots, two Router slots, two Crossbows and
twelve XIO slots, plus the module system controller (MSC). The deskside
is equivalent to one rack module (*established*,
:src:`007-3456-003 p. 30`, :src:`007-3456-003 p. 44`;
:src:`007-3453-002 p. 19-20`). The wiring summary is two Routers per
module, two Crossbows per midplane, and the BaseIO board in slot IO1
(*established*, :src:`108-0170-001 pp. 1-1 to 1-4` and
:src:`108-0170-001 pp. 6-3 to 6-6`). This
section is what the ``origin2000``
and ``onyx2-rack`` models cite for how a module is populated, how its
management bus is wired and how the processor's reset mode is chosen.

The module's Crossbows reach node boards at widgets 9 and A: N1 at
Crossbow 0 widget 9, N2 at Crossbow 1 widget A, N3 at Crossbow 0 widget
A and N4 at Crossbow 1 widget 9. The node rows are the stock PROM's own
naming (:ref:`sgi-onyx2-rack-widget-map`, *software expectation*); which
board is physically wired to which port is *unknown*. Each node's Hub
reads its slot through the slot-identity register: raw values 7 to 4 for
N1 to N4 (:ref:`sgi-onyx2-node-slot-codes`; the register is on
:ref:`sgi-hub-memory`).

An absent node board has no Hub, processors, boot flash or place in the
module controller's arbitration. A board fitted at launch in a slot the
row cannot use is refused with the node board it needs.

The deskside inference: a deskside is one module
(:src:`007-3456-003 p. 44`), :src:`108-0170-001 section 6.2.1` gives "a
typical fully-populated single-module system" two Routers, and the
Standard Router joins 2 to 32 node boards in 1 to 8 enclosures
(:src:`007-3439-002 p. 57`).

The Star Router is a carrier with no Router ASIC. With the Router in R1,
R1 port 5 reaches N1, port 4 N2, port 6 N3 through the midplane, and
port 3 N4 through an external jumper to the Star's one connector, where
its XC chip converts the differential cable signals to single-ended;
ports 1 and 2 stay free (*established*,
:src:`108-0170-001 section 6.2.2`; :src:`007-3456-003 p. 32`). The model
does not fit it. The stock PROM checks each Hub's partner on the same
Crossbow through a fixed two-Router vector route, ``0x56`` or ``0x46``
(:src:`108-0170-001 Table 6-1`; :src:`ip27-prom-6.156 0x1fc470a0`,
*software expectation*). On the Star wiring Router port 6 leads straight
to N3, so that vector reaches a Hub with a route step left over. What a
real Hub answers is *unknown*, and the model gives no answer: on the
model the PROM then reports a peer Hub on the Crossbow with no :term:`NUMAlink`
connection and stops discovery. A Hub specification, or a boot log from
a three- or four-node Star deskside, would settle it.

.. _sgi-origin2000-module-number:

Module number
~~~~~~~~~~~~~

Each module is assigned a unique module number from 1 to 255; 0 means
none has been assigned. IRIX names devices by module number. The number
is stored in MSC NVRAM, and a backup copy in each node card's PROM log,
from which it is voted if the NVRAM is inaccessible (*established*,
:src:`108-0170-001 p. 1-4`). :ref:`sgi-elsc-nvram` gives the controller
block's layout and how a store with no backing file is seeded. The
model numbers its one module 1, a selected installation rather than a
reset default (*approximation*). With 0 the stock PROM votes a number
and resets once more before it settles (*software expectation*,
:src:`ip27-prom-6.156`).

The per-node PROM logs are separate storage from the shared NVRAM and
from the BaseIO's own Timekeeper.

.. _sgi-origin2000-module-identity:

Module serial and midplane parts
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Each module carries two module-level one-wire parts: a family ``0x09``
part whose record is named ``MODULEID`` and holds the module serial, and
a family ``0x0b`` midplane part holding the midplane's board record.
Published inventories list one of each per module (*observed*,
:src:`usenet-9uhh6o`). Rack inventories print them under node slot
``n1``, and the firmware and kernel print a record under the node whose
Hub bus it came from, so the two parts are on the ``n1`` Hub's one-wire
bus and no other (*inferred* from software and captures; a continuity
check on a real midplane would settle it).

The model puts both parts on the controller's midplane one-wire net and
wires the ``n1`` Hub's line to that net as well, so the ``n1`` Hub
reaches its own node part and both module parts. The connection is
one-way: the controller's ``nic`` line reaches the two module parts but
not the ``n1`` node's own part (*approximation*). The other nodes' Hub
buses carry only their own node part.

The ``MODULEID`` pages carry the module serial in the layout the Hub
module-serial record uses: format byte ``0x01``, the ten-character
serial, the name at page one offset sixteen, ``0xff`` in every other
field and a stored CRC per page. The serial is a synthetic value
marked as the model's own: ``KEMU``, the kind digit, the machine's ``emu-id``
as four digits and the module number 0 to 9, so ``emu-id=42`` gives
``KEMU100420`` for the first module and ``KEMU100421`` for the next
(*approximation*; :ref:`sgi-identity`). A machine with no ``emu-id`` has
``KEMU100000``. ``serial=`` gives module 0 a text that starts with ``K``, because the
guest ignores a module serial that does not (*software expectation*, from the
analysis of the IRIX 6.5.30 IP27 kernel, entry ``unix.IP27-6.5.30``, at address
``0xc000000000040974``; see :ref:`sgi-identity`), padded on the left with ``K`` to the record's ten
characters (*approximation*), so ``K0017299`` is ``KKK0017299`` and folds to
``b0017299``. ``hostid=`` gives ``KK`` and the eight-character spelling of an
id; module ``i`` then has the id plus ``i``, spelled the same way. They must
agree when both are given, and ``mac=`` sets only the port's address. The first
module is module 0, which the catalogue calls module 1. The module's catalogue serial is no longer used. A machine with
more than ten modules is refused, as the digit cannot name an eleventh. The
FLEXlm host id folds the serial's low nibbles, ``d5100420`` for the first
module here; IRIX prints one id per module on a real Origin 2000, and the
machine's ``hostids`` lists one per module (the catalogue has no Origin 2000
or Onyx2 of more than one module, so the list holds one id).
The four-node module's midplane record is ``8P12_MPLN``, part
030-0762-006 revision H (*approximation*: the rack inventories of
:src:`nekonomicon-16285` print this part at revision K); which midplane
an IP27-era module carried is *unknown*. Its barcode and both ROM
serials are synthetic, letter ``Y`` for ``MODULEID`` and ``L`` for the
midplane.

The Onyx2 deskside carries the ``MODULEID`` part only. Its two-slot
``4P1G5_MPLN`` midplane's record values are *unknown*, so the model fits
no midplane part there. A real Onyx2 deskside inventory would settle
them.

A Hub that does not master its Crossbow marks its midplane record a
duplicate, and the IRIX 6.5.30 kernel skips duplicate records (*software
expectation*, :src:`ip27-prom-6.156 midplane record, duplicate mark`).
With the parts on ``n1`` only, the ``n1`` Hub must master its Crossbow or
IRIX warns that the module's serial is invalid. The model does not choose
the Crossbow master; the firmware does. Which serial the kernel reports
when several records are present is *unknown*.

.. _sgi-origin2000-module-grants:

Processor grants
~~~~~~~~~~~~~~~~

The controller's per-processor grant bytes on the shared bus, their
rotation and recovery are described as model behaviour in
:ref:`sgi-elsc-arbitration`. No public source documents the Origin 2000
controller's grant values, ordering or recovery timer, so all of that is
*unknown* as hardware and an emulator choice as model behaviour.

.. _sgi-origin2000-reset-mode:

Processor reset mode
--------------------

The R10000 loads a 25-bit mode word from the system data bus at power-on
or cold reset. It becomes CP0 Config bits 24:0, a soft reset preserves
it, and the primary-cache size fields are hardwired (*established*,
:src:`r10000-users-manual-2.0 p. 160-165`,
:src:`r10000-users-manual-2.0 p. 256`). The secondary-cache size field,
Config bits 18:16, encodes 1 for 1 MB and 3 for 4 MB (*established*,
:src:`r10000-users-manual-2.0 p. 165`).

SGI's booklet pairs the IP27 node-board assemblies as a 1 MB cache with a
180 MHz processor and a 4 MB cache with a 195 MHz processor
(*established*, :src:`origin-onyx2-quick-reference-booklet p. 93`). The
diagnostic roadmap's reconfiguration examples give the same two
configurations, 180 MHz with a 90 MHz Hub and 195 MHz with a 97.5 MHz
Hub, both machine type 0 (*established*, :src:`108-0164-002 p. E-4`).
The stock PROM 6.156 configuration block carries mode word
``0x1211a785`` with a 180 MHz processor clock, a 90 MHz Hub clock and
machine type 0, whose cache size field is 1 (*software expectation*,
:src:`ip27-prom-6.156 0x1fc00064`; the block layout is on
:ref:`sgi-prom-image-config-block`). The machines therefore select a
180 MHz R10000, a 90 MHz Hub and 1 MiB of cache, and leave the stock
word unchanged. A published pairing agreeing with the image's own record
picks a documented real composition; neither alone does. The 4 MB
encoding would change bit 17 and give ``0x1213a785``, which does not
match the stock image, so the 195 MHz composition is not built.

The procedure by which the firmware compares the flash word with CP0
Config is not stated by any public source and is *unknown* here. Its
outcome is visible on the model: a node flash whose word disagrees with
the processors' Config stops every processor with boot-progress code
``0xb4`` before the console opens. The model's processor reset
configuration must therefore equal the flash word, and a stock PROM boot
is the discriminating test.

.. _sgi-sn-family-origin2000-xpress:

Two-module racks and Xpress links
---------------------------------

A rack holds two modules. Within and between modules, Link 1 runs
vertically between the upper and lower Routers of the same letter, and
Link 2 is the Xpress link, which must cross. Xpress links are only used
in systems of 16 or 32 processors (*established*,
:src:`007-3439-002 p. 59`). No source cited here draws the full
cable-by-cable wiring, and which SGI document does is *unknown*. The
``origin2000-two-module-xpress`` layer records the link rule as a
reference configuration. No machine builds it, and its fitted memory is
a model choice (*approximation*).

.. _sgi-onyx2:

Onyx2 deskside and rack
=======================

An Onyx2 is Origin 2000 silicon with graphics. The node boards, Hub,
Crossbow, Router and Bridge are the Origin 2000 parts, built by the
``onyx2`` machine on the same stock IP27 PROM. What differs is physical:
a graphics BaseIO (BaseIO-G) in XIO slot 1 and one or more
InfiniteReality ("KONA") graphics pipes. The deskside and the rack attach
a pipe in two different ways, and the firmware names their slots from
two different tables. The pipe's registers are on :doc:`hardware/kona`.

.. _sgi-onyx2-role:

Role
----

The deskside (regulatory model CMN A015) has its own midplane with two
node slots, a Null Router, five XIO slots and four graphics slots. The
pipe's geometry board sits on the midplane and takes XIO slot 4
directly; there is no Ktown board. The rack (CMN A017) is an ordinary
eight-processor compute module plus a separate graphics module holding
up to two pipes. Each pipe reaches the compute module over a Crosstown
cable from an Xtown board in a compute-module XIO slot to a Ktown board
in the graphics module (*established*, :src:`007-3454-005 p. 1-2`,
:src:`007-3454-005 p. 8-9`; :src:`007-3457-005 p. 1`,
:src:`007-3457-005 p. 14`, :src:`007-3457-005 p. 31`,
:src:`007-3457-005 p. 48`).

.. _sgi-onyx2-deskside-slots:

Deskside slots
--------------

From the rear the deskside midplane carries node slots 2 and 1, four
graphics slots (GE, RM/TM, RM/TM, DG5) and five XIO slots numbered 1, 2,
3, 5 and 6. XIO slot 4 is the graphics board set (*established*,
:src:`007-3454-005 p. 8-9`, :src:`007-3454-005 p. 16` Figure 2-2; the
Null Router on :src:`007-3454-005 p. 19`; :src:`007-3439-002 p. 57`).

XIO slot rules (*established*, :src:`007-3454-005 p. 24`): the BaseIO-G
stays in XIO slot 1; the optional three-slot PCI module goes in slot 2
and a SCSI board never does; slots 3 and 5 fill first.

The guide also says there is no functional XIO connection below XIO
slot 3, and its Figure 1-4 draws that position as a solid blank. The
reading is that this one position has no connector because the graphics
set uses XIO 4, not that ``io2`` or ``io6`` are dead: a real deskside
runs boards in both (*inferred*, :src:`007-3454-005 p. 8-9`;
:src:`irixnet-post-32192`). The model offers ``io2``, ``io3``, ``io5``
and ``io6`` for boards fitted at launch.

.. _sgi-onyx2-node-slot-codes:

Deskside node slot codes
~~~~~~~~~~~~~~~~~~~~~~~~

The deskside's two node slots have their own slot codes, ``0x51`` for
``n1`` and ``0x52`` for ``n2``. The PROM's decoder
(:src:`ip27-prom-6.156 0x1fc461fc`) turns the low three bits of the Hub
slot-identity register into them: raw 3 gives ``n1`` and raw 2 gives
``n2``, where an eight-processor module uses raw 7 to 4 for ``n1`` to
``n4``. Only the low three bits decode; raw 0 and 1 decode as invalid
(*software expectation*). A real deskside's IRIX ``hinv`` prints node
memory as ``Module 1/Slot 81`` and ``Slot 82``, the two codes in decimal
(*observed*, :src:`irixnet-post-32192`). The model's deskside node
records carry ``hub-slot-bits`` 3 and 2, which the builder hands each
Hub as its ``slot-bits`` property.

The deskside decode needs bit 0 of the 32-bit word at physical
``0x100000a8`` clear. That word is the configuration-flags field of the
boot flash's configuration block. With the bit set, raw 3 and 2 decode
as ordinary node slots 5 and 6 instead (*software expectation*, the same
decoder and its caller). The real deskside's ``Slot 81/82`` shows it
clear, and the stock image carries it clear, so the model needs no
setting. What the bit means otherwise is *unknown*, and so is what the
deskside midplane drives on the upper identity bits. A deskside midplane
drawing, or a capture that prints the identity register, would settle
the second.

The Origin 2000 deskside is not the Onyx2 deskside. It is the
eight-processor module in a deskside enclosure and uses the module's
Crossbow 0 and 1 tables (*established*, :src:`007-3453-002 p. 1`,
:src:`007-3453-002 p. 19-24`).

.. _sgi-onyx2-two-node:

The two-node deskside
~~~~~~~~~~~~~~~~~~~~~

No inventory lists the Null Router: neither the PROM ``hinv -v`` nor
IRIX's lists one, where the rack lists ``r1`` and ``r2`` (*observed*,
:src:`nekonomicon-16723250`, :src:`irixnet-post-32192`,
:src:`nekonomicon-16285`).

The PROM's partner-node probe tries an empty route, then a one-hop route
out of port 4 or 5 chosen by slot parity, for a deskside slot code;
otherwise it routes through Router port 6 (*software expectation*,
:src:`ip27-prom-6.156 0x1fc470a0`). That this models a direct
Hub-to-Hub link through the Null Router is *inferred*.

In both deskside captures ``n2`` holds node number 0 and ``n1`` node
number 1, and ``n2`` is the global master (*observed*,
:src:`nekonomicon-16723250`, :src:`irixnet-post-32192`,
:src:`nekonomicon-16727032`). The model's deskside boots the same way.
What makes ``n2`` node 0 is *unknown*; the PROM's node numbering for
class 5 slots would settle it. One IRIX ``hinv`` also prints the global
master BaseIO in ``Module 1/Slot io2`` while the BaseIO's hardware-graph
path is ``io1/baseio``; why is *unknown* (:src:`irixnet-post-32192`).

Both node boards are host ports of the one Crossbow. The firmware's
Crossbow record must name each port's Hub by node number: the master
Hub's processor reads every other Hub port's number through a big
window addressed with its own node number (*software expectation*,
:src:`ip27-prom-6.156 0x1fc42758`). In the model a big-window address
reaches the Hub programmed with the node number it carries, like every
other node-qualified address (:doc:`hardware/hub`). With that routing
the record names node 0 at widget 9 and node 1 at widget A, as the real
console's warning-free boot implies.

.. _sgi-onyx2-graphics-module:

Graphics module
---------------

The graphics module holds up to two pipes. Each pipe's boards plug into
the rear of the graphics-module midplane, and the Ktown board sits
between the two board sets. The right-hand pipe, seen from the rear,

chain, between the Ktown board and the GE14
(:src:`origin-onyx2-quick-reference-booklet p. 251`). That this is the
graphics-module midplane is *inferred* from its place in that chain. No
capture shows a graphics-module midplane board record, so that record is
*unknown*.

.. _sgi-onyx2-pipe-link:

How a pipe reaches the compute module
-------------------------------------

Each pipe needs its own Crosstown cable from a Crosstown XIO board
("Xtown") in a compute-module XIO slot to the Ktown board
(*established*, :src:`007-3457-005 p. 48`). The Crosstown board converts
the XIO link's on-board signalling to differential levels for a cable of
up to 3 metres (*established*, :src:`007-3439-002 p. 73`). The Theory of
Operations manual (:src:`007-3439-002 p. 73`, Figure 2-28) calls the
XIO-slot board "the Crosstown (KTOWN) conversion board"; the rack guide
and the captures use KTOWN for the graphics-module board, so this page
calls the XIO-slot board Xtown and keeps Ktown for the graphics-module
end.

The host's path ends at the GE board's XIO-to-graphics ASIC (XG): the
booklet's "XBOW-to-GE14 path" lists the midplane, the XIO board, the
Crosstown cable, the Ktown board, the KCAR midplane and the "GE14
(XGASIC)" (*established*,
:src:`origin-onyx2-quick-reference-booklet p. 251`;
:src:`007-3454-005 p. 28`). The Xtown and Ktown are therefore link

.. _sgi-onyx2-populations:

Node-board populations
----------------------

Both chassis ship with fewer node boards than they hold, filled from
``n1``.

Deskside: the standard deskside has one node board, the entry level one
processor, and a second board is an option. The first node board always
sits in the right-hand slot, ``n1`` (*established*,
:src:`007-3454-005 p. 1-2`, :src:`007-3454-005 p. 21`). With one node
board, ``n1`` is the only Hub on the one Crossbow (widget A), so it
controls every widget (*inferred*); widget 9, where ``n2`` would be, is
an empty port. The rack guide says the Null Router is used in desksides
with one or two node boards (:src:`007-3457-005 p. 45-47`), so a real
one-node deskside probably carries one with its far end empty. The
model's one-node row fits no link at all; that the two are the same to
firmware is *inferred*.

Rack: a single rack holds two to eight processors, and the booklet lists
a one-node, one-pipe system with node 1 controlling the BaseIO-G and the
Xtown in ``io2`` to ``io6`` (*established*,
:src:`origin-onyx2-quick-reference-booklet p. 131`). The rack guide
names the Null Router for one or two node boards and the Star Router for
a single-rack Onyx2 with three or four (:src:`007-3457-005 p. 45-47`). A
real rack's module 1 carries Router board records with two node boards
and later with four (*observed*, :src:`nekonomicon-16285`). The model's
rack rows are the Origin 2000 rack module's: no Router for one node, two
Standard Routers from two. The pipe's Xtown in ``io3`` is Crossbow 0
widget F, which ``n1`` controls at every count, so one pipe needs only
one node board.

.. _sgi-onyx2-widget-selection:

How firmware chooses the widget map
-----------------------------------

There is no machine-type word for an Onyx2. The stock PROM's
widget-to-slot routine picks a table from the hardware, in this order
(*software expectation*, :src:`ip27-prom-6.156 0x1fc419cc`):

1. Widgets outside 8 to 15 give an invalid slot.
2. The routine reads the local node's slot code. A code of class 5, an
   Onyx2 deskside node slot, selects the deskside table. Only Crossbow 0
   is legal on a deskside; any other Crossbow prints an error and gives
   an invalid slot.
3. Otherwise a nonzero machine-type word at physical ``0x10000090``
   selects the Origin 200 GIGAchannel table (:doc:`hardware/gigachannel`).
4. Otherwise the Crossbow number picks the Crossbow 0 or Crossbow 1
   table of the eight-processor module. An Onyx2 rack takes this path
   and is named exactly as an Origin 2000.

Recognition is by slot code. An Onyx2 deskside is the only chassis whose
node slots decode to class 5. An Onyx2 rack compute module is an Origin
2000 module; what makes it an Onyx2 is the hardware in it: a BaseIO-G
with MediaIO, one or more Xtown boards and KONA widgets behind them. The
model therefore builds the deskside from its midplane's slot values and
a KONA widget at widget 8, and the rack from an Origin 2000 module with
a BaseIO-G and a KONA widget on an Xtown slot.

.. _sgi-onyx2-pipe-identity:

Pipe identity
-------------

The pipe's XIO identity, the PROM's classification of it and the widget
revision are on :ref:`sgi-kona-identity`. The deskside pipe presents the
same identity: its PROM prints the KONA graphics board in ``io4``
(*observed*, :src:`nekonomicon-16723250`). The same deskside's IRIX
``gfxinfo -v`` reports "KONAL" graphics with its GE, RM, TM and DG
records (*observed*, :src:`irixnet-post-32192`). That the PROM's
classification follows from that identity is *inferred*, and so is that
both chassis end the host path at the same XG ASIC, which accounts for
the shared identity.

The IRIX 6.5.30 kernel accepts a widget as a pipe only if firmware wrote
a matching graphics board record into the node's configuration data: it
builds its pipe list from those records, keyed by module and ``io``
slot, and rejects a widget with no matching entry (*software
expectation*). On a deskside the entries come from the deskside table,
so the pipe must be widget 8 for firmware to name its board ``io4`` and
for IRIX to find it.

.. _sgi-ip27-address-map:

Address map
===========

Every node shares one 40-bit physical address space. The node number is
bits 39:32 (M mode), so each node owns a 4 GiB window and a node's
resources sit at its base plus the number shifted left 32 (*established*,
Linux ``asm/sn/sn0/addrs.h``; OpenBSD ``hub.h``). OpenBSD reads the mode
from a Hub network-interface status bit rather than assuming it, and the
model resets that bit to M mode (:doc:`hardware/hub`).

The processor drives a two-bit uncached attribute beside the address,
recorded in virtual-address bits 58:57, which picks one of four spaces
(*established*, Linux ``mach-ip27/spaces.h``):

.. list-table::
   :header-rows: 1

   * - Processor address, node 0
     - Space
     - Attribute
   * - ``0xa800_0000_0000_0000``
     - cached memory
     - none
   * - ``0x9600_0000_0000_0000``
     - uncached memory
     - 3
   * - ``0x9000_0000_0000_0000``
     - Hub special
     - 0
   * - ``0x9200_0000_0000_0000``
     - I/O
     - 1
   * - ``0x9400_0000_0000_0000``
     - memory special (fetch-and-op)
     - 2
   * - ``0xffff_ffff_a000_0000``
     - compatibility uncached segment, node-local physical
       ``0x0000_0000`` to ``0x1fff_ffff``; the reset vector is
       ``0xffff_ffff_bfc0_0000``
     - 3

The bases are the public headers'. Linux states that attribute 3 selects
uncached memory; the other three numbers follow from bits 58:57 of each
base (*inferred*). The model carries the attribute as bits 41:40 of a
42-bit machine bus address, rotated so plain memory is window 0: Hub
special at ``0x100_0000_0000``, I/O at ``0x200_0000_0000`` and memory
special at ``0x300_0000_0000``. That is an emulator representation, not
hardware; qtests and the monitor speak it.

Node offsets in each space (*established* from the Linux and OpenBSD
headers):

.. list-table::
   :header-rows: 1

   * - Space and node offset
     - Size
     - Contents
   * - memory, bank × 512 MiB
     - up to 512 MiB a bank
     - Node memory: eight banks on IP27, four on IP29
       (:ref:`sgi-ip27-memory`).
   * - memory, ``0x1fc0_0000``
     - 1 MiB
     - Boot flash reset view (:ref:`sgi-ip27-bank0-flash`).
   * - I/O, widget × 16 MiB
     - 16 MiB each
     - Small window onto widget 0 to 15.
   * - I/O, ``0x0100_0000``
     - 8 MiB
     - Hub registers of the reader's own node, addressed with node
       number 0.
   * - I/O, ``0x0180_0000``
     - 8 MiB
     - Hub registers of the node named in the address.
   * - I/O, ``0x2000_0000`` + n × 512 MiB
     - 512 MiB each
     - Big windows 0 to 6, each a programmable slice of a widget.
   * - Hub special, ``0x0000_0000``
     - 256 MiB
     - The reader's own node memory, uncached; the low 128 KiB is private
       to each processor of the pair.
   * - Hub special, ``0x1000_0000``
     - 256 MiB
     - The reader's own boot flash.
   * - Hub special, ``0x2000_0000``
     - 256 MiB
     - The named node's uncached memory.
   * - Hub special, ``0x3000_0000``
     - 256 MiB
     - The named node's boot flash.
   * - Hub special, ``0x8000_0000`` and ``0xc000_0000``
     - 1 GiB each
     - Back doors onto the ECC bytes and the directory entries.

The Hub's own register window splits into its processor, memory,
I/O and network interfaces at offsets ``0x00_0000``, ``0x20_0000``,
``0x40_0000`` and ``0x60_0000``; :doc:`hardware/hub` describes them and
the back doors. The boot flash views are on :doc:`prom-image`.

On the Origin 200 the Hub's XIO link goes straight to the IP29 board's
Bridge with no Crossbow (*established*, :src:`007-3708-002 p. 6-7`,
Figures 1-4 and 1-5). The Bridge therefore answers every small window
except widget 1, the Hub itself; firmware numbers it widget 8. On the
Origin 2000 and Onyx2 each widget number reaches the port of that number
on the node's Crossbow (:doc:`hardware/xbow`).

.. _sgi-ip27-power:

Power and reset domains
=======================

A module has three power domains (*established* except where marked):

.. list-table::
   :header-rows: 1

   * - Domain
     - Fed by
     - Contains
   * - Standby
     - the supply's 5 V auxiliary output, present whenever the master
       switch (Origin 200) or circuit breaker (Origin 2000) is on
     - the module system controller and its serial port
       (:src:`007-3708-002 p. 97-98`; :src:`108-0164-002`, appendix A)
   * - Module
     - the supply's main outputs, switched by the controller
     - everything else: node boards, Routers, Crossbows, base I/O, XIO
       and PCI boards, disk bays (:src:`007-3708-002 p. 97`;
       :src:`007-3456-003 p. 113`; Router and XIO membership on the
       Origin 2000 *inferred* from the single switched supply)
   * - Battery
     - a cell inside the part
     - the base I/O Timekeeper's clock and RAM

The controller issues the reset at power-on (:src:`007-3456-003 p. 113`).
An Origin 2000 rack's modules are independent power domains: "if you
power off an individual module, the other module(s) in the configuration
can still operate fully" (:src:`007-3456-003 p. 82`). An Origin 200
master controller forwards power-up and power-down to its slave
(:ref:`sgi-elsc-master-slave`). A GIGAchannel cabinet's switched domain
follows the module it is attached to (*established*,
:src:`108-0187-001 p. 3-7`, :src:`007-3709-002 p. 2`;
:ref:`sgi-gigachannel`).

The R10000 distinguishes three entries by its Status register: a cold
reset (``SR`` clear, mode bits reloaded), a soft reset (``SR`` set,
``NMI`` clear) and an NMI (both set) (*established*,
:src:`r10000-users-manual-2.0 p. 337-339`). The stock PROM tests these
bits first and takes its NMI path, a separate soft-reset path or the
cold-start path (*software expectation*,
:src:`ip27-prom-6.156 0x1fc00854`, :src:`ip27-prom-6.156 0x1fc00c20`).

What the model does:

- A controller's ``pwr d``, ``pwr c`` and ``rst`` act on its own module.
  The machine derives the module's parts from the topology: its node
  boards with their Hubs, boot flash and everything behind them, its
  Routers, Crossbows and I/O boards, and any board in its XIO slots. The
  controller is in none of it.
- Power off resets and halts the module's processors with their Hub's
  processor enables clear. Power on, and ``rst``, cold-start the module:
  every part resets and the processors run from the reset vector. Memory
  keeps its bytes, an *approximation* the PROM's own memory
  initialisation hides. Other modules keep running.
- While a module is off its Hubs refuse register accesses and inbound
  XIO packets with the bus's unassigned-access result, its I/O windows
  are disabled and its Routers answer no vector access. Its ports read
  down to their peers. The Hub's I2C adapter window keeps answering from
  the module's own view, so the standby controller stays reachable.
- A Hub network-interface port reset with bit 0 set restarts the whole
  machine, not one node: every module with power cold-starts together
  and the standby controllers are not reset, so the PROM sees a warm
  start. Every software reboot path writes bits 7 and 0 together, so no
  supported guest sees the difference from the node reset the Hub
  describes (*approximation*; :ref:`sgi-hub-link-reset`).
- ``system_reset`` is an AC cycle: every module and controller starts
  over. Once every module is off with no power-up to come the machine
  powers down; IRIX 6.5.30 sends ``pwr d 1`` at ``shutdown -p`` (*software
  expectation*; :doc:`hardware/elsc`).
- The controller's NMI output and the Hub's per-processor NMI trigger
  reach each processor through an OR gate, so neither hides the other.

Whether ``rst`` reaches the Routers, Crossbows and XIO boards, whether it
gives the processors a cold or a soft entry, and which Hub error
registers survive it are *unknown*; the model resets every part and gives
the cold entry.

.. _sgi-ip27-power-implementation:

How the model sequences module power
------------------------------------

The cold start of a module runs from a bottom half and not from the
controller's own timer. It stops the module's processors with work queued
on each of them and does not wait. The last completion schedules the rest
of the start (the parts' reset and the processors' release) as a bottom
half, so the start never blocks on a processor thread and runs under
record and replay, where that thread needs a lock the main loop holds. A
processor that runs no guest code, in a paused machine or under qtest, is
stopped on the spot, and a start with no running processor to wait for
goes on at once. The start is owed until that bottom half has run, so a
start owed when a migration stream was taken, including one still
waiting for its processors, is part of that stream and is carried out
once the destination runs.

The module start also resets every Crossbow the module's nodes reach and
the boards behind them. Whether a module reset reaches the Crossbows and
XIO boards on hardware is *unknown*. A midplane schematic or a register
capture across a module reset would settle it. The stock IP27 PROM sends
a warm reset down each XIO link on every cold entry (*software
expectation*), and a Crossbow treats one as a power-on reset of its core
(*established*, :src:`crossbow-asic-spec-12.0 pp. 132-133`). The firmware
therefore resets them either way. The model resets them at module start
as well, because the PROM's warm reset does not reach a Bridge's PCI
side, and the stock PROM cannot read a Bridge that kept a running
kernel's PCI setup.

While a module is off its ports read disabled to their peers, the state a
cable marked down already has. A peer Hub reads link-up zero with the
down reason clear, which Linux ``hubni.h`` defines as a link that failed
(*software expectation*). Treating a lost peer as failed and not as never
reset is an *approximation*. A peer Router reads the port not working.
Whether a Router port facing a lost peer reads reset-failed is *unknown*,
and the model leaves it clear. Power returning brings the links up
through the normal flood after the module's parts have reset and before
its processors run. An off module keeps its register state until the
reset that comes first at power-up.

Power state is derived from the controllers' power, which migrates, so
none of it does. It is applied when a machine starts running and after
the machine's own reset, and by the machine's migrated section, which
loads after every device, so a load shows the right gating even while
the destination is paused.

The Hub's I2C adapter window is the one register window that keeps
answering while its module is off, and only from the off module's own
view. A peer module's access to it fails like the rest of the Hub. The
adapter is a Hub register window, and the Hub is in the module's switched
power domain (*established* for the Origin 200,
:src:`007-3708-002 p. 97`, and for the Origin 2000 rails,
:src:`007-3456-003 p. 113`). On hardware the adapter is therefore off
with the module and no host could use it (*inferred*). Keeping it
answering is an *approximation*. It keeps the host side of the standby
controller reachable over the module's own bus, which the controller
tests and the Origin 200 controller's grants rely on. In the
model an operator reaches an off Origin 2000 module's controller through
its serial line, and an off Origin 200 slave's through its master. The
slave has no connector of its own, and a ``pwr u`` the master accepts
while it is itself off powers the master up, whose forward then starts
the slave (:ref:`sgi-elsc-master-slave`). A ``pwr u`` sent to a master
that is already on has nothing to power up and forwards nothing, so the
model has no way to start only the slave from a peer's bus. No topology
with more than one Origin 2000 module is built, so the several-module
Origin 2000 path is the same code as the Origin 200 pair's and is only
exercised there.

.. _sgi-ip27-cache:

Cache configuration
===================

Every Origin 2000 and Onyx2 processor has 1 MiB of secondary cache, the
size the stock PROM's mode word encodes and the 180 MHz assembly the
booklet documents (:ref:`sgi-origin2000-reset-mode`). The primary caches
are 32 KiB each, hardwired (*established*,
:src:`r10000-users-manual-2.0 p. 165`). A processor's CP0 Config at reset
is the mode word's bits 24:0 with the hardwired primary-cache fields
above them: ``0x6c11a785`` for the stock word (*inferred*, arithmetic on
the manual's fields). :doc:`hardware/r10000` describes the identity
words and the cache model.

The 4 MiB, 195 MHz composition is documented hardware
(:src:`108-0164-002 p. E-4`; :src:`007-3439-002 p. 33`), and its mode
word ``0x1213a785`` is in the architecture layer. No Origin 2000 or
Onyx2 topology selects it. The only 4 MiB configuration is the Origin 200
R12000 module (:ref:`sgi-ip27-processors`), and no test exercises 4 MiB
indexing. All node boards in a system
must be the same speed (*established*, :src:`108-0164-002 p. E-2 to E-3`);
the model applies one mode word to every processor. The Origin 200
modules' caches are in :ref:`sgi-ip27-processors`.

.. _sgi-ip27-firmware:

Firmware and boot
=================

The machines boot only a stock IP27 PROM, given with ``-bios`` or bound
per node as ``node<N>-flash``. ``-bios`` takes a raw image or SGI's
distribution container; :doc:`prom-image` describes both, the node
flash, the template a node with no image starts from and the
configuration values the machine patches into each block
(:ref:`sgi-prom-image-ip27-values`). The Origin 200 block carries machine
type 1, which OpenBSD reads as an Origin 200; the Origin 2000 and Onyx2
keep the stock image's type 0. ``-kernel`` is refused: a guest reaches
its kernel through the PROM's netboot or a disk.

The Origin 2000 and Onyx2 BaseIO cards and the GIGAchannel cabinet carry
their own BASEIO PROM flash. The ``io-prom`` machine property stores an
original I/O PROM image in every such part with no drive bound, and
``io<N>-flash`` binds one (:ref:`sgi-baseio-flash`). With neither, the
IP27 PROM finds no valid image there, reports it, and runs its own
internal copy of the BASEIO PROM (*software expectation*,
:src:`ip27-prom-6.156`).

Writable stores, each bound through the machine property of the same
name (:ref:`sgi-sn-storage`):

- ``node<N>-flash``, 1 MiB, one per node board;
- ``io<N>-flash``, the BASEIO PROM flash of each BaseIO card or
  GIGAchannel cabinet;
- ``nvram<N>`` and ``nvram<N>-clock``, each base I/O board's Timekeeper
  NVRAM and clock record;
- ``module<N>-nvram``, the 2048-byte NVRAM of each module's system
  controller (:ref:`sgi-elsc-nvram`).

Launch notes, emulator choices rather than hardware facts:

- The console is the first IOC3 UART of the console node's base I/O.
  Serial backends are assigned node by node, six lines each: IOC3 port

   * - ``origin2000-rack``, ``origin2000-deskside``
     - every empty XIO slot, ``io2`` to ``io12``; ``io7`` up from two
       nodes
     - none
     - every IMPACT product
   * - ``onyx2-deskside``
     - ``io4``, widget 8
     - ``ir2``: GE14-4, two RM7, ``dg5-8``
     - ``ir2``, ``ir2e``; one or two RMs; ``dg5-8``, ``dg5-2``
   * - ``onyx2-rack``
     - ``io3``, the Xtown's slot, Crossbow 0 widget F
     - ``ir3``: GE16-4, one RM, 256 MB texture, ``dg5-2``
     - ``ir2e``, ``ir3``; one, two or four RMs; ``dg5-2``, ``dg5-8``

The Origin 200 and Origin 2000 fit no pipe by default and may run
without one. Each Onyx2 topology fits its default unless a graphics
``-device`` replaces it; ``-vga none`` leaves it out, though SGI sold no
Onyx2 without a pipe. The deskside default is the captured deskside's
(:src:`irixnet-post-32192`). The rack default is the captured rack's
configuration (:src:`nekonomicon-16285`) with a plain DG5-2 in place of
its DG5-2 with GVO, which has no video output in the model; the plain
DG5-2 presents 030-1055-001, the part :src:`sgi-pca-numbers` gives for
a DG5-2, since no capture shows a plain DG5-2 in an
Onyx2 rack (*approximation*). A pipe in either slot takes that slot's board
records (:ref:`sgi-onyx2-one-wire`).

The catalogue refuses, with its reason: an InfiniteReality pipe on an
Origin 2000 (that machine is an Onyx2) or on the Origin 200's
GIGAchannel cabinet slot (the other Origin 200 slots take only PCI
cards); four RMs in the deskside, which has no Ktown; an
InfiniteReality3 in the deskside, which no source places there; and a
GE14 InfiniteReality2 in the rack. On the Origin 2000 a launch that fits
a pipe should add ``baseio-preset=io6g``: the plain BaseIO has no
keyboard or mouse port, and the BaseIO-G's MediaIO daughtercard has them
(:ref:`sgi-baseio-g`). The machine does not add it itself, because the
BaseIO is built before any ``-device`` exists.

The PsiTech RAD1 is a plain PCI card on the Origin 200's Bridge,
``-device psitech-rad1,addr=N`` (:doc:`hardware/psitech-rad1`). It is not
a catalogued pipe, so the machine does not check its placement.

.. _sgi-ip27-unknowns:

Open questions
==============

Origin 200 and Origin 2000:

- Which source a real Origin 200 node takes its processor configuration
  from on every boot, flash block or module (:ref:`sgi-ip27-processors`).
- The processor and device split at a 512 MiB bank 0
  (:ref:`sgi-ip27-bank0-flash`).
- What a Hub does with a vector request that arrives with route steps
  left, which decides whether the stock PROM discovers a Star deskside.
- Whether a one-node deskside or rack module carries a Router board.
- Which controller a real three-node module gives IO8, IO10 and IO12.
- The MSC's I2C address, the physical EEPROM count and the UST control
  part (:ref:`sgi-origin2000-module-management`).
- Which midplane record an IP27-era module carried.
- How the firmware compares the flash mode word with Config.
- What ``rst`` reaches and which processor entry it gives.

.. _sgi-ip27-tests:

Tests
=====

qtests:

- ``tests/qtest/sn0-origin2000-test.c``: the four-node module's remote
  interrupts, processor mode reset, Crossbow links and warm reset,
  Router inventory and routes, block transfers, firmware supply checks
  migration, and the port reset restarting the machine on the Origin
  2000 and the Onyx2 deskside.
- ``tests/qtest/sn0-onyx2-test.c``: the pipe at ``io3`` on the rack and
  ``io4`` on the deskside, each pipe's board-record chain and product,
  and the deskside's peer Hubs naming each other.
- ``tests/qtest/sn0-module-management-test.c``: the shared Origin 2000
  module bus, separate adapters, one controller, shared NVRAM, the UST
  control port, the module serial and midplane parts, grants, and the
  controller's power, reset and NMI outputs.
- ``tests/qtest/sn0-module-domain-test.c``: module power and reset
  reach, off-module gating, Origin 200 master and slave forwarding,
  port resets and migration of a pending start.
- ``tests/qtest/sn0-address-map-test.c``: the node address map and back
  doors, and the per-node bank layouts, including the 512 MiB bank 0.
- ``tests/qtest/sgi-graphics-pipes-test.c``: the graphics-pipe placement
  and refusals.

Functional tests, which boot the stock PROM:

- ``tests/functional/mips64/test_origin200_prom.py`` and
  ``test_origin200_gigachannel_prom.py``: the Origin 200 topologies.
- ``tests/functional/mips64/test_onyx2_deskside_prom.py`` and
  ``test_onyx2_rack_prom.py``: the slots the PROM's ``hinv -v`` names on
  each Onyx2 chassis.
- ``tests/functional/mips64/test_origin2000_cache_reset.py``: each
  processor's secondary-cache field at reset, with test ROMs.
