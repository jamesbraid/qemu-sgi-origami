.. _sgi-ip30:

========================
IP30: Octane and Octane2
========================

The ``octane`` and ``octane2`` machines (``hw/mips/sgi/octane.c``) each
build one :term:`IP30 <IP number>` board with one processor, a serial console and the
onboard I/O, booting a stock IP30 :term:`PROM` that the user supplies. Each fits
a default graphics pipe, which ``-vga none`` leaves out and a graphics
``-device`` replaces (:ref:`sgi-ip30-graphics`); the boards themselves
are outside this page. This page is the hardware contract
the machine models in ``hw/mips/sgi/models/`` cite for these two
products: what is fitted, how it is wired, what the emulator chose
where the hardware is not known, and which sources back each statement.

Facts are rated as described in :ref:`sgi-ratings`.

The two machine names select two fitted populations, not two hardware
architectures. Register behaviour follows the fitted chip and board
revisions, not the product badge: SGI sold upgraded older boards under
the Octane2 name, and some Octane2 changes reached older systems
(:src:`sgistuff-octane`).

.. _sgi-ip30-processors:

Processors
----------

``octane`` fits an R10000 at 195 MHz with 1 MiB secondary cache
(*observed*, :ref:`sgi-ip30-products`; the cache size is *inferred*). Its processor identification
word ``0x927`` is *inferred*: Linux ``cpu.h`` gives the R10000
implementation code ``0x09``, and the published inventory reports chip
revision 2.7. No raw PRId read was published.

``octane2`` fits an R12000 at 360 MHz with 2 MiB secondary cache
(*established*, :ref:`sgi-measured-octane2-hinv`). The catalogue supplies its
identity, reset mode word and cache geometry, so ``-M octane2`` starts
without CPU options.

CP0 Count runs at half the processor clock
(:src:`r10000-users-manual-2.0 section 14.8`, *established*), 97.5 MHz on
``octane`` and 180 MHz on ``octane2``. Both machines turn on the CPU's
count-sample window, which keeps the IRIX scheduler tick from being lost
when the host delays a vCPU. :doc:`hardware/r10000` describes the identity
words, the reset mode word and that window.

.. _sgi-ip30-memory:

Memory kits and capacity
------------------------

Both owner's guides describe four DIMM banks of two sockets each. Bank 1
must be filled, banks fill in order without gaps, and each populated
bank holds two DIMMs of the same capacity and type (*established*:
:src:`007-3435-004 p. 54`, :src:`007-4207-002 p. 47`).

- Octane (:src:`007-3435-004 p. 54-55`): 32, 64, 128 and 256 MB DIMMs, so
  64 to 512 MiB a bank and at most 2 GiB. The guide sets no order of
  bank sizes.
- Octane2 (:src:`007-4207-002 p. 47`): DIMMs from 32 MB to 1 GB, so 64 MiB
  to 2 GiB a bank and at most 8 GiB, highest-density DIMMs in bank 1
  and the rest in descending order.

An SGI engineer wrote in 2000 that the older IP30 board stops at 2 GB and
that board ``030-1467-001``, which the ``octane2`` profile carries, takes
2 GB memory kits (:src:`usenet-39b750e0`), *observed*, agreeing with the
owner's guides.

The catalogue carries each product's rule as ``accepted_bank_sizes_mib``
(64 to 512 on ``octane``, 64 to 2048 on ``octane2``) and, for
``octane2``, ``bank_order: descending``. The generator emits the bank
sizes, the order rule and every total one to four banks make (27 totals
on ``octane``, 79 on ``octane2``). ``-m`` alone fills the fewest banks,
largest first: ``-m 3072`` on ``octane2`` is 2048+1024. ``bank<N>-size``
selects a layout explicitly; setting any bank leaves the unset ones
empty, and the banks must hold exactly ``-m``. Anything else is
refused with the rule it breaks.

.. list-table::
   :header-rows: 1

   * - Kit
     - DIMMs
     - Bank
     - Default of
   * - ``kit-128``
     - two 64 MiB
     - one 128 MiB bank
     - ``octane``
   * - ``kit-256``
     - two 128 MiB
     - one 256 MiB bank
     - ``octane2``

The default kits are model choices (*approximation*): the profiles'
inventories report only their totals. The guides number physical banks
1 to 4; public software indexes HEART bank descriptors 0 to 3. Treating
them as the same positions is *inferred*, not a measured board wiring fact.

The stock 6.5.30 PROM sizes each bank itself and writes HEART's bank
descriptors; the IRIX 6.5.30 kernel only reads them. How the model answers
the PROM's probe, and the density codes the PROM then writes, are on
:ref:`sgi-heart-memory`.

.. _sgi-ip30-topology:

Topology and population
-----------------------

Each product has one :term:`node` (the IP30 board), one processor and no
fabric. Dual-processor Octanes exist (Technical Report page 7-1) but are
not modelled; the
capacity notes restrict both machines to the single-processor profile.
This is a scope limit, not a hardware claim.

Revisions fitted by the model (``widget_revision`` in the module
layers):

  prints HEART revision D and Xbow ASIC revision 1.2; IRIX's lettered
  and dotted forms are not the raw register fields, and their mapping is
  *inferred*, not *established*.
- ``octane2``: HEART widget identification word ``0x6c00106d`` (revision 6,
  part ``0xc001``, manufacturer ``0x36``), read on the reference Octane2 from
  the PROM monitor (:ref:`measured <sgi-heart-octane2-id>`) and consistent
  with its inventory's HEART revision F (*established*). Crossbow revision
  5, from a PROM-monitor read of its identification word ``0x50000001``
  (:ref:`measured <sgi-xbow-octane2-id>`) beside an inventory revision of

  identification word ``0x4c00206d``
  (:ref:`measured <sgi-bridge-measurements>`), *established*; the Bridge
  specification letters revision 4 as D (:src:`bridge-asic-spec-4.0 p.
  19`).

The machine hands the module's Bridge revision to the Bridge, so
``octane`` reports revision 3 and ``octane2`` revision 4 in the Bridge
identification word (:doc:`hardware/bridge`).

IOC3 general-purpose pin 2 is read by OpenBSD to tell the two products
apart. ``ip30.h`` comments it as 1 for the classic Octane and 0 for the
Octane2 (``IP30_GPIO_CLASSIC``), and ``ip30_machdep.c`` lines 193-202
read pin register 2, IOC3 offset ``0x48``, and name the machine Octane
when it is nonzero, a *software expectation*. Mainline Linux does not
read the pin. The reference Octane2, board ``030-1467-001`` revision B,
reads 1 in pin register 2 and bit 2 set in the pin data register at
``0x3c`` after PROM start-up (:ref:`measured <sgi-ioc3-octane2-pins>`); pin register 3
also reads 1. This is *established* for that board. OpenBSD's rule would name it an Octane, so
the comment does not hold for this board, and what the pin senses is
*unknown*. The measurement outweighs the driver comment, so both
machines drive IOC3 inputs 2 and 3 high, as the reference board reads
them. No input tells the two products apart. The classic Octane's inputs
are unmeasured, so matching the Octane2 there is an *approximation*. Pin
8 also reads high on the reference Octane2 and is not modelled. Whether
the inputs are board straps or floating pull-ups is *unknown*. OpenBSD
names both machines an Octane, as it would the reference unit if it
samples the same pin.

The board's IOC3 drives the front lightbar from pins 0 (white) and 1
(red), high meaning lit. Red's polarity is *established* for the
reference Octane2, and white's follows mainline Linux's LED driver, a
*software expectation*. The IOC3
publishes the two lamps as read-only properties (:doc:`hardware/ioc3`).
The board has no other lamp model.

The onboard IOC3 repeats its first 32 configuration bytes in the next 32,
as the reference Octane2's chip does, so a guest reads no subsystem
registers and no interrupt pin from it; Linux takes the board id from its
Bridge table instead (:doc:`hardware/ioc3`). The first five dwords of its
register block read the configuration header, and pin control clear reads
the control word.

.. _sgi-ip30-address-map:

Processor address map
---------------------

A *software expectation* from OpenBSD ``ip30.h`` and ``ip30_machdep.c``,
with Linux ``ip30-xtalk.c`` and ``mach-ip30/spaces.h`` agreeing on the
widget windows and the memory offset:

.. list-table::
   :header-rows: 1

   * - Physical address
     - Contents
   * - ``0x10000000 + (widget << 24)``
     - 16 MiB small window for each widget
   * - ``2^35 + (widget << 31)``
     - 2 GiB window for each widget: bit 35 set, the widget in bits 34:31
       and the widget offset in bits 30:0. Present for the onboard Bridge
       (widget 15) and for each fitted board; see below
   * - ``widget << 36``
     - 64 GiB large window for each widget
   * - ``0x1fc00000``
     - Bridge PROM aperture: widget 15's small window at offset
       ``0xc00000``, 2 MiB long; *inferred* to be the reset fetch address
       from that placement
   * - ``0x1fe00000``
     - alternate PROM aperture, widget 15 offset ``0xe00000``
   * - ``0x20000000``
     - first SDRAM address. The model makes the first 16 KiB,
       ``0x20000000`` to ``0x20003fff``, fail with a bus error and log
       ``LOG_UNIMP``, above every bank view and ECC overlay, an
       *approximation*: what a real HEART answers there is *unknown*

The IRIX 6.5.13f kernel chooses among the three windows by the end of the
range it maps, so a mapping that ends within 16 MiB of a widget's offsets
uses the small window, one that ends past that and within 2 GiB uses the
2 GiB window, and one that ends within 64 GiB uses the large window. It
takes the widget
number from its widget registry, not from a HEART or Crossbow register, and
its inverse for an error address reads all three windows back to a widget
and offset (:src:`ip30-kernel-6.5.13f 0xa800000020077be4`,
:src:`ip30-kernel-6.5.13f 0xa8000000200785f8`). That is a *software
expectation*; the 6.5.22 and 6.5.30 kernels form the same addresses
(*inferred* from matching routines). Every PCI memory mapping through a Bridge
(widget offsets from ``0x40000000``) ends past 16 MiB and within 2 GiB, so
IRIX reaches PCI memory behind the PCI module's Bridge at ``2^35 +
13 * 2^31 + 0x40000000 + <PCI address>``. A BAR at PCI address
``0x08000000`` and a 4-byte register at its offset ``0x40`` is then at
physical ``0xec8000040``. No manual describes HEART's decode of this
window. That a real Octane decodes it follows from IRIX relying on it for
every Bridge PCI memory mapping, and is *inferred*; nothing measured it.
The model maps it for the same widgets as their large window, onto the
same XIO offsets, so it carries the widget offset with no bit 47, the same
*inferred* detail as the large window, and the uncached processor
attribute reaches it as it reaches every address. Widget 0 and the
widgets with no board answer neither the 64 GiB nor the 2 GiB window, an
*approximation*: what a real HEART does with them is *unknown*.

.. _sgi-ip30-space-selection:

Address-space selection
~~~~~~~~~~~~~~~~~~~~~~~

The architecture layer records the selector as a two-bit processor
attribute in virtual-address bits 58:57, giving four spaces. The
R10000 family drives such an uncached attribute beside the address,
and the public :term:`SN0` header (Linux ``arch/mips/include/asm/mach-ip27/spaces.h``)
documents its use on :term:`Hub` systems. That HEART decodes it the same way is
*inferred* from the shared processor family, not *established*; no public
HEART specification describes it.

  family (``0x0b``). OpenBSD's ``owserial.c`` accepts a two-page record

  code drivers match on, then the ``EMU`` marker. None is taken from a
  real machine.
- Physical ROM serials, page checksums, padding and unused memory on real
  IP30 boards are *unknown*.

.. _sgi-ip30-system-id:

System id
---------

IRIX reports a 32-bit system id through ``sysinfo -s`` and, as the
FLEXlm host id, through ``lmhostid``. On an Octane it is the last four
bytes of the onboard station address, so a card at
``08:00:69:0b:ea:40`` gives ``0x690bea40``, decimal 1762388544
(*inferred*). The basis is public newsgroup posts that show an Octane's
``sysinfo`` output next to its station address, and a reply that gives
the same rule. No IP30 kernel was available to
confirm which source the kernel reads, the IOC3 Ethernet-address part or
the PROM's copy of it, and the model gives both the same address.

The model keeps no separate system id. It follows the ``mac`` property:
the address in the IOC3 Ethernet-address part (:doc:`hardware/ioc3`). With
no ``mac=`` the address comes from the machine's identity inputs
(:ref:`sgi-identity`): ``emu-id=42`` gives ``08:00:69:e1:02:a0`` and the id
``0x69e102a0``, and no input gives ``08:00:69:e1:00:00``. ``hostid=`` sets the
address directly, as 8 digits starting ``69`` or as the 6-digit shorthand with
the ``69`` implied, so ``hostid=0bea40`` gives ``08:00:69:0b:ea:40``.
``serial=`` is accepted only when its text folds to an id starting ``69``.
``mac=``, ``hostid=`` and ``serial=`` must agree when more than one is given.
The id is therefore never zero and differs between guests with different
inputs. The read-only ``hostids`` property reports the id from the address the
machine holds. A guest started with no input shares the ``emu-id`` 0 id with
every other such guest. These ids are synthetic and are not any machine's
factory identity. The register-level station address and ``hostids`` are
tested, and Octane and Octane2 guests printed the last four bytes of their
station address as ``lmhostid`` (*software expectation*, measured on
this model).

.. _sgi-ip30-missing:

Missing devices
===============

- The second processor of dual-processor Octanes. Both machines are
  single-processor (:ref:`sgi-ip30-topology`).
- The expansion Bridge and its four PCI slots. Its widget number is
  *unknown*, so no slot is offered.
- A visible front lightbar. The IOC3's pins 0 and 1, which OpenBSD
  names the white and red lights (``ip30.h``, a *software expectation*),
  reach only the IOC3's ``lightbar-white`` and ``lightbar-red``
  properties and a trace event (:ref:`sgi-ip30-components`). The
  reference Octane2 runs both pins as outputs, pin 0 high and pin 1 low,
  at the PROM menu (:ref:`sgi-ioc3-octane2-pins`).

.. _sgi-ip30-firmware:

Firmware and boot
=================

The machines boot only a stock IP30 PROM, given with ``-bios`` or bound
as ``node0-flash``. ``-kernel`` is refused.

.. _sgi-ip30-flash-wiring:

Boot flash wiring
-----------------

What is known:

- The Bridge ASIC provides two 2 MiB flash regions, at widget offsets
  ``0xc00000`` and ``0xe00000``. A strap pin, read back as status bit 6,
  chooses which chip select answers at the lower region: 0 for chip
  select 0, 1 for chip select 1 (*established* for the ASIC,
  :src:`bridge-asic-spec-4.0 p. 20 and 115`). Its target parts are 256K
  or 512K 16-bit words.
- OpenBSD names the same two apertures (``ip30.h`` lines 49-55).
- Two IP30 board families exist, ``030-0887`` and ``030-1467`` (the
  inventories; the SGIStuff page describes the board change). Neither
  source identifies a flash part.
- On the :ref:`sgi-measured-octane2`, board ``030-1467-001`` revision B,
  the Bridge status word reads ``0x62``: the strap is 1, so chip select 1
  is the boot select at ``0xc00000`` and chip select 0 the alternate at
  ``0xe00000`` (*established* for that board,
  :ref:`sgi-bridge-octane2-status`).
- On the same board the boot select returns the same words 1 MiB in as at
  its start and all ones at the top of both halves (*established* at
  those offsets). That it repeats every 1 MiB, so the part decodes
  1 MiB, is *inferred* (:ref:`sgi-bridge-octane2-flash`).
- The alternate select returns all ones to 16- and 32-bit reads at four
  places across its 2 MiB, with no exception (*established* at those
  offsets).

Unknown: the flash part number and command set, whether a part sits on
the alternate select, the protection pins, and all of these on the
``030-0887`` board. A public service drawing or a readable board
photograph identifying the flash package, followed by that part's manual,
would settle the part.

The model's choices:

- ``flash-select`` and ``flash-strap`` true in the ``octane2`` layer
  (``boot_flash_wiring``): the boot flash on select 1, with the strap
  set. This matches the reference Octane2: on the model the part
  answers at ``0xc00000`` and the Bridge status reads ``0x60``, the strap and PCI
  mode that board reads. The outstanding-read count of 2 in that board's
  ``0x62`` reads zero on the model (:ref:`sgi-bridge-limits`).
- ``flash-select`` and ``flash-strap`` false in the ``octane`` layer:
  the boot flash on select 0, strapped to boot from it, status ``0x20``.
  The part answers at the same address. No Octane board has been read,
  so this is an *approximation*.
- The machine properties of the same names override either layer.
- A 1 MiB array (``firmware_bytes``), implemented with QEMU's
  Intel-command-set ``pflash_cfi01`` and compatibility identifiers,
  repeating across the 2 MiB select. The size and the repeat match the
  reference Octane2's boot select. The command set and identifiers are
  an *approximation*: the fitted part is *unknown*.
- Only one select has a part. A read of the other select completes with
  all ones, as the reference Octane2 measured, and a write to it fails
  (the Bridge's ``flash-empty-reads-high`` property, set on both
  machines).

.. _sgi-ip30-octane2-alt-flash:

The first read of the alternate select, at physical ``0x1fe00000``
(Bridge widget 15 offset ``0xe00000``):

.. code-block:: text

   >> dump -h -x 0xffffffffbfe00000#1
   0xffffffffbfe00000:   ffff

The other reads of both selects are under :ref:`sgi-bridge-octane2-flash`.
None of them names a fitted part.

.. _sgi-ip30-launch:

Launch metadata
---------------

These are emulator choices for launchers, not hardware facts.

- Console ``ioc3-serial-a``. The Octane2 guide assigns a console terminal to
  serial port 1 (:src:`007-4207-002 p. 148`), OpenBSD's early console uses
  IOC3 UART A behind the onboard Bridge (``ip30_machdep.c`` lines 163-182),
  and the OpenBSD capture shows ``com0`` at IOC3 offset ``0x20178`` as
  console. That the stock PROM selects that port with no graphics board
  fitted was seen only on the model.
- Serial lines. ``ioc3-a`` is the first ``-serial``, ``ioc3-b`` the second,
  and the transcripts of A and B follow as the third and fourth, which
  the catalogue lists as ``ioc3-a-record`` and ``ioc3-b-record``. Both
  products have two ports: the Octane guide shows two DB9 connectors
  labelled 1 and 2 on the back (:src:`007-3435-004 p. 202`, *established*),
  and the measured Octane2 inventory lists IOC3 ``tty1`` and ``tty2``
  (:ref:`sgi-measured-octane2-hinv`, *established*). Port B is the IRIX
  ``ttyd2`` device: *inferred* on the Octane2 from the measured ``tty2``
  entry, and *observed* on the model, where IRIX 6.5.13f lists IOC3 serial
  ``tty2`` and a guest write to ``/dev/ttyd2`` reached the backend and a
  reply was read back. Timing and flow control on a real port are
  *unknown*.
- PROM dialogue ``none``: no launcher-driven PROM dialogue is defined.
- Disk bus ``scsi``: the boot disk attaches to the first onboard SCSI
  controller. The reference Octane2's hardware graph places its disk at PCI
  device 0, target 1 (:ref:`sgi-measured-octane2-graph`); the physical bay
  and channel wiring are *unknown*.
- Disk placement: the catalogue lists ``scsi.0`` at targets 1 to 3 and
  ``scsi.1`` at targets 1 to 15, in that fill order, for the Octane and the
  Octane2. The 4.17 PROM sets its target limit by controller index, 4 for
  index 0 and 16 for every other, and asks at LUN 0 only, skipping the
  controller's own ID (:src:`ip30-prom-4.17 0x1fc43730-0x1fc43744`). Its
  power-on scan uses the same limits (:src:`ip30-prom-4.17 0x1fc385b0`).
  The 3.7 PROM of the 6.5 base release makes the same choice
  (:src:`ip30-prom-3.7 0x1fc445a8-0x1fc445b8`). The QLogic driver in the
  IRIX kernel limits the first controller it attaches to 4 and each later
  one to 16, and probes LUNs 1 to 7 on every ID that answers at LUN 0, in
  6.5.30 (:src:`ip30-scsi-driver-6.5.30 0x4b80`) and in the 6.5 base
  release (:src:`ip30-scsi-driver-6.5 0x482c`). Each of these is a
  *software expectation*. The own ID defaults to 0 in the PROM
  (:src:`ip30-prom-4.17 0x1fc44350-0x1fc44374`) and in the 6.5.30 driver
  (:src:`ip30-scsi-driver-6.5.30 0x56b8-0x56c8`), so ID 0 is skipped and IDs
  1 to 3 are probed on the first controller, a *software expectation*. The
  PROM's ``scsihostid`` variable (0 to 7) and the driver's own host-ID
  setting move the skipped ID and make ID 0 visible there. A bus rescan
  asks for IDs 0 to 15 on every controller, so it reaches IDs 4 to 15 on
  the first (6.5.30, :src:`ip30-scsi-driver-6.5.30 0x5ed8`), a *software
  expectation*; the 6.5 base driver's rescan was not examined. A disk at
  ``scsi.0`` target 4 or above is therefore not found at boot, while IDs 1
  to 15 on ``scsi.1`` are all asked about; whether a device answers at IDs 8
  to 15 depends on wiring that is *unknown* (below). These are the defaults
  only. The factory ``scsihostid`` is *unknown*.

  That IRIX 6.5.13f and 6.5.23m use the same limits is *inferred*: their
  kernels were not examined, and the 6.5 base and 6.5.30 drivers agree.
  That the Octane2 uses the same stock PROM is *inferred*. That the
  driver's limit follows attach order rather than PCI device number is
  *inferred*, so a QLogic controller attached before the onboard pair would
  take the limit of 4. That PROM controller index 0 is the model's
  ``scsi.0`` is *inferred*. Two newsgroup posters say the Octane has three
  internal 3.5-inch SCA bays and that a CD-ROM goes only on the external
  connector (:src:`usenet-b92bss`, :src:`usenet-3cc2392b`). They name no
  controller number or ID range, so that the internal bus is controller 0,
  ``scsi.0``, and the external connector ``scsi.1`` is *inferred* from the
  limits above. The kernel driver supports wide operation, a *software
  expectation* (:src:`ip30-scsi-driver-6.5.30`). The PROM does not enable
  it, *inferred* from one cleared bit in its default controller flags
  (:src:`ip30-prom-4.17 0x1fc4444c`). Whether the second controller is
  wired for 16 bits, and so whether IDs 8 to 15 are reachable on the
  hardware, is *unknown*.
- CD-ROM: ``-cdrom FILE`` puts a ``scsi-cd`` on the first onboard
  controller's bus, ``scsi.0``, at target 2. The second controller's bus
  is ``scsi.1``. On the model, the stock Octane2 PROM never selects a
  target above 3 on ``scsi.0``, so a ``scsi-cd`` there at target 4 is not
  found; at target 4 on ``scsi.1`` it is, as ``scsi(1)cdrom(4)``. The PROM's
  code probes targets 0 to 3 on controller index 0 and 0 to 15 on the
  others, skipping the adapter's own ID (:src:`ip30-prom-4.17
  0x1fc43730-0x1fc43744`), a *software expectation*; which index is
  ``scsi.0`` comes from model runs. The machine's ``scsi-cd`` reports a
  block descriptor and takes a MODE SELECT block length, and the PROM sets
  the 512-byte blocks it reads a CD in (``hw/mips/sgi/board-cdrom.c``).
- Netboot adapter ``ioc3-ethernet``, the onboard IOC3's Ethernet; install
  media ``disk-image`` and ``netboot``. The stock PROM's "Install System
  Software" netbooted the IRIX 6.5.30 miniroot through it on the model,
  and complete installs on an Octane with SI and an Octane2 with V12
  reach the installed system's login prompt
  (:ref:`sgi-sn-launch-disk-bus`). The physical PROM's network install
  rests on the IRIX 6.5.30 ``prom(1M)`` page, not on a measurement of
  this board. Supported guest ``irix``; default CPU model R10000 or
  R12000.

.. _sgi-cdrom-identity:

CD-ROM drive identity
---------------------

This section covers every SGI machine model that boots from a SCSI
CD-ROM, not only the Octane. A CD-ROM the model attaches reports the
vendor and product text its ``scsi-cd`` device carries; what the guests
do with that text decides what to choose.

The drive must report peripheral type 5. The stock PROMs classify a unit
by type first, and a type-0 unit is a disk to them, apart from the three
names in the table below. The IRIX kernel presents a type-0 unit as a
CD-ROM only if its text names one (*software expectation*).

No stock PROM examined reads the vendor of a type-5 unit (*software
expectation*, read from the shipped firmware):

.. list-table::
   :header-rows: 1
   :widths: 24 76

   * - PROM
     - What it does with the INQUIRY text
   * - Octane, Octane2 (:src:`ip30-prom-4.17 0x1fc439e4`)
     - Only for a type-0 unit: if its text starts ``TOSHIBA CD``,
       ``SONY    CD`` or ``LMS     CD`` the PROM sends REQUEST SENSE, a
       vendor command ``0xc9`` and INQUIRY again. Any other type-0 text
       is a disk. A type-5 unit takes neither path.
   * - Origin 200, Origin 2000, Onyx2 (:src:`io6-prom-6.156 0xc000000011c3cd38`)
     - The base-I/O PROM has the Octane's logic and the same three names;
       the node-board PROM probes no SCSI targets.
   * - Origin 300, Origin 3000 (:src:`ip35-prom-6.210 0xc000000013098f18`)
     - The base-I/O PROM nested in the node PROM (the address is in the
       unpacked nested image) has the same logic. The
       base-I/O PROMs of the Origin 350, Tezro and Fuel are not examined:
       *unknown*.
   * - O2 (:src:`ip32-prom-4.18 0x8101ea68`)
     - None. It holds no vendor string and tests only the type. It sends
       MODE SELECT to 512-byte blocks to every type-5 unit without
       reading the block length first, unlike the Octane's PROM, which
       sends it only when MODE SENSE reports another length. Addresses
       assume the load base the image's call targets imply.

The Indy and Indigo2 PROM is not examined: *unknown*.

IRIX 6.5.30 and 6.5.22 do not need a vendor either, with one cost
(*software expectation*, read from the installed kernels and the media
daemon of 6.5.30; no installed 6.5.22 media daemon was examined):

- The kernel treats a text as a CD-ROM if it contains ``CDROM``,
  ``CD-ROM``, ``CD ROM`` or ``DVD-ROM``. The test matters only for a
  unit that reports type 0. It matches no CD-ROM brand, but a separate
  lookup compares the vendor against ``TEAC``, ``INSITE``,
  ``IOMEGA  Io20S`` and ``SyQuest``; what that changes is *unknown*.
- The removable-media daemon's CD-ROM module matches the text against
  eight brand prefixes, among them ``TOSHIBA CD``, ``SONY    CD`` and
  ``MATSHITACD``. Toshiba texts select vendor opcodes ``0xc4`` and
  ``0xc9``; an unlisted text gets the standard commands. QEMU's
  ``scsi-cd`` implements neither vendor opcode and answers them with
  ILLEGAL REQUEST, so a Toshiba text sends the daemon down paths the
  model cannot serve, while an unlisted text containing ``CD-ROM`` does
  not. That the daemon's software eject then fails was not run:
  *inferred*.

So a ``scsi-cd`` drive on these machines may keep QEMU's default text or
carry the real inventory string ``TOSHIBA CD-ROM XM-5701TA``; the
PROMs examined do not tell them apart. Prefer a text that is not a
CD-ROM brand the daemon knows or a vendor the kernel looks up, unless
the model answers that brand's vendor opcodes. What ``0xc4`` and ``0xc9`` do to a drive is *unknown*.
:ref:`sgi-ip32-storage` and :ref:`sgi-sn-launch-disk-bus` add the
machine-specific limits.

.. _sgi-ip30-graphics:

Graphics
========

A graphics pipe is a ``-device sgi-mgras`` or ``-device sgi-odyssey``
in one of the four Crossbow ports the Octane gives graphics boards,
named ``slot=widget-9`` to ``slot=widget-12``, checked against the
catalogue as every SGI machine's pipes are (:ref:`sgi-sn-graphics-pipes`).
Published inventories show IMPACT boards at widgets 10, 11 and 12, the
stock IDE probes 9 to 12, and the Octane2 inventory above shows its V12
at 11 (*established*). The default pipe is an SI at ``widget-11`` on
``octane`` and a V12 there on ``octane2``; that SGI shipped either
machine with no graphics is *unknown*, and both accept ``-vga none``.
The catalogue offers every IMPACT product in every port and the V12 only
at ``widget-11`` on ``octane2``; on ``octane`` it refuses VPro with the
upgrade guide's conditions (:src:`007-4210-003 preface`), Crossbow 1.4 and the
ER supply, which this model's Crossbow revision code 4 and SR supply do
not meet.

A port starts empty, its presence clear, as it is with no board. A board
claims its port when it realizes: it takes its fabric from the port's
link, attaches to the realized Crossbow, and maps its 64 GiB long window
at widget times 64 GiB of physical space and its 2 GiB window at 2^35 plus
widget times 2 GiB, through HEART's port with the widget number in address
bits 51:48. The windows carry the widget offset (36 bits for the long
window, 31 for the 2 GiB one) with no bit 47, *inferred*: the Bridge
specification puts the Bridge's registers at large-window offset 0
(:src:`bridge-asic-spec-4.0` Appendix B, Table 98) and these pages do not
state the address HEART sends on the link. Fitted Bridge boards, graphics
boards and the onboard Bridge are all reached the same way. The machine's
init-done notifier then brings the link alive with the same pre-reset
health restore the HEART and Bridge links get. On an IMPACT board the
machine sets the serial-number record the PROM names the board by, whose
barcode and ROM serial are the marked synthetic ``EMUG00``, and 32-bit
DMA page-list entries, which IRIX 6.5.30's X server and kernel and the
Linux IMPACTSR driver write.

.. _sgi-ip30-pci-boards:

PCI option boards
=================

The four graphics ports also take the one-slot PCI-XTALK adapter (the PCI
shoehorn), and Crossbow port 13 takes the Octane PCI module, a three-slot
PCI card cage. Each is a Bridge on a port of its own with its own PCI bus
(``-device sgi-pci-shoehorn,slot=widget-10``, ``-device
sgi-octane-pci-cage,slot=widget-13``, or ``--board
pci-shoehorn@widget-10`` and ``--board pci-cage@widget-13`` through the
catalogue). Their identity, slots, interrupt wiring and what is
*unknown* about them are on :ref:`sgi-pci-expansion-octane`. The Sonic
HDSP audio card, a PCI card that Discreet used with these boards, is on
:doc:`hardware/sonic-hdsp`.

.. _sgi-ip30-video-io:

Video input and output
======================

The DMediaPro DM2 (XT-DIGVID) digital video board is an XIO option board
for the Octane2, one widget on a Crossbow option port beside the graphics
board, with two cables to an external breakout box
(:src:`007-4317-001 13`, *established*). ``-device
sgi-xt-digvid,slot=widget-10`` fits it. Its widget, register and DMA
contract, and the virtual breakout box the model stops at, are on
:ref:`sgi-xt-digvid`.
