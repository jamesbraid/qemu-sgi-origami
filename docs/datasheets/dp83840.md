## Role

The physical-layer transceiver the base I/O controller's ethernet block drives through its
two management registers. It is not on any address map: software reaches it only by writing a
PHY address and a register number to the controller's management control register and reading
the result back, five bits of address and five of register number at a time. The controller's
own datasheet (`docs/datasheets/ioc3.md`) owns that path; this document owns what answers at
the other end of it.

## What is observed, and it is unusually complete

**All thirty-one captures that reach the ethernet driver print the same line**, varying only
in the description string that different OpenBSD versions attach:

```
nsphy0 at iec0 phy 31: DP83840 10/100 PHY, rev. 1
```

Three facts come straight off that, on real Origin 200 hardware rather than by inference:

- **The transceiver is at MII address 31.** Both drivers scan all thirty-two addresses and
  take the first that answers, so the address is not forced on us by either — but 31 is what
  the board has, and the nine captures with a second controller show `nsphy1 at iec1 phy 31`
  as well, so it is the wiring rather than an accident of one machine.
- **The part is a DP83840**, which is a statement about the identity registers rather than
  about the silicon: OpenBSD prints that string because it matched the identity words against
  its own table.
- **The revision is 1.**

**The identity words follow exactly**, and are given here as values rather than as a
description, because an implementer needs the two sixteen-bit numbers:

| Register | Value | How it decomposes |
|---|---|---|
| `PHYIDR1` (2) | `0x2000` | OUI bits 3–18 |
| `PHYIDR2` (3) | `0x5C01` | OUI bits 19–24 in 15:10, model `0x00` in 9:4, revision `1` in 3:0 |

Together they decode to OUI `0x080017` — National Semiconductor — model zero, revision one,
which is what `nsphy`'s match table contains and what produces the observed line. `0x2000`
also satisfies mainline Linux's scan, which accepts any first identity word that is neither
`0x0000` nor `0xFFFF`.

## Presenting the real identity binds a specific driver, and that is the decision

**`GENERIC-IP27` includes `nsphy`, and `nsphy`'s match table is exactly this part.** So a
model that answers with the identity above is choosing to satisfy `nsphy` rather than
OpenBSD's generic fallback, and the contract widens accordingly: beyond the standard
management registers, `nsphy` reads and writes two registers that belong to this part alone.

The alternative — answering with an identity no driver recognises, so that OpenBSD falls back
to its generic transceiver driver — would be a smaller contract and a machine that differs
from every real Origin 200 in a way a guest prints on its console. **This document assumes the
real identity**, and the two part-specific registers are specified below rather than wished
away. Recording the alternative because it is the kind of choice that looks like an
implementation detail and is not.

## Register map

Only the registers the two drivers touch. Numbers are MII register numbers, not byte offsets.

| Reg | Name | Reset | R/W | What our drivers need of it |
|---|---|---|---|---|
| 0 | Control (`BMCR`) | — | RW | Written to reset, to isolate, to select speed and duplex, and to enable and restart autonegotiation. Read back by the status path, which checks the isolate and loopback bits and whether autonegotiation is enabled. A self-clearing reset bit is expected: the generic layer writes reset and then waits for the bit to clear. |
| 1 | Status (`BMSR`) | `0x7809` (bench) | RO | Link status, autonegotiation ability and completion, and the capability bits the generic layer uses to build its media list. **The link bit latches low and both drivers read the register twice**, taking the union — a model reporting the live level in one read is fine, but one that latches must clear on read or the second read reports a link that is not there. Out of reset, before a guest has driven the control register, the link and completion bits read clear — a board on a bench with no cable, which is what the firmware's power-on diagnostic checks. |
| 2 | Identity 1 (`PHYIDR1`) | `0x2000` | RO | The scan. Linux accepts anything but all-zeroes and all-ones; OpenBSD matches the pair against its table. |
| 3 | Identity 2 (`PHYIDR2`) | `0x5C01` | RO | As above, and it carries the revision the console line prints. |
| 4 | Advertisement (`ANAR`) | — | RW | Written with what the station will advertise; read back by the status path, which intersects it with the link partner's word to decide the media. |
| 5 | Link partner (`ANLPAR`) | `0x0000` (bench) | RO | What the far end advertises. The status path reads it only after seeing that the partner is capable of autonegotiation. Its contents are not valid until autonegotiation completes — the part's own datasheet says so — so before a link comes up it reads zero, matching the bench state the diagnostic expects. |
| 6 | Expansion (`ANER`) | `0x0000` (bench) | RO | One bit matters: whether the link partner is autonegotiation-capable. It selects which of two routes the status path takes to a media type. Zero until a link comes up, for the same reason as the link-partner register. |
| 0x17 | PCS configuration (`PCR`) | — | RW | Part-specific. Read-modify-written once on a media change, setting the LED4 mode, the congestion control and transmit-ready select bits, forcing the hundred-megabit link-good override back to its normal (non-debug) mode, and clearing the carrier integrity monitor. **Nothing reads it back for a decision**, so storage that reads back what was written satisfies both drivers. |
| 0x19 | Address and status (`PAR`) | — | RO | Part-specific. Read on one path only — when the link partner cannot autonegotiate — where bit 6 distinguishes 10 from 100 Mbit. Its low five bits report the transceiver's own address, which for this board is 31. |

**Everything else is unmodelled**, including the remaining part-specific registers, the far-end
fault facility, and the loopback and diagnostic modes. Neither driver reads them.

## Behavioral contract

**The scan.** Both drivers walk the thirty-two addresses and stop at the first that answers.
A model must therefore answer at its own address and **not** at the other thirty-one — an
address that answers everywhere is found at zero, which is not where the board's is, and the
console line would say so.

**Reset.** The generic layer writes the reset bit and polls for it to clear. A model that
never clears it hangs the attach in a timeout loop; a model that clears it immediately is
indistinguishable from real hardware at this timescale.

**Autonegotiation, which is the path our guests actually take.** OpenBSD's driver enables it
and then reports media from what it reads back, and its route is worth stating exactly,
because a model can satisfy the letter of it and still report no link:

1. It reads the status register twice and takes the union, looking for the link bit.
2. If autonegotiation is enabled in the control register, it requires the completion bit in
   the status register before believing anything else — without it the interface reports no
   media at all, which is a working link that looks dead.
3. It then reads the expansion register. **If the link partner is autonegotiation-capable**,
   it intersects the advertisement and link-partner registers and derives the media from the
   result — this is the path that yields 100baseTX full duplex.
4. **Only if the partner is not capable** does it fall back to the part-specific address and
   status register, and the driver's own comment records that this register does not report
   duplex properly.

So a model that wants a guest to see a full-duplex hundred-megabit link should complete
autonegotiation, report the partner as capable, and advertise the same capability on both
sides. Reporting an incapable partner works and lands the guest on the fallback path, which
is the one the driver distrusts.

**The link comes up when a guest brings the interface into use, not from reset.** There is no
cable in the machine model, so the model stands in as a cooperative far end: once a guest writes
the control register to configure the interface — enabling or restarting autonegotiation, or
forcing a speed and duplex — the link comes up at once and stays up. Before that, out of reset,
it reads down, which is what the firmware's power-on diagnostic expects.

This is what a real Origin 200 does, and it is why a real machine does not print the diagnostic's
three transceiver reset-value warnings while this model, for a time, did. The firmware reads the
status, link-partner and expansion registers **early, as pure reads, before it has written the
control register at all** — measured at roughly 250 seconds of virtual time into the boot, well
before any transceiver configuration. On real silicon those reads return the bench state (no
link, no completed autonegotiation, no partner) because nothing has established a link yet; a
model that came up with the link already live answered them with a link present, and the
diagnostic flagged the mismatch. Bringing the link up on the guest's first configuring write
rather than from reset makes the model answer as the hardware does, and costs nothing downstream:
every guest that needs the link — the firmware's own network boot, and both OS drivers — writes
the control register to configure it before using it. A model of link *loss* after that point
would still need something to drive it, and no guest on our path asks for one.

## Interrupts

None. The part has an interrupt facility this board does not use and neither driver enables;
the controller's ethernet block raises the interrupts a guest sees, and the transceiver is
reached only by polling through the management registers.

## DMA

None. The transceiver is reached exclusively through the controller's management registers,
one sixteen-bit word at a time.

## Out of scope

- **The far-end fault facility, the loopback and diagnostic modes, and every part-specific
  register other than the two above.** Neither driver touches them.
- **Link loss and cable state.** No guest asks and nothing would drive it.
- **The real timing.** Autonegotiation takes hundreds of milliseconds on real hardware and
  completes immediately here; both drivers poll with generous timeouts and cannot tell.
- **Anything at the other thirty-one addresses.** They must not answer.

## Origin 300 IO-8 board: address 1, a different part

**Status: independently reviewed 2026-09-14 for MII address 1, DP83843 model and
revision identity, and the register `0x17` loopback-select bits.** The separate
DP83843 reset value remains the approximation identified below. Everything above
describes the Origin 200; this section adds the bounded Origin 300 differences.

**The Origin 300 addresses this controller's transceiver at MII address 1, not 31.**
The IP35 BASEIO PROM 6.210's MII helper functions never vary the address field: the
read helper (`func_c0000000130679e4`) ORs the fixed value `0x420` into the management
control register, and the write helper (`func_c0000000130676f0`) ORs `0x20` — which
decode as `READ|addr 1|reg 0` and `addr 1|reg 0`. One is not a default the firmware
falls back to; it is the only address the firmware ever asks. A real Origin 300's
OpenBSD capture confirms hardware answers there:

```
ioc0 at pci0 dev 4 function 0 "SGI IOC3" rev 0x01
...
iec0 at ioc0: 128KB SSRAM, address ff:ff:ff:ff:ff:ff
nsphyter0 at iec0 phy 1: DP83843 10/100 PHY, rev. 0
```

(Maurice Janssen, "Origin 300 with NUMA link", `openbsd-sgi` mailing list,
2014-02-12, `docs/library/cache/boot-logs/openbsd-sgi-list/`
`marc-139223952727384-origin-300-numalink-1.html` line 173 — already a source for
[the IOC3 Origin 300 supplement](ioc3.md#origin-300-io-8-population-supplement),
which cites the same capture for the board's other IOC3 facts.) `hw/mips/sn1.c`'s
`sn1_configure_ioc3` sets `dp83840`'s `addr` property to 1 for the IO-8 board's IOC3,
through a `phy-addr` alias chain (`sgi-ioc3` → `sgi-ioc3-eth` → `dp83840`) carrying a
per-board value from `sn1-model.h`'s device descriptor. `dp83840.c`'s own default of
31 is unchanged, and is still what the Origin 200 gets.

**The real part is a DP83843, not a DP83840A, and the model now carries that
identity and its loopback contract behind a `dp83843` property.** OpenBSD binds
`nsphyter`, the National Semiconductor PHYTER-family driver — a different match
table, not the same part under a different silicon revision. The Origin 300 BASEIO
PROM's `enet_phy_reg` power-on diagnostic checks the identity and several reset
values against tables calibrated for what it calls "IO7" transceivers, and only
*warns* on a mismatch rather than failing the sub-test:

```
enet_phy_reg     : Warning - PHY Identifier register #2 value 0x5c01
                    is not supported for IO7 by this diag!
enet_phy_reg     : Warning - PHY Silicon Revision Register value 0x0000
                    is not supported for IO7 by this diag!
```

(observed live, `-M origin300`, command monitor `diag_enet -v`, 2026-09-14, before
the identity fix below.) `PHYIDR1` stays `0x2000` on both parts — the OUI's upper
bits, which OpenBSD's `nsphyter` and `nsphy` both accept identically — but
`PHYIDR2` differs: OpenBSD's `sys/dev/mii/miidevs.h` (`$OpenBSD: nsphyterreg.h,v
1.2 2008/06/26 05:42:16 ray Exp $` for the register, `miidevs`/`miidevs.h` for the
model number) gives `MII_MODEL_NATSEMI_DP83843` as `0x0001`, which decodes against
the same OUI as the DP83840A's `0x5C01` to `0x5C10` at revision 0 — the revision
the real board's OpenBSD capture prints (`nsphyter0 at iec0 phy 1: DP83843 10/100
PHY, rev. 0`) and the exact value the diagnostic's own warning text names as
expected. `dp83840.c`'s `dp83843` property, set through a `phy-dp83843` alias
chain mirroring `phy-addr`'s (`sn1-model.h`'s `phy_dp83843` field →
`sn1_configure_ioc3` → `sgi-ioc3` → `sgi-ioc3-eth` → `dp83840`'s own `dp83843`),
switches `PHYIDR2` to `0x5C10` for the IO-8 board and leaves the Origin 200 at
`0x5C01`. Live, this clears both `enet_phy_reg` warnings above.

**Reaching the transceiver exposed a second sub-test, `enet_tw_loop`, that the
address fix alone left failing**, and its cause is a second identity-shaped gap:
what selects PHY loopback is itself part-specific, not merely which identity
registers answer. The Twister/PHY loopback diagnostic writes `BMCR = 0x2100`
(autonegotiation off, 100 Mb, full duplex — no `BMCR` loopback bit) and then ORs
`0x20` into MII register `0x17`. On the DP83840A this register is `PCS_CONFIG`,
plain storage (the reviewed table above), so the write selects nothing and no
loopback happens — the ten test frames reach the network backend, none return,
and the diagnostic reports "DMA t.o. polling valid bit / 0 of 10 packets were
received" (observed live, `-M origin300`, `diag_enet -v`, 2026-09-14, before the
fix below). On the real DP83843 this register is instead the **Loopback Register
(LBR)**: OpenBSD's `sys/dev/mii/nsphyterreg.h` names it `MII_NSPHYTER_LBR` at
`0x17` ("loopback and bypass") with `LBR_TW_LBEN` (`0x0020`, "TWISTER loopback
enable") and `LBR_10_ENDEC_LB` (`0x0010`, "10Mb/s ENDEC loopback"). The
diagnostic's `0x20` write is exactly `LBR_TW_LBEN`. Register `0x18`, the
DP83840A's `LBREMR` loopback-select storage, is a different register on the
DP83843 — OpenBSD names it `MII_NSPHYTER_10BTSCR` ("10baseT status and control"),
plain storage with no loopback function there. Neither of OpenBSD's `nsphy` or
`nsphyter` drivers ever writes `LBR`; only the firmware diagnostic does, so this
is a PROM-only fact with no OS-driver corroboration.

`dp83840_in_loopback()` now takes a third path guarded on the `dp83843` property:
when set, it reads `LBR_TW_LBEN | LBR_10_ENDEC_LB` out of register `0x17`'s
storage instead of register `0x18`'s. **This must not become true on the default
DP83840A part**, because register `0x17` bit 5 there is `PCR.CIM_DIS` (carrier
integrity monitor disable), which OpenBSD's `nsphy` driver sets on every media
change and which `tests/qtest/sn0-ioc3-test.c` exercises as ordinary storage — an
Origin 200 write of that same bit must keep reading back as configuration, not
close a loop. The property keeps the two parts' register `0x17` semantics
disjoint by construction rather than by a shared bit happening not to collide.

A PHY reset clears register `0x17` to the DP83840A's `PCS_CONFIG` reset value
(`0x8040`) regardless of part, which already clears bits 4 and 5 — the DP83843's
loopback-select bits — along with everything else a reset must clear. This is
reused rather than an independent DP83843 `LBR` reset value because the DP83843
datasheet is not in the Library and OpenBSD's header supplies bit names, not
power-on defaults; it is an approximation, not an observed value, and is recorded
as such in `hw/net/dp83840.c`.

The independent evidence review (citation: `docs/reviews/origin300-pr637-pr638-contract-evidence-review-20260914.md`)
clears the address, identity and loopback selection above, but not a DP83843-specific
power-on value for register `0x17`. `tests/qtest/sgi-ioc3-eth-test.c` and
`tests/qtest/sn1-io8-ioc3-test.c` carry the qtest checklist below; `-M origin300`
boots showing `enet_tw_loop` passing and the "IOC3 ENET failed diag" summary
line gone are the acceptance evidence, alongside `tests/qtest/sn0-ioc3-test.c`
staying green as the Origin 200 non-regression check.

Everything else in this document is unchanged: the register map, the
reset-then-guest-configures link behavior, and the scan contract of answering at
exactly one address all still hold. The Origin 300 gets the same part behavior at a
different address with two exceptions — its identity register and its loopback
select — both specified above rather than left as the DP83840A's.

### DP83843 qtest checklist (additional to the DP83840A's own, above)

- **`PHYIDR2` reads `0x5C10` at address 1**, and `PHYIDR1` still reads `0x2000`
  (`tests/qtest/sn1-io8-ioc3-test.c`).
- **Register `0x17` reads back a written value**, the same read-after-write
  contract as the DP83840A's `PCS_CONFIG` (`tests/qtest/sn1-io8-ioc3-test.c`).
- **Writing `BMCR = 0x2100` then OR-ing `0x20` into register `0x17` loops a
  transmitted frame back to the receive ring without reaching the network
  backend**, matching the firmware's exact Twister sub-test sequence
  (`tests/qtest/sgi-ioc3-eth-test.c`).
- **The same sequence with bit 5 clear does not loop**: the frame reaches the
  backend and the receive ring stays empty — separates "this write loops" from
  "any register `0x17` write loops" (`tests/qtest/sgi-ioc3-eth-test.c`).
- **The identical `0x20` write on the default DP83840A part does not loop**: the
  frame reaches the backend. This is the Origin 200 / `nsphy` `PCR.CIM_DIS`
  non-regression check (`tests/qtest/sgi-ioc3-eth-test.c`).
- **A PHY reset (`BMCR` bit 15) while in DP83843 loopback re-opens the backend**:
  a frame offered during loopback is refused, then lands once reset clears `LBR`
  (`tests/qtest/sgi-ioc3-eth-test.c`).

## What the gate settled, and what is still a choice rather than a finding

**The name and the shape were one question, and the gate resolved it: a device of its own.**
Having no address and being reached only through another device's registers describes an
MDIO-attached PHY's normal interface, not a reason to fold its state into the controller —
see the fork-file section above for the precedent that settles it.

**What to advertise remains a choice, not a finding, and stays open on purpose.**
Full-duplex hundred-megabit is the obvious choice and matches what the hardware is, but
nothing observed says what the real board negotiates on a given network, and the captures do
not print the negotiated media. The implementer picks a default; no source here overrides
that pick.

## qtest checklist

- **The identity words read exactly `0x2000` and `0x5C01`.** Assert the values, not that they
  are non-zero: an identity that merely passes Linux's filter still fails OpenBSD's table
  match, and the failure mode is a console line naming the wrong part or none.
- **The transceiver answers at address 31 and at no other address.** Read the identity at all
  thirty-two and assert exactly one responds. This is the assertion that catches a model
  answering everywhere, which a boot cannot catch — the scan stops at the first answer, so a
  model answering at zero produces a working link at the wrong address.
- **The reset bit is self-clearing.** Write reset, read the control register, assert the bit
  is clear.
- **The bench state comes up from reset.** Before any control-register write, assert the status
  register reads no link and no completed autonegotiation (`0x7809` through the diagnostic's
  `0xf83f` mask) and that the link-partner and expansion registers read zero. This is the state
  the firmware's power-on diagnostic checks, and a model that came up with the link already live
  answers it wrong — which is exactly the divergence the diagnostic's reset-value warnings named.
- **A guest write brings the link up.** After writing the control register to enable
  autonegotiation, assert the status register reports both the completion bit and the link bit,
  and that the link-partner and expansion registers now answer non-zero. The link is a
  consequence of the guest configuring the interface, not of reset.
- **The status register survives two reads.** With the link up, read it twice and assert the link
  bit is set both times, since the driver takes the union of two reads and a model that latched
  the bit low without clearing it would report a dead link on the second.
- **The advertisement register reads back what was written**, since the status path intersects
  it with the partner's word rather than re-deriving it.
- **The part-specific configuration register reads back what was written.** Nothing reads it
  for a decision, so this is the only place its contract is checked at all.
- **The address and status register reports 31 in its low five bits**, which is the one field
  in it that must agree with something else in the machine.
