## Role

The ISP1040 is the SCSI host adapter that an Origin 200 boots its disks from. It is a
32-bit PCI device sitting behind the same Bridge as the IOC3, and **a real Origin 200
carries two of them, at PCI devices 0 and 1**, with the IOC3 at device 2. The firmware's
hardware inventory on a captured machine lists two `PCI-SCSI Rev 5` adapters at those two
identifiers, and Linux 2.6.12 on the same class of machine probes a disk controller at PCI
device 0 and another at device 1.

SGI's own board drawing agrees and says what the two are for: the Origin 200 motherboard
carries **SCSI channel 0 on a 50-pin connector serving the 5.25-inch drive bay, and SCSI
channel 1 on a 68-pin connector serving the 3.5-inch bays.** The Origin 2000's BaseIO board
is described the same way — one external single-ended wide SCSI port and one internal
Fast-20 SCSI port — and its block diagram draws two SCSI controllers, each with its own
static RAM, on the same PCI bus as the IOC3. So two adapters is the standard arrangement
across the family rather than a peculiarity of one capture, and a model that wires one is
modelling half the machine's disk topology.

The adapter is not a register-level SCSI sequencer that a driver drives phase by phase.
It is an intelligent controller: the host hands it whole SCSI commands as descriptors in a
memory queue, and it does selection, message and data phases itself and posts completions
back in a second queue. Everything the host needs beyond those two queues goes through a
mailbox protocol. That shape determines how it is emulated, and the section on firmware
below is the most important part of this document.

For origami the adapter is not on the path to the OpenBSD banner — that path needs the
Hub, the Crossbow, the Bridge and the IOC3 UART, and nothing else. It is on the path to a
guest that mounts a root filesystem, which is what turns a banner into a usable machine
and a boot into a CI test.

## Identity, and why the revision is functional

| Field | Value |
|---|---|
| PCI vendor | `0x1077` |
| PCI device | `0x1020` |
| PCI configuration-space revision | **`5`** |
| Bus configuration 0 hardware-revision field | **`6`** |
| Class | SCSI bus controller |

**One PCI device identification covers the whole family.** Vendor `0x1077` with device
`0x1020` is answered by every member from the ISP1020 through the ISP1040C. The string a
driver prints from it — OpenBSD prints "QLogic ISP1020" on a real Origin 200 — names the
identification, not the silicon. The revision selects the part.

**The revision is a functional decision, not a label.** OpenBSD reads the PCI revision byte
and programs the adapter's clock from it: 40 MHz below revision 2, 60 MHz at revision 2 and
above. A model reporting the wrong revision is driven at the wrong clock, and every
synchronous transfer negotiation is then computed against a reference the model does not
have. The transcript of a real machine settles which value to report — OpenBSD 7.9 prints
`rev 0x05`, and the firmware inventory calls the same adapters revision 5 — so **the model
reports PCI revision 5** and gets the 60 MHz path.

**Two different registers carry a revision, and they are numbered from different origins.**
This is the trap. IRIX and OpenBSD both read the *PCI configuration-space revision byte*.
Mainline Linux reads the low four bits of the *bus configuration 0 register*, inside the
chip's own register window, which is a different field entirely. The two encodings run one
apart across the whole family:

| Part | PCI revision byte (IRIX, OpenBSD) | Bus configuration 0 field (Linux) |
|---|---|---|
| ISP1020 | 0 | 1 |
| ISP1020A | 1 | 2 |
| ISP1040 | 2 | 3 |
| ISP1040A | 3 | 4 |
| ISP1040B | 4 | 5 |
| ISP1040C | **5** | **6** |

So the model reports the PCI revision byte as 5 *and* the bus configuration 0 field as 6.
**The two halves are not equally load-bearing, and an earlier version of this datasheet
claimed a consequence that does not exist.**

**The PCI configuration-space byte is the one that matters.** OpenBSD switches on it to name
the part and derives the 60 MHz adapter clock from it, IRIX reads the same byte, and a real
Origin 200 prints revision 5. Get it wrong and the adapter is driven at the wrong clock.

**The bus configuration 0 field is fidelity, and only one value in it changes any
behaviour.** Linux reads it in exactly three lines — a local, a read, and a comparison
against the ISP1040A value — and never stores it. Five of the six part constants its header
defines for that field are referenced nowhere in the driver; only the 1040A one is, and the
board name Linux prints comes from a table indexed by the PCI device identity rather than
from the revision at all. So the field decides one thing: whether to suppress the
FIFO-threshold write as a workaround for the ISP1040A's broken FIFO. **Any value except 4
takes the ordinary path**, which makes 6 correct because it names the right part, and safe
because it is not 4.

An earlier version said that setting both registers to 5 "would name a 1040B to Linux". It
would not — Linux does not name the part from that field. The defined-but-unreferenced
constants in its header are what make the claim look true, which is the same trap as the SXP
bank select two sections down, where the value to distrust was also the one no code path
touches. Worth stating because the pairing survived the correction and only the reasoning
changed.

**Three names describe revision 5 and none of them is wrong.** IRIX's own driver header
calls it a 1040B version 2; OpenBSD's revision table calls the same silicon an ISP1040C;
SGI's hardware inventory prints `QL1040B (rev. 2)`. A trap lives in that last string: the
parenthesised "rev. 2" is the sub-version letter, matching IRIX's naming, **not** the PCI
revision byte. Setting the model's revision register to 2 because the inventory said "rev.
2" would report an ISP1040 to OpenBSD, which is above the clock threshold and so would not
even fail loudly — it would just misname the part to every guest.

## Register map

### PCI configuration space

Configuration space is a separate address space from the operating register window, reached
a different way: the guest reads it through the Bridge's PCI type-0 configuration path at the
adapter's per-device window, not through either base address register. **Configuration offset
`0x04` here is not operating-register offset `0x04` ("Bus configuration 0") in the operating
register window — they are different registers in different address spaces that happen to
share a number.** The one this section names is the standard PCI Command and Status register;
the one in the operating window carries the hardware-revision field.

| Offset | Name | Width | Reset | R/W | Behavior |
|---|---|---|---|---|---|
| `0x00` | Identity | 32 | `0x10201077` | RO | Device `0x1020` in the high half, vendor `0x1077` in the low half — the word the type-0 read returns first. |
| `0x04` | Command and Status | 32 | `0x02000000` | mixed | Command in the low half, Status in the high half. Reset Command `0`, reset Status `0x0200`. |
| `0x08` | Revision and class | 32 | fixed | RO | Low byte is the PCI configuration-space revision — `5` for this part, the value the identity fields settle. The upper three bytes are the SCSI-bus-controller class code. |

The base address registers that map the operating register window — the I/O window at `0x10`
and the memory window at `0x14` — are described with that window.

**Configuration offset `0x04` is the standard PCI Command and Status register**, Command in
the low sixteen bits and Status in the high sixteen. At reset Command is `0` — the adapter
answers no memory or I/O cycles and is not a bus master until the guest enables it — and
Status is `0x0200`, so a 32-bit read of the register at reset returns `0x02000000`.

**The Status half must present that reset value as readable state, and a model that leaves it
zero fails this machine.** The single-CPU IRIX miniroot's `io_config_space` diagnostic
(`diag_io6confSpace_sanity`) reads this register at reset for each PCI device and compares the
full 32 bits against an expected value; for this adapter it expects `0x02000000`. A model that
presents a zero Status half miscompares, the diagnostic fails the I/O slot, and the miniroot
takes a general exception and drops to its monitor before it reaches the installer. That is
observed on the console of a real boot, captured in `docs/boot-logs/irix.boot.2026-08-23T09:15-07:00`
and analysed in the config-space reset-value finding (citation: `docs/plans/archive/pci-confspace-reset-values-handoff.md`).

**What the Status bits mean, and how well each part is known.** The PCI Local Bus
Specification — revision 2.2 of December 1998, held as
`docs/library/cache/io-chip/pci-local-bus-spec-2.2-1998.pdf` — defines the Status half's
layout. The only bit set here is bit 9: the specification makes Status bits 10:9 the DEVSEL
decode-timing field, and the value `01` reports medium timing. So the adapter reports medium
DEVSEL and no other capability. That reading is a derivation, not two separate observations:
the reset value `0x0200` is what the machine's diagnostic requires (observed on the console),
and "medium DEVSEL" is the specification's meaning of the single bit that value sets. **No
QLogic document in our collection documents this part's PCI configuration-space Command and
Status register.** The collection holds several — the ISP1020B/ISP1040B, ISP1040B and ISP1040C
datasheets (`qlogic-isp1020b-isp1040b-datasheet-1996.pdf`,
`qlogic-isp1040b-datasheet-1997.pdf`, `qlogic-isp1040c-datasheet.pdf`), the ISP1040B SCSI
controller manual (`qlogic-isp1040b-scsi-controller-manual-1997.pdf`) and the register
transcription — and each names DEVSEL only as a block-diagram signal, none giving a reset
value for the configuration register. So the diagnostic contract is the authority for the
value, exactly as this datasheet's other reset values rest on demonstrated behaviour rather
than a vendor register table.

For the write mask an implementer needs, the Status half splits into read-only capability bits
and write-one-to-clear error latches, and only the second group is writable:

- **Read-only reset state, writes ignored:** DEVSEL timing (bits 10:9, `01` here), Fast
  Back-to-Back Capable (bit 7, clear here), 66 MHz Capable (bit 5, clear), Capabilities List
  (bit 4, clear). For this part only bit 9 is set; the rest read zero.
- **Write-one-to-clear error latches, reset `0`:** Master Data Parity Error (bit 8), Signaled
  Target Abort (bit 11), Received Target Abort (bit 12), Received Master Abort (bit 13),
  Signaled System Error (bit 14) and Detected Parity Error (bit 15). A model with no PCI error
  injection can implement these as reset-zero latches that never set: a guest write of one
  clears the addressed latch, a write of zero leaves it.
- **The Command half** is the ordinary PCI Command register, writable per its own mask. The
  diagnostic reads offset `0x04` before the guest enables anything, which is why it expects
  Command `0` at this point.

### The operating register window

The whole register window is `0x100` bytes and **every register in it is 16 bits wide**.
The adapter presents it through two base address registers: a memory window at
configuration offset `0x14` and an I/O window at `0x10`. OpenBSD tries the memory window
first and falls back to the I/O window, so both must decode. The registers are
little-endian on a big-endian machine; the byte swap belongs to the Bridge model and the
PCI memory region, not smeared into this device.

**The same is true of everything this device transfers, and it was briefly not.** For a
while this model corrected the byte order of its own command rings and data buffers,
choosing which order applied from whether an address had a non-zero upper half. That was
wrong twice over: the chip decides per device from two swap bits in the Bridge's own
per-device register, one for each mapping window, and the address a transfer uses does
not select between them. Linux puts every DMA address in the 64-bit window, so the guess
would have called its disk blocks byte-reversed and corrupted them in both directions.

**So this device does plain little-endian DMA and holds no byte-order rule at all.** Rings,
descriptors, command blocks, data segments and the adapter's own block RAM transfers all
go through the ordinary PCI DMA accessors, and whatever permutation this machine needs
happens in the Bridge on the strength of the requesting slot's swap bits. The rule itself,
including where a transfer shorter than a word lands, is written down in the
[Bridge datasheet](bridge.md). Nothing here needs to know which window a ring sits in.

**One coupling worth stating because it is invisible from this file.** If the Bridge's DMA
swap were ever removed or made conditional on something else, this device would need its
correction back — and if a correction were ever added here without removing the Bridge's,
the two would cancel and every guest would break. They moved together once already.

### Bus interface registers

The eight offsets from `0x00` to `0x0E` are confirmed by both cross-checked drivers. The two
flash-BIOS rows below them are not: Linux and OpenBSD both name `0x10` and `0x12` as the
flash data and address registers for this generation, while NetBSD assigns those same
offsets to request-queue pointers it marks as specific to the much later ISP2300. That is
two independent sources for the flash naming on this part and no contradiction — a different
chip generation reusing the addresses is not a disagreement about this one — but it is a
weaker footing than the eight above, and neither register is on any path we need.

| Offset | Name | Width | Reset | R/W | Behavior |
|---|---|---|---|---|---|
| `0x00` | Bus identity, low | 16 | fixed | RO | Chip identity, read back after reset. |
| `0x02` | Bus identity, high | 16 | fixed | RO | Chip identity, high half. |
| `0x04` | Bus configuration 0 | 16 | see above | RO | Low four bits are the hardware revision field; report `6`. |
| `0x06` | Bus configuration 1 | 16 | `0` | RW | FIFO threshold, burst enable and the register bank select. Fields below. |
| `0x08` | Bus interface control | 16 | `0` | RW | Bit 0 is a soft reset that hardware clears when it completes. Bit 1 is the global interrupt enable, bit 2 the RISC interrupt enable. |
| `0x0A` | Bus interface status | 16 | `0` | RO | Bit 1 reports an interrupt request pending, bit 2 a RISC interrupt pending. |
| `0x0C` | Semaphore | 16 | `0` | RW | Bit 0 is the lock the adapter takes when it has posted a mailbox or asynchronous event; bit 1 is its status. The host clears the register to release it. |
| `0x0E` | NVRAM interface | 16 | `0` | RW | Bit-banged serial EEPROM: bit 0 clock, bit 1 chip select, bit 2 data out to the part, bit 3 data in from it. |
| `0x10` | Flash BIOS data | 16 | `0` | RW | Named by Linux and OpenBSD. |
| `0x12` | Flash BIOS address | 16 | `0` | RW | Named by Linux and OpenBSD. |

Bus configuration 1's fields, all confirmed by both drivers: FIFO threshold at `0x0040` for
128 bytes, `0x0030` for 64, `0x0020` for 32 and `0x0010` for 16; global bus burst enable at
`0x0004`. OpenBSD configures this adapter with burst enable and a 64-byte threshold.

Bus interface control's fields, all confirmed by both drivers: soft reset `0x0001`, global
interrupt enable `0x0002`, RISC interrupt enable `0x0004`. Linux additionally puts flash
BIOS read/write enable at `0x0100` and an upper-bank select at `0x0200` here; single-source.

### The bank select at bus configuration 1 bit 3, and why it matters

**The SXP register bank select is bit 3, value `0x0008` — not bit 0.** This is the one
place the two cross-checked drivers disagree, and the disagreement is resolved rather than
split, because the evidence is asymmetric. NetBSD's constant is used in its PCI attachment
code, twice, to select the bank before every read or write of an SXP register, so it is
exercised against real hardware on every machine that runs the driver. Linux's constant is
defined and referenced nowhere in the tree — a dead value no code path can have validated.
A structural check adds a little: on the SBus variant of the same chip the low two bits of
this register are the FIFO threshold field, so bit 0 is not free there.

**Bit 3 does not mean the same thing on both bus variants**, and an earlier draft of this
document claimed it did. On SBus, `0x0008` enables 8-byte bursts; the SXP select is a
PCI-only meaning of that bit. That kills one of the three arguments for bit 3 but not the
conclusion, which rests on the other two: NetBSD's constant is exercised on real hardware
and Linux's is dead code.

The bit matters more than "one register bank is missing" suggests. On the PCI variant the
SXP block and the RISC block are mapped at the *same* window offset, `0x80`, and this bit
is what chooses between them. A model implementing the select at bit 0 would leave a guest
that sets bit 3 reading RISC registers where it expected SXP registers, and the failure
would look like a firmware bug rather than a wrong constant.

The access pattern to model, which NetBSD performs for every SXP access, is: read bus
configuration 1, write it back with bit 3 set, do the access at `0x80` and up, then write
the saved value back. The driver assumes the RISC processor is paused across it.

### Mailbox registers

The mailbox block begins at **`0x70`** on the PCI variant, agreed by both cross-checked
drivers, and OpenBSD uses eight 16-bit mailboxes at `0x70` through `0x7E`. Mailbox 0 is
the command and the result; the rest are arguments and returns, selected by per-call input
and output bit masks.

Three queue pointers are read and written at fixed offsets *from the mailbox base*, not
from the window base, which is easy to misread: the request queue in and out pointers both
at mailbox base plus `0x08`, the response queue in and out pointers both at mailbox base
plus `0x0A`. In and out share an address because one direction is the read and the other
the write.

**The driver's write of the response-out value is not a courtesy the adapter can ignore.**
OpenBSD's `qlw_handle_intr()` reads the response-in value this model posts and compares it
against its own consumption cursor; if the two are equal, it treats the interrupt as
spurious and returns without processing anything, because an empty ring and a completely
full one both leave producer and consumer at the same index. Real hardware never reaches
the full case — it completes one command at a time with real bus latency between them, so
the driver always services each interrupt long before enough could pile up to wrap. A model
with no such latency can reach it directly: four commands issued as separate doorbells, the
way the driver actually issues them, can all complete before the guest ever reads the
response queue once. The adapter has to track what the driver has acknowledged and refuse
to let a new completion erase the gap between producer and consumer — the same
reserve-one-slot convention any ring buffer needs to tell full from empty — rather than
trust that real timing will keep it from mattering.

**The response-in a driver reads must always be this adapter's own current count, never
whatever a guest last wrote to that address.** In and out sharing one address means a
guest's ack write and this adapter's own publish of its producer count land in the same
storage unless the model keeps them apart. OpenBSD's `qlw_handle_intr()` reads the
response-in value once, at the top of the handler, and does not re-read it before writing
that same value back as its own ack at the end. Under sustained write traffic — the
shape of a disk-image extraction, not an edge case — one command's completion is what
starts the next one queued behind it, so a fresh doorbell can run, and complete
synchronously, from inside that same handler: between the value already read and the ack
not yet written. A model that answers a read from plain storage hands back whatever the
guest's own stale ack just wrote, erasing the newer count the device already published and
reproducing the same aliasing the reserve-one-slot rule above exists to prevent — reached
by ordering this time, not by exhausting the ring. Answer a read of this register from the
adapter's own producer count directly; a guest's write of its ack must never be able to
overwrite it.

**The request-in value the guest writes is always a wrapped ring index, never a
free-running count.** OpenBSD's own driver enforces this on the way out —
`sc_next_req_id` resets to 0 the instant it would reach the queue's own entry
count — so nothing well-behaved ever writes a value at or above the queue length. A
model that trusts that guarantee rather than enforcing it has a real gap: the
device's own read cursor is always kept wrapped, and comparing a wrapped cursor
against an unwrapped guest value can never terminate once the guest value reaches
the queue length, because the wrapped cursor can never equal it. That is not a
theoretical guest bug — it is any value a guest, buggy or malicious, chooses to
write to a plain register, and a model that hangs on it has handed the guest a way
to wedge the host process. Wrap the guest's value on the way in, the same way the
device's own cursor is always wrapped, rather than trust the guest to have done it.

### Host command and control

| Offset | Name | Width | R/W | Behavior |
|---|---|---|---|---|
| `0xC0` | Host command and control | 16 | RW | Write: a command in the top four bits. Read: RISC state flags. |
| `0xCC` | GPIO data | 16 | RW | SCSI termination control on later parts; not used on this one. |
| `0xCE` | GPIO enable | 16 | RW | As above. |

The commands written to the top four bits are: no-op `0x0`, reset the RISC `0x1`, pause it
`0x2`, release it `0x3`, mask parity `0x4`, set the host interrupt `0x5`, clear the host
interrupt `0x6`, clear the RISC interrupt `0x7`, a BIOS-enable command `0x9`, enable parity
`0xA`, and report a parity error `0xE`. Reading the register returns flags: host interrupt
set at `0x0080`, RISC in reset at `0x0040`, RISC paused at `0x0020`, RISC external at
`0x0010`.

Setting the host interrupt is how the driver tells the adapter a mailbox command is ready;
clearing the RISC interrupt is the first half of every interrupt acknowledgement.

Mask parity (`0x4`), BIOS-enable (`0x9`), enable parity (`0xA`) and report parity error
(`0xE`) are all decoded — a guest issuing any of them gets no bus error and no
unknown-command log line — but none has behavior modelled, and none needs it. Parity
checking has no observable effect for a guest that never injects a parity fault, and
BIOS-enable is the command counterpart to the flash BIOS registers already out of scope:
an emulated Origin 200 has no option ROM on this adapter for the command to enable. A
guest issuing one of these logs "host command 0x* accepted, not modelled" and continues;
that line is the intended, correct behavior for these four commands, not a gap.

### DMA blocks

A command DMA block at `0x20` and a data DMA block at `0x40`, each carrying configuration,
control, status, FIFO status, transfer count and address registers. The cross-check treats
these offsets as single-source because NetBSD reaches them through a block selector rather
than flat offsets. **They are in fact dual-sourced**: OpenBSD's own header states them
flatly at `0x20` and `0x40` for this generation, matching Linux, and moves them to `0x80`
and `0xA0` behind a bank select only for the later ISP1080. Resolving NetBSD's block
selector for the non-1080 case gives the same two numbers. Treat `0x20` and `0x40` as
confirmed.

Only one register of either block is on the boot path: the config register, at the block's
base offset (`0x20` for the command block, `0x40` for the data block), and only one bit of
it — burst enable, value `0x0002`. OpenBSD's attach sequence reads the current value,
OR's in that bit, and writes it back to both blocks' config registers whenever the
FIFO/burst configuration it already wrote to bus configuration 1 asks for bursts. The
model stores each block's config register as independent state and masks writes to the
one bit confirmed on the boot path, so this round-trips instead of falling through to the
generic unimplemented-register default the rest of either block still uses.

**One further register of each block is on the firmware's path: the control register**, one
word past the config register at `0x22` for the command block and `0x42` for the data block.
NetBSD's `ispreg.h` names both and defines the bits; the SGI PROM's SCSI diagnostic writes
`0x000a` to each, which is that header's clear-channel (`0x0008`) and reset-interrupt
(`0x0002`) together — quiescing each engine and dropping its pending interrupt, the
housekeeping around a transfer rather than a transfer itself.

**Nothing reads either register back, and the model keeps no value in them.** The firmware
writes each once per adapter and never reads either back, which a register trace of the whole
boot shows directly: no read of an unimplemented register on this device appears anywhere in
it. So there is no value to keep and nothing for a guest to observe, and the model accepts the
write and does nothing. Recognising them rather than letting them fall through the
unimplemented-register default is what stops a normal boot logging four spurious warnings
about registers the firmware is entitled to write.

**This is also the answer to whether the diagnostic drives DMA through these block registers
directly**, which would have been a much larger contract than the mailbox commands. It does
not. The two writes carry no descriptor, no transfer count and no address, and they follow the
RAM-access mailbox commands rather than replacing them.

## Behavioral contract

### The firmware question, which decides the whole design

**The adapter runs QLogic microcode on an internal RISC processor, and the guest downloads
that microcode at every attach.** OpenBSD 7.9's `qlw` driver ships a firmware image, and
the `ISP_NOFIRMWARE` build option that would skip the download is set only in some Alpha
RAMDISK configurations — never in `GENERIC-IP27`. So the IP27 kernel we boot always
downloads.

**We do not run that microcode, and we must not try.** The emulated device implements what
the *firmware* does — the mailbox command set and the two IOCB queues — the same way
QEMU's other intelligent storage controllers implement a message interface rather than
executing vendor firmware. `hw/scsi/mptsas.c` is the in-tree device to copy the shape from,
which is the precedent the architecture notes (citation: `docs/architecture.md`) already picked for this
device. The download therefore has to be *accepted and answered*, not executed. Concretely
the model must:

- Accept the word-at-a-time RAM write command for as many words as the guest sends,
  storing them or discarding them. The guest sends one mailbox command per 16-bit word, so
  this path runs thousands of times per attach and must be cheap.
- Answer the checksum verify command with success. We are not running the code, so there is
  nothing to check; a model that returned failure would abort the attach.
- Answer the execute-firmware command with success and thereafter behave as though firmware
  is running — which for us means the mailbox commands below start working.
- Answer the about-firmware command with a plausible version triple and attribute word,
  because the driver prints it and aborts if the command fails. This is the model's chance
  to declare a version; it does not have to match any real QLogic release.

Nothing about this requires QLogic firmware to be present, distributed, or decoded, which
is what makes it the only acceptable design: **the fork ships no vendor firmware.**

**Someone else has shipped this exact approach, which is worth knowing before anyone
re-litigates it.** 86Box carries a full ISP1020/ISP1040 device model under GPL-2.0 that does
not emulate the RISC either: it holds the downloaded firmware as a plain array of 16-bit
words standing in for RISC memory, moves data in and out of that array for the RAM load and
dump commands, re-implements the checksum verify as the real sum-to-zero check over the
loaded image rather than executing anything, and answers the about-firmware command by
finding a version string inside the guest-supplied blob and parsing the digits after it.
That last detail is a nicer answer than this datasheet's — reporting a version taken from
the guest's own image beats inventing one, and it costs nothing.

Treat that model as evidence about **the approach**, not about the registers. Its register
definitions derive from Matthew Jacob's driver, so where it agrees with NetBSD it is
inheriting rather than confirming, and it cannot independently corroborate the SXP bank
select or any other value this datasheet took from that side of the cross-check. Its state
machine and firmware handling are its own, and that is the part worth reading.

### Reset and identity handshake, in the order OpenBSD performs it

This sequence is the first thing to test a model against, because everything else depends
on completing it.

1. Pause the RISC through the host command register.
2. Write the soft reset bit in bus interface control, then poll that register until
   hardware clears the bit. **The model must clear it**; the driver gives up after a
   thousand polls and fails the attach.
3. Zero bus configuration 1.
4. Reset the RISC, zero the semaphore, release the RISC.
5. Zero all four queue pointers.
6. Enable both interrupt enables in bus interface control, then issue the BIOS-enable host
   command.
7. Issue a no-op mailbox command and require it to complete. This is the liveness check;
   failing it fails the attach.

**OpenBSD reads the signature too, and this document once said it did not.** The claim was
that no such step exists, on the strength of `qlw_softreset()` not containing one. It does
not — the check is in the caller. `qlw_attach()` (`sys/dev/ic/qlw.c` on the pinned
OpenBSD/sgi branch, around lines 212 to 218) reads mailboxes 1, 2 and 3 and compares them
against `0x4953`, `0x5020` and `0x2020` before it pauses the processor and resets it.

Two things make it different from Linux's version rather than absent. It is a hint rather
than a verdict: a mismatch issues a processor-release command and carries on, where Linux
fails the attach. And it runs *before* OpenBSD's own reset, so what it inspects is whatever
state the previous owner of the adapter left behind. But it is a real guest reading a real
mailbox for a real value, and this model answers it correctly today — so the retracted
paragraph was a binding document arguing against working code.

The retraction is replaced rather than annotated because its premise was wrong, not its
wording. The lesson it leaves is worth more than the fact: it was reached by opening the
function whose name matched the claim, finding nothing, and stopping. The right file was
open the whole time.

### Reset and identity handshake, Linux's addition

**Linux's qla1280 driver performs a check nothing in OpenBSD's sequence does, and it is
fatal.** `qla1280_chip_diag()` reads mailboxes 1 through 4 immediately after reset, before
any mailbox command is issued, and compares them against `PROD_ID_1` through `PROD_ID_4`
(`drivers/scsi/qla1280.h`): `0x4953` (ASCII `IS`), `0x0000` or `0x5020` (`P `), `0x2020`
(two spaces), and `0x0001` — a plain word, not ASCII. A mismatch on any of the four aborts
the adapter's attach outright with "Wrong product ID". 86Box's `ql_reset_asic` sets the
identical four values in a second, unrelated implementation, which is corroboration this
is a real fact about ISP1040-family hardware rather than one driver's idiosyncrasy.

Presenting the first three of these four costs OpenBSD nothing, since it never looks — that
much was already modelled, on the mistaken belief that OpenBSD needed it. Mailbox 4 was the
value this model omitted, and Linux is the guest whose attach that omission actually broke.

### The SSRAM RAM-access commands, which no OS driver needs

**Three RAM-access mailbox commands sit on the SGI PROM's power-on path and on no OS
driver's path**, which is why a model built from OpenBSD and Linux behaviour answers a
booting OS and still fails the firmware. An OS driver pushes firmware into the adapter one
word at a time and then drives the command rings; it never asks the adapter to move a block
of its own memory. The PROM's SCSI power-on diagnostic does exactly that, and until these
commands were traced this model answered all three with the invalid-command result.

| Opcode | Command | Direction | Arguments |
|---|---|---|---|
| `0x0001` | load RAM | host memory to SSRAM, a block | `mb1` SSRAM word offset, `mb2` host address bits 31:16, `mb3` host address bits 15:0, `mb4` word count |
| `0x0003` | dump RAM | SSRAM to host memory, a block | the same four |
| `0x0005` | read RAM word | SSRAM to mailbox, one word | `mb1` the SSRAM word offset in, `mb2` the word out |

The opcode numbers are sourced, but not all of them equally, and the difference matters
because the two thinnest rows are the ones this model newly implements. Load RAM is
quadruple-sourced — Linux's `qla1280.h`, NetBSD's `ispmbox.h`, OpenBSD's `qlwreg.h` and
86Box's own ISP model all number it identically. Dump RAM and read RAM word are
triple-sourced: OpenBSD's header defines neither, carrying only load RAM and write RAM
word, so those two rest on Linux, NetBSD and an emulator. Three independent readings still
agree on the numbers; the point is that one of the three is not a driver lineage, and a
count of four would have hidden that.

**The 64-bit forms of these commands are not implemented, and a guest can ask for them.**
Linux selects opcodes `0x0009` and `0x000A` for load and dump when it is built for 64-bit
DMA addresses, which is true on this target, so Linux's own firmware download reaches this
model's invalid-command answer rather than either handler. That is pre-existing rather than
introduced here, and it is listed because a reader of the table above would otherwise
conclude the RAM-access surface is complete. The four mailboxes already carry a 64-bit
address, so the gap is the opcodes rather than the layout.

**Running off the end of the adapter's memory is this model's choice, not a shared contract.**
An offset and count that would pass the end wrap inside the adapter's own memory here; 86Box
answers a parameter error instead. The firmware's transfers are small and low, so nothing on
the boot path distinguishes the two, and no source we hold says which the silicon does.

The block commands' argument layout comes from Linux's `qla1280_load_firmware_dma()`, which
builds precisely these mailboxes for both the load and the dump and adds the two high halves
of a 64-bit host address in `mb7` and `mb6`. This model's existing address-reassembly macros
already combine those same four mailboxes in that arrangement for the command rings, so one
expression serves both paths, and a 32-bit host address is the case where the high halves are
zero rather than a second layout to write.

**Read-RAM-word answers in `mb2`, and answers `mb3` zero.** Two public sources witness this
and they do not quite agree. NetBSD's per-opcode mailbox masks give the command two inputs and
three outputs — mailboxes 0, 1 and 2 — which pins the word to `mb2`. 86Box's model of the same
chip declares `mb2` and `mb3` outputs and clears `mb3` explicitly. Take 86Box on `mb3`: it is
the one that implements the handler rather than merely declaring a mask, and a driver reading
only as far as NetBSD's mask cannot tell the difference, so zeroing `mb3` is right under one
reading and invisible under the other. Answering only `mb2` leaves `mb3` holding whatever the
previous command put there, which is a value this command never wrote.

**Byte order: this model moves host memory little-endian**, matching the accessors the
command-ring path already uses. The chip is a little-endian PCI device, and the Bridge
translates addresses without swapping the DMA payload, so the accessor this device picks is
the byte order that lands in guest memory. **That is a decision rather than an observation,
and the firmware diagnostic cannot settle it**: a load followed by a dump uses one accessor in
both directions and round-trips cleanly whichever way it is set. The board-level test driving
these commands through the Bridge is what settles it, and it is a one-line change if it lands
the other way.

**The mailbox register test needs both queue-pointer mailboxes to answer as storage**, and
for a time neither did. That was a defect rather than a gap — introduced when the queue
pointers stopped reading from the mailbox array, and invisible until a guest reached the
register test, which none had. The test writes a walking pattern across mailboxes 1 through 7
and reads it back, and two of the seven answered something else.

Measured before the gate below was added, writing `0x1111 * n` to mailbox *n* and reading each
back:

| Mailbox | Written | Read | What answers instead |
|---|---|---|---|
| 1, 2, 3, 6, 7 | pattern | pattern | the mailbox array |
| 4 | `4444` | `0001` | the request queue's consumer cursor |
| 5 | `5555` | `0000` | the response queue's producer count |

The two failed differently, which is why a fix has to cover both. Mailbox 4's write reaches
the array and only its read was diverted; mailbox 5's write is consumed by the
acknowledgement path and never reached the array at all. Both diversions exist for the rings: a read of the request pointer
must answer this adapter's own consumer position, and a read of the response pointer its own
producer count, or a guest's stale acknowledgement erases a completion already published.

The firmware's `scsi_ram: SCSI mailbox test failed` was this comparison failing, not a
RAM-access command being refused.

**One register serving two purposes is resolved by gating on the queue's own length.** Hardware
has one register at each of these addresses. The register test runs before any queue is
initialised, so at that moment each address is plain storage; only once the queue behind it is
live does it carry a pointer. The model now says exactly that: a read answers the adapter's own
cursor or producer count only while that queue's length is non-zero, and otherwise answers the
mailbox. The response side's write is gated the same way, because with no queue there is no
acknowledgement to record and nothing to drain.

**This preserves the completion-erasure rule rather than weakening it.** While a response queue
exists the behaviour is unchanged in both directions — a read answers the adapter's published
count, a write records the guest's consumer position, and the mailbox behind the address is not
consulted. The mailbox is reachable only when no queue exists, which is precisely when there is
no completion to erase. Mailbox 4's identity value moves back into the mailbox array, where the
register test can reach it and where the product-ID check still reads `0x0001` after reset.

**Do not read the firmware's `diag_rc` numbers against the published diagnostics manual.**
One test returns different codes on different firmware releases: the serial DMA test answers
63 on the 6.11 PROM and 79 on the 6.156 PROM, while the manual assigns 63 to a SCSI mailbox
failure and lists 79 as unused, so its table describes neither release. The trap is that the
table is partly right — the Ethernet SSRAM and PHY-register codes it gives do match what the
6.156 PROM prints — so an entry that happens to agree is no evidence the next one does. Read
the failure strings, which are stable across both releases, and read the register trace.

### NVRAM

The adapter carries a 128-byte serial EEPROM read through the NVRAM register by
bit-banging: assert chip select, shift out a read command and a word address most
significant bit first, then shift in sixteen bits, toggling the clock bit by hand and
reading the data-in bit each cycle. The contents open with the ASCII identifier `ISP ` and
a version byte, and the whole 128 bytes sum to zero over an 8-bit accumulator.

**The model does not need to answer.** If the identifier is wrong, the version is below the
minimum, or the checksum fails, OpenBSD prints that the NVRAM is corrupt and proceeds with
its built-in defaults — which is a clean, well-trodden path, and is the same path an
adapter with a blank EEPROM takes. Leaving the data-in bit low produces all-ones or
all-zeros data and lands there.

Two things argue for eventually supplying a valid image rather than staying silent. The
NVRAM is where the adapter's SCSI initiator identifier lives, and OpenBSD notes in its own
code that SGI machines use initiator 0 on the on-board adapter where the standard default
is 7 — it hard-codes 0 for SGI targets, so the fallback is right for us. And a valid image
would let us set per-target parameters instead of accepting defaults. Neither is needed for
a first boot. **Start silent; the printed "nvram corrupt" line is expected, not a defect.**

### Bring-up after firmware starts

In order, each a mailbox command that must succeed or the attach fails: about-firmware,
which the driver prints; get-firmware-status, whose second return word tells the driver how
many requests the adapter can hold and therefore sizes every queue it allocates; then a
write of bus configuration 1 with the burst and FIFO settings, and burst enable into both
DMA blocks. Then set-firmware-features, set-clock-rate with the 60 MHz value the revision
selected, set-retry-count, set-async-data-setup, and the per-bus and per-target parameter
commands.

**"The attach fails" here is not a log line — it is the whole SCSI bus never being
created.** `qlw_attach()` returns an error the instant any one of these answers invalid,
before it ever calls the autoconf routine that creates the adapter's `scsibus` and probes
targets on it. A model that answers every earlier command correctly and then leaves even
one of this bucket unimplemented produces a driver that attaches (`qlw0 at pci0 ...`
prints, because that happens before any of these) and then goes silent — no `scsibus`, no
target, no disk, and nothing past the one printed failure line names why. This is not
theoretical: an early build of this model implemented everything through get-firmware-status
and bus-reset but none of this bucket, and a real OpenBSD 7.9 boot against it printed
exactly that shape of failure, immediately after the firmware banner and with no SCSI
adapter ever appearing for the rest of the boot.

The full bucket, in the order `qlw_attach()` and `qlw_config_bus()`/`qlw_config_target()`
issue them, with the opcodes OpenBSD's own `qlwreg.h` gives every one of them (shared,
public constants — not a QLogic manual this project holds):

| Opcode | Command | Called |
|---|---|---|
| `0x004A` | set-firmware-features | once, only if the adapter's feature flags are non-zero — skipped entirely when they are 0, which is what a plain PCI attach with no NVRAM-supplied features does |
| `0x0034` | set-clock-rate | once |
| `0x0032` | set-retry-count | once |
| `0x0036` | set-async-data-setup | once |
| `0x0035` | set-active-negation | once |
| `0x0033` | set-tag-age-limit | once |
| `0x0031` | set-selection-timeout | once |
| `0x0030` | set-initiator-id | once per bus |
| `0x0038` | set-target-parameters | once per target, every target the bus can address, whether or not anything answers there |
| `0x0039` | set-device-queue | once per target per LUN |

Every one of these is a host-to-device configuration write — clock rate, retry timing,
negotiation defaults, queue depth — that the driver never reads back on the boot path, and
this model does not negotiate a bus or throttle a target, so **the only contract is that
each one completes.** This is the same reasoning bus-reset already uses: nothing here
distinguishes a bus configured one way from one configured another, because nothing later
depends on which.

Two more mailbox commands, issued by guests other than OpenBSD, complete the set the model
must answer. Neither is in `qlw_attach()`'s bucket, and both were traced falling into the
invalid-command answer:

| Opcode | Command | Issued by |
|---|---|---|
| `0x003A` | set-reset-delay-parameters | IRIX, during adapter init before its bus scan |
| `0x0028` | get-target-parameters | Linux `qla1280`, once per enumerated target |

`0x003A` is another host-to-device configuration write — the SCSI bus-reset delay — with the
same property as the bucket above: this model tracks no reset timing, so the only contract is
that it completes. The opcode is `MBC_SET_RESET_DELAY_PARAMETERS` in Linux's `qla1280.h` and
`MBOX_SET_RESET_DELAY_PARAMS` in NetBSD's `ispmbox.h`.

`0x0028` is a read: it returns the negotiated transfer parameters for a target the driver
names in mailbox 1. The output layout is the input layout of set-target-parameters (`0x0038`)
read back — mailbox 2 the parameter flags (sync-enable, wide-enable, disconnect, parity and so
on, the bit positions Linux's `qla1280_set_target_parameters()` writes), mailbox 3 the
synchronous period and offset — confirmed by NetBSD's per-opcode mailbox mask for it,
`ISPOPMAP(0x03, 0x4f)`: two inputs, outputs in mailboxes 0-3 and 6. This model negotiates
nothing, so it reports every target as asynchronous and narrow with no options set — mailbox 2
and mailbox 3 both zero — the true state of a bus it does not negotiate; a guest reads it back
and configures the target async/narrow, matching what the model does. `MBC_GET_TARGET_PARAMETERS`
in `qla1280.h`, `MBOX_GET_TARGET_PARAMS` in NetBSD's `ispmbox.h`.

The request queue count the model returns is load-bearing in a quiet way: the driver caps
it at 512, sizes the response queue at half of it with a floor of 64, and allows one
outstanding command per three request entries. Returning a small number throttles the
guest; returning zero would divide the guest's command budget to nothing.

Then initialise the two queues — one mailbox command each, carrying the entry count and
the queue's physical address — and issue a bus reset per bus with the configured delay.
After the reset the driver requires a marker entry at the head of the request queue before
it will send commands.

### Steady state

**Queue entries are 64 bytes and both queues are rings of them.** The host writes a request
entry at the index it holds, advances the request-in pointer, and the adapter consumes from
there. Completions are posted into the response queue and the adapter advances the
response-in pointer; the host consumes entries up to that index and then writes the
response-out pointer back.

Four entry types are distinguished by the first byte of a four-byte header: **`0x01` a type
0 command, `0x02` a type 0 continuation, `0x03` a status entry, `0x04` a marker.** The
header's remaining bytes are an entry count, a sequence number and flags.

A command entry carries a host handle, the target and bus, the command-block length, flags,
a timeout, a segment count, twelve bytes of SCSI command block, and four scatter-gather
segments of a 32-bit address and a 32-bit length each. A command needing more than four
segments is followed by continuation entries carrying seven segments apiece, and the entry
count in the header says how many entries the whole command occupies. A status entry
returns the handle, SCSI status, a completion code, state and status flags, response and
sense lengths, a residual count, and up to 32 bytes of sense data -- byte offsets 4, 8, 10,
12, 14, 16, 18 and 20 within the 64-byte entry, confirmed identical (including the reserved
eight bytes at offset 24 before sense data at 32) against both OpenBSD's `struct
qlw_iocb_status` (`qlwreg.h`) and Linux's `struct response` (`qla1280.h`) -- two independent
drivers agreeing on the wire format of a part neither vendor documented for us. The two
sources disagree only on what to call offset 16: Linux's own field is `time`, OpenBSD's is
`rsp_len`. Neither driver reads that offset anywhere in either source, so the disagreement
does not need resolving to model the entry correctly.

**State flags (offset 12), status flags (offset 14) and sense length (offset 18) are the
fields with a confirmed reader.** Linux reads state flags on an incomplete completion, and
only then, to decide which of several specific failure reasons to report rather than lump
every incomplete command together, and NetBSD reads the same field for its got-target
decision. OpenBSD's `qlw` does not read offset 12 at all — its got-target test reads the
IOCB header flags byte at offset 3, which for bit 9 (`0x0200`) in a single byte is always
false, so `qlw` collapses every incomplete completion to a selection timeout. Linux reads
sense length directly to decide how many bytes of the sense data field to trust. Status
flags is read by IRIX for the missing-target case below; none of the public parallel drivers
reads it there — NetBSD's `isp` (shared by FreeBSD) touches the status-flags word only on a
different completion code, and only to name bits in a transport-error log line, never to
decide the no-device case. A model that leaves any of these fields unwritten hands back
whatever a previous occupant of that ring slot left there, since the ring is reused — caught
by the adversarial review (task #74/#97) as the same stale-bytes shape the completion-erasure
bug already had, on a different part of the same structure.

**On a normal completion the state flags name the phases the command reached, and the sense
phase is set only when the completion carries sense.** The sense-phase bit (`0x2000`) in the
offset-12 field means the adapter ran auto-sense, which a target triggers only by returning
CHECK CONDITION; a command that ends GOOD took no sense, so the bit must be left clear. This
matters to a guest and is not cosmetic. Observed: with the model raising the sense phase on
every completion, IRIX booted with a CD-ROM reissues the CD's GOOD MODE SELECT(6) — the one
that restores the block descriptor — without bound and wedges at the failsoft daemon start;
with the same bit gated on sense length the boot reaches a login. The mechanism — that IRIX
validates the phases a completed command reached and reads an unexpected sense phase as a
completion other than the one it issued, and so retries — is inferred from that A/B, not read
from the driver; the IRIX completion path is what would settle it, and a cleanroom reader
would confirm it. The faithful hardware behavior is unambiguous regardless: real firmware
raises got-sense only after auto-sense, so the model sets that bit from whether the completion
carries sense; the other phase bits keep the all-phases mask a completed command traverses.
Confirmed end-to-end by a boot that
reaches a login with a CD-ROM attached (boot-log under `docs/boot-logs/`).

**A command for an absent target completes incomplete with both flag words saying so.** When
the adapter selects a target that has no device it posts completion code incomplete
(`0x0001`) with, in state flags (offset 12), got-bus set and got-target clear — reached the
bus, selected nothing — and, in status flags (offset 14), the selection-timeout bit `0x0040`
set. Those byte offsets come from the public IOCB layout that Linux's `qla1280.h` and
OpenBSD's `qlwreg.h` agree on byte-for-byte, not from IRIX, whose big-endian layout mirrors
field order within each 32-bit word and so cannot supply a byte offset. The public parallel
drivers accept the empty slot without reading status flags at all: Linux's
`qla1280_return_status()` branches on the got-target bit of the offset-12 state-flags field
and NetBSD's `isp` returns a selection timeout on the same got-target-clear condition, while
OpenBSD's `qlw` reaches selection timeout for any incomplete completion through a header-byte
test that inspects neither offset 12 nor offset 14. NetBSD reads the status-flags timeout bit
only to label an unrelated transport error. IRIX is stricter: it treats the target as absent
only when got-target is clear AND the status-flags timeout bit is set, faulting the probe
otherwise. IRIX does not test got-bus — got-bus is the faithful real-adapter representation,
the bit Linux keys on, not part of IRIX's decision. So a model that leaves offset 14 at zero
satisfies the public drivers, which never look at offset 14, but not IRIX's added timeout
requirement, and IRIX turns every empty target on the bus into a fatal error — the shape of
the failure the IRIX installer hits, selecting each target in turn. The bit value `0x0040`
is NetBSD's `RQSTF_TIMEOUT` (`ispmbox.h`); the cleanroom source-reader confirmed IRIX's own
selection-timeout constant has the same value.
Linux's `qla1280.h` declares the status-flags field but enumerates none of its bits, and
OpenBSD's `qlw` never reads it.

The two-field structure, the offsets, the `0x0040` value and the public drivers' behavior are
all public-grounded and independently verified. The one IRIX-specific claim — that IRIX gates
the no-device decision on the status-flags timeout bit — is confirmed two ways: against the
IRIX driver by a cleanroom source-reader, and end-to-end by a boot. With the bit set, IRIX's
PROM SCSI walk completes clean — it finds the disk at target 1, skips the empty targets with
no incomplete-completion error and no controller reset, and netboots the miniroot. This is no
longer only what the model does; it is an observed fact about the machine.

The completion codes a model has to be able to produce are complete `0x0000`, incomplete
`0x0001`, DMA error `0x0002`, reset `0x0004`, aborted `0x0005`, timeout `0x0006`, data
overrun `0x0007`, data underrun `0x0015`, queue full `0x001C`, and the two negotiation
failures at `0x001F` and `0x0020`. Sense data is valid when bit 9 of the SCSI status word
is set.

Everything in these structures is little-endian, written by the driver with explicit
conversions on this bus. The big-endian variant of the byte order applies only to the SBus
ISP1000, which is not this part and not this machine.

### 64-bit addressing entries — Linux's only request format

**A second pair of entry types, `0x09` and `0x0A`, carries the same command as the type-0
pair above but with 64-bit scatter-gather addresses instead of 32-bit ones.** Confirmed
directly against `qla1280.h`: `cmd_a64_entry_t` (`COMMAND_A64_TYPE = 9`) and `struct
cont_a64_entry` (`CONTINUE_A64_TYPE = 0xA`), both `typedef`'d/aliased so that
`cmd_a64_entry_t` is also `request_t`. That alias does not mean Linux's source has only
one request format — it defines a separate `struct cmd_entry` for type `0x01` too, used by
`qla1280_32bit_start_scsi()` — only that on this build, `request_t` (the name the rest of
the driver uses to type and size the ring) resolves to the 64-bit one, because of which
function is compiled in.

**Linux/IP27 uses this format unconditionally, never the type-0 pair.** `qla1280.c` picks
between `qla1280_64bit_start_scsi()` and `qla1280_32bit_start_scsi()` at compile time on
`#ifdef QLA_64BIT_PTR`, which is itself `#ifdef CONFIG_ARCH_DMA_ADDR_T_64BIT`. That config
is `def_bool 64BIT || PHYS_ADDR_T_64BIT` (`kernel/dma/Kconfig`) — true for every 64-bit
kernel, mips64 included, with no runtime fallback. A real Linux/IP27 boot confirms this:
every SCSI command past chip_diag/firmware-load/ring-init is a `0x09`/`0x0A` pair, none a
type 0 — live-confirmed by task #106's fix answering them (INCOMPLETE, but answered) and
linux-shell's capture of the guest re-issuing them at increasing ring indices afterward;
this specific observation is this fork's own project history, not something the qla1280
source states.

**OpenBSD's `qlw` never issues either type.** `qlwreg.h` defines the A64 *mailbox* opcodes
(`QLW_MBOX_INIT_REQ_QUEUE_A64`/`_RSP_QUEUE_A64`, already modelled, though OpenBSD's own
queue-init call site uses the plain opcodes instead — see "Reset and identity handshake"
above) but no A64 *entry* type at all — its only command entry is `QLW_IOCB_CMD_TYPE_0`
(`0x01`), matching this datasheet's type-0 command entry above. An exhaustive check of
every `qlw_put_header()` call site in `qlw.c` (there are exactly three) finds none passing
`0x09` or `0x0A`, not a name search that merely failed to find one. So of the two guests
this fork runs, only Linux emits this format, and modelling it changes nothing OpenBSD
depends on.

**The command entry (`0x09`), byte-exact, 64 bytes, and offsets 0-31 of it are
byte-identical to the type-0 command entry above, field for field** — confirmed directly
against Linux's own headers: `struct cmd_entry` (type-0) and `cmd_a64_entry_t` declare the
same sequence of fields at the same offsets through the end of the CDB, and only diverge
where the wider segments need more room. Concretely: entry header at 0-3; handle at 4
(`__le32`); LUN at offset 8 (one byte); target at offset 9 (one byte, bit 7 the bus flag —
this is `ISP_REQ_OFF_DEVICE`'s own two bytes, decoded the same way as the type-0 format's,
not a second field that happens to share a number with it; also confirmed against
OpenBSD's single packed `u_int16_t device`, which `qlw_swap16()` stores little-endian for
this part, landing LUN at the low byte and `bus<<7|target` at the high byte — the same two
wire bytes, just declared as one 16-bit C field there instead of two `uint8_t` fields the
way both of Linux's formats declare it); CDB length at offset 10 (`__le16`); control flags
at 12 (`__le16`, direction and tag-queuing bits Linux sets but which this model does not
need to read, the same as the type-0 format's control flags are not read today — QEMU's
generic SCSI layer infers transfer direction from the CDB itself); two reserved bytes at
14; timeout at 16 (`__le16`); segment count at 18 (`__le16`); twelve bytes of CDB at 20-31
(`MAX_CMDSZ`, identical length to the type-0 format). Only past offset 31 does the format
change: eight reserved/unused bytes at 32-39, then two inline scatter-gather segments —
not four, because each one is wider. Each A64 segment is 12 bytes instead of the type-0
format's 8: a 64-bit address as two `__le32` words followed by a `__le32` length. Segment
0's address spans offset 40-47, length at 48-51; segment 1's address spans 52-59, length at
60-63. `32 (shared header) + 8 (reserved) + 2 × 12 (segments) = 64` — the same fixed entry
size every other entry type in this datasheet already fits.

**Word order within a 64-bit address is low half first, confirmed from how the driver
writes it, not inferred from the field's name:** `qla1280_64bit_start_scsi()` walks a
scatter-gather list writing `cpu_to_le32(lower_32_bits(dma_handle))` then
`cpu_to_le32(upper_32_bits(dma_handle))` into consecutive words — the same low-then-high
convention this datasheet's mailbox section already documents for the A64 queue-init
mailbox commands (`ISP_MBOX_ADDR_LOW`/`_HIGH`/`_MID`/`_TOP`), not a new convention specific
to entries.

**The continuation entry (`0x0A`), byte-exact, 64 bytes:** entry header at 0-3, identical
shape to every other entry type; no handle, no reserved gap — segments start immediately
at offset 4. Five 12-byte segments fill the rest of the entry exactly: segment 0 at 4-15
(address 4-11, length 12-15), segment 1 at 16-27, segment 2 at 28-39, segment 3 at 40-51,
segment 4 at 52-63. Five per continuation rather than the type-0 format's seven, again
because each segment is wider. **Offset 4 here is the low 32 bits of a DMA buffer address,
not a handle** — the fact that makes a continuation entry dangerous to answer as though it
were a command entry, which is exactly why the earlier fail-visibly fix (task #106) only
ever reads offset 4 for entries the request-processing loop actually dispatches
independently, and a continuation entry is never one of those: the loop advances past a
command's own continuations using the command's `entry_count`, the same mechanism that
already skips the type-0 continuation entries today.

**Everything else about this format matches the type-0 pair already documented above**:
the entry-count-driven ring-walking mechanism, the response/status entry format (unified
across both request formats — `struct response` names no entry-type-specific field), the
completion codes, and the little-endian byte order throughout.

## Interrupts

The adapter presents one PCI interrupt line, and it is a level.

**Decoding an interrupt starts at the semaphore, not the status register**, which is the
part most likely to be modelled backwards. The driver first reads the semaphore register.
If its lock bit is set, the adapter has posted something in mailbox 0, and the value there
distinguishes the two cases: a mailbox command completion if bit 14 is set, an asynchronous
event otherwise. Only if the semaphore lock is clear does the driver read the bus interface
status register, and a set interrupt-request or RISC-interrupt-request bit there means
completions are waiting in the response queue.

So a model must take the semaphore lock when it posts a mailbox result or an asynchronous
event, and must not take it when it posts an I/O completion.

Acknowledgement is two steps and the second is conditional. Every acknowledgement issues
the clear-RISC-interrupt host command. For a mailbox completion or an asynchronous event
the driver *also* writes zero to the semaphore register to release the lock; for an I/O
completion it does not.

Mailbox 0 carries the result of a completed mailbox command: `0x4000` means complete,
`0x4001` means the command was invalid, and other values are command-specific errors. The
asynchronous events the driver understands are a bus reset `0x8001`, a system error
`0x8002`, request and response transfer errors `0x8003` and `0x8004`, a SCSI command
completion `0x8020` and a target-mode completion `0x8021`.

There is a race the driver guards against and a model should not provoke: if a response-queue
interrupt arrives while a mailbox command is outstanding and the response-in pointer has not
actually moved, the driver declines to acknowledge it. Post an I/O interrupt only when the
response-in pointer has genuinely advanced.

## DMA

Every transfer this adapter makes crosses the Bridge, so all of it goes through
`dma_memory_read` and `dma_memory_write` and honours the Bridge's address translation.
Using the physical-memory accessors would bypass the translation the guest programmed and
is wrong for every path here.

Three kinds of access:

- **The request queue**, read by the adapter. Its base address is given once by mailbox
  command, its entry count separately, and entries are 64 bytes.
- **The response queue**, written by the adapter. Same shape, its own base and count.
- **Data buffers**, addressed by the scatter-gather segments inside command and
  continuation entries. Segment addresses are 32 bits in the entry format this generation
  uses, which bounds where a guest can place buffers and is worth logging rather than
  silently truncating if a guest ever presents more.

The queue base addresses are handed over as a 64-bit value split across mailboxes, so a
model reassembling them must take all the words the command's input mask covers rather than
the low pair.

Byte order: queue entries and their fields are little-endian as the driver writes them, and
this device reads them that way with the ordinary DMA accessors. Any byte-lane permutation
the machine needs is the Bridge's, keyed on the requesting slot's swap bits and the window
the address falls in — stated in full under the DMA byte lanes section of the
[Bridge datasheet](bridge.md).

## Out of scope

- **The SXP and RISC register blocks at `0x80`.** No guest on origami's path reads them;
  NetBSD's driver does, and NetBSD is a cross-check source rather than a target guest. The
  bank select bit must still be implemented, because a model that ignores writes to bus
  configuration 1 bit 3 and always presents one bank would mislead anyone who later needs
  the other. Accesses to the block log as unimplemented.
- **The flash BIOS data and address registers**, and the flash enable and bank bits in bus
  interface control. The adapter's option ROM is not something an emulated Origin 200 needs;
  the machine boots from its own firmware.
- **The GPIO data and enable registers.** They carry SCSI termination control on later parts
  of the family and are unused on this one.
- **Target mode.** The adapter can act as a SCSI target and the entry formats have the
  fields for it. No guest we care about configures it.
- **The second SCSI bus.** This part is single-channel; the driver's per-bus loops run once.
  The dual-channel ISP1240 and ISP1280 are different devices.
- **The second adapter.** A real Origin 200 carries two, at PCI devices 0 and 1, serving the
  5.25-inch and 3.5-inch drive bays. The device model must be instantiable twice, but which
  the machine wires is the machine's business and a first implementation may wire one —
  noting that a guest will then see half the machine's disk topology, which is fine for a
  root filesystem and wrong for reproducing a captured inventory.

Everything out of scope gets a catch-all that logs unimplemented accesses rather than
failing silently.

## Behavioral notes

**There is no reset-value table for this part and there will not be one.** Both the IOC3
and the Bridge have SGI-authored register tables giving a reset value for every register;
this part has no vendor documentation at all beyond a product brief. Reset values in this
document are the ones the drivers demonstrably depend on — the identity words, the
revision fields, the soft reset bit clearing itself, the mailbox signature — and everything
else resets to zero because nothing contradicts it. That is weaker evidence than the other
datasheets rest on, and it is worth saying plainly rather than presenting a table that
looks equally authoritative.

**The absence of a manual is settled, not merely unsearched.** The QLogic documents in our
collection were checked page by page, including a scan with no text layer that was put
through OCR specifically to rule it out, and the bitsavers directory they came from holds
no programming manual for the part. Anyone who thinks they can close the gap by finding the
datasheet should read the cross-check note first and save the time.

**Three lineages, and it is worth knowing which is which**, because this family's sources are
not as independent as their names suggest. NetBSD's `isp` is Matthew Jacob's multiplatform
driver, carrying NASA and Jacob copyrights from 1997 onward, and it is the upstream that most
ISP code descends from. Linux's `qla1280` is a separate line. **OpenBSD's `qlw` is a third,
written fresh by OpenBSD developers between 2011 and 2014 and mentioning Jacob nowhere** — so
the behavioural contract in this datasheet, which is `qlw`-sourced, is genuinely independent
of the register cross-check, which is Linux against NetBSD. Anything else in this family
should be checked for Jacob descent before being counted as corroboration: a source that
inherits his register definitions agreeing with NetBSD is inheritance, not confirmation.

**Two drivers agreeing is the strongest evidence available here**, which is why this
document distinguishes throughout between values confirmed by both and values only one
tree carries. The single-source values — the flash BIOS registers, the flash bits in bus
interface control, and the family's revision encoding — are marked as such so that a
failure in one of them is looked at differently from a failure in a confirmed one.

**The IRIX driver is a third opinion and it agrees where it overlaps.** SGI reads the same
PCI revision byte the OpenBSD driver reads, names revision 5 with its own constant for a
1040B version 2, and programs a 60 MHz clock for this device identification
unconditionally rather than by threshold. That is a slightly different rule from OpenBSD's
and produces the same answer on this machine.

## Open questions for review

1. **How much of the firmware download should the model retain?** Storing every downloaded
   word costs a modest allocation and buys nothing we can name today, since we never
   execute it. Discarding the words is simpler. The one argument for keeping them is that a
   checksum verify we answer blindly could instead be answered honestly, which would catch a
   guest with a corrupt image — an unlikely fault we would rather see than not. The
   recommendation is to discard and answer success, and to revisit if a guest ever fails
   here.

2. **Should the model supply a valid NVRAM image?** Staying silent sends OpenBSD to its
   defaults, which are correct for this machine, at the cost of a "nvram corrupt" line at
   every boot. Supplying an image removes the line and would let us set per-target
   parameters, but means implementing the serial EEPROM protocol and choosing a
   configuration that no source documents for SGI's board. The recommendation is to stay
   silent because the guest's fallback path is clean and well-trodden. The earlier analogy
   to IOC3 one-wire silence no longer applies; that decision was withdrawn when hardware
   inventory and guest evidence established IOC3's responder.

3. **What request count should get-firmware-status report?** It sizes every queue the guest
   allocates and its command budget. A real adapter's number is a property of its firmware
   and no source we hold states it. Reporting 512, the driver's own cap, gives the guest the
   most room and exercises the ring arithmetic hardest; a smaller number would be more
   conservative and less well tested by the guest. Needs a decision before the queues are
   implemented.

4. **This document now rests on running guests as well as on driver agreement.** Every
   other datasheet in this set rests on at least one vendor-authored table. This one was
   written from driver agreement alone, naming a boot on our own emulator as the arbiter
   and warning the first implementation to expect to correct it rather than satisfy it.
   That correction happened, more than once: the queue-pointer mailboxes, the RAM-access
   commands and the ring's byte order were each settled by a running guest and each sent
   this document back for rewriting. What a guest has actually exercised is recorded
   separately from what was reasoned about, so the two are not read as one.

## What a running guest has exercised

The vendor firmware's three power-on SCSI diagnostics pass, both adapters walk the bus, and
the disk at target 1 enumerates. OpenBSD 7.9 GENERIC-IP27 attaches its driver to both
adapters and reports the disk's capacity correctly, which needs inquiry and read-capacity to
have both moved their data in the right order.

The write path is checked on the medium rather than through the adapter. The firmware
netboots the vendor's standalone partitioning tool, which writes a volume header to a disk
that was empty beforehand, and a host program then reads the image file directly. The
label's own checksum is the test worth running: it covers every word of the block, so a
byte-order fault anywhere in the sector breaks it, where the header's leading magic is four
bytes that can land correctly while the rest of the block is swapped. A reader inside the
guest cannot perform this test at all, because it would share the byte-order correction
under test and would agree with itself. The transcript is in the boot archive under the
IRIX partitioning capture.

**That check was run again after the correction moved into the Bridge, and the label is
byte-identical to the one written before it** — same magic, same checksum, same partition
table. A transform that merely worked would have produced some valid label; only the same
transform produces the same bytes, which is what makes the move a relocation rather than a
rewrite that happens to agree.

Two complaints in that transcript are not this device's, and are recorded here so they are
not read as SCSI regressions. The standalone tool's drive selftest asks for a diagnostic
command the generic SCSI disk model does not implement. Its geometry request is answered
from disk properties that were never set on the emulator command line, so the rigid-geometry
mode page reports zeros; the tool falls back to the capacity it reads and produces a correct
label regardless.

## qtest checklist

The register-contract assertions the device's qtest must cover.

- **Identity.** PCI vendor `0x1077`, device `0x1020`, and configuration-space revision
  byte `5`. The bus configuration 0 hardware-revision field reads `6`.
- **The configuration Command and Status register reads `0x02000000` at reset.** A 32-bit
  read of configuration offset `0x04` returns Command `0` in the low half and Status `0x0200`
  in the high half — the value the IRIX `io_config_space` diagnostic compares against, and the
  reason a zero Status half fails the I/O slot. Assert the Status capability bits are read-only
  (a write leaves bit 9 set and sets no other) and the error latches clear on a write of one.
- **The window is 16-bit and `0x100` bytes.** Adjacent 16-bit registers do not alias, and
  both the memory base address register at configuration offset `0x14` and the I/O one at
  `0x10` reach the same registers.
- **Soft reset clears itself.** Writing bit 0 of bus interface control and then reading the
  register back returns it clear, within the thousand polls the guest allows.
- **The mailbox signature is present after reset.** Mailboxes 1, 2 and 3 read the ASCII
  values for `IS`, `P ` and two spaces; mailbox 4 reads `0x0001`. Assert Linux's exact
  `qla1280_chip_diag()` comparison too — mailbox 1 equal to `0x4953`, mailbox 2 equal to
  `0x0000` *or* `0x5020`, mailbox 3 equal to `0x2020`, mailbox 4 equal to `0x0001` — since
  that is the check a real guest performs and a wrong value anywhere in the four fails it.
- **The mailbox register test echoes all seven arguments when no queue exists**, and the queue
  pointers still answer their own counts when one does. Both halves are needed: the first is
  what the firmware's diagnostic checks, and the second is what the rings depend on. Do not
  assert an echo on the second — a write to the response pointer with a live queue is an
  acknowledgement, and asserting it reads back would re-encode the completion-erasure defect.
- **The queue pointers round-trip a write**, at mailbox base plus `0x08` and plus `0x0A`.
  Response-in (`0x0A`, mailbox 5) resets to zero. Request-in (`0x08`, mailbox 4) does not —
  it resets to `0x0001`, the same value the mailbox-signature check above requires there;
  this offset is mailbox 4 reached under a second name, not separate storage. Corrected
  2026-08-12: this bullet previously claimed both reset to zero, which was never checked
  against a source observing the raw hardware value rather than OpenBSD's own defensive
  `qlw_softreset()` write of zero to this offset before it is ever treated as a live
  pointer — the same misattribution as the mailbox-signature claim, caught by the same
  investigation.
- **The bank select is bit 3.** With bus configuration 1 bit 3 clear, the window at `0x80`
  presents the RISC block; with it set, the SXP block. Assert that bit 0 does *not* switch
  banks, because that is the wrong constant a model is most likely to inherit.
- **Bus configuration 1 round-trips its documented fields** — the four FIFO threshold
  encodings and burst enable — and the reserved bits it does not own read back zero.
- **The host command register decodes the top four bits.** A pause command sets the paused
  flag in the read-back value and a release command clears it; a reset command sets the
  reset flag.
- **The mailbox protocol completes a no-op.** Writing the no-op command to mailbox 0 and
  setting the host interrupt produces the complete result `0x4000` in mailbox 0, with the
  semaphore lock taken.
- **Interrupt decode goes through the semaphore.** A posted mailbox result sets the
  semaphore lock and raises the line; the clear-RISC-interrupt host command plus a write of
  zero to the semaphore lowers it. A posted I/O completion raises the line with the
  semaphore lock *clear* and the bus interface status request bit set, and the
  clear-RISC-interrupt command alone lowers it.
- **The interrupt output is a level.** With both interrupt enables clear in bus interface
  control, a pending source does not raise the line; enabling then raises it.
- **The firmware download path survives.** A sequence of RAM-write commands followed by a
  checksum verify and an execute all report complete, and mailbox commands work afterwards
  that did not work before.
- **Every command in the config-setters bucket completes.** Set-firmware-features,
  set-clock-rate, set-retry-count, set-async-data-setup, set-active-negation,
  set-tag-age-limit, set-selection-timeout, set-initiator-id, set-target-parameters and
  set-device-queue each answer `0x4000`. This is the bucket whose absence a real driver
  found as a silent, un-probed SCSI bus — see "Bring-up after firmware starts" — so the
  check is not decorative: every command missing from it is a command that aborts the
  guest's attach one command earlier than the last one that shipped.
- **NVRAM reads fail cleanly.** Bit-banging a read with the data-in bit never asserted
  yields data whose identifier and checksum both fail, which is the state the guest's
  fallback expects.
- **The DMA blocks' config registers round-trip the burst-enable bit and reset to zero.**
  Writing burst enable to the command block's config register at `0x20` and reading it back
  returns the bit set; the data block's config register at `0x40` is independent storage,
  not an alias of the same value. Reserved bits in either write read back zero. This is the
  read-modify-write OpenBSD's own attach sequence performs on both blocks together, and
  before this register was named the read half always saw zero regardless of what had been
  written, since the offset fell through to the generic unimplemented-register default.
- **A RAM word written is the RAM word read back, and mailbox 3 comes back zero.** Write two
  different offsets before reading either, and read the first: reading back the offset just
  written cannot tell a correct model from one answering with the most recently written word.
  Load mailbox 2 and mailbox 3 with values that are not the answer beforehand — 2 carries the
  word out and 3 is an output that reads zero, so both would otherwise pass by accident.
- **A block loaded and dumped is the same block.** Load-RAM a patterned buffer from guest
  memory into the adapter, dump-RAM it back to a different guest address, and compare the two
  buffers; then read-RAM-word one of the loaded offsets and confirm the single-word path agrees
  with the block path. Assert the exact argument layout while doing it — the SSRAM offset in
  mailbox 1, the host address split across mailboxes 2 and 3 high half first, the word count in
  mailbox 4 — because that layout is taken from a driver's source rather than observed on this
  machine, and a transposition of the two address halves is the error it would take a
  900-second firmware boot to notice otherwise.
- **The block path moves bytes in the order this model says it does.** Write a known word
  through write-RAM-word, dump it to guest memory, and read the raw bytes back rather than a
  word, asserting the little-endian order the device's accessor writes; then drive the reverse,
  planting raw bytes in guest memory, loading them, and reading the word through
  read-RAM-word. A load-then-dump round trip passes under either byte order because it uses
  one accessor twice, so only a raw-byte assertion tests the choice at all.
- **The block path reaches guest memory through the Bridge, not around it.** The board-level
  test drives load-RAM and dump-RAM at big-endian offsets through the crosstalk window with a
  Bridge address-translation entry programmed, and checks the round trip end to end. This is
  the only check before a firmware boot that the adapter's memory DMA traverses the same
  translation the command rings do; the device-level tests above pass equally well against a
  model that bypassed it.
- **A write to either DMA block's control register leaves the config register beside it
  alone.** Set burst enable in both config registers, write the firmware's clear-channel value
  to `0x22` and `0x42`, and assert both config registers still read burst enable. Asserting
  anything about the control registers themselves is not possible and not the point: nothing
  keeps a value there. The failure this catches is a control register implemented by widening
  the config register's case or by an address mask that swallows the low bit — which lands the
  write on the config register and changes a value the guest set, invisibly, because the
  control side is never read back.
- **A command round-trips through the queues.** With both queues initialised, a command
  entry written at the request-in index and the pointer advanced produces a status entry in
  the response queue carrying the same handle, the response-in pointer advanced, and an
  interrupt raised with the semaphore lock clear.
- **A command that carries data actually moves it.** The check above is satisfiable by a
  command with no data phase at all — test unit ready, which is all it happens to use — and
  a real OpenBSD boot found exactly the gap that leaves open: a command with a data phase
  crashed the emulator itself, on the guest's very first inquiry, right after the SCSI bus
  was created. Send an inquiry through the ring with a real scatter-gather segment and read
  the answer back out of guest memory — the device-type byte and the disk's vendor and
  product strings — rather than only checking that the command completed.
- **A command needing a continuation entry actually reaches it, and the ring survives
  being filled completely.** Every check above fits inside the four segments a request
  entry carries inline — nothing had ever forced a fifth segment into a continuation
  entry, and nothing had ever written a request-in value equal to the queue's own
  length. The second of those hung the emulator outright: the device's read cursor is
  always wrapped, comparing it against an unwrapped guest value can never terminate
  once that value reaches the queue length. Split a transfer across an inline and a
  continuation segment into non-adjacent destinations and reassemble them, and drive
  the queue to exactly full as part of the same check — both because a smaller queue
  makes the full case easy to reach directly and because a real driver's own
  throttling would otherwise make it a rare accident to test.
- **The response queue survives the same treatment on the side this model produces
  into.** Four commands issued as separate doorbells with no ack in between, on a
  four-entry response queue, must not let the fourth completion wrap the response
  producer onto its own untouched starting value — that alias is exactly what the
  driver's own "is anything new here" check cannot tell apart from an empty ring. And
  the held-back completion must not simply vanish: once the driver's ack frees a
  slot, it has to complete and its status has to be readable, the same as any other
  command's. A fix that only clears the first assertion and drops the fourth command
  on the floor is not a fix.
- **A stale ack must not be able to erase a completion the adapter already published.**
  Read the response-in value once, complete a second command synchronously — a fresh
  doorbell running from inside the same handler that read it, exactly how a completion
  callback starting the next queued command reaches this device — and only then write
  the first ack, still carrying the value read before the second command's completion
  moved the count past it. A read afterward has to answer with what the adapter has
  actually produced, not with the ack that just landed behind it; the alias this checks
  for is invisible to any test that only ever acks in the same order it reads, because
  in that order the two values never diverge.
- **A status entry posted into a ring slot a previous completion occupied must not carry
  any of that previous completion's bytes.** A slot with real sense data (test unit
  ready's automatic power-on unit attention) followed, after the ring wraps, by a clean
  command reusing the same slot: the second command's entry has to read sense length
  zero and thirty-two zero sense bytes, not the first command's leftovers. A check that
  only reads a fresh slot's fields cannot tell "correctly zeroed" from "never written,
  and happens to still be zero" apart — this needs a slot with real prior content to
  show the difference.
- **The missing-target completion sets the right bits in both flag words.** No SCSI
  device at the requested target and lun posts an incomplete completion with the
  bus-reached bit set in state flags (offset 12) and nothing past it, matching what
  actually happened, and the selection-timeout bit `0x0040` in status flags (offset 14).
  Linux reads the offset-12 state-flags field on an incomplete completion to pick a specific
  failure reason, OpenBSD collapses the case to a selection timeout through a header-byte
  test, and neither reads status flags; IRIX additionally reads the status-flags timeout bit
  and faults an empty target without it, so both flag words are asserted. Removing the
  status-flags write makes the check fail on exactly that field.
- **The A64 command entry (`0x09`) reaches a real target with data**, the same "does not
  crash, actually moves bytes" bar the type-0 inquiry check above sets, but through the
  64-bit-address fields: two inline 12-byte segments instead of four 8-byte ones, a real
  inquiry answered through them and read back out of guest memory. LUN and target decode
  the same way as the type-0 format's device field, at the same offset — confirming that
  is worth its own assertion, since the two formats' fields only look different in how
  Linux's and OpenBSD's headers each declare them, not on the wire.
- **An A64 command needing a continuation entry reaches all five of its segments**, split
  across non-adjacent destinations the same way the type-0 continuation check does, so a
  model that only wired the two inline A64 segments cannot pass by accident.
- **A continuation entry (`0x0A`) is never dispatched as an entry in its own right.**
  Build one immediately after a command whose `entry_count` claims it, plant a value at
  its offset 4 that would misread as a wildly wrong handle if it were ever read as one,
  and assert exactly one completion posts, carrying the command's own handle — not the
  continuation's DMA address, and not a second, spurious completion.
- **A64 and type-0 commands round-trip on the same ring without either one's ring-walk
  arithmetic assuming the other's segment width or entry count.** Interleave a type-0
  command with data, then an A64 command with data, then a type-0 command needing a
  continuation, and confirm every completion carries its own command's real handle.

Boot-test assertions come after all of these pass: first that OpenBSD 7.9 attaches the
adapter and prints `rev 0x05`, then that it enumerates targets, then that it mounts a root
filesystem from one. Linux/IP27 gets its own boot-test line once the A64 checks above pass:
the adapter attaching was never the gate for it — chip_diag through firmware-load and ring-
init already work — enumerating and reading a target through the A64 format is.
